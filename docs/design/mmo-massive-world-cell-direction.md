## 0. 结论

1. **不能全量同步。** 1 万人互相同步是 1 亿对关系，服务器、网络、客户端都扛不住。每个客户端只全量同步身边几十到一百多人，中圈几百到一千人低频、低精度，再远的只给聚合。这样每个客户端的开销是常数，跟总人数无关。
2. **一张图要拆到多个进程。** 实时战斗下单个 scene 线程估计只能扛 1500~2000 人（§4.2）。世界切成固定大小的 chunk，每个 chunk 归一个或多个 cell 进程。每个 cell 内部仍是今天的单线程 ECS，线程模型不变。
3. **玩家拆成两半。** 持久数据（base）留在一个进程不动，战斗和空间状态（cell）跟着人走。这样过边界不需要交接存盘写权，现有的存盘、资产、交接机制基本不用动。
4. **一个模型覆盖三种形态。** 一张 chunk 目录同时解决大地图局部交战、1 万人同地互砍、大世界和无限世界（§5.2、§5.7）。
5. **现在什么都不用做**，只守住 §7 的三条现有规范。

## 2. 术语

| 词 | 意思 |
|---|---|
| space | 一个世界：一张大地图或一个无限世界。分线时每条线是一个 space |
| chunk | 世界按固定大小切成的方块（起步 256m 见方），是"归谁模拟"的最小单位 |
| cell | 负责若干 chunk 的一个 scene 进程。和容量文档、无单点文档里的"多 cell / 区域单元"（部署单元）不是一回事 |
| real / ghost | 实体的权威副本 / 其他 cell 里的只读影子 |
| base | 玩家的持久部分，留在一个进程不动 |
| 同步格 | 中远圈同步用的小方块（起步 64m），一个 chunk 分成几个 |
| 近圈 / 中圈 / 远圈 | 客户端同步的三档，也写作 L0 / L1 / L2 |
| K0 / K1 | 近圈 / 中圈的人数上限 |
| margin | cell 要看到自己地盘外多远，不小于"近圈半径"和"最远技能射程"中较大的那个 |
| 协调者 | 维护 chunk 目录的控制面，放在 SceneManager |

## 4. 量级估算（全部未实测）

### 4.1 网络

假设：同图 1 万人，人均每秒 1 次移动事件，一条 `ActorMoveS2C` 约 100B。中圈每人 12B（id 增量 2B、相对同步格原点的 x/y/z 各 16 位、朝向 1B、状态位 1B、外观模板 2B），2Hz。

| 做法 | 每个客户端下行 | 全服下行 | gate 写 socket 次数（全服） | 判断 |
|---|---|---|---|---|
| 全量互见 | 约 1 MB/s | 约 10 GB/s | 约 1 亿次/s | 不可能 |
| 现在的形状（兴趣表 100） | 约 10 KB/s | 约 100 MB/s | 约 100 万次/s，每个目标一次 | 带宽够，但只看得到 100 人，写次数先到顶 |
| 三圈（K0=100、K1=1000） | 近圈 10 + 中圈 24 + 远圈 3，约 40 KB/s | 约 400 MB/s | 每人每 100ms 一次，约 10 万次/s | 可行，待实测 |

加上战斗事件（近圈人数 × 每秒 1~2 次 × 约 50B）后，设备档起步值：

| 档 | K0 | K1 | 近圈移动 | 近圈战斗 | 中圈 | 远圈 | 合计 |
|---|---|---|---|---|---|---|---|
| 手机（预算 ≤ 30 KB/s） | 30 | 200 | 3 | 3 | 5 | 3 | 约 14 KB/s |
| PC | 150 | 1000 | 15 | 15 | 24 | 3 | 约 57 KB/s |

中远圈每个同步格只编码一次，全图约 1 万 × 2Hz × 12B ≈ 240 KB/s，再乘 gate 台数，跟有多少人在看无关。"一份数据发给很多人"这一步落在能横向加机器的 gate 上。

### 4.2 单个 cell 的 CPU

按 P0 改完之后的形状估，实时战斗下每人每秒：

| 项 | CPU |
|---|---|
| 移动积分 + 导航校验 | 30~60 µs |
| 近圈兴趣维护 | 20~50 µs |
| 技能 1~2 次（范围查询 + 约 10 个目标的伤害和 buff） | 60~100 µs |
| buff / 持续伤害 | 10~20 µs |
| 收包（移动、技能请求） | 30~50 µs |
| 近圈事件扇出与编码 | 约 100 µs |
| **合计** | **约 300~400 µs**（上面各项之和约 250~380，再加没列出的杂项） |

留三成余量，单线程约 1750~2300 人。这个估算偏乐观，按 1500~2000 人规划。1 万人至少 5~7 个 cell，算上分布不均要 8~16 个。

现状代码在高密度下的热点：

- **属性同步循环**：1 万人 × 视野内 35~100 人 × 20 帧 = 每秒 700 万~2000 万次距离计算（每次还有组件查找），和有没有变化无关，单这一项就可能吃满一个核。
- **导航校验**：5000 人在走 × 20 帧 = 每秒 10 万次射线。
- **兴趣表线性扫描**只在表满时发生：

| 场景 | 密度 | 每格人数 | 半径内人数 | 表会满吗 |
|---|---|---|---|---|
| 1 万人在 300m 见方，半径 10 | 0.11/㎡ | 约 115 | 约 35 | 不会；跨格开销主要是几百次距离判定 |
| 1 万人在 100m 见方，半径 10 | 1/㎡ | 约 1000 | 约 310 | 会；先到先得，每次插入扫一遍 |
| 1 万人在 300m 见方，半径放大到 50 | 0.11/㎡ | 随格子放大 | 约 860 | 会 |

### 4.3 多进程的额外开销

**大地图局部交战**：ghost 只出现在 chunk 边界附近，开销小。

**1 万人同地互砍**（同一 chunk 由 8 个 cell 共管，各 1250 个 real）：

- **ghost 更新**：每条约 40B、10Hz。每对 cell 单向约 0.5 MB/s，每个 cell 收发各约 3.5 MB/s，全部约 28 MB/s。应用更新约占每个 cell 1%~2% CPU。
- **跨 cell 命中**：每人每秒 1.5 次技能 × 10 个目标 × 7/8 ≈ 全图 13 万次/s，每个 cell 约 1.6 万次/s。按每次几微秒算，约占 5%~10% CPU。
- **gate**：一条近圈事件的 100 个观察者分散在 8 个 cell、10 台 gate 上，会被拆成几十份很小的广播，每台 gate 每秒要解析十几万份。这是热点形态最大的未知数。每台 gate 起步按约 1000 个活跃玩家规划，远低于 `GateMaxConnections` 的 2 万。

## 5. 目标架构

base / cell、real / ghost 的分法来自 BigWorld 这一类引擎；chunk 目录是为了同时覆盖本文三种形态做的简化。

### 5.1 三层与玩家拆分

```
客户端（Unity）：只连一台 gate，感知不到 cell 和迁移
   │ TCP
   ▼
gate：按消息类型分流、按会话合包、中远圈订阅
   │ RPC0（背包、任务、社交……）        │ RPC0（移动、技能……）
   ▼                                   ▼
base 进程  ◀────────── RPC0 ─────────▶ cell 进程 × N ◀── RPC0 ──▶ 其他 cell
玩家持久数据、写权、存盘、资产          real + ghost，单线程 ECS
   │                                   ▲
   ▼                                   │ chunk 目录（副本，不上热路径）
  TiDB                                协调者（SceneManager）
```

**为什么必须拆**：如果整个玩家跟着过边界，每次过边界都要最终存盘并移交写权（TiDB 方案 §3.3），资产、收件箱、存盘回包这些异步链路也都要追着玩家跑。拆开后，这些都留在不动的 base 上，`player/` 那 3.3 万行和现有的数据一致性机制基本不用改。

| 放 base（不动） | 放 cell（跟人走） |
|---|---|
| 背包、货币、装备、任务、邮件、社交、成就 | 位置、移动、兴趣表、技能释放、buff、仇恨、冷却 |
| 写权、存盘、资产幂等、发持久 id（AGENTS §7.1：一种 id 只由一种节点类型生产） | 血量等战斗当前值（定期回写 base 用于存档） |
| 最终属性计算 | base 推过来的属性副本（只读） |

上表只是方向，P2 要产出逐组件的归属表。

两半之间用消息互调：

- **杀怪奖励**：cell 发给 base，带操作号，幂等。
- **吃药**：客户端 → base 扣道具 → 通知 cell 回血。
- **换装**：base 重算属性 → 推给 cell。

副本、小地图这类单 cell 的世界，两半放在同一进程，不走网络。接口一开始就按异步语义写：调用方不依赖返回值，也不依赖同一 tick 生效。

### 5.2 chunk 目录

核心数据是 `(space, chunk) → [cell...]`，带版本号。协调者维护，cell 和 gate 各持一份副本。

两条规则：

1. **real 归谁**：查实体所在 chunk。目录里只有一个 cell 就归它；有多个就按实体 id 哈希选一个（增减 cell 时只搬必要的那部分人，比如用 rendezvous 哈希）。
2. **ghost 从哪来**：cell 订阅"自己负责的 chunk，外扩 margin"范围内所有不归自己的实体。发送方按 margin 过滤，只发靠近边界的。

| 形态 | 目录长什么样 | 代价 |
|---|---|---|
| 大地图、局部几百人交战 | 每个 chunk 一个 cell，一个 cell 管多个 chunk | ghost 只在边界，开销小 |
| 1 万人同地互砍 | 热点 chunk 同时归 S 个 cell（起步 8 个），每个 cell 负责一部分人，其余都是 ghost | 见 §4.3 |
| 大世界、无限世界 | 目录里只有有人的 chunk | 见 §5.7 |

负载均衡就是改目录：搬 chunk（人随之迁移），或给热点 chunk 加 cell。先配置（活动前预标热点区），后动态。

chunk 不能切到比 margin 还小，否则人人都同时是好几个 cell 的 ghost，开销反而爆炸。所以热点不能靠继续切小解决，要靠多 cell 共管。玩法上也要配合：范围技能设目标数上限、多个目标点分流。

### 5.3 real、ghost 与跨 cell 修改

- **ghost 的内容**：位置、速度、外观、阵营、血量比例、关键状态。和 real 放在同一个 registry，AOI 和命中判定可以统一处理。它没有业务组件，多数系统自然跳过；只看 `Transform` 的系统要显式排除。
- **改别人一律发请求**：攻击者所在 cell 用 ghost 做命中判定，把"技能、攻击者属性快照、目标"发给目标 real 所在的 cell，由它按防御和当前状态结算，结果经 ghost 更新和回执传回。不直接发"扣 N 点血"，因为护盾和减伤都在目标那边。
- **时序**：cell 之间不做帧同步（不 lockstep）。每 tick 每对 cell 一条批量消息。跨 cell 的效果晚一个 tick 加网络延迟，约 50~100ms。
- **发包**：每个 cell 只给自己 real 的客户端发包。别的 cell 的实体先走 ghost 更新，再由本 cell 发出，所以近圈里跨 cell 的人也晚一个 tick。
- **可靠性**：消息带序号、可幂等；对方实例换代就丢弃。连接和回调遵守 AGENTS §11.7。

### 5.4 迁移

触发条件：real 所在位置查目录已不归本 cell，且超过回滞距离（防止在边界来回抖）。每 tick 限制迁移人数。

1. 旧 cell 在 tick 末尾把 real 的运行时状态打包发给新 cell，自己降为 ghost，并转发此后收到的消息。
2. 新 cell 把已有的 ghost 升为 real，通知 base 和 gate。
3. gate 切路由时往旧 cell 发一个路由栅栏。旧 cell 把迟到的包和栅栏依次转给新 cell。新 cell 收到栅栏之前，先缓存 gate 直接发来的包（有上限，超时丢弃并打点）。这样同一玩家的消息不乱序。
4. base 发往旧 cell 的消息同样转发。

要先解决的三件事：

- **定时器和闭包不能搬**（`TimerTaskComp`），技能和 buff 要改成存到期时间，到新 cell 再挂定时器。
- **EnTT 句柄不能跨进程**，实体间的跨帧引用要改成稳定 id。
- **actor 网络号要在整个 space 内稳定**，现在的 `node_id<<32|seq` 节点重启会重发，要改（比如按 space 发号段）。迁移不能触发客户端"换节点清空 actor 表"。

### 5.5 客户端同步

| 圈 | 人数（起步） | 内容 | 频率 | 怎么选人 |
|---|---|---|---|---|
| 近圈 L0 | 30~150 | 完整外观、移动事件、属性分频同步、战斗事件 | 事件驱动 | 现有兴趣表 + 优先级；人挤时改成按预算轮询"最近 K0 + 优先级" |
| 中圈 L1 | 200~1000 | 外观模板、量化坐标、朝向、状态位；只发大招、死亡、大范围技能这类远处看得见的事件 | 约 2Hz | 按同步格 |
| 远圈 L2 | 其余 | 每格人数、状态分布、几个抽样点、交战热度 | 0.5~1Hz | 按同步格 |

伤害数字只发给攻击者和受击者，血条只给近圈。

**近圈的发送**：cell 每 tick 每台 gate 合成一条 RPC0。gate 按会话攒起来，每 50~100ms 写一次。客户端帧本来就自带长度，合包不改帧格式，也就不影响客户端契约。

**中远圈的发送**：

- 每个 cell 每 200~500ms 给每个有订阅的同步格编码一份**全量快照**（明细档 + 抽样档），发给订阅了该 chunk 的 gate。全量快照丢了、跳了都能自愈，不需要关键帧；新订阅者直接拿 gate 缓存的最新一份。
- gate 不解析内容，只看头部（同步格、来源 cell、档位、人数、序号），按会话离格子的远近和预算选档、拼包。
- gate 按本机会话的需要向 chunk 所属的 cell 订阅（引用计数，0→1 订阅，1→0 退订）。会话的中心位置由玩家所在 cell 告知 gate，跨同步格时才发，按 tick 合批。
- 抽样按 id 哈希稳定取，防止人物闪烁。
- 客户端按（同步格，来源 cell）覆盖，约 3 秒没刷新就过期。同一个人同时在近圈和中圈时，以近圈为准。

gate 复用[观战分级](battle-spectate-tiered-fanout.md) §7 的思路：分批扇出、新帧覆盖旧帧、软水位跳帧。写不动时只丢中远圈，不丢近圈和业务回包。gate 仍然不懂玩法。以上都不进 Kafka。

**量化坐标**：权威坐标和近圈仍是 double（AGENTS §4），只有中远圈量化，且相对同步格原点，坐标再大也不损失精度。

**可见性**：共享流没法按观察者区分，所以隐身、GM 隐藏的实体不进流，只走近圈。中圈比近圈看得远，外挂可以据此透视，敏感的 PVP 玩法可以收窄中远圈范围。

### 5.6 故障

| 故障 | 处理 |
|---|---|
| cell 崩溃 | 只影响它的 real。玩家到 gate 的连接和 base 都还在，不掉线。协调者改派 chunk，base 用最近的检查点（位置、血量）把玩家放回世界；只在 cell 内存里的 buff、冷却丢失。相邻 cell 删掉来自它的 ghost |
| 僵尸 cell | 不持有玩家持久数据，污染不了存档；发给 base 的消息带 cell 代次，旧的丢弃 |
| base 崩溃 | 等同今天的节点崩溃（回到上一次成功存盘）；cell 删掉该玩家的 real，玩家重连 |
| gate 崩溃 | 同今天 |
| 协调者不可用 | cell 按本地目录副本继续跑，不进未知 chunk（玩家停在边界，fail-closed） |
| 大面积重连 | 进场排队（[登录排队](login-queue-2026-05.md) §"进场景排队"留了同一模板） |

### 5.7 大世界、无限世界

适用。目录里只有有人的 chunk，没人的地方不占进程，所以成本只和在线人数、人群分布有关，和世界多大无关。

在上面的基础上还要多做：

1. **chunk 按需分配**：玩家接近未分配的 chunk 时提前申请，申请不到就停在边界。没人、也没有活动世界对象的 chunk 回收。
2. **导航和地形按 chunk 增量加载**：现在是启动时整文件加载；Detour 的 tile 结构支持增删。程序生成的世界要保证同一种子处处结果一致。
3. **世界状态持久化**：采集点、建筑、掉落这类世界对象按 chunk 落 TiDB，有自己的写权代次，chunk 换 cell 时交接。这是 cell 上唯一的持久数据，和玩家数据分开。TiDB 方案 §10 的 SLG 地块是同一思路。
4. **中远圈范围按渲染距离截断**，不是全世界，所以 gate 必须按 chunk 订阅。
5. **坐标**：服务端 double 够用；Unity 的 float 要做原点漂移。
6. **目录规模**：协调者只存活跃 chunk，写入低频（分配、回收、搬迁）。全世界范围的事件不走 ghost，走专门的服务。
7. **分线仍可叠加**：一条线就是一个 space。

### 5.8 客户端（Unity，方向）

- **渲染分三档**：近圈才用 SkinnedMesh、Animator、名字板和特效；中圈用 GPU 实例化加烘焙的顶点动画贴图，按职业和性别共用低模；远圈用 impostor 或粒子人海。1 万个 GameObject 各挂一个 Animator 一定撑不住。具体 API 以当时的 Unity 版本为准。
- **UI**：FairyGUI 名字板只给近圈和选中目标。
- **解码**：中远圈用打包的 bytes 解码进结构体数组，不要每人一个 protobuf 对象，否则 C# GC 会抖。
- **特效**：分档并设同屏上限。
- **设备档**：按 §4.1 上报 K0 / K1。

### 5.9 业务代码的约束

1. ghost 只读，改别人一律发请求，下一 tick 生效。首选用类型卡住（查询返回只读句柄）。EnTT 里难以完全做到的地方，用写入口断言和静态检查脚本兜底（仓里有 `check_no_raw_pointer_member.ps1` 这类先例）。
2. 跨帧引用别的实体用稳定 id，不存 EnTT 句柄。
3. 定时状态存到期时间。
4. cell 不碰背包、货币、任务，走 base 接口。
5. 范围技能必须有目标数上限。

## 6. 比较过的方案

| 方案 | 结论 | 原因 |
|---|---|---|
| 全量同步 | 否 | N² |
| 只靠分线 | 否，保留做兜底 | 不同线互相看不见 |
| 一张图一个进程，只做网络分层 | 否 | 单线程扛不住实时战斗；只有回合制、只走路时才够 |
| 同进程多线程 cell（每 cell 一条 loop） | 否，负责人选多进程 | 优点是迁移不交接写权、可以暂不拆 base / cell；但上限是一台机器，一张图一个故障域，还要把 scene 改成多 loop |
| 整个玩家跨进程搬 | 否 | 每次过边界都要交接写权，异步链路全要追着玩家跑 |
| 同一个 ECS 多线程并行 | 否 | 所有系统都要改成并行安全，串行部分限制上限 |
| 整体时间变慢（EVE 的时间膨胀） | 只作最后的保险 | 动作战斗体验差 |
| 任意形状的动态边界 | 否，改用 chunk 目录 | 搬 chunk 更简单，也能表达多 cell 共管 |

## 7. 现在要守住什么

不改代码，也不预留扩展点。下面三条本来就是现有规范或现状，继续守住，以后改起来就不会更难：

1. **新组件分清持久、按需、派生三类**（[组件访问规则](ecs-component-access-rules.md)）。以后 base / cell 基本按这个分类切。
2. **客户端看到的 actor 号保持不透明**，不让客户端从里面解析节点或实体信息。以后号规则才改得动。
3. **`combat/`、`spatial/` 继续不直接碰背包、货币、任务和存盘**，走业务入口。现在就是这样，这条缝就是以后 base / cell 的边界。

## 8. 启动时的落地顺序

每一轮都按 AGENTS §6 出对比表；编译、测试、压测由 Codex 执行（§10.1）。robot 要能模拟走动和放技能。每个阶段都要 C++/Go 与 Java 同批（§10）。

| 阶段 | 内容 | 通过标准 |
|---|---|---|
| **P0 单进程做到极限** | gate 按会话合包、软水位；属性同步先判脏；导航校验降频；接上压力因子和客户端上报；人挤时轮询刷新兴趣表；视野半径和格子尺寸可配；实测单 cell 上限 | 帧耗时 p99 ≤ 33ms、gate IO 线程 CPU < 70%（[容量文档](capacity-model-hok-scale.md) V1 判据）；得出单 cell 人数，决定要切多少 cell |
| **P1 中远圈 + 客户端分档** | 协议（改 AGENTS §4）、同步格编码、gate 订阅与拼包、Unity 人海 | 单进程下能看见全图人群；下行不超过预算 |
| **P2 base / cell 接缝** | 组件归属表；两半同进程、接口异步；战斗入口改成统一的修改请求；稳定 id；定时状态改到期时间 | 全量回归行为不变；帧耗时不退化 |
| **P3 多进程 cell** | cell 直连、ghost、跨 cell 修改、迁移与路由栅栏、故障处理、静态 chunk 目录 | 1 万人大地图局部交战；来回过边界不丢、不重、不乱序；杀掉 cell 玩家不掉线 |
| **P4 热点与动态** | 多 cell 共管 chunk（先配置后动态）、按负载搬 chunk、降级 | 1 万人同地互砍达标 |
| **P5 无限世界（按需）** | §5.7 | 玩家走向未加载区域不卡；空 chunk 能回收 |

## 9. 启动时还要定的问题
