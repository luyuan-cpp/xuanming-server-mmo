# AOI 单向关注与范围外同步

状态：服务端已落码（2026-11-05），未编译，待 Codex 按文末「验证」执行；Java 版待做。2026-11-10 空间关注改为任一方位置变化后按距离重判（见「空间关注的评估时机」），这部分 Java 版早已按同一口径实现；同日加了战斗关注与名额空出后补回附近的人（见「战斗关注」「名额空出后补回附近的人」）；2026-11-11 加了 NPC 仇恨名单与服务器压力裁表（见「仇恨名单」「服务器压力」）。这三批 Java 版待做，C++ 都未编译。网格、容量和优先级规则见 [AOI 优先级、容量与可见性设计](aoi_priority_design_zh.md)。

## 前言

本项目的 AOI 关注机制采用 kasan 在知乎文章[《如何实现一个强大的 MMO 技能系统——AOI》](https://zhuanlan.zhihu.com/p/148077453)里提出的做法：空间查询负责发现候选对象，实际关注关系决定客户端显示谁、接收谁的动态。原文用微博举例：A 关注 B，A 就能收到 B 的更新；B 是否关注 A，是另一件事。另一篇由负责人提供的参考：[知乎专栏文章（147681650）](https://zhuanlan.zhihu.com/p/147681650)。

比如任务允许玩家通过鹰眼术追踪远处目标：技能生效时，玩法把该目标加入玩家的关注列表；效果结束时，只撤销鹰眼术加上的这条关注。即使目标离得很远，玩家也能持续收到它的移动；如果效果结束时目标仍在附近且满足可见条件，客户端继续显示它。好友、队友、任务 NPC、切磋对象或其他玩法指定的实体，都可以使用同一机制。

## 关注关系

- **空间关注**按距离判定：候选取同场景六边形网格的本格及相邻六格，距离不超过视野半径时建立，超过离开半径时撤销；任一方位置变化后重新评估，规则见「空间关注的评估时机」。优先级按现有规则计算。评估节奏按位移走，与已关注目标的移动发送频率分开。
- **显式关注**由服务端玩法按需建立和撤销。目标为任意符合条件的同场景实体，范围外也可以关注。玩法负责目标授权和关注时机；AOI 不负责查询好友关系，也不自动关注全部好友。队伍要互相同步时，由队伍逻辑分别建立两个方向的关注。
- 同一观察者和目标之间可以同时有空间关注和多个显式来源。每个显式来源有自己的身份，例如队伍、任务或技能实例；重复添加同一来源不会产生重复关系。取消关注只撤销调用方指定的来源。
- 关注按有向关系维护。观察者的正向索引用于查询自己关注的目标，目标的反向索引用于找到它的观察者。两个索引描述同一批关系，创建、撤销、淘汰、离场和销毁时都要保持一致。

## 可见与同步

首次有效可见时，先发创建和当前位置，再接收后续移动。创建消息的 `Transform` 位置恒带、朝向写过才带、缩放不发（朝向 2026-11-12 补上，`ViewSystem::FillActorCreateMessageInfo`，与 Java 版同一口径）：站着不动的目标不会再发带朝向的消息，后来的观察者只能从创建消息知道他朝哪边站。目标正在走时，创建之后紧跟一条它此刻的移动状态（一个目标发 133，几个目标合成一条 135；2026-11-12，`AoiSystem::SendVisibilityChanges` 第 4 步，只发给有客户端的观察者）：移动广播只发给当时已经在看的人，不补的话后来者要等它的下一次广播才看到它在走。"正在走"指服务器在推进它的位置（`spatial/system/actor_motion.h` 的 `IsAdvancing`）：挂机、冻结、战斗在途的人不算（进入这些状态时服务器已清速并给旁人发停步，`MovementSystem::HaltMotion`）；组队随从由队形每 tick 推，算。目标每次发布移动时，按反向索引找到当前有效且可见的观察者。目标或观察者位置变化时，只重判空间来源；显式关注仍有效就继续同步。同一个目标只有一份客户端可见状态，不能因为同时来自网格、队伍和技能就重复创建或重复发送。

距离、隐身和容量是不同的条件。显式关注允许超出网格距离，普通关注仍遵守隐身规则；只有明确具备侦测能力的玩法才能授权看见隐身目标。隐藏期间暂停投递；如果业务来源还在，恢复可见后先发送当前状态。容量沿用现有优先级策略，已有关注的有效性和淘汰通知按每个观察者独立判断，不要求互相占位。

取消一个来源后，只要还有其他有效来源，就继续同步。最后一个有效来源消失或因隐身、淘汰而不再可见时，通知客户端移除一次。进出视野用两个半径，中间是滞后区间，目标在视野边界附近来回走不会反复创建、移除；滞后只作用于空间来源，不绑到显式关注的存续上。

## 空间关注的评估时机

2026-11-10 冒烟发现：玩家移动进入新的一组格子时，对方被 `ViewSystem::CanSee` 的距离判定挡住，之后无论在格子里怎么走，双方都互相看不见。原因是距离只在跨格那一刻判一次：

- 格子尺寸 20 m（格心到顶点），视野半径 10 m。跨格那一刻，新进入的格子里的人离自己至少 20 m，`CanSee` 必然不通过；
- 同一组格子里的靠近（包括走进对方所在的格子，它早已是邻格）不会再判，走到跟前也建立不了关系；
- 反过来，一旦可见，要等对方离开七格邻域（相距 20～73 m）才移除，满表时远处的旧关系还会挤掉近处的新人。

条件是连续变化的距离，触发却只有跨格这个离散事件，所以中间的变化全漏掉了。现在的规则与 Java 版一致（Java 仓 `docs/reference/mmorpg-client-contract-aoi.md` §8「重判」、`PARITY.md`「视野（AOI）进出通知」行）：

| 规则 | 口径 |
| --- | --- |
| 进视野 | 三维距离 ≤ 视野半径（玩家 10 m，含等号），候选取本格及六个邻格；容量与优先级照旧由 `InterestSystem` 裁决 |
| 出视野 | 三维距离 > 离开半径（视野半径 × 2，即 20 m），或目标隐身且没有侦测授权；按距离判，与格子无关。两个半径之间是滞后区间 |
| 何时重判 | 每个模拟步比较当前位置和上次评估位置：没变不判；静止的实体（速度为零：刚停步、被挪位、没有 `Velocity` 的 NPC）位置一变就判；移动中的实体累计位移 ≥ 1 m 才判。首次入格（进场、换场景、同场景瞬移之后）立即判 |
| 判什么 | 两个方向都判：先撤它关注的、关注它的超出离开半径的空间来源，再在本格及邻格里给两个方向补上进入视野半径的。静止的一方不会自己评估，反向关系在位置变化的这一方评估时一并建立 |

几点说明：

- **为什么按位移而不是按时间刷新。** 距离只在有人移动时才变，按位移触发不会漏判，也不在静止的人群上空转。移动中的进出视野最多晚约 1 m 位移（双方都在动时合计约 2 m，以 9 m/s 跑约晚 100 ms），相对 10 m 的滞后区间可以忽略；停下来的那一刻一定按精确位置判一次，不会停在 9 m 处却看不见。
- **容量拒收会自愈。** 满表时被拒的普通候选不记关系；名额空出后，任一方下一次重判时补上。
- **格子只负责找候选。** 格心到顶点 20 m 时，本格加六邻格对格内任意一点至少覆盖 20 m，所以 10 m 内的目标一定在候选里（`spatial/constants/view.h` 用 `static_assert` 守住视野半径不超过格子尺寸）。离开按距离判，滞后区间不受格子形状影响。
- **同场景瞬移仍走 `ResetEntityVisibility`。** 位移重判按滞后区间处理，旧位置 20 m 内的观察者会继续看见；瞬移不是走过去的，旧位置的观察者要立刻收到移除，新位置只按进视野半径重建。
- **隐身结束不等位移。** `RefreshTargetVisibility` 当场让附近能看见它的实体补上空间来源。
- 口径常量集中在 `spatial/constants/view.h`：`kMaxViewRadius`、`kAoiLeaveRadiusFactor`、`kAoiReevaluateDistance`、`kAoiHexSize`。上次评估用的位置与视野半径存在按需组件 `AoiEvaluatedAtComp`。
- **一帧合并下发**：`AoiSystem::Update` 把这一帧所有重判的变化记进同一批，帧末统一下发。同一观察者这一帧新看见、看不见的几个目标合成一条列表消息；Update 期间位置不变，批内不会来回翻转，下发也早于随后的移动广播。

### 可见性判定的输入与触发

`CanSee` 当时返回 false 可以完全正确，问题只在条件变了之后有没有人再判一次。所以判定用到的每个输入，都必须有一个入口在它变化时触发重判：

| 输入 | 变化时由谁重判 | 范围 |
| --- | --- | --- |
| 观察者或目标的位置 | `AoiSystem::Update` 按位移重判（静止的下一帧、移动中每 1 m） | 位置变化的一方，两个方向都判，含按离开半径撤销 |
| 观察者的视野半径（`ViewRadius`） | `AoiSystem::Update`：与上次评估用的半径不同就立即重判 | 它看别人的方向 |
| 首次入场、换场景、同场景瞬移 | `AoiSystem::Update` 的首次入格分支；瞬移先经 `ResetEntityVisibility` 清掉旧位置的空间来源 | 两个方向 |
| 目标隐身开始、结束 | `BuffSystem` 在第一个隐身效果开始、最后一个结束时调 `AoiSystem::RefreshTargetVisibility`：开始时没侦测授权的观察者移除一次；结束时恢复暂隐的显式关注，并重查附近七格的观察者，不只看此刻还关注它的人 | 别人看它的方向；它看别人不受影响 |
| 观察者的侦测授权 | 带 `revealsStealth` 的显式来源登记、撤销时，`InterestSystem::Follow` / `Unfollow` 当场校正 | 这一对 |
| 观察者的容量（名额空出、压力变化） | 名额空出：补回标记让 `Update` 重扫；压力：`AoiSystem::ApplyServerPressure` 当场裁表或补回 | 这个观察者 |
| 交手关系 | `CombatEngagementSystem` 登记、续期、脱战、死亡时经 `AoiSystem::Follow` / `Unfollow` | 这一对 |

不留「被拒的候选」名单：被拒只影响这一次的显示结果，之后任何一个输入变化都会重查网格，被拒的目标自然再被检查。只发状态变化：原先没显示、这次该显示的发创建（带当前状态）；原先显示、这次不该显示的发移除；其余不发。

`ViewRadius` 目前只在玩家进场时写一次（取 `kMaxViewRadius`），按半径重判这一条给以后改视野的效果用。半径不能超过 `kAoiHexSize`，否则半径内的目标可能不在候选格里；更远的视野（鹰眼术）用显式关注。

## 关注列表优先于格子

关注列表是结果，格子只是手段。格子和距离只负责找附近的候选；客户端显示谁，由关注列表决定。名额满了、服务器压力上来时，比的是「我现在有多在意它」，不是谁离得近：

- 每条关注记着它的来源，权重取各来源标签里最高的一个（标签与权重表见 [AOI 优先级设计](aoi_priority_design_zh.md)）。
- 满表时新来的只有权重严格更高才能挤掉最低的那条；被挤掉的只剩空间来源时整条删除，有显式来源时暂隐、关系保留。
- 显式来源不看距离：交手对象、技能追踪的目标在视野外也照常显示和同步。

## 战斗关注

战斗时先看交手的人，包括敌人和友方；不在战斗时，任务 NPC 排在前面。兴趣随时在变，实现方式是**来源有寿命，权重表不变**：

| 规则 | 口径 |
| --- | --- |
| 什么算交手 | 三种来路：① 敌对——一次伤害（`SkillSystem` 的 `DealDamage`，目标没死时），我打的、打我的；② 治疗——一跳真回了血、施法者是别人的治疗（`kBuffTypeHealthRegenerationBasedOnLostHealth`），我治疗的、治疗我的；③ 一起打同一个怪——同在一个 NPC 的仇恨名单里，见下文「仇恨名单」 |
| 交手时做什么 | 双方互相登记显式来源 `AoiFollowKind::kCombat`（每对最多一份，id 恒为 0），标签 `AoiPriority::kCombat`，脱战计时重新开始。离得再远也互相看得见、收得到对方的移动与技能 |
| 权重 | `kCombat` 在每张权重表里都高于除 `kPinned` 外的所有标签（`aoi_priority.h` 用 `static_assert` 守住）。满表时交手对象先挤掉别的 |
| 脱战 | 一对实体 `kCombatDisengageSeconds`（10 秒）没有再交手，双方撤销交手来源，这就是知乎原文的 lazy time。对方仍在附近就照旧按空间来源显示，不发移除 |
| 死亡 | 死者的全部交手关系立即结束（`HandleTargetDeath` 调 `CombatEngagementSystem::OnDeath`）；致死的一击不再登记交手 |
| 离场 | `AoiSystem::OnLeaveScene` 照常清掉全部关注并发一次移除；交手记录在下一次脱战计时里因为不在同一场景而清掉，不再发消息 |

于是「战斗中交手对象排在最前、脱战后任务 NPC 自然回到最前」不需要任何人去切换表：交手来源只在交手期间存在，它一撤，原来被挤成暂隐的任务 NPC 由 `FillFreeSlots` 补回，被挤掉的附近的人由下一节补回。

实现在 `combat/engagement/`：`CombatEngagementSystem`（`RecordDamage` / `RecordHeal` / `Update` / `OnDeath`），按需组件 `CombatEngagementComp`（对方 → 交手记录：距脱战还剩的秒数、有没有敌对；两边各记一份、互为镜像）与 `CombatAllyRosterComp`（NPC 的仇恨名单）。`World::Update` 每个模拟步在 `BuffSystem::Update` 之后调一次 `CombatEngagementSystem::Update`。

### 仇恨名单：一起打同一个怪的人互相算友方

「和我打同一个怪的其他人」也是我在意的战斗对象。每个 NPC 记一份仇恨名单（`CombatAllyRosterComp`）：正在和它敌对交手的非 NPC 实体，按加入先后最多 `kMaxCombatAllyRoster`（40，一个团队副本的人数）名。

| 规则 | 口径 |
| --- | --- |
| 进名单 | 一次伤害里一方是 NPC、另一方不是时，不是 NPC 的一方进这个 NPC 的名单（谁先动手都一样） |
| 互相算友方 | 进名单或再次出手时，与名单里的其他人互相登记（续期）交手来源，离得再远也互相看得见。没有专门的友方来源：一起打怪也是交手，和敌对、治疗共用同一份 `kCombat` 来源与同一个脱战计时 |
| 治疗仇恨 | 给正在和 NPC 敌对交手的人加血，治疗者也和那个 NPC 敌对交手、进它的名单（MMO 的标准治疗仇恨）。治疗者因此看得见怪，也和打这个怪的其他人互相算友方 |
| 名单满了 | 后来的人照样和这个 NPC 交手、看得见它，只是不和名单里的人互相关注；名单里有人离开后，它下一次出手时补进来。名单里两两互相关注，开销 O(K²) 有界；更多人的混战靠空间关注 |
| 出名单 | 成员和这个 NPC 的交手记录结束（脱战、死亡、离场）时移出；空了摘除组件，NPC 销毁时随实体清理 |
| 友方何时撤销 | 不在出名单时撤：友方交手各自计时，不再一起打就按脱战时间结束。一方停手后最多再保留约两个脱战时间（它离开名单前，同伴的出手还会续一次） |
| 只对 NPC 推 | 玩家之间的混战里，打同一个人的两个人可能彼此也是敌人，不推友方；NPC 之间互相治疗没有阵营规则，也不推治疗仇恨 |

名单只记成员、不记仇恨值：AOI 只需要知道谁在打这个怪。以后 AI 选目标需要仇恨值时，在这份名单上加。生产代码目前还不刷怪（没有地方给实体挂 `Npc`），名单在刷怪接上后才会生效；用例里自己造 NPC 验证。

## 名额空出后补回附近的人

被拒或被挤掉的附近候选不留条目（空间来源以「在显示」为前提），所以名额空出时 `FillFreeSlots` 只能补回暂隐的显式关注，补不回附近的人。打完架站着不动时，战斗期间被挤掉的 NPC 会一直不回来。规则：

- `InterestSystem` 拒收附近候选、或挤掉只剩空间来源的条目时，给观察者打上空标记 `AoiNearbyRefillComp`。
- `AoiSystem::Update` 发现带标记的观察者又有空名额，就对它做一次完整重判（同位移重判），并在重判开始时摘掉标记；重判中再被拒会重新打上。
- 只有真被拒过的观察者才会重扫，名额没空不重扫，开销有界。

## 服务器压力：容量收缩时按权重裁表

场景线程忙不过来时，每个观察者少显示、少同步几个，先保住模拟步不超时。容量 = min(客户端期望数, 服务器压力给的上限)，压力 0 时上限 200、压力 1 时 20（`ScenePressureComp::GetServerCapacity`）。

**压力从哪来**（`spatial/system/aoi_load.h` 的 `AoiLoadMonitor`，常量在 `aoi_priority.h`）：

- 每个模拟步把这一步的耗时报进来，利用率 = 耗时 / 步长（50 ms），按指数平均平滑（每步权重 0.05，20 FPS 下时间常数约 1 秒）。这是 MSPT 一类的信号，事件循环里处理 RPC 的耗时不在内；要不要并入，等压测数据再定。
- 平滑利用率 0.5 以下压力为 0，0.9 时压力为 1，中间线性；量化成 10 档。每秒最多决定一次，偏离当前档位超过 3/4 档才换档，档位边界附近的抖动不会让容量来回变。
- 档位变化打一条 INFO 日志；`/metrics` 有 `scene_aoi_load_step_utilization_percent`、`scene_aoi_load_pressure_percent`、`scene_aoi_load_trimmed_entries_total`（`RegisterAoiLoadMetrics`，scene 节点启动时登记）。
- 这些阈值已定（2026-11-12），压测出基线后可调。依据：到 0.9 时一次一成的抖动就会超步，排队论里响应时间按 1/(1−利用率) 增长，0.9 已是十倍区；从 0.5 起线性逐档收缩，容量慢慢降而不是到顶才猛砍；决策每秒一次与平滑的时间常数同量级，加 3/4 档防抖不来回换档（详见 [AOI 优先级设计](aoi_priority_design_zh.md)「后续计划」）。

**压力怎么用**（`AoiSystem::ApplyServerPressure`，`World::Update` 每秒调一次）：

- 把压力写进本线程的每个场景（`ScenePressureComp` 的唯一写入口）。新建的场景在下一次调用时拿到当前压力，最多晚 1 秒。
- 值真有变化的场景里，每个观察者按新容量校正名额（`InterestSystem::ApplyCapacity`）。超出的按权重从低到高、同权重先远后近裁掉（再按句柄排，结果不依赖容器遍历顺序）。只剩空间来源的删除并打补回标记，有显式来源的转暂隐、关系保留。
- 容量回升时，暂隐的显式关注当场补回，被裁掉的附近的人由上一节的补回重扫在下一帧补回。
- 所有观察者的变化合成一批下发，每个观察者收一条列表消息。

客户端上报期望显示数的 RPC 还没接（`AoiClientCapacityComp` 没人写）；接上时，改完容量对这个观察者调一次 `InterestSystem::ApplyCapacity`，经 `AoiSystem` 下发。

## 被否掉的做法：按观察者状态切换权重表

另一种思路是让权重本身随观察者状态变化：给每种场景配「平时」「战斗中」等几张表，观察者进战、脱战时换表并整表重排。负责人 2026-11-10 讨论时提出过，比较后定为不用，作为反例记在这里：

- **两份真相**。「我在和谁交手」本身就是事实；换表还得再维护一个「观察者处于什么状态」，两者要时时对齐。换了表也照样要知道具体在和谁交手，模式替代不了逐个目标的来源，只是在上面又叠了一层。
- **整表重排、来回闪**。一次换表会同时改变表里所有条目的权重，进战、脱战在混战里来回切，每次都整表重排，客户端收到成批的创建、移除。来源有寿命只影响来源真有变化的那几条，10 秒的寿命本身就是防抖。
- **组合爆炸**。边打架边做任务、PvP 里有 Boss、组队又被别人打，该用哪张表？状态一多，表就要按组合配。来源模型里这些只是同一条目上多了几个来源，取最高的那个。
- **难测、难讲清**。静态表下一条关注的权重只取决于它有哪些来源，是纯函数；换表之后还取决于观察者此刻的模式和切换顺序。

以后加新的兴趣（选中目标、交易对象、任务追踪目标），做法都一样：加一种有寿命的来源，在权重表里给它的标签排个位置，不改流程。

## 离场和销毁

玩家、NPC 或其他实体离场、换场景或销毁时，从该实体的两张索引清理所有入边和出边，并通知仍需收到移除消息的观察者。清理只访问与该实体直接关联的关系，不遍历全节点的 `AoiListComp`，也不依赖实体仍有网格组件。清理应可重复调用，旧实体关系不能泄漏给复用的实体句柄。需要在新场景继续关注的关系，由玩法在双方重新满足场景条件后建立。

## 验收场景

| 场景 | 预期结果 |
| --- | --- |
| A 在邻格外关注 NPC B 或玩家 B | A 先收到 B 的创建和当前位置，再连续收到 B 的移动；B 不因此收到 A 的移动 |
| B 进出 A 的邻格，显式来源未变 | A 的客户端持续显示 B，不重复创建或移除 |
| A 同时因队伍与技能关注 B | 结束技能不影响队伍来源；最后一个来源撤销时，只发送一次移除 |
| A 解除对 B 的最后一个显式关注 | B 仍在附近且可见时继续显示，否则立即移除 |
| B 隐身，随后恢复可见 | 普通关注期间暂停投递；恢复时用最新状态重新创建。侦测能力按玩法授权判断 |
| B 在范围外离场或销毁，且网格组件已清 | A 收到一次移除；双方索引清干净，其他实体的关系不受影响 |
| A、B 同在一格相距 14 m，B 走到 5 m（不跨格）；或 B 跨进以 A 所在格为邻格的格子后再走近 | 走进 10 m 后双方各收一次创建；位置不再变时不重复发送 |
| A、B 互相可见，B 走到 15 m 再到 21 m（仍在邻格内），再回到 15 m、10 m | 15 m 保持显示；21 m 双方各收一次移除；回到 15 m 不重新创建，10 m（含等号）重新创建 |
| B 移动中走进视野半径但累计位移不足 1 m，随后停步 | 不足 1 m 时先不评估；停步当帧按精确位置评估并创建 |
| A 满表拒收 B，之后 A 空出名额 | 下一帧补上 A 对 B 的关注，不用等谁走动；名额没空时不重扫 |
| A、B 相距 120 m，A 打了 B 一下 | 双方各收一次创建，互相收得到移动；再打只续期，不重复创建 |
| 交手后 10 秒没再交手 | 双方各收一次移除；对方仍在附近就继续显示，不发移除 |
| A 的表满了全是任务 NPC，A 被远处的敌人打 | 敌人挤掉一个任务 NPC（转暂隐）；脱战后敌人移除、那个任务 NPC 重新创建 |
| 打架时附近的 NPC 被交手对象挤掉，脱战后 A 站着不动 | 下一帧把附近的 NPC 补回来 |
| B 被打死；或 B 离场 | 死亡：交手双方立即各收一次移除；离场：只收离场那一次移除，交手记录随后清掉 |
| A、B 相距 240 m，先后打同一个怪 | B 出手时 A、B 互相创建；怪的仇恨名单按先后记着 A、B |
| H 给正在打怪的 A 加血 | H 看见 A 和那个怪，并和打这个怪的其他人互相创建 |
| 两个玩家打同一个玩家 | 两人之间不建关系 |
| 怪死了 | 打它的人各收一次它的移除；彼此之间的友方关系按脱战时间结束 |
| 第 41 个人打一个已有 40 人的怪 | 看得见怪，但不和名单里的人互相关注；名单里有人死了，它下一次出手补进名单 |
| 场景线程持续满负荷 | 压力升到顶，容量降到 20：权重高的留下，同权重近的留下，其余各收一次移除；负载回落后补回 |
| A、B 都不动，B 隐身再显形 | 隐身时 A 收一次移除、B 照样看得见 A；隐身期间 B 走动也不会被加回来；还有别的隐身效果时不显形；最后一个结束时 A 收一次创建 |
| A 不动，视野半径从 10 改成 15、再改成 5 | 14 m 外的 B：改成 15 的下一帧创建，改成 5 的下一帧移除；B 看 A 不受影响 |
| 同一帧两个人走近同一个观察者 | 观察者只收一条列表创建，里面两个人都在 |

## 实现

### 数据结构

两张索引描述同一批有向关系，只由 [`InterestSystem`](../../cpp/libs/services/scene/spatial/system/interest.h) 写，定义在 [`scene_node_scene_comp.h`](../../cpp/libs/services/scene/spatial/comp/scene_node_scene_comp.h)：

| 组件 | 所在实体 | 内容 | 创建 |
| --- | --- | --- | --- |
| `AoiListComp`（正向） | 观察者 | 目标 → `AoiEntry`；`visibleCount` 为已占用的容量 | 第一次建立关系时（空间来源被接纳或显式关注登记） |
| `AoiWatchersComp`（反向） | 目标 | 观察者 → 是否显示 | 第一次有人关注它时 |

`AoiEntry` 记录空间来源（`spatial` 与空间标签 `priority`）、显式来源列表 `follows` 和显示状态 `visible`。显式来源 `AoiFollowGrant` 由身份 `AoiFollowSource`（种类 `AoiFollowKind` + 实例号，如 `team_id`、`buff_id`）、淘汰权重标签和侦测授权 `revealsStealth` 组成。两个组件都是按需状态，不入库。

不变量：条目存在当且仅当有空间来源或显式来源；有空间来源必然在显示；在显示必然满足可见条件（未隐身，或某个显式来源授予侦测）并占一个名额；正向条目与反向记录一一对应，显示状态一致。所有改动经 `interest.cpp` 里的插入、删除、显示、隐藏四个原语完成。

### 入口

| 入口 | 用途 |
| --- | --- |
| `AoiSystem::Follow(watcher, target, grant)` / `Unfollow(watcher, target, source)` | 玩法建立和撤销显式关注，必要时立即下发创建或移除 |
| `AoiSystem::RefreshTargetVisibility(target)` | `BuffSystem` 在隐身标签出现、消失时调用 |
| `AoiSystem::OnLeaveScene(entity)` | 离场、换场景、销毁前的唯一 AOI 清理入口；`DestroyPlayer` 兜底补调 `LeaveCurrentScene` |
| `AoiSystem::Update` | 更新格子成员；首次入格、位置变化到了重判时机、或有待补回的附近候选且有空名额时，按距离重判空间来源（两个方向），只增删空间来源 |
| `CombatEngagementSystem::RecordDamage(attacker, target)` | 一次伤害：双方登记或续期交手来源；打的是 NPC 时进它的仇恨名单、与名单里的人续期友方交手 |
| `CombatEngagementSystem::RecordHeal(healer, target)` | 一跳治疗：双方登记或续期交手来源；治疗仇恨推给 target 正在打的 NPC |
| `CombatEngagementSystem::Update(delta)` / `OnDeath(entity)` | 脱战计时到时、死亡时撤销交手来源并移出仇恨名单 |
| `AoiLoadMonitor::Observe(stepSeconds, fixedDeltaSeconds)` | 每个模拟步报耗时，每秒给出一次压力档位 |
| `AoiSystem::ApplyServerPressure(pressureFactor)` | 压力写进各场景，容量变了的场景按权重裁表或补回 |
| `InterestSystem::ApplyCapacity(watcher, changes)` | 按当前有效容量校正一个观察者的名额，返回裁掉的条数 |
| `InterestSystem::GetVisibleWatchers(target, out)` | 移动、属性、技能广播的接收者 |

`InterestSystem` 的写函数把可见性变化按发生顺序写进 `AoiVisibilityChanges`。`AoiSystem::SendVisibilityChanges` 求出每对（观察者，目标）的净变化，同一批里显示又隐藏的不发；只涉及一个目标的观察者按目标合并成一次广播，涉及多个目标的收一条列表消息；离场者的移除用 `ActorDestroyS2C`。消息号、消息体与客户端契约不变。

### 投递

- 移动（`MovementSystem::BroadcastMove`）、属性同步（`ActorStateAttributeSyncSystem`）和技能广播（`ViewSystem::BroadcastMessageToVisiblePlayers`）都发给反向索引里正在显示目标、且有网关会话的观察者。视野半径外的显式关注者按最低档接收属性增量。
- 同场景瞬移只撤空间来源；`TeleportWithinScene` 随后补发一次移动广播，让仍在显示它的显式关注者立即拿到新位置。
- 队伍逻辑没有改：队友在视野内仍按空间标签 `kTeammate` 提高优先级（[team-system.md](team-system.md) §F.4），视野外不同步。需要视野外同步时，由队伍逻辑按两个方向分别 `Follow`，来源种类用 `AoiFollowKind::kTeam`。

### 代价

- 离场清理只访问该实体的出边与入边，复杂度与它的关系数成正比，不扫描全节点。
- 补位只在观察者有暂不显示的显式关注时才扫描它自己的表；多数观察者一条都没有，直接返回。
- 每个条目多一个空的 `std::vector` 和两个布尔，约增加 24～32 字节，反向索引与正向条目一一对应。没有压测数据，上线前随 AOI 压测复核。
- 位移重判：每个模拟步每个在场实体做一次位置比较；真正评估时的开销是 O(七格内人数 + 它的关注表 + 关注它的人数)。移动中的玩家约每走 1 m 评估一次（20 FPS、9 m/s 约每 2～3 帧一次），静止的人群不评估。满表时普通候选在 `EvictForWeight` 入口直接拒绝，不再逐条扫表。Java 版同一口径的出生点人群基准：1000 人全在 15 m 内时整帧均值 42.7 ms → 4.2 ms（见 Java 仓 `PARITY.md` 同一行）；本仓没有压测数据，上线前随 AOI 压测复核。
