文件描述符（下文写 fd）：进程每打开一个文件、每建一条网络连接都占一个。进程能同时打开多少个由 `RLIMIT_NOFILE` 限制，分软限（当前生效的值）和硬限（软限最多能抬到的值）。

## 1. 设计要点速览

一共五道防线，前一道挡不住的情形由后一道接住。

| 防线 | 做法 | 为什么这样做 | 位置 |
| --- | --- | --- | --- |
| 发布前读硬限 | 运维在每个节点池读一次容器的 nofile 硬限，不够就先改节点运行时 | 硬限由节点的容器运行时决定，K8s 没有按容器声明的字段，进程自己改不了 | 运维手册 §3.1 |
| 启动门槛 | 进程启动时把软限抬到硬限；抬完仍低于「客户端准入上限 + 4096」就拒绝启动 | 起不来只影响这一台新 Pod；跑到半路 fd 用尽影响一整台在线玩家 | `open_file_limit.h`、`node.cpp` 的 `EnsureOpenFileLimitOrDie` |
| 用量告警 | 导出 `process_open_fds` 与 `process_max_fds`，超过 80% 持续 5 分钟告警 | 启动门槛只保证下限；泄漏、余量估小、带豁免运行都要靠运行期的数看出来 | `process_fd_metrics.h`、`deploy/k8s/cpp-node-resource-alerts.yaml` |
| accept 降级 | fd 或内存耗尽时不再崩溃：排掉一条排队的连接，或暂停监听 100ms | 上游 muduo 在这里直接终止进程，一台 gate 的全部在线连接一起断 | muduo 的 `Acceptor`、`SocketsOps`（三份副本） |
| 崩溃原因可见 | 任何一处 `LOG_FATAL` 在终止进程前把最后一行日志同步写进 stderr | Linux 上业务日志走异步文件，终止时来不及落盘，`kubectl logs --previous` 里是空的 | `node.cpp` 的 `EchoFatalLineToStderr` |

## 2. 需求分析：不处理会发生什么

- **准入上限够不着**。容器里软限常见是 1024（外部常识，各集群还没有实测）。gate 配的客户端连接上限是 2 万，实际到一千条左右 accept 就开始失败，配置的上限成了死代码。
- **耗尽即崩溃**。上游 muduo 的 accept 遇到全机 fd 用尽（`ENFILE`）、内核缓冲不足（`ENOBUFS`）、内存不足（`ENOMEM`）直接 `LOG_FATAL`。这类错误正是连接洪峰的典型产物，一次洪峰就能让整台 gate 的在线玩家掉线。
- **进程级 fd 用尽时空转**。遇到 `EMFILE`，监听 fd 一直可读，事件循环原地打转，每转一圈打两行日志。
- **影响不止新连接**。fd 用尽之后，到 Redis、Kafka、etcd 的重连同样失败。etcd 租约续不上，节点会被摘除；日志滚动时打开新文件失败，Release 构建下随即崩溃。
- **崩溃后找不到原因**。Pod 反复重启，运维在 `kubectl logs --previous` 里看不到任何一行。

由此得到的要求：资源耗尽不能让已在线的玩家掉线；耗尽之前要有预警；耗尽期间可观测，压力过去后自己恢复；进程真的退出时要留下原因。约束：不新开线程（AGENTS §9）；muduo 的三份副本行为一致。

## 3. 设计分析：每道防线的做法与取舍

### 3.1 发布前读节点池硬限

容器的 nofile 由节点池的容器运行时决定，与容器里跑什么进程无关。已有旧 Pod 的集群直接读旧 Pod 的限值。首次上线的集群没有旧 Pod，就在每个节点池起一个一次性的探针 Pod 读 `ulimit -Sn` 与 `ulimit -Hn`，读完自动删除，镜像用要发布的节点镜像。命令在运维手册 §3.1。

硬限要不低于启动门槛算出的需求：gate 24096、battle 8192、scene 4096，改过准入上限的按「上限 + 4096」算。

这一步是硬前置。启动门槛会拒绝启动，battle 的 hostPort 形态单副本时拒启等于整体停服，所以不能把「发布后看它起不起得来」当成检查手段。

### 3.2 启动门槛

- 位置在引擎的 `Node::Initialize`，读完配置、初始化日志之后，打开任何网络 fd 之前。三类节点都经过这里。
- 软限抬到「硬限与 1048576 中较小的那个」，只抬不降，不动硬限。非特权进程本来就有权把软限抬到硬限，不需要特权容器。
- 需求 = 客户端面的准入上限 + 4096。gate 取 `GateMaxConnections`，battle 取 `BattleMaxConnections`，scene 没有客户端面，按 0 算。
- 抬完仍不够就拒绝启动：先写一行 `FATAL open file limit config: ...` 到 stderr，再退出。
- 纯判定（算需求、判结果、拼文案）放在 `open_file_limit.h`，不做系统调用，Windows 上也能跑单测。

没选的做法：

| 做法 | 不选的原因 |
| --- | --- |
| initContainer 加特权去改 ulimit | 为一个进程自己就能改的值给节点提权 |
| 学 Redis：抬不够就自动调低连接上限 | 准入上限悄悄失真，login 仍按配置的上限往这台 gate 派人；scene 也没有上限可调 |
| 在启动壳里加 `ulimit -n` | 同一件事的第二份实现，两处会不一致 |
| 放在 gate 自己的 `main.cpp` | 那时 Redis、Kafka、etcd 已经初始化；放引擎里 scene 与 battle 也一并覆盖 |

余量 4096 的依据（2026-11-12 定案，不等实测）：它覆盖节点间连接、Redis、Kafka、etcd 客户端、日志文件和事件循环自己用的 fd。早先最大的一项是「到全服 scene_manager 的连接随区服数增长」，2026-11-05 起 scene_manager 按 zone 收窄、gate 到路由服只连按 zone 取的几台，这一项不再增长。这个数只决定启动时要不要拒绝，运行期够不够由 3.3 的告警看，不靠它估得准。

运维豁免：环境变量 `NODE_OPEN_FILE_LIMIT_MODE=warn` 时只打警告、继续启动。它只豁免「限值不够」，不豁免「读不到限值」。这是「硬限暂时改不了又必须先起服」的短时手段，带着它运行等于随时可能 fd 用尽，所以超过 1 小时会告警。gate 与 battle 的应急首选是把准入上限调到「软限 − 4096」以内，那样检查直接通过，用不着豁免。

### 3.3 运行期用量指标与告警

指标由 C++ 节点已有的 Prometheus 出口导出，定义在 `process_fd_metrics.h`：

| 指标 | 含义 |
| --- | --- |
| `process_open_fds` | 本进程当前打开的 fd 数，只在 Linux 上有 |
| `process_max_fds` | `RLIMIT_NOFILE` 软限，只在 Linux 上有 |
| `cpp_node_open_file_limit_required` | 启动门槛算出的需求 |
| `cpp_node_open_file_limit_exempted` | 1 表示带豁免启动 |
| `cpp_node_accept_exhausted_total{reason}` | accept 因耗尽失败的累计次数，`reason` 取 `descriptors` 或 `memory` |
| `cpp_node_accept_paused_total` | 暂停监听的累计次数 |

几处取舍：

- **前两个用 Prometheus 客户端库的标准名字**。Go 服务的进程采集器导出同名指标，所以一条告警规则同时管住 C++ 节点与 Go 服务，现成的面板也直接能用。
- **fd 数怎么读**。对 `/proc/self/fd` 做一次 `stat`：Linux 6.2 起这个目录的大小就是 fd 数，一次系统调用。更老的内核目录大小是 0，退回逐项数，再减去扫描时自己占的那一个。
- **不缓存**。只在被抓取时读，读在主循环线程上，不加线程也不加定时器。缓存会让告警读到旧值；老内核上逐项数的开销见 5.5。
- **读不到就不导出这个序列，而不是导出 0**。导出 0 时比值规则永远不响，面板上还显得一切正常；序列缺失在面板上是空的，一眼看得出没数据。
- **accept 计数从进程启动起就以 0 导出**。计数器第一次出现时如果已经是 1，`increase()` 抓不到这一次。

告警在 `deploy/k8s/cpp-node-resource-alerts.yaml`：

| 告警 | 条件 | 级别 | 含义 |
| --- | --- | --- | --- |
| `ProcessOpenFilesNearLimit` | 用量超过软限的 80%，持续 5 分钟 | warning | 泄漏、容量不够或余量估小，赶在耗尽之前处理 |
| `CppNodeAcceptResourceExhausted` | 5 分钟内 accept 因耗尽失败过 | warning | 已经降级过一次，新连接有一段进不来 |
| `CppNodeAcceptResourceExhaustedSustained` | 上一条持续 5 分钟 | critical | 这台节点一直接不进新连接，先从入口摘掉 |
| `CppNodeOpenFileLimitExempted` | 带豁免运行超过 1 小时 | warning | 应急手段被留成了常态 |

规则引用的指标名与标签取值由 `tools/scripts/tests/cpp_node_resource_alerts_contract.tests.ps1` 对照 C++ 源码钉住。原因是这类错误不报错：指标改了名，告警只会永远不响。

### 3.4 accept 失败的降级

accept 返回失败之后怎么办，只由 errno 决定。`Acceptor::classifyAcceptFailure` 是纯函数，分成下面几类：

| 类别 | errno | 处置 |
| --- | --- | --- |
| 等下一次 | `EAGAIN`、`EINTR` | 什么都不做 |
| 这一条连接自己没了 | `ECONNABORTED`、`EPROTO`、`EPERM`，以及已排队连接上的网络错误（`ENETDOWN`、`EHOSTUNREACH` 等） | 跳过，接下一条 |
| fd 用尽 | `EMFILE`（进程级）、`ENFILE`（全机级） | 让位排掉一条；让位做不成就暂停监听 |
| 内核缓冲或内存不足 | `ENOBUFS`、`ENOMEM` | 暂停监听 |
| 编程错误 | `EBADF`、`EFAULT`、`EINVAL`、`ENOTSOCK` 与不认识的 errno | 仍然 `LOG_FATAL` |

**让位**。进程平时预留一个空闲 fd（开着 `/dev/null`）。fd 用尽时关掉它腾出一个名额，把排在最前的连接接进来立刻关掉，再把空闲 fd 占回去。这样对端马上看到连接断开，可以换一台重试，不用在队列里等到超时。排掉时以 RST 关闭，不留 60 秒的 `TIME_WAIT`。做法出自 libev 文档里「接不进来时怎么 accept」一节。

**空闲 fd 占不回来的情形**。别的线程（Kafka、日志滚动）可能在「关掉空闲 fd」与「占回去」之间抢走名额。上游不检查这一步，之后永远让不了位。现在记成「没占上」，下次进来先补占；补占也失败就退回暂停监听。

**暂停监听 100ms**。监听 fd 是水平触发的，接不进来又排不掉时它一直可读，不暂停就是原地空转。暂停期间新连接留在内核的全连接队列里，队列满了由内核丢 SYN、客户端重传。取 100ms 的理由：比一次 TCP 重传（1 秒起）短得多，恢复后排队的客户端不会多等一轮；又足够长，耗尽持续期间每秒最多醒 10 次。恢复监听的定时器回调只持存活令牌的弱引用，先查令牌再碰对象（AGENTS §11.7）。

**每次可读事件只接一条**，不循环接到队列空。连接风暴时一次事件接几千条，会饿死同一个事件循环上已有连接的读写。Envoy 的 `max_connections_to_accept_per_socket_event` 设 1 是同一个理由。

**日志限频**。失败日志最多每秒一行，带上这一秒里攒下的次数，用单调时钟计时。连接自己没了是公网上的常态，打 WARN；资源耗尽打 ERROR。

**计数**。三个累计次数是进程级的原子量：写在事件循环线程，读在指标出口，只做累计。

没选的做法：

| 做法 | 不选的原因 |
| --- | --- |
| 只把三个 errno 从「致命」挪到「预期错误」（设计稿最初写的「3 行改动」） | 不崩溃了，但监听 fd 一直可读，循环空转并刷日志 |
| 耗尽时关掉监听 socket，过后重开 | 队列里排着的连接全丢，重新绑定端口有窗口；停掉读事件就够了 |
| 监听 fd 改成边沿触发 | 必须循环接到队列空，与「每次只接一条」冲突；耗尽时照样要让位或暂停 |
| 耗尽就退出，让 K8s 重启 | 一台上的在线玩家全掉线，而压力多半还在，重启后再次耗尽 |

### 3.5 进程因致命错误退出时原因可见

muduo 的日志对象析构时先调输出函数，级别是 FATAL 时紧接着调一次冲刷函数，然后终止进程。两次调用在同一线程、同一次析构里。利用这一点：

- 输出函数把「本线程最近一行日志」记在线程局部变量里（一次赋值，不拷贝内容）。
- 把冲刷函数换成自己的 `EchoFatalLineToStderr`，它把记下的那一行同步写进 stderr。

这样全进程任何一处 `LOG_FATAL` 都留得下最后一句，不用逐个调用点改，也不靠写代码的人记得先写一遍 stderr。

- 不在这里等异步日志落盘。后端线程卡在磁盘上时，致命错误也必须立刻终止进程。
- `FatalClientEndpoint` 与 `FatalStartupConfig` 仍然自己先写一行带固定前缀的 stderr，因为部署脚本与运维手册按前缀去找。它们写过之后置一个标记，冲刷函数不再重复写。
- LogLevel 配置错误的拒启（`node_log_level::RejectStartup`）自己写一行 stderr 后直接退出，不经过 `LOG_FATAL`，不会走到冲刷函数，也就没有重复行。
- Windows 上每一行日志本来就写到控制台，不重复写。

### 3.6 muduo 的网络源码有三份副本，要一起改

| 副本 | 用途 |
| --- | --- |
| `cpp/libs/engine/muduo_windows/src/muduo/net/` | Windows 上编进 muduo.lib |
| `third_party/muduo/muduo/net/` | 业务代码与测试 `#include` 实际命中的头文件 |
| `tools/archived/muduo_linux_overlay/muduo/net/` | Linux 构建时覆盖进上游源码，生产用的是这份 |

只改其中一份不会当场报错。最隐蔽的是前两份不一致：`Acceptor` 加了成员之后，业务代码按一种类布局分配对象，库按另一种布局构造，链接照样成功，运行期才堆损坏。Linux 那份是整文件覆盖，目标文件必须在上游存在，并且要同时兼容子模块指向过的两个上游版本（成员函数 `listenning` 与 `listening` 的拼写不同）。

`tools/scripts/tests/muduo_acceptor_copies_contract.tests.ps1` 守着这件事：前两份逐字节一致，Linux 那份去掉注释后类体与分类函数一致，三份都把资源耗尽的 errno 交回调用方。

## 4. 思想分析：这套做法背后的几条判断

1. **分层兜底，没有哪一层要求估得准**。硬限读错了有启动门槛，余量估小了有用量告警，告警没人看还有降级。
2. **拒绝放在启动期，降级放在运行期**。启动时拒绝的代价是一台新 Pod 起不来，旧 Pod 还在服务；运行期崩溃的代价是一整台在线玩家掉线。同一个问题，越早暴露越便宜。
3. **资源耗尽与编程错误分开对待**。前者是外部压力，过去了就能恢复，所以降级；后者说明程序状态已经不可信，所以立刻终止。
4. **观测走标准名字**。同名指标让 C++ 与 Go 共用一条规则，不为 C++ 另造一套。
5. **常量不做成配置**。100ms、每秒一行、4096、80% 都写死，依据写在代码旁边。它们没有需要按环境调整的理由，多一个配置项就多一处配错。
6. **不加线程**。计数、读 fd 数、恢复监听都挂在已有的事件循环上。

## 5. 漏洞分析：已知残余与为什么接受

1. **暂停期间新连接进不来**，直到压力解除。这是有意的：在内核队列里排队比进程崩溃好。持续 5 分钟会升到 critical，处置是把这台节点从入口摘掉。
2. **让位排掉的可能是正常玩家**。对端看到连接被重置，与断线一样走重连流程。
3. **全机级 fd 用尽时同一节点上的其他进程也受影响**。本进程能做到的只是自己不崩，要对照节点的 `fs.file-nr` 排查。
4. **带豁免运行**。准入闸门在 accept 拿到 fd 之后才判，上限没调时客户端连接会先占满 fd 表，随后 etcd 续约失败被摘除，或日志滚动失败崩溃。所以豁免超过 1 小时告警。
5. **内核低于 6.2 时每次抓取要逐项数 fd**。2 万条连接就是 2 万个目录项，在主循环线程上，按抓取间隔每 15 到 30 秒一次。定案不改：Prometheus 各语言的客户端库都是这样读的，开销估计在毫秒级（没有实测）。
6. **三种错误码与暂停路径在单测里造不出来**。`ENFILE`、`ENOBUFS`、`ENOMEM` 只有分类表有单测；让位、暂停、暂停期间对象析构都靠容器里压低 `ulimit` 的那一步验证。
7. **回显只有最后一行**。更早的上下文在日志文件里，终止时没落盘的部分会丢。
8. **Windows 上没有 fd 两个序列**，比值规则在 Windows 上没有数据、不会响。Windows 只用于开发，不部署。

## 6. 步骤分析与执行步骤
