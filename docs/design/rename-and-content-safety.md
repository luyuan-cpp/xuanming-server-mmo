## 3. 存储与扩缩容:继续用 TiDB

名字判重的全部实现是「以名字为主键的一行,写成功就算占到」。不同名字是不同的行,互不相干,所以按名字哈希分片之后天然能水平扩展,不需要全局锁。

扩和缩都分两层,都已经有:

| 层 | 怎么扩 | 怎么缩 | 应用要改吗 |
|---|---|---|---|
| 一个 TiDB 集群之内 | 加 TiKV / TiDB 节点,数据自动重新均衡 | 下线节点,数据先自动迁走 | 不用 |
| 跨集群 | 用 `tools/dbmove` 把整个逻辑库搬到新集群 | 搬回来,旧集群下线 | 不用,改目录指向 |
| data_service 进程 | 无状态,加副本 | 减副本 | 不用 |

名字按 `crc32(name_norm) % 64` 落到 64 个固定的槽,再合并成 K 个逻辑库(`go/shared/dirshard`)。**K 在建表之后不能改**,生产首次上线定 64(`Directory.LogicalShards`),所以上线那一次要定对;之后扩容只搬库,不改 K。

帮会名在 `mmorpg_guild` 一个逻辑库里,靠唯一索引判重。它用的是第一层(集群内加减节点)。帮会数量比角色少一到两个数量级,够用很久。以后 `mmorpg_guild` 按业务键拆库时,唯一索引管不了全服,帮会名要搬到按名字分片的登记表(和角色名同样的做法),到时另写。

## 4. 角色改名

### 4.1 规则

数值全部进配表 `RoleNameRule`(单行表,现有 `min_chars` / `max_chars` 等),新增四列:

| 列 | 值 | 含义 |
|---|---|---|
| `rename_cooldown_seconds` | 604800 | 两次改名成功之间的最短间隔(7 天) |
| `old_name_hold_seconds` | 604800 | 旧名留在原主名下的时长(7 天) |
| `rename_item_id` | 改名卡的道具 id | 新道具,`Item` 表加一行 |
| `rename_item_count` | 1 | 一次改名消耗几张 |

改名卡卖 30 元,价格配在支付商品那条线(`proto/payment/payment_table.proto`),不在这张表里。

冷却只从上一次改名成功算起,新建的角色可以立刻改。新名的字数、字符集和建角是同一套规则。

改名入口在 scene(4.3)。这张表 C++ 已经有生成物(`cpp/generated/table/code/rolenamerule_table.h`),scene 直接读新列,再把规则数值随请求带给 data_service。data_service 不加载玩法配表,现有的规则包也是「数值由调用方传进来」这个口径。

### 4.2 名字行的三个状态

`player_name` 加一列 `held_until_ms`(默认 0)。一行名字有三个状态:

| 状态 | 判据 | 含义 |
|---|---|---|
| 预留 | `bound_ms = 0` 且 `held_until_ms = 0` | 有人正在建角或改名,想要这个名字 |
| 已绑定 | `bound_ms ≠ 0` 且 `held_until_ms = 0` | 某个角色现在的名字 |
| 保护 | `held_until_ms ≠ 0` | 某个角色改名之前的名字,`player_id` 仍是原主,到 `held_until_ms` 为止别人拿不到 |

保护到期**不用后台扫描**。别人来占这个名字时撞上这一行,发现已过期,就用一条带条件的 UPDATE 把它改成自己的预留行:

```sql
UPDATE player_name
   SET player_id = ?, name = ?, created_ms = ?, bound_ms = 0, held_until_ms = 0
 WHERE name_norm = ? AND player_id = ?原主 AND held_until_ms = ?读到的值 AND held_until_ms <= ?现在
```

改到 1 行就是占到了;改到 0 行说明别人抢先了,重新读这一行再判。全程是主键上的单行操作,不需要给名字表加二级索引。这张表刻意没有二级索引,加了会破坏 `Reserve` 现有的锁顺序结论。建角的 `Reserve` 也走这条规则:没过期的保护行算「已被占用」,过期的可以接管。

原主在保护期内改回旧名是允许的(要过了冷却):预留那一步发现这一行是自己的保护行,不动它,绑定时把它直接改回已绑定。

### 4.3 流程

入口在 scene(C++),因为改名卡在背包里。scene 先把「正在改名」记进存档,再去请求 data_service,这样任何一步断掉都能从存档接着做。

1. **客户端 → scene**:`RenamePlayer{name, request_id}`。
2. **scene 预检**(不改任何状态):没有进行中的改名;背包里有改名卡,而且没有被别的操作占用;角色不在交接、退出中;本地记的上次改名时刻已过冷却。冷却的预检只是为了少发一次无用请求,真正的判定在提交点。
3. **scene → 内容安全服务**:`CheckText(ROLE_NAME)`。不通过就回 tip,到此为止。
4. **scene 记下进行中的改名**:流水号 `seq`(上一次的值加 1)、新名原文、占用的那张改名卡。这条记录放在 `PlayerProfileComp` 里,和背包在同一条存档记录,一起落库。卡还在背包里,只是被这次改名占用,别的入口移不走它。随后立刻存盘,并回客户端「已受理」。
5. **存盘确认落库之后**,scene → data_service:`RenameRole{player_id, seq, name, 规则数值, 调用方签名}`。data_service 依次做:
   1. 规范化与结构校验(和建角同一个函数)。
   2. 玩家分片:登记改名记录,状态「进行中」。`seq` 比已有记录小,回「过期请求」;相同,直接回已有的结局。
   3. 新名所在分片:预留新名。只写名字行,不动 `player_name_owner`。被别人占着就中止这次改名,回「已被占用」。
   4. 玩家分片一个事务,**这是提交点**(4.4)。
   5. 收尾:新名置为已绑定 → 旧名置为保护 → 覆盖 Redis 名字缓存 → 改名记录标成「已收尾」。
6. **scene 收到结局**:
   - 成功:扣掉占用的那张卡,`PlayerProfileComp.name` 改成新名,清掉进行中的记录,存盘,推送结果给客户端。
   - 明确失败(已被占用、不合规、冷却中、角色冻结):清掉记录,卡自动解除占用,存盘,推送 tip。
   - 结果未知(超时、服务不可用、`BUSY`,以及本版本不认识的结局取值):记录和占用都留着,按 1 秒到 30 秒的退避重发同一个 `seq`。玩家下线了,下次入场接着发。没有单独的中止接口:data_service 的后台把超过 10 分钟没有结局的「进行中」作废(结局 `EXPIRED`),scene 重发时拿到它再解除占用。
   - 结局回来时玩家正在交接、退出(存档此刻不可改):一个字都不动,记录留着,稍后或由下一个持有者重发同一个 `seq`。
   - 成功但改名卡没扣成:不落结局。记录和占用留着继续重发,直到扣成;占用挡着别的入口拿走这张卡,正常走不到这里,走到了每次都报 `player_rename_card_not_consumed`。

第 4、5 步之间等落库,是为了不出现「名字已经改了,存档里却没有这次改名」:那样一次崩溃就会让改名卡没扣、存档里的名字还是旧的。等待多一次存盘往返,改名是低频操作,可以接受。

客户端这次请求的回包只表示「已受理」或「立即拒绝」,最终结局走推送。原因是结局要等两次跨服务往返。scene 的玩家 RPC 能否延后回包,落码前核对;能的话可以省掉推送(第 10 节)。

### 4.4 提交点

玩家分片上的一个本地事务。改名记录、`player_name_owner`、角色行都在同一个逻辑库,所以不跨库:

1. 锁路由行,再锁角色行。锁序和建角提交相同。
2. 角色在役;没有过户冻结(`trade_listing_id = 0`),没有准备令牌(`prepare_token = 0`)。
3. 锁改名记录:`seq` 相同,状态是「进行中」。
4. 冷却:现在距上次改名成功不少于 `rename_cooldown_seconds`。第一次改名直接过。
5. `player_name_owner` 这一行从旧名改成新名(条件里带旧名)。
6. 角色行 `role_proto` 里的名字改成新名。
7. 改名记录置为「已提交」,记下这次成功的时刻和旧名保护的到期时刻。

提交之前失败,角色还是旧名,新名最多留下一行预留,由中止清掉。提交之后,角色就是新名,剩下的都是可以重做的收尾。

改名记录按玩家一行(主键 `player_id`),只保留最近一次,不删除。它同时承担三件事:

- **幂等**:同一个 `seq` 重发,回同一个结局。
- **挡住迟到的请求**:`seq` 比记录小的请求一律拒绝。号是 scene 按玩家递增发的,不用发号器的 ID,因为那种 ID 不能比先后。
- **让作废安全**:作废是「把进行中改成已拒绝」的条件更新,和提交抢同一行。作废成功之后,这次改名再也提交不了,这时删预留的名字行才不会出现「名字放掉了,迟到的提交又把角色改成这个名字」。被拒绝的 `seq`(名字被占、不合规、冷却中、角色冻结)同样记下来:否则同一个请求的迟到副本以后条件变了又能提交,而 scene 早已把改名卡还给了玩家。

存档回档会让 scene 的 `seq` 变小。data_service 的回包带当前 `seq`,scene 收到「过期请求」时把自己的号追上去,让玩家重试。

### 4.5 收尾、作废与崩溃窗口

| 断在哪 | 当时的状态 | 怎么恢复 |
|---|---|---|
| scene 记了进行中,存盘之前崩 | 什么都没发生 | 玩家重连后重新发起 |
| 记录已落库,`RenameRole` 没发出或结局未知 | 存档里有进行中的记录,卡被占用 | 下次入场接着发同一个 `seq` |
| data_service 登记了记录,提交之前崩 | 记录「进行中」,新名可能已预留 | scene 重发,从断点接着做;一直没人重发的,后台 10 分钟后作废并删预留行 |
| 提交之后,收尾之前崩 | 角色已是新名;新名行还是预留,旧名行还是已绑定 | 后台循环扫「已提交、未收尾」的记录接着做,做法同删角的 `ResumeRemovals`。这段时间两个名字都在本人名下,别人拿不到 |
| 作废成功,删预留行失败 | 新名留着一行预留 | 记录保持「已拒绝、未清理」,后台接着删 |
| scene 收到成功,扣卡存盘之前崩 | 存档里还是进行中 | 下次入场重发同一个 `seq`,得到「已提交」,再扣卡、改名 |
| 覆盖名字缓存失败 | 缓存里还是旧名 | 没覆盖成功就不标「已收尾」,后台重试 |

核账工具 `cmd/create_residual` 不用改判定:保护行的绑定时刻非 0,不在它扫的预留态里;在役角色名下多出来的预留行(改名进行中会短暂这样)老到被扫出来时按「要人看」报告,不自动删。

### 4.6 与删角、过户的关系

三者互斥,判定都在玩家分片的角色行锁之下:

- 改名提交时,角色挂着过户冻结或准备令牌就拒绝。
- 删角、过户开始时,这名角色的改名记录是「进行中」或「已提交、未收尾」就拒绝,可重试。收尾正常在毫秒级完成;卡住的由后台做完,并有告警。

不让两者交错,是因为删角按角色当前的名字释放名字行。改名收尾到一半时删角,旧名那一行会永远留成「已绑定」,新名那一行会被收尾重新登记到一个已删的角色名下。

删角之后,这名角色的保护行不用特别处理,到期自然可以被接管。

改名真正的工作量在这里。核对到的副本和读者:

| 位置 | 性质 | 改名后谁更新 |

## 5. 帮会改名

入口在 guild 服务:`RenameGuild{guild_id, name, request_id}`,只有帮主能发。先送检(`GUILD_NAME`),再进事务。

规则进 `GuildRule` 表:`rename_cooldown_seconds`(604800)、`name_hold_seconds`(604800)、`rename_cost_funds`(扣帮会资金,数值待定,见第 10 节)。

帮会行、唯一索引、资金都在 `mmorpg_guild` 一个库里,所以改名是**一个本地事务**,不需要角色改名那套分步流程。只新增一张表 `guild_name_hold(name_norm 主键, guild_id, held_until_ms)` 存保护中的旧名。事务里的顺序固定:

1. 锁帮会行。核帮主身份、冷却(`guild` 表加 `renamed_ms`)、资金够。
2. 改帮会行的 `name`、`name_norm`。唯一索引判重,撞了就是已被占用。
3. 加锁读保护表里新名那一行。是别的帮会的、没过期,回滚,回已被占用;过期的,或者是自己的,删掉。
4. 把旧名写进保护表,到期时刻是现在加 `name_hold_seconds`。
5. 扣资金,写 `renamed_ms`。提交。

**必须先做第 2 步、再做第 3 步。** 反过来的话:甲帮正把 A 改成 B(还没提交),乙帮想改成 A。乙先查保护表,看不到甲那条还没提交的保护行;然后乙改帮会行,在唯一索引上等甲;甲提交后乙改成功,拿走了甲刚放下、本该保护 7 天的名字。先改帮会行,乙就先在唯一索引上等到甲提交,再读保护表时能看到甲的保护行。

建帮也要在插入帮会行之后做第 3 步,否则建帮可以绕过保护期。

帮会解散时名字直接放掉,不进保护期(和删角一致)。

帮会名的副本:帮会的各个查询接口都是现读帮会行。落码前再扫一遍别的服务有没有存帮会名(帮会榜、聊天、scene);核对时在 C++ 和 `proto/scene` 里没有找到。

## 6. 内容安全服务

新增一个 Go 服务 `go/content_guard`。所有收玩家文字的服务在落库或转发之前调它。

### 6.1 边界

它只回答一个问题:**这段文字在这个场景能不能用,打码之后是什么。**

- 它不知道玩家的等级、发言频率、私聊对象。这些行为规则留在 chat(第 7 节)。
- 由**收文字的那个服务**送检:login(建角名)、scene(角色改名、宠物名)、guild(帮会名、公告)、chat(聊天)。data_service 不调它。原因是内容安全服务调平台接口时要查玩家的渠道身份(6.5),那要问 data_service;data_service 再反过来调它就成了循环依赖。data_service 保留现在的结构校验和那几个防冒充官方的内置词。
- 集中成一个服务的原因:调用方有 Go 也有 C++,只有一份实现,各处判定才一致;平台和第三方的密钥、配额、审计只放一处。

### 6.2 接口

内部 gRPC,不对客户端开放:

```proto
service ContentGuard {
  rpc CheckText(CheckTextRequest) returns (CheckTextResponse);
}

enum TextScene {            // 场景决定用哪套动作
  TEXT_SCENE_UNSPECIFIED = 0;
  TEXT_SCENE_ROLE_NAME = 1;
  TEXT_SCENE_GUILD_NAME = 2;
  TEXT_SCENE_PET_NAME = 3;
  TEXT_SCENE_GUILD_ANNOUNCEMENT = 4;
  TEXT_SCENE_CHAT_WORLD = 5;
  TEXT_SCENE_CHAT_TEAM = 6;
  TEXT_SCENE_CHAT_PRIVATE = 7;
  TEXT_SCENE_PRIVATE_LABEL = 8;   // 只有自己看得到的文字(属性方案名),只走本地层
}

enum TextVerdict {
  TEXT_VERDICT_UNSPECIFIED = 0;   // 调用方一律当拒绝
  TEXT_VERDICT_PASS = 1;
  TEXT_VERDICT_MASKED = 2;        // 用 masked_text
  TEXT_VERDICT_REJECT = 3;
}

message CheckTextRequest  { TextScene scene = 1; string text = 2; uint64 player_id = 3; }
message CheckTextResponse { TextVerdict verdict = 1; string masked_text = 2; TextCategory category = 3; uint64 lexicon_version = 4; }
```

`category` 是枚举 `TextCategory`(政治、色情、辱骂、广告引流、冒充官方、其他),给 tip 和指标用。指标不带 `player_id`,也不带被检文字。协议原文在 `proto/content_guard/content_guard.proto`。

`CheckText` 没有调用方签名:它只读、没有副作用,客户端经路由服到不了它(路由表里没有这个服务)。K8s 上靠 gRPC 口准入名单限制来源(`k8s_deploy.ps1` 的 `$script:GrpcAllowLists`)。被检文字不进日志:配置校验强制把 `CheckText` 列进 go-zero 的 `IgnoreContentMethods`。

### 6.3 本地层

对每段文字做两步:

**归一化**(只用于匹配,不改玩家原文):

1. 逐字符 NFKD:全角转半角,带圈数字、上下标折成数字,兼容字形折回正字,带音标的字母拆成字母加组合记号。
2. 转小写。
3. 繁体转简体(内嵌一张字表)。
4. 标出「可跳过」的字符:空白、标点、符号、零宽字符、表情、组合记号。

**匹配**:词库编成字典树,从每个位置起向下走,走的过程中跳过第 4 步标出的字符。每个起点上所有成立的词都报告,不只报最长的:同一个起点上短词和长词的类别可能不同(一个打码、一个拒绝),只报最长的会漏掉该拒绝的那一个。归一化是逐字符做的,所以每个命中都能对回原文的起止位置;打码只替换原文里命中的那一段(连同夹在中间的可跳过字符),一个字符换一个 `*`,其余原样保留,字节数不会比原文多。这一点决定了现成的 Go 库不合用(6.8)。

词库的每一条有三项:

| 项 | 取值 | 作用 |
|---|---|---|
| 词 | 任意写法,加载时按同一套规则折叠 | — |
| 类别 | 政治、色情、辱骂、广告引流、冒充官方、其他 | 决定动作 |
| 匹配方式 | 子串、整词、开头 | 见下 |

- **子串**:任何位置都算,字和字之间可以夹可跳过的字符。中文词用它。
- **整词**:必须连续出现,前后不能紧挨英文字母或数字。英文短词用它,否则 `gm` 会命中 `sigma`。
- **开头**:只在整段文字的开头命中。给名字用:冒充 GM 的名字都是 `GM01` 这种以它开头的形态。

词条没写匹配方式时,不超过 3 个字符的纯英文数字词按整词,其余按子串。

另有一份白名单:命中如果整个落在某个白名单词里面,就不算。用来处理误伤。

有几个词不依赖词库、永远生效:`官方`、`客服`、`管理员`、`系统`、`运营`(子串)和 `gm`(开头),类别是冒充官方。它们和 `go/shared/playername` 的内置词是同一批,让帮会名、宠物名也有同样的底线。

动作按场景定,写在内容安全服务里(`internal/engine` 的 `actionFor`),调用方不用知道:

| 场景 | 冒充官方 | 辱骂 | 其余类别 |
|---|---|---|---|
| 角色名、帮会名、宠物名、私有标签 | 拒绝 | 拒绝 | 拒绝 |
| 帮会公告 | 不管 | 拒绝 | 拒绝 |
| 聊天 | 不管 | 打码后放行 | 拒绝 |

「官方」「系统」这类词在聊天和公告里是正常用语,只有出现在名字里才构成冒充,所以冒充官方那一类只对名字生效。

### 6.4 词库

词库放在 etcd,不进 git(内容不适合进仓库,而且运营要随时改)。

- `/mmorpg/content_guard/lexicon/v/<版本>/<四位序号>`:词库正文,gzip 压缩后分块,每块不超过 512 KiB(etcd 单次请求默认上限约 1.5 MiB)。
- `/mmorpg/content_guard/lexicon/current`:指针,写着当前版本、块数、正文的校验和与大小、谁在什么时候发布的。

发布 = 先写完新版本的全部分块,再用一次带条件的写入换指针(指针在读出之后被别人换过就不换)。各副本监听指针,读到新版本后按指针核对块数、大小和校验和,再解析、编译,成功才把内存里的字典树整体换掉;任何一步失败都保留旧的,计数并告警。运营临时加一个词也是发一个新版本,几秒内全部副本生效,不用发版。etcd 里保留最近 3 个版本,回滚是把旧版本的正文重新发布成新版本,版本号只增不减。

管理入口只有命令行工具 `go/content_guard/cmd/lexicon`(`publish`、`add`、`remove`、`rollback`、`show`),它直接读写 etcd。服务本身没有发布接口:能连上 etcd 就能发布,权限就是 etcd 的权限,不用再设一套口令。词库原件由运营保管。

staging、prod 下(`RequireLexicon: true`),没有加载到词库的副本**不监听 gRPC 口、不注册进 etcd**,`/healthz` 回 503。调用方按 etcd 里的注册找实例,K8s 的就绪探针摘不掉一个已经注册的副本,所以「没准备好」只能靠不注册来表达。新版本读不了线上的词库时,滚动发布停在这一步,旧副本继续服务。所以**首次部署前要先发布词库**。开发环境(`RequireLexicon: false`)没有词库也照常判定,只有内置的防冒充词生效。

开发期的词库来源:[konsheng/Sensitive-lexicon](https://github.com/konsheng/Sensitive-lexicon)(MIT),用导入工具灌进 etcd,不提交进仓库。

### 6.5 平台接口与第三方

本地词库拦不住变体、谐音、语义和引流话术,这一层靠外部的模型。按玩家所在渠道选:

| 渠道 | 用什么 | 说明 |
|---|---|---|
| 微信小游戏 | `msgSecCheck` | 免费。官方文档写每个 AppID 每分钟 4000 次、每天 200 万次。新版接口要带玩家的 openid |
| 抖音小游戏 | `antidirt` | 平台自带。调用量上限没有查到 |
| App(iOS / Android) | 商业供应商(易盾、数美、腾讯云、阿里云等) | 要签约付费,未定 |

所以第三方不用现在就签:小游戏渠道先用平台自带的接口,App 渠道上线之前再定供应商。代码上是同一个接口后面的不同实现。

**用哪个平台、带哪个用户标识,都从账号目录查。** login 每次第三方登录都把「渠道(`auth_type`)和这个渠道给的 openid」记到账号所在分片的 `account_channel_identity`(`UpsertAccountChannelIdentity`,只认 login 的调用证明)。内容安全服务按填写者去查(`GetPlayerChannelIdentity`):有 `player_id` 按角色查;建角时角色还没发号,按请求里的 `account` 查。结果在副本内存里缓存 5 分钟。

只认两个渠道:`wechat_minigame` 送微信,`douyin_minigame` 送抖音。其余渠道(口令,App 端的微信、QQ、Apple、Google 登录)只走本地词库。2026-11-26 复核时改成这样,原实现有两处错:

- 账号名 `wx_…` 的后缀是 **unionid**,不是 openid。微信的审核接口要的是「本小游戏 AppID 下的 openid」,拿 unionid 去调会被平台按 openid 无效拒掉。原实现从账号名里截后缀当 openid 用,而名字类场景对平台不可用的口径是拒绝:接上微信凭证之后,小游戏玩家建不了自定义名字的角色。
- App 端微信登录记下的 openid 属于 App 那个 AppID,同样不能拿去调小游戏的接口。原实现把 `wechat` 渠道也送了微信。

同一个账号可以先后从小游戏和 App 登录,目录里记的是最近一次,所以这个映射会变,缓存的 5 分钟是它滞后的上限。login 记渠道身份失败只打错误日志、不拦登录,后果是这个账号在下次登录之前只过本地词库。

**微信的调用凭据用稳定版接口取**(`/cgi-bin/stable_token`)。老接口每取一次就让上一个凭据在几分钟后失效,多副本各取各的会互相挤掉,副本越多越频繁,还会撞每天的取用次数上限;稳定版在有效期内重复取到的是同一个凭据。所以副本之间不用共享凭据,不用为它引入共享存储,服务照旧无状态。AppSecret 放在请求体里,不进 URL;审核接口的 URL 上带着凭据,请求失败的日志先去掉 URL 再记。

平台的两种答复不是故障,单独处理:

- 微信回「用户近两小时没有访问过小游戏」(61010):平台不审这名用户的内容,重试也不会变。按「不走平台」处理,只过本地词库。当成不可用的话,连续在线超过两小时的玩家会一直改不了名、建不了帮、发不了公告。
- 微信用错误码回「内容违规」(87014,旧版接口的做法):按违规算,不当成没答复。

外部接口失败或超时的口径:

| 场景 | 口径 |
|---|---|
| 各种名字、公告、寄售标题 | 拒绝,回可重试的 tip。名字是长期公开展示的,宁可让玩家稍后再试 |
| 世界频道 | 短超时;超时先按本地层的结果发出,由 chat 异步补审,违规的撤回(第 7 节) |
| 队伍、私聊、私有标签 | 只走本地层。全量送审费用和配额都撑不住 |

**时限是一条链,后一环要盖住前一环**,否则前面那一环永远等不满(2026-11-26 复核前,服务端超时只有 1 秒,名字类的 1.5 秒平台调用必然被掐断):

| 环 | 值(毫秒) | 位置 |
|---|---|---|
| 平台调用:名字类 / 世界频道先行 / 世界频道补审 | 1500 / 250 / 2500 | content_guard `Platform.SyncTimeoutMs` / `WorldTimeoutMs` / `AsyncTimeoutMs` |
| 查渠道身份 | 150 | `Platform.LookupTimeoutMs` |
| content_guard 的 zrpc 服务端超时 | 3000 | `go/content_guard/etc/content_guard.yaml` 的 `Timeout`;接了平台而它小于「最长的平台调用 + 查渠道身份 + 200」时拒启 |
| Go 调用方的预算:聊天与私有标签 / 名字类 / 补审 | 600 / 2000 / 3000 | 各服务 `ContentGuard.TimeoutMs` / `NameTimeoutMs` / `go/shared/contentguard` 的常量 |
| Go 调用方的 zrpc 连接时限 | 3500 | 各服务 `ContentGuard.Rpc.Timeout`;小于上一行最大的预算时拒启 |
| scene(C++)的 gRPC 截止时间 | 5500 | `bin/etc/base_deploy_config.yaml` 的 `CallDeadlineMs.ContentGuardNodeService`,等于服务端超时 + 2000 + 500 |

接了平台却没配账号目录连接(`DataServiceRpc`)时 content_guard 拒启:调用方只带 `player_id`,查不了渠道身份的话每一次平台审核都会被悄悄跳过,而配置看起来是接了的。目录这一次没读成(应答里的 `Retry`)按查失败算,不当成「这名玩家没有渠道身份」。

### 6.6 各入口接线

| 入口 | 谁送检 | 场景 | 内容安全服务不可用时 |
|---|---|---|---|
| 建角名 `CreatePlayer` | login | 角色名 | 拒绝,可重试。服务端生成的默认名(「道友」加随机后缀)不送检 |
| 角色改名 | scene | 角色名 | 拒绝 |
| 建帮、帮会改名 | guild | 帮会名 | 拒绝 |
| 帮会公告 | guild | 帮会公告 | 拒绝 |
| 宠物改名 | scene | 宠物名 | 拒绝 |
| 聊天 | chat | 按频道 | 这条消息发送失败,回 tip。不放行没过滤的内容 |
| 聚宝斋人民币寄售标题、买家评价 | trade | 寄售标题 | 拒绝 |
| 赛事战队名 | match | 帮会名 | 拒绝(回服务端故障,可重试) |

只有填写者自己看得到的名字(加点方案、装备预设、技能装配方案、流派收藏)不送检:送检是异步的,会破坏这些同步接口的契约。

chat 现有的 `textfilter` 和配置项 `SensitiveWords` 在接线那一批删掉,不留两套。

**防漏的契约测试**(`tools/scripts/tests/test_client_text_fields_reviewed.py`,CI 每次提交都跑):枚举客户端请求消息里的 `string` 字段,每一个必须登记成「送检(哪个场景)」或「豁免(原因)」。新加字段没登记,测试就红。只靠约定的话,下一个加文字入口的人不会知道要接。登记「送检」只说明有人表了态,调用方有没有真的装配内容安全客户端要另看:2026-11-26 复核时发现 match 的战队名写了送检代码、却从没装配客户端(字段恒为空),当天补上。

### 6.7 扩缩容与可用性

服务无状态,每个副本内存里一份字典树,按 CPU 加减副本即可。本地层在请求路径上不依赖 etcd、Redis 或数据库:etcd 挂了,副本继续用已加载的词库。

副本之间不共享任何运行期状态,也不需要把同一名玩家的请求固定到同一个副本:

- 词库:每个副本各自监听 etcd 里的指针,各自编译、各自整体替换(6.4)。
- 微信的调用凭据:稳定版接口在有效期内给每个副本的是同一个凭据,不用共享(6.5)。
- 渠道身份:每个副本各自缓存 5 分钟,事实源在账号目录。
- 要跨副本一致的东西(重复内容的计数、撤回记录、举报)不在这个服务里,在 chat 的库里(第 7 节)。

建角(自定义名字)和聊天因此依赖这个服务在线,所以它至少两个副本,并要有可用性告警。聊天的调用量是唯一需要看的:每条消息一次本机房调用加一次内存匹配。压测时如果它成了瓶颈,再把本地层做成 chat 进程内的库;接口形状不变。现在不提前做。

### 6.8 选库

| 用途 | 选择 | 原因 |
|---|---|---|
| Java 版本地层 | [houbb/sensitive-word](https://github.com/houbb/sensitive-word)(6.1k star,Apache-2.0) | 大小写、全半角、繁简、跳过字符、黑白名单、分类标签、运行期加删词都自带。不到 2 万 star,负责人 2026-11-19 同意例外;落码时登记进 Java 仓 `docs/design/tech-stack.md` |
| Go 版本地层 | 自己写(`internal/textnorm`、`internal/wordlist`);归一化用已在依赖里的 `golang.org/x/text`;繁简字表 `t2s.txt` 约 2500 对,由 Windows 自带的简繁转换生成(`gen_t2s.ps1`),另手工补了它不转的几个常用字 | 现成的 Go 库不合用,见下。字表没有用 OpenCC 的:那要从外网下载文件,本机生成不需要。这张表比 OpenCC 的小:表里没有的繁体字不会折成简体,用它写的词会漏掉(简体写法照常命中)。以后要换成 OpenCC 的表只换这一个文件 |
| 开发期词库 | konsheng/Sensitive-lexicon(4.4k star,MIT) | 只是数据,导入 etcd |

Go 这边看过的两个库:

- [toolgood/ToolGood.Words](https://github.com/toolgood/ToolGood.Words) 的 Go 版:仓库里没有 `go.mod`,不是能直接引用的模块,要把约 160 KB 源码(其中 125 KB 是字典)整份拷进来自己维护。
- [importcjj/sensitive](https://github.com/importcjj/sensitive):2022 年之后没有更新;它要么不跳过干扰字符,要么把干扰字符从原文里删掉再替换,做不到「跳过干扰字符匹配,同时只对原文命中的那一段打码」。

两版的匹配引擎不同,所以共用一份测试向量文件,只约定两版都必须满足的那部分行为(基本命中、全半角、繁简、跳过字符、白名单)。打码结果是服务端输出,客户端只管显示,两版不要求逐字节相同。

### 6.9 在 K8s 上开启平台审核(部署接线,2026-11-26)

> 状态:部署脚本、清单、包装入口、告警、契约测试与 content_guard 的平台调用计数都已落码;**未运行**(命令在 `docs/PROGRESS.md` 2026-11-26「content-guard 平台审核的 K8s 部署接线」)。

服务读凭据的那一半(6.5)早就有了:`Platform.WeChat` / `Platform.Douyin` 写 `AppID` 和 `AppSecretEnv`(环境变量名),AppSecret 从环境变量读。缺的是部署那一半:`tools/scripts/k8s_deploy.ps1` 生成的 ConfigMap 里没有 `Platform` 段,也没有把 AppSecret 注入容器,集群上开不了。现在照 login 小游戏登录的接线补上。

**怎么开**(content-guard 是全局服务,只在 `infra-up`、或不带 `-SkipInfra` 的 `all-up` 里部署;`zone-up` 给了这些参数只告警「不生效」):

```powershell
$env:MMORPG_CONTENT_GUARD_WECHAT_APP_SECRET = '<微信小游戏的 AppSecret>'
$env:MMORPG_CONTENT_GUARD_DOUYIN_APP_SECRET = '<抖音小游戏的 AppSecret>'
pwsh -File tools/scripts/k8s_deploy.ps1 -Command infra-up <其余参数照常> -ContentGuardWeChatAppId <微信小游戏 AppID> -ContentGuardDouyinAppId <抖音小游戏 AppID>
```

只接一个平台就只给那一个。之后每次部署都要照传(参数不粘滞,见第 4 步);包装入口 `dev_tools.ps1 -Command k8s-infra-up / k8s-all-up` 同名参数照传,`k8s-image-*` / `k8s-release-*` 给了即拒绝。

**接线一步步怎么走**:

1. **参数 → ConfigMap**:给了 AppID 才在 `go-svc-content-guard-config` 里写 `Platform.<WeChat|Douyin>`,只写 `AppID` 与 `AppSecretEnv`(变量名字面量 `MMORPG_CONTENT_GUARD_<平台>_APP_SECRET`,不是 `${...}`,服务对含 `${` 的值拒启)。`BaseURL` 与四个时限都不写,用服务的缺省值(生产地址;1500 / 250 / 2500 / 150 毫秒)。两个都不给时不写 `Platform`:Deployment 与接线之前一样,ConfigMap 只有 `Timeout` 上面那句注释换了(旧注释说「纯内存计算,超时只是兜底」,接了平台就不对了),另外多出两条带 `--ignore-not-found` 的删 Secret(集群里没有就是空操作)和一行开关摘要。
2. **AppSecret → Secret → 容器**:部署机的环境变量 → infra namespace 的单键 Secret `content-guard-wechat` / `content-guard-douyin`(键 `secret`)→ secretKeyRef 注入同名环境变量,不写 `optional`(Secret 缺失时 Pod 起不来,而不是带着空密钥起来)。走工作负载密钥目录 `$script:WorkloadSecretCatalog`(docs/design/workload-secrets-via-k8s-secret.md):建 Secret、注入、指纹都按这张表,不在 content-guard 的分支里另写一遍。Pod 模板带 `mmorpg.io/content-guard-<平台>-hash` 指纹,只换 AppSecret 也会滚动。`deploy/k8s/manifests/go-svc/content-guard.yaml` 不写这两个变量:没接平台时不能要求 Secret 存在。
3. **在任何写操作之前拒绝**:AppID 不是 `[A-Za-z0-9_.-]`;给了 AppID 却没设环境变量(任何档位都没有回落值);AppSecret 首尾带空白或含 `${`;staging / prod 的占位串或短于 16 位。content-guard 自己不核 AppSecret 的形状,拿到错的值照样起得来,只是每一次平台调用都失败,而名字类场景对平台不可用的口径是拒绝,玩家就起不了名字。所以在部署时拦,报错只点参数名与变量名,不回显值。
4. **不粘滞,加防误关闸**:每次部署按本次参数重写;本次没给的平台,它的 Secret 在 content-guard 部署之后删掉,平台审核随新 Pod 一起关闭。漏传的后果是平台审核被悄悄关掉:名字与聊天只剩本地词库,哪里都不报错,对内容安全是 fail-open。所以和 login 的第三方登录一样设闸(`Assert-ContentGuardPlatformClusterState`,真跑才查,DryRun 只打一行说明):先读线上 content-guard 的 ConfigMap,线上接着某个平台而本次漏传、换了 AppID、或线上那一段认不出,就在任何写操作之前拒绝,报错给出照传现状的参数串;确实要关或换时加 `-ConfirmContentGuardPlatformChange`(给了只告警放行)。线上没有、本次新开不需要确认。读集群失败一律拒绝:查不到不等于没开。
5. **微信的 AppID 必须就是 login 的微信小游戏 AppID**。送平台的 openid 是账号目录里记的、玩家经 login 小游戏登录拿到的那个(6.5),openid 只在那个小游戏的 AppID 下有效;拿另一个应用的凭据去调,平台按 openid 无效拒掉每一次审核,名字类全部被拒。同一次运行里两个参数都给了(`all-up`)才比得上,不同就拒绝;分两次部署时比不上,靠下面的告警兜底。抖音的内容检测只带应用的调用凭据、不带玩家标识,AppID 与 login 的不同也调得通,不比(仍按同一个小游戏填,调用量按应用算)。
6. **时限**:接了平台,服务端 `Timeout`(服务 yaml 的 3000,ConfigMap 镜像同一个值)要不小于「最长的平台调用 + 查渠道身份 + 200」= 2850,否则 content-guard 拒启。生成器不写时限,就是为了让这条不等式按缺省值成立;契约测试读 `config.go` 的缺省值核它。
7. **依赖**:接了平台还要连 data-service 查渠道身份(`DataServiceRpc`,模板里一直有),并出集群调平台的 HTTPS 接口。本仓的 gRPC 准入策略只管入站;集群若另限出站,要放行 `api.weixin.qq.com`、`developer.toutiao.com` 的 443。

**怎么看出平台出了问题**:

- 指标 `content_guard_platform_reviews_total{provider, outcome}`(`go/content_guard/internal/metrics`):每一次平台调用记一次最终结局,`outcome` ∈ pass / reject / unavailable / skip / deferred。世界频道先行的 250 毫秒没等到记 `deferred`:交给后台补审,补审那一次另记结局,所以不算失败,否则平台只是慢一点告警就会响。补这个指标的原因:世界频道补审再不可用时消息照常留着、只打错误日志,之前平台挂了没有任何指标看得见。
- 告警 `ContentGuardPlatformFailing`(warning,`deploy/k8s/content-guard-alerts.yaml`):某个平台最近 10 分钟 `unavailable` 占非 `deferred` 调用超过 5%,持续 10 分钟。5% / 10 分钟是起步值,接实网后按平时的失败率调。名字类不可用同时会触发已有的 `ContentGuardRefusingChecks`(critical),两条一起看就分得清是词库还是平台。
- 平台整体故障一时恢复不了:不带该平台的参数、加 `-ConfirmContentGuardPlatformChange` 重新部署 `infra-up`,退回只用本地词库;恢复后再带上。

**为什么这样做**:

- Secret 放 infra namespace:content-guard 只在那里部署一份,Secret 不能跨 namespace 引用。
- 一个平台一把单键 Secret,不是一个 Secret 两个键:与目录表「一把密钥一个 Secret」的口径一致;只接一个平台时另一把不存在、也不被引用;换密钥、关平台各管各的。
- 部署侧比对微信的 AppID、不比抖音的:按平台接口的实际要求定,不拦一个调得通的配置。
- 不加 `BaseURL` 参数:沙箱 mock 只在本机开发用,K8s 上就是生产地址;以后要在集群里对着 mock 测,再加。

**没做的与残余**:

- 全局服务分两步部署(先 ConfigMap、等 data-service 就绪后再起进程)。第一次开平台审核时,这两步之间如果旧 Pod 重启,它会读到带 `Platform` 段的新配置、却是没注入 AppSecret 的旧模板,起不来,直到进程那一步把新模板发下去(通常几分钟,另一个副本照常服务)。所有带工作负载密钥的全局服务都有这个窗口,不单独处理。
- 微信 AppID 与 login 的对齐只在同一次运行里给了两个参数时查得到(第 5 步)。
- 微信两个错误码与调用上限还没有实网凭证验证过(第 10 节)。

## 7. 聊天反广告(批 6 已做;「仅自己可见」留后)

广告主要靠识别行为。规则放在 chat,因为只有它知道等级、频率和对象。chat 全服一份、多副本、无状态,所以**凡是要跨副本一致的计数和记录都落在聊天自己的库里,和消息在同一个事务里读写**,不放进程内存。

| 规则 | 做法 | 配置(`go/chat/etc/chat.yaml`) |
|---|---|---|
| 世界频道等级门槛 | 发言前按角色等级判;等级从账号目录读,副本内缓存至少 30 秒 | `WorldMinLevel: 5` |
| 同一个人重复发同一段话 | 只判世界频道;归一化后 4 个字以上的内容,时间窗内到次数就拒 | `DuplicateSpamWindowMs: 60000`、`DuplicateSpamMaxPerSender: 2` |
| 多个号发同一段话 | 只判世界频道;归一化后 **10 个字以上**的内容,时间窗内已有这么多个别的号发过就拒 | `DuplicateSpamMaxSenders: 2` |
| 新号私聊人数上限 | 建号不满 24 小时的账号,每天最多主动私聊这么多个不同的人;聊过的人可以继续聊 | `NewAccountAgeHours: 24`、`NewAccountDailyPrivateLimit: 10` |
| 联系方式与网址 | 内容安全服务的本地层(下文) | — |
| 举报 | 核对被举报的消息确实存在、举报人看得到,追加写 `chat_report` | — |
| 撤回 | 追加写 `chat_world_retraction`,拉历史时滤掉,并向在线玩家推撤回 | — |

### 7.1 重复内容的计数放 TiDB,不放 Redis

设计稿原来写的是「按内容哈希在 Redis Cluster 计数,键不带 `player_id`」。落地时改成聊天库里的 `chat_repeat_event` 表(主键 `content_hash, accepted_ms, sender_player_id`)。键的形状没变,换了存放的地方:

- 计数和消息在同一个事务里。消息没落库(被限流挡下、请求重放、事务回滚),这一次就不计数。放 Redis 的话要先加后补偿,补偿丢了就多算。
- 键是内容的哈希,不是 `player_id`。同一段内容的记录落在主键的同一段上,「这段话最近谁发过」是一次主键前缀扫描;不同内容的哈希均匀散开,没有写热点。
- 过期靠表上的 TTL 属性,不用自己清。
- chat 的写路径本来只依赖自己的库,不多一个依赖,也不用处理「库写成了、Redis 没写成」。

代价是每条世界消息多一次索引读和一次插入。世界频道有等级门槛和发言间隔,量有上界。压测显示它是瓶颈时再换成 Redis Cluster,规则和键的形状不用变。

归一化只用于算哈希:去掉空白、标点、符号,全角转半角,转小写。「限 时 特 惠!」和「限时特惠」是同一段话。

两条重复规则的范围是 2026-11-26 复核时收窄的。原实现对私聊也判,而且 4 个字起就按人数判。聊天服务全服一份,「哈哈哈哈」「在吗在吗」一分钟里有三个人说得一模一样是常态:第三个人会被当成刷屏拒掉,私聊里互不相干的两个对话也会互相挡。现在只判世界频道;按人数判只对 10 个字以上的内容,因为多号群发的广告要写卖点和去处,短不了。私聊里的群发由新号私聊人数上限、联系方式识别、每秒限流和举报来管。

### 7.2 联系方式与网址识别

在内容安全服务的本地层(`go/content_guard/internal/contact`),对名字、公告、聊天都生效,私有标签除外:

- 渠道线索词(微信、vx、加v、qq、企鹅……)后面跟着 5 位以上数字或像账号的字母数字串。线索词后面的汉字数字和谐音(幺、两、拐……)折回数字再数。
- 裸的 11 位大陆手机号。
- 带协议头或 `www.` 的网址,以及「一段字母数字 + 点 + 常见顶级域」的域名。

全部在折叠后的文字上判(NFKD、转小写、繁转简、同形字折回拉丁字母)。2026-11-26 复核前,网址和域名是在原文上用正则找的,切一下全角输入(`ａｂｃ．ｃｏｍ`)就绕过去了。

白名单词库(类别「允许」)盖住的片段不算。网址只比对主机名:登记了 `xuanming.com`,`https://www.xuanming.com/pay` 照样放行,`https://xuanming.com.evil.top` 不放行。域名比对的范围恰好是域名本身;复核前比对范围多带了前后各一个字,登记进白名单的官网域名只有顶格写才放得过去,紧挨着的第二个域名还会漏判。

### 7.3 撤回

世界频道的消息先按本地层的结果发出。平台没在 250 毫秒内答复时,chat 落库、推送之后在后台再送一次平台(最长约 3 秒),平台判违规就撤回。送检和撤回各用各的时限(4 秒、3 秒):共用一个的话,送检等满之后留给撤回落库的时间不到半秒,平台判了违规却撤不掉。

撤回只追加一行记录,不改不删消息原件(聊天的运行账号没有 UPDATE、DELETE 权限)。拉历史时按时间范围读出撤回记录滤掉。别的副本的近窗缓存最多再留这条消息 `WorldHistoryCacheMs`(500 毫秒);客户端收到撤回推送后记住这条(发送者 + 发送时刻),之后到达的历史应答或乱序的推送再带着它也不收。

撤回推送和发言走同一个 Kafka topic,键都是发送者,所以同一个人的发言和它的撤回有序。每台 gate 对世界频道的推送有预算(刷屏时超出的发言不推,只留在历史里)。撤回单独一份预算:和发言共用的话,刷屏把预算打满的时候撤回也推不出去,而那正是最需要把违规消息撤下来的时候;也不能不设预算,一条发言最多带来一次撤回,不限的话撤回就成了绕过预算的路。

运维撤回入口 `RetractWorldChat` 是服务端方法,要带运维口令:环境变量 `MMORPG_CHAT_ADMIN_TOKEN`(经 Secret 注入,至少 16 字节),请求的 gRPC metadata 带 `x-admin-token`。**没设这个变量时入口整体停用**,每次调用回 PermissionDenied。在线域的入口准入只挡带会话的客户端请求,不带会话的内部调用一律放行,所以这种处置动作必须自己核调用方;写法和 login 的运维面相同。服务自己的后台补审不走这个入口。

### 7.4 举报

客户端在世界频道每条别人的消息旁有举报入口,选原因(广告引流、辱骂骚扰、涉政涉黄、其他),可填补充说明。服务端按字节收补充说明(200 字节),客户端限 60 个字,发出前再按字节核一次。同一个人对同一条消息重复举报只记一次。

举报目前只落库,处置由运维查表后调撤回入口。

### 7.5 没做的

- 「仅自己可见」:广告号自己看得到,别人看不到。要改聊天历史的可见性模型。
- 多人举报后的自动处置、禁言。
- 建号超过 24 小时的号在私聊里群发不带联系方式的话术,目前只能靠举报。

## 8. 比较过的做法

| 做法 | 结论 | 原因 |
|---|---|---|
| 允许重名,用「名字#数字」区分 | 不选 | 没有抢注和改名冲突,但产品已定名字全服唯一 |
| Redis SETNX 判重 | 不选 | 主从切换会丢已确认的写入,只能当缓存 |
| 把名字和角色放进同一个 TiDB 集群,用一个跨库事务改名 | 不选 | 代码最少,但逻辑库就不能各自搬到别的集群,违反 AGENTS.md §7「逻辑库自治」 |
| Go 服务发起改名,通过资产通道去 scene 扣卡 | 不选 | 要新开一条资产流和一套待办表;卡本来就在 scene,由 scene 发起只需要一条存档记录 |
| 改名卡先扣、失败再退 | 不选 | 退卡会遇到背包满;让卡留在背包里被占用、成功才扣,没有退的问题 |
| 后台定时清过期的保护名 | 不选 | 要给名字表加索引或全表翻页;占用时顺手接管就够 |
| 帮会名也做成按名字分片的登记表 | 现在不做 | 帮会库没有分片,一个本地事务更简单也更强;拆库时再搬 |
| 屏蔽词做成各服务进程内的库 | 现在不做 | C++ 也要用,而且第三方密钥只该放一处;压测有数据再把本地层挪进 chat |
| data_service 统一检查角色名内容 | 不选 | 会和「内容安全服务查渠道身份」形成循环依赖;改由收文字的服务送检,加契约测试防漏 |
