# 队伍补位匹配(已组好的队伍进人数档队列凑满 N 人)

## 2026-10-29：统一个人与整队入口

负责人已确认：默认PVE按当前人数直接开战（散人1人、整队1～5人）；PVP等待真人，支持每侧1～5人，预组队不可拆开或分到对面，不补机器人。下文原PVE补位协议保留为显式选项，不再作为默认PVE入口。

- 战斗面板与组队面板共用发起规则；已有队伍只能由队长发起，不能把整队意图静默降为队长个人的`JoinQueue`。队伍视图过期时先同步，离线或不满足准入条件的成员明确报错。
- `StartTeamMatchRequest.match_mode`的0/5沿用PVE，7为`PVP_TEAM`；目标0取当前人数。`TeamView.pvp_match_supported`为能力位，客户端不能把新PVP请求发给会忽略模式的旧服务端。
- PVP按每侧目标人数分池，把预组队视为不可拆单位，可与散人补齐同侧；两侧均凑够同一人数才开战。任意成员取消或名单变化时撤整单，对方继续等待。
- Redis与SQL权威路径都保留整队原子入队、取消、失败补偿和恢复。PVP显式保存分边，不能再按个人评分蛇形重分队；SQL通过`MatchFormationMember.team_index`恢复原分边。
- 连续战斗保留模式、目标和队伍身份；只有同队的现任队长可以续排。随队开战必须清除旧个人排队记忆，换队、离队、换号或断线后不能按旧意图独自入队。

## 1. 要解决什么

人数档匹配上线后,PVE 有两条互不相通的路:

- 单人在排队面板选「N 人」,进 `size{N}` 队列和陌生人凑满;
- 已组好的队伍由队长「开始战斗」,有几个人就几个人直接开战,**不补位**。

所以「我和朋友两个人,想再匹配三个路人打 5 人本」做不到。本文补上这一条:队伍整体进人数档队列,
和路人、和别的队伍一起凑满 N 人,凑满后同场开战。怪物数量仍由引擎按进攻方人数成倍生成,不需要新规则。

## 2. 玩家看到的规则

1. 队长在「开始战斗」的确认框里选目标人数 N(当前人数 k ~ 副本上限)。N = k 就是原来的直接开战;N > k 进队列补位。
2. 进队列后全队每个人都看到「队伍匹配中(目标 N 人)」,都有「取消」按钮。**任何一名队员取消 = 整队退出匹配**。
3. 队伍在队列里**不可拆**:要么全队一起进同一场战斗,要么全队都不进。
4. 匹配期间队伍名单有任何变化(有人离队、被踢、新人加入、解散)→ 整队自动退出匹配,全员收到提示。队长转让不影响。
5. 匹配期间有队员下线(会话消失或明确下线)→ 轮到这支队伍成组时发现,整队退出匹配,其余人收到提示。
   断线后还在 30 秒重连宽限期内的不算下线;没连回来的人会在开局备战时失败,按第 6 条处理。
6. 凑满后与单人排队完全一样:收到开战推送进战斗。凑满后开局失败时,出问题的若是本队队员,整队退出匹配;
   出问题的是别人,本队整体回到队首继续等。
7. 匹配期间有队员应战切磋并开打 → 他进了别的战斗,整队立即退出匹配,其余人收到提示(点名是他)。单人排队同理:开打即退出排队。

## 3. 方案总览

一句话:**队列里仍然是一个人一个位置,票据上多记一个「同一支补位单」的标记;匹配器按标记把同队的人当成一整块来凑人数。**

为什么不把队伍做成队列里的一个元素(team-system.md §E.6 当时设想的方向):现行队列的一整套不变量与自愈
都建立在「元素 = 十进制 player_id」上 —— list 与评分镜像 ZSET 成员集相等、`LLEN` 就是人数(凑单门槛和 queue_depth 指标)、
`healOrphanTicket` 用 `LPOS player_id` 判孤儿、`validate` 核对票据 `queue_key`、非数字元素被当异物删除。一人一个元素时这些全部原样成立,
改动集中在「怎么选人」这一处;换成队伍元素则每一条都要改。

为什么不把「匹配中」写进队伍记录(TeamRecord):那样同一个事实有两份(队伍记录说在排、票据说没在排),两个库之间没有原子性,
每一种不一致都要专门的补偿;而开战锁是带截止时间的短时锁(5 人 101 秒),排队可能很久,套不上。
本方案里**票据是「是否在排」的唯一事实来源**,队伍记录不新增任何字段,队伍视图里的匹配态是构建视图时按接收者自己的票据现算的。

### 3.1 数据

票据 `match:ticket:{player_id}` 新增字段(只有相关票据写,其余票据字段集不变):

| 字段 | 谁写 | 含义 |
|---|---|---|
| `party_id` | 补位入队 | 这一单的 uuid;同一单的所有成员相同。开局失败回队首后仍是同一个 |
| `party_members` | 补位入队 | 这一单的名单,逗号分隔的 player_id,队长在前、其余按 join_seq(就是进战斗的站位顺序) |
| `team_id` | 补位入队 | 既有字段(整队开战已在用),补位票同样写 |
| `last_failed_battle_id` | 开局失败回队首 | 上一局开局失败的 battle_id,用来认出那一局没清掉的备战锁(§4.4);单人票也写 |

补位票其余字段与单人排队票相同:`state=queued`、`queue_key=match:{mq}:size{N}:queue:{mode}:{config}`、长 TTL。
队列 list / 评分镜像 ZSET / 注册集的格式**完全不变**:每名成员各占一个十进制 player_id 元素,整单用一条 Lua 一次性 RPUSH,所以同单成员在 list 里相邻。

另有两个短期标记(单 key、TTL 120 秒,不进任何多 key Lua):`match:party:end:reason:{party_id}`(最先登记的撤单原因)与
`match:party:end:notified:{party_id}`(保证全队只收到一条通知),见 §4.3。

读取契约:matcher 校验排队成员时读 `battle:lock:{player_id}` 的**值**(scene 写的 battle_id),不只是看它在不在(§4.4)。
scene 侧「锁值 = battle_id、非空」因此是 match 依赖的契约(C++ 那边的注释仍写着「match 只 EXISTS」,等 C++ 线空出来时顺手改)。

### 3.2 协议(只加字段与枚举值,零新消息号、零新 tip)

`proto/team/team.proto`:

- `StartTeamMatchRequest.target_team_size = 3`:0 或等于当前人数 = 原来的直接开战;大于当前人数 = 进队列补位;
  小于当前人数或超过副本上限 → 既有的 `kTeamSizeExceeded`。
- `TeamMatchState.TEAM_MATCH_STATE_QUEUED = 2`。
- `TeamView.match_target_size = 13`、`match_queued_at_ms = 14`、`match_battle_config_id = 15`(只在 QUEUED 时有值)。
  其中 `match_queued_at_ms` 是「这一次排队」的**身份**:同一支队伍重新发起匹配会得到新的值,开局失败回队首不变。
  客户端用它区分「这一次排队已经结束」与「队长又发起了一次」(§5 规则 2),不是用来显示已等时长的。
- `TeamView.match_fill_supported = 16`:**能力位**。服务端支持补位且开关未关时,凡是有队伍的视图都置 true。
  客户端只在它为 true 时给出目标人数选项 —— 不认识 `target_team_size` 的服务端(旧版本、Java 版、混跑窗口里的旧实例)会把它
  静默当成直接开战,选了「凑满 5 人」却被当场拉进 2 人战斗。
- `TeamChangeReason.MATCH_QUEUED = 15`、`MATCH_QUEUE_CANCELED = 16`。

取消沿用 `MatchService.CancelQueue`(调用者持有补位票时撤整单)。老客户端:不认识的 `match_state` 被当成「未在集合」、
不认识的 reason 只应用视图不写文案,行为与今天一致。

生成物是用 protoc 窄面重生成的(只动 team 这一个 proto):`go/proto/team/team.pb.go`、`robot/vendor/proto/team/team.pb.go`、
`cpp/generated/proto/team/team.pb.{h,cc}`、客户端 `Team.cs`;重生成前先用旧 proto 生成一遍与入库产物逐字节比对,确认工具链版本一致。
三份暂存副本 `generated/proto/{_unified,db,login}/proto/team/team.proto` 同步改了。grpc 桩不受影响(服务定义没变)。

## 4. 服务端

依赖方向不变:team → 接口(`team.BattleStarter`)← logic;反方向新增 logic → 接口(`svc.PartyTeamPort`)← team,
同样只用内建类型,装配在 `match_service.go`(`svcCtx.SetPartyTeam(teamService)`,**必须先于** `StartMatcherLoop`)。
原因码放 `internal/constants/party.go`(两边都能 import)。`team_logic_layering_test.go` 的「两包互不 import」护栏照常成立。

| 方向 | 方法 | 作用 |
|---|---|---|
| team → logic | `EnqueueParty` | 逐人建补位票 + 整单入队 + 入队后复读 |
| team → logic | `CancelParty` | 名单变化 / 入队回滚时撤单 |
| team → logic | `PartyQueueState` | 视图装饰:这名玩家是否随本队在排 |
| logic → team | `CheckParty` | 弹组前 / 回队首前 / 自愈时复核队伍 |
| logic → team | `PartyEnded` | 撤单后推 `MATCH_QUEUE_CANCELED` |
| logic → team | `PartyStarted` | 凑满开局成功后推 `MATCH_ENDED`,面板归位 |

端口没注入(`PartyTeam() == nil`)时:弹组前复核按「读不到」处理,这一单本轮搁置 —— 进程重启后 Redis 里还留着存量补位单,
「没人能复核」不等于「仍然有效」,不复核就成组会把已离队 / 已掉线的人拉进战斗。撤单照常做,只是没人推通知(记 Error)。

### 4.1 进队列(`team.Service.StartTeamMatch` 的补位分支,`team/party.go startBackfill`)

1. 与直接开战相同的第 1~5 步:绑定读 + 惰性转让、队长 / 开战锁校验、人数校验、名单、逐成员预检(会话 → 战斗锁 → 位置 → 票据)。
   预检在票据项上被拦下、且调用者自己持有本队补位票时,回 `kTeamInMatch` + 当前视图(重复点击按「进行中」处理)。
   这个判定有意放在预检**之后**:预检里的票据自愈要先跑,否则持有残留补位票的队长永远开不了战。
2. `starter.EnqueueParty(config, N, team_id, roster, zones)`:逐人「不存在才创建」queued 补位票(任何一人已有票 → 回滚已建的票,
   回 `kTeamMemberNotReady` + 该成员),全部建好后一条 Lua 把整单 RPUSH 进队列,**再逐人复读一遍票据**:
   建票循环中途若有一次迟到的撤单落下来(§6),已建好的票被删、后面的照常建,入队的就是半单 ——
   发现有人名下不是本次建的那张票,就静默撤掉整单并按「该成员没能入队」返回。**不加开战锁**。
3. 入队后再读一次队伍成员(S_READ_MEMBERS):成员集合与入队名单不同、有人的索引不指向本队、或名单持续在变 → 用独立预算**静默**撤单,
   回 `kTeamStateChanged`;读失败同样撤单(fail-closed),回 `kTeamInternal`。
   预检到入队之间的名单变化由这一步接住;这一步之后的名单变化由 4.3 的主动撤单接住。
4. 给其余队员推 `MATCH_QUEUED` 视图;回包是调用者的 QUEUED 视图。两者都取自第 3 步那一次 S_READ_MEMBERS。

### 4.2 成组(matcher,`logic/party_match.go`)

非评分队列(PVE)的选人改成按「单位」凑:一个单人是 1 人单位,一支补位单是 k 人单位。评分队列(1v1 / 5v5)不变。

- 按等待序扫快照,逐个校验(沿用 `validate`:票据存在且 queued、`queue_key` 相符、无战斗锁),读到的票据带 `party_id` 就归到那一单;
  一单的全部成员都在快照里且校验通过才算「完整」。
- 每凑出一个新的完整单位就判一次:在已有的完整单位里找一个**人数之和恰好等于 N** 的子集,多解时取等待序字典序最小的那个
  (队首单位能成组时一定优先;队首是放不下的大队时后面的人照常成组,不堵队)。没有补位单时结果与改动前逐位相同(前 N 个有效且不重复的成员)。
  人数够了却凑不出恰好 N 人的组合时(例如 3 人档里两支 2 人队),限频(每队列 10 秒)记一条 Info,带各单位人数 —— 这种时候
  `queue_depth` 不降、饥饿等待上涨,只看指标与「matcher 卡住」分不出来。
- 选中的组里若有补位单,摘出前逐单问 team 一次 `CheckParty(team_id, members)`:

  | 读到的情况 | 结论 |
  |---|---|
  | 记录不存在、成员集合不等、有人索引不指向本队、名单持续在变 | 名单变化 → 整单撤出 |
  | 有人的会话 key 不存在,或状态明确是 OFFLINE | 掉线 → 整单撤出(带出是谁) |
  | 全员 ONLINE 或在断线重连宽限期(DISCONNECTING) | 有效 |
  | 记录或会话读失败 | 返回 err,不做判定 |

  在线口径比开战预检(严格 ONLINE)宽,是有意的:单人排队本来就不看会话。
- 复核不过 → 整单撤出队列(4.3)并重新选。**复核读不到(team 的 Redis 抖动、本轮 3 秒复核预算用完、端口未注入)→ 这一单本轮搁置,用其余单位重新选**,
  不撤单、不通知;限频(每队列 10 秒)记一条 Error。票据 / 队列自身的 Redis 读写出错才结束本轮。
- 扫完仍不完整的补位单(有成员不在 list 里 / 票据无效 / 各人票据上的名单对不上)整单撤出。入队、回队首、摘出、撤单都是整单一条 Lua,
  所以持锁期间不存在「只有一部分成员在 list 里」的合法瞬间。三种情况不判:快照读满(队列比 256 还长);本轮被搁置的单;
  缺席成员仍持有本单的票(凑单锁过期 / 丢锁后,另一个实例可能正在对这一单逐人推进 matched)。
- 摘出仍是一条 Lua;摘出人数不足(并发取消)时按单位放回队首。放回那一条 Lua 失败的单位不能留成「票据 queued 但人不在队列」
  (matcher 再也弹不到,客户端排队态不会再发 JoinQueue,自愈也触发不了):补位单走撤单(4.3)并通知,单人删票让他可以立刻重排。
- 摘出后逐人把票据 CAS 到 matched。补位单里任何一人 CAS 失败(并发取消 / 票据被替换)→ 这一轮凑不满,进入回队首;
  回队首的完整性规则(4.4)会让这一单已 CAS 成功的人删票出局。**一支补位单进 gather 的充要条件是全体成员的票都被 CAS 成了 matched**,
  「取消太迟」的判定因此仍然落在每个人自己的票据上。
- 凑单锁不续期:持锁期间连续凑多组时,用掉锁时长的一半就收手,剩下的留给下一轮。

### 4.3 撤单(`logic/party.go cancelParty`)

先快照全体成员的队列写入版本 → 登记撤单原因 → 逐人「票据属于这一单且仍是 queued 才删」→ 一条 Lua 只摘版本仍与快照相同的成员 → 通知 team。

版本保存在同一 `{mq}` slot 的 `queueKey + ":versions"` hash,字段为 player_id。单人 / 整队入队与回队首的每次实际 Lua 执行,
都从永久计数器 `match:{mq}:write_sequence` 分配新版本,与 list、评分镜像、注册集一起原子写入;先 LREM 同成员旧项再 push,
确保重排或透明重试后仍严格只有一个队列位置。INCR 后用 GET 取十进制字符串,避免 Lua 浮点精度把大于 2^53 的相邻版本混为一谈。

快照必须在 `cancelParty` 读 / 删任何成员票据之前完成:某成员的旧票一旦删除,其独立会话就能成功重新入队,
若收尾仍只按 player_id 做 LREM,会把新队列项删掉而留下 queued 新票。版本变化时保留新项及其评分、版本字段。
快照失败时继续按票据 CAS 撤旧单,但跳过主动摘队列,由既有 matcher 校验 / 自愈清残留,不降级为无条件删除。
普通摘项同时清对应版本字段,空队列 prune 清版本 hash,但永不删除全局计数器,避免清空后重排复用版本。
读票 / 删票出错的成员跳过(不摘 list),由下面的自愈兜底。五个入口:

- **队员取消**:`CancelQueue` 发现调用者的票带 `party_id` → 先删自己的票(既有的 queued CAS;失败 = 太迟,什么都不做),成功后撤其余人。
- **名单变化**:任何改了成员集合的已落盘提交(`Decision.Joined` 或 `Left` 非空,含解散与修复提交)—— 钩子挂在 `team.Service.publish` 上,
  不按 RPC 列举。它是提交之后异步执行的(每条提交自己一个后台任务、自己的时间预算,票据库慢不拖累这次提交的推送),
  所以带着「提交后的成员集合」:找到的那一单名单若恰好等于它就不撤,迟到执行不会误杀队长已经按新名单重新入队的单。
- **matcher**:弹组前复核不过、扫到不完整的单、放回队首失败(4.2);回队首的完整性规则与压回后复读(4.4)。
- **自愈**(`healPartyTicket`,JoinQueue、开战预检、活动战斗入口共用):遇到 queued 的补位票时 ——
  不在 list 且超过 15 秒入队宽限 → 崩溃残留,撤整单;在 list → 先核对同单其他人是否还持有本单的票(撤单逐人删票中途出错留下的「半撤」状态),
  再问 `CheckParty`,任一项不过就撤整单。队列人数不到凑满人数时 matcher 根本不扫这条队列,这类残留只能靠自愈发现。
- **进了别的战斗**(`leaveQueueForOtherBattle`,切磋开局成功时对每名参战者调用):他若还持有 queued 的补位票,删掉自己的票并撤整单
  (原因:该成员未就绪);单人票删票出队。票据已是 matched / ready 的不动 —— 那一局走到他时会因他已在战斗中而开局失败,按肇事者收尾;
  那一局若先败在别人身上,回队首时会看到他的战斗锁而不让他回队(4.4)。
  这条规则本来就有(matcher 见战斗锁就删票),但那是惰性的:人数不够凑满的队列 matcher 不扫,票据会留到切磋打完之后。

并发:取消与弹组抢的是每个人票据上的 queued → (删除 | matched) CAS,一张票只有一方能赢。取消方先赢了任何一张票,
matcher 在校验(票据缺失 → 单不完整)或推进 matched(CAS 失败 → 回队首时整单出局)时必然发现。
反方向(matched → queued,回队首逐人改回)没有这个保证,由 4.4 的「压回后复读」接住。

删票没删到时要分清三种情况(复读一次票据):仍是本单的 matched 票 = 真的太迟;票已不在 / 换成了别的票 = 另一条撤单路径刚处理过,
这一单其实已经收干净(两名队员同时取消时,若都当成太迟,双方各自以为该由对方通知,结果谁都不通知);
仍是本单的票且已是 queued = 刚被回队首改回来,再删一次。

通知:原因以**最先登记**的为准,登记在撤单入口(先登记、后删票)—— 收尾方要看到某张票被删了才会去通知,先登记保证它沿用的是
真实原因,而不是它自己推断的「某队员未就绪」。全队只收到一条,由**把这一单收干净的那一方**发:
撤单时发现有人「太迟」(票已 matched)就不通知,留给 matcher 侧收尾时带着终态视图通知。静默撤单(入队回滚)不登记、不通知。

### 4.4 开局失败(gather)与回队首(`logic/queue.go requeueFront`)

回队首按「单位」逐个处理(从最后一个单位往前,最先弹出的仍在最前),gather 的失败出口与 matcher 都不需要认识补位单:

- **单人**:票据 CAS 回 queued → 看战斗锁 → 一条 Lua LPUSH。做法与失败半径与加补位之前相同;CAS 与 LPUSH 之间多了一次读锁
  (上限 500ms,超时按读锁失败、照常回队),「票据 queued 但人不在队列」的窗口相应变宽一点,窗口里落下的取消 / 重排
  由 matcher 的票据校验与 JoinQueue 自愈收尾,与此前同一形状。
- **补位单**:本单全员票据 CAS 回 queued(gather 的失败出口顺手记下 `last_failed_battle_id`)→ 看战斗锁 → 完整性 → 回队前复核 →
  一条 Lua 整单压回 → 压回后复读。
  - *看战斗锁*:逐人读一次锁值(与 matcher 校验同口径):锁值是刚失败那一局的备战锁照常回队;是别的战斗的锁 = 弹出到回队之间他进了别的战斗
    (例如组被弹出、票据 matched 时他应战切磋并开打,随后这一局败在别人身上),删掉他的票、所在补位单整单出局并点名是他。
    不拦的话他人在切磋里、票据却回到 queued,人数不够凑满的队列 matcher 不扫,打完切磋就被直接拉进副本。读锁失败照常回队。
  - *完整性*:名单里只要有一个人回不来(肇事者、弹出后票据 CAS 失败的人、票据已被替换的人)→ 这一单其余人也不回队,删票并通知。
  - *回队前复核*:再问一次 `CheckParty`,不过的整单不放回队列 —— 弹出到回队之间票据是 matched,那段时间的名单变化撤单按「太迟」不动。
    复核读不到的照常回队。**复核必须在 CAS 之后**:名单变化的撤单只找 queued 的票,复核若放在 CAS 之前,落在两者之间的那次撤单会扑空,
    整单带着旧名单回队;先 CAS 后复核没有这个窗口。
  - *压回后复读*:逐人 CAS 的那几次往返里,先改回来的人已经可以被取消 —— 取消方删得掉他的票,却删不掉还是 matched 的队友。
    所以整单压回之后逐人复读票据,有人的票不在了就整单撤掉;通知沿用取消方登记的原因(「某某取消了匹配」)。
- 任何一个单位的那条 Lua 失败,只影响这个单位:删票(补位单整单删并通知)、把可能已压进去的队列项摘一次。

残留备战锁:开局失败后 scene 的解冻若丢了(CancelBattlePrepare 超时),`battle:lock` 会残留到自己过期(备战期限 + 60 秒;
那一局若其实建成过又被销毁,最长到战斗截止时间 + 60 秒,默认约 6 分钟)。改动前 matcher 见到战斗锁就删票;放到补位单上会连带整队被踢。
现在 matcher 读锁值(一次 GET,同一次读给出「在不在」和「是哪一局」):空 = 没有锁;等于票据的 `last_failed_battle_id` = 残留锁,
只在本轮搁置该成员(所在补位单本轮不可用,但不算不完整;搁置结论在本轮内缓存,评分队列里每个锚点不重读);
其余 = 真的进了别的战斗,按原规则删票。单人同样受益。搁置期间整单显示匹配中但不会成组,也不会被撤,上限就是锁的寿命。

### 4.5 队伍视图

构建视图时(回包与推送都一样)按接收者自己的票据装饰:票据属于本队补位单且 `queued` → `QUEUED` + 目标人数 / 入队时间 / 副本;
`matched` → `STARTING`;其余(含 ready)不动。装饰不进队伍记录、不改 version(客户端对同版本视图是「后到者生效」)。
改了成员集合的提交,其回包与推送**不装饰**(那一单马上会被撤掉)。能力位 `match_fill_supported` 不受这些条件影响,有队伍就标。

票据读失败按未在排处理、只记日志,视图照常下发 —— 队伍视图的可用性不依赖排队票据所在的库;客户端不据此退出排队态(§5 规则 3)。
读票带熔断:一次读失败或超过 300ms 后的 5 秒内不再读,一律按未在排下发。一批推送要逐个接收者各读一次,
不熔断的话票据库一慢,与匹配无关的队伍推送和组队回包会被它拖到超时。只认票据库自己的问题,按这一次读自己的耗时判断:
调用方的时间预算在读之前就用完了(同一批推送里前面的接收者卡在 Kafka 上、组队请求的预算用尽)→ 不读、不熔断;
读得慢(超过 300ms)→ 熔断,哪怕调用方的预算因此到期 —— 票据库慢到把调用方拖到期恰恰是最该熔断的情形
(go-redis 的单次读只受自身读超时约束,不看调用方的 ctx);读得不慢、只是调用方的预算到期 → 不熔断。
熔断期间下发的「没在排」由客户端的有界重拉接住(§5)。

推送(都至多一次,接收者是这一单名单里索引仍指向本队的人):

| 时机 | reason | 备注 |
|---|---|---|
| 入队成功 | `MATCH_QUEUED` | `actor_id` = 队长;调用者不收(回包里已有) |
| 撤单 | `MATCH_QUEUE_CANCELED` | 主动取消:`actor_id` = 取消者;其余:`tip` = `kTeamStateChanged` / `kTeamMemberOffline` / `kTeamMemberNotReady` |
| 凑满开局成功 | `MATCH_ENDED` | 与直接开战清锁后的推送同一个原因 |

入队流程内部的回滚与第 3 步自撤单是静默的,结果只由 `StartTeamMatch` 的回包表达。`matched` 对应的 `STARTING` 没有专门推送,恰好拉取时才看得到。

### 4.6 配置、指标与上线顺序

- `Team.FillQueueDisabled`(默认 false = 开放;`go/match/etc/match_service.yaml` 与 K8s ConfigMap 模板 `tools/scripts/k8s_deploy.ps1` 都有这一项):
  置 true 并重启所有 match 实例后,补位分支回 `kTeamDungeonNotOpen`,视图的 `match_fill_supported` 为 false(客户端不再给出目标人数);
  已在队列里的补位单不受影响,直接开战也不受影响。混跑窗口看 gauge `team_fill_queue_disabled`。
- **上线顺序**:match 必须整批替换(与人数档同口径)—— 旧实例不认识 `party_id`,会把补位单拆开成组。
  稳妥的做法是先带着 `FillQueueDisabled: true` 把所有实例换成新版本(此时没人能发起补位),确认没有旧实例后再改回 false 重启。
  回滚同理:先置 true 重启、等队列里的补位单排空(`team_match_total{outcome="queued"}` 不再增长且没有 QUEUED 视图),再回退版本。
- 指标:`team_match_total{outcome}` 新增取值 `queued` / `queue_canceled`,补位开局成功计入既有的 `success`;
  `join_queue_total{outcome}` 新增 `party_ok` / `party_conflict` / `party_withdrawn`(一支补位单记一次,不按人头)。
  队列指标口径不变(`LLEN` 仍是人数)。没有任何带 player_id / team_id 的 label。

## 5. 客户端(`mmorpg-client`)

「我在不在排」有两个来源:队伍视图的匹配态(提示:不带版本号,可能迟到、乱序、丢失)和排队票据(权威:`BattleClient` 进入排队态后每 3 秒问一次 `GetQueueStatus`;开战推送人人必达)。
同步规则在纯逻辑类 `TeamBackfillQueueSync` 里,`TeamUiRoot` 每帧调一次:

1. **采纳**:队伍视图说在排、`BattleClient` 空闲 → `BattleClient.AdoptQueue`(进入排队态,不发 JoinQueue、票据置空、不写连续战斗记忆)。
   之后排队面板、轮询、取消、凑满开战全部沿用单人排队的实现。
2. **结束只认票据**:`BattleClient` 离开了被带入的排队(轮询到已不在排 / 已开战)→ `TeamClient.ConsumeBackfillQueue(team_id, queued_at_ms)`:
   这一次排队记为已结束,此后同一次排队的视图既不显示「匹配中」也不再被采纳;队长重新发起会有新的入队时刻。会话重置时清掉这个记录。
   「已开战 = 结束」靠服务端保证:排队中进了任何别的战斗,服务端都会立即撤掉排队(§4.3 第五个入口、§4.4 看战斗锁)。
   兜底(服务端那一步遇到 Redis 抖动没撤成):规则 2 若是由开战(而不是票据)触发的,`BattleClient` 回到空闲后**探测一次**
   `GetQueueStatus`(`ProbeQueueStatus`,不改相位),服务端说仍在排(Queued / Matched)就撤销这个记录、重拉视图,由规则 1 重新采纳;
   Ready(刚打完的那一局留下的,最长 60 秒)按已结束处理;探测失败也按已结束处理、不重试。队长、队员都适用。
   另外,自己点开战被 `kTeamInMatch` 拒绝且回包视图就是 QUEUED 时,同样撤销这个记录。
3. **视图说没在排、而还在被带入的排队态** → 不直接改相位,立刻补问一次 `GetQueueStatus`(同一份视图只问一次),并补拉一次队伍视图(每次采纳至多一次)。

`BattleClient`:`QueueAdopted` 在排队态与凑满后的准备阶段保持为真;被带入的排队在准备超时后**回到排队态并立刻求证**(开局失败回队首时服务端不推送),不报「已退出匹配」。
**取消也要求证**:`CancelQueue` 的回包是 Empty,分不出「整队已退出」和「太迟」(队伍已凑满弹出,取消被忽略);太迟之后若开局失败,整队会回到队列。
所以被带入的排队点了取消不直接回空闲,而是立刻问一次 `GetQueueStatus`:已不在排才结束,仍在排 / 已凑满就照实处理并提示「取消未生效」。
求证只认取消回包之后才发出的那一次轮询(之前就在途的那次,服务端可能还没处理取消)。自己排的队行为不变。

`GetQueueStatus` 同一时刻至多一个在途(轮询与探测共用):大厅对零编号回包按消息号先进先出配对,两个同号请求同时在途时,
先到的回包可能被配给后发的回调。在途期间再要求轮询只记一笔「回来后再问一次」;`GameClient.Call` 在超时、断线、换 gate 时一定回调失败,
在途标记不会卡住。每次 JoinQueue / AdoptQueue 进入排队、以及断线时,排队会话序号加一;轮询与取消的回包只处理发出时那一次排队的,
上一次排队迟到的结果整包丢弃 —— 否则上一次排队迟到的「已不在排」会结束新的被带入排队并把它记成已结束。

「应当在排、视图却没在排」时有界重拉:收到 `MATCH_QUEUED` 推送、或自己的补位入队成功了,但手里的视图不是 QUEUED(服务端读票据失败、熔断),
就隔 6 秒静默重拉一次 `GetMyTeam`,最多 2 次,视图在排就停 —— 间隔跨过服务端 5 秒的熔断窗口。没有在排的视图就不会被带入排队,也就没有排队面板和取消入口。

界面:
- `TeamWindow` 的开战确认框在队伍没满副本上限、且视图带 `match_fill_supported` 时多一排目标人数(「现有 k 人」= 直接开战,「凑满 N 人」= 补位,经 `BackfillRequested` 事件)。
  确认框的选项、说明与确认后的行为都按打开时的人数算,名单人数一变就自动关框。
- 匹配中只锁「开始战斗」(显示「匹配中…」),请离 / 转让 / 解散 / 离队照常可点(名单不冻结)。
- 队员收到「队长发起了匹配 / 某某取消了匹配 / 因为谁被撤单」时队伍面板通常没开:`TeamClient.BackfillNotice` → `TeamUiRoot` 转给
  `BattleUiRoot.ShowQueueNotice` 弹 toast,结束类的还写进排队面板状态行。被带入的排队结束后,排队面板状态行不再停在
  「队伍匹配中…」,改成中性的「队伍匹配已结束。」(若已被取消原因改写则保留原因)。

## 6. 已知边界

- 掉线队员只在「轮到这支队伍成组」或有人触发自愈时才被发现;在那之前其余队员一直显示匹配中(可随时取消)。
- 队首是一支凑不满的大队时,后面的人会先成组;这支大队只要有合适的补位就优先(字典序最小),但没有「等太久就放宽」的机制。
- 一个人数档里全是互相凑不成 N 的补位单时(例如 3 人档里两支 2 人队),matcher 每轮(500ms)会把快照里的票据都读一遍
  (上限 256 张)再放弃;队列长度有限,暂不做「同一份快照不重复校验」的优化。
- 队列比 256 人还长时不判「不完整的单」,那种残留要等队列变短或由自愈清掉。
- 名单变化撤单的「提交后的成员集合」是集合比较:连续两次名单提交加一次重新入队都抢在第一次异步撤单之前时仍可能误撤(窗口极窄)。
  误撤落在建票循环中途时由入队后的复读接住(整单撤掉、队长重试),不会留半单。要精确需在补位票上记入队时的队伍记录 version,只登记、未做。
- 弹组摘出那条 Lua 自身报错(超时,结果未知)时直接结束本轮(既有形状,评分队列也是如此):若它其实执行了,被选中的人票据 queued 却不在 list,
  要等有人取消、或 JoinQueue / 开战预检触发自愈。
- 匹配态不带版本号:极端乱序下队伍面板可能短暂显示旧状态(排队面板与相位以票据为准,不受影响)。
- 断线重连后的第一份队伍视图恰好落在服务端读票熔断的 5 秒窗口里时,这名队员看不到「匹配中」,直到下一份视图到达
  (任何一次队伍推送、打开队伍面板)。期间他没有排队面板和取消入口,但队友可以取消。有界重拉只覆盖「发起匹配」那一刻,不覆盖重连。
- 排队中进了别的战斗、服务端撤排队又恰好遇到 Redis 出错,而客户端回到空闲后的那一次探测也失败时,本机会一直把那一次排队当成已结束
  (直到重登);队友可以取消,凑满时他会被直接拉进副本。三件事叠加,只登记。
- 大厅对零编号回包按消息号先进先出配对:一次排队查询超时(15 秒)后,更晚到的回包会被下一次同号请求领走。需要超过 15 秒的延迟,只登记。
- 新客户端连到不认识补位的服务端(旧版本 / Java 版)时看不到目标人数选项(能力位为 false),只能直接开战,不会出错。
- 奖励仍是每人全额;与路人同场不改变队伍记录,打完各回各队。
- 连续战斗开关与队伍的既有交互(打完按上次单人排队参数自动重排)没有动。
- 怪物数量成倍仍取决于 battle 节点重编(见 pve-team-size-matching.md);只换 match 时凑满 N 人进同一场,怪物是固定一组。

- 撤单版本保护兼容没有版本的静态旧队列项,但不支持旧实例继续无版本写入;仍须按 §4.6 整批升级 match。
  保护依赖 Redis 不丢失已确认的序列写入,不保证故障切换导致计数器回退后的 ABA 安全。
  此次只修 `cancelParty` 的旧撤单误删新入队项,普通 matcher 与既存入队 / 回队失败收尾的无条件删除竞态未扩修。

### 7.3 联机验收(三个客户端,match 已替换;battle 未重编时怪物是固定一组)

1. A、B 组队,A 在队伍面板「开始战斗」→ 选「凑满 3 人」→ 确认:A、B 都弹出排队面板,写着「队伍匹配中(目标 3 人)」,B 还会看到一条「队长已发起队伍匹配」的提示。
2. C 单人在排队面板选「3 人」档匹配:三个人进同一场战斗(battle 重编后应是 3 人份的怪)。
3. 重复第 1 步后 B 点「取消排队」:A、B 都退出匹配,A 弹出「B 取消了队伍匹配」,A 的排队面板状态行也是这句话。
4. 重复第 1 步后 B 离队:A 退出匹配并看到提示;A 可以立刻再次发起。
5. 打完一场补位战斗回到主城:队伍面板不再显示匹配中,排队面板不会自己弹出来。
6. 重复第 1 步后,C 向 A 发起切磋、A 应战并开打:B 立刻退出匹配并看到提示;A 打完切磋后不在排队里,可以重新发起。
7. A 打开开战确认框不点确认,此时 B 离队:确认框自动关闭。
