## 0. 结论(先读)

1. **玩家数据只放 SQL。** 本 MMO 用 TiDB。Redis 不撤,只做协调:会话、位置、交接标记、锁与租约、排队限流、Pub/Sub、能从 TiDB 重建的缓存。(用户 10-24 定,TiDB 决策 §9)
2. **存盘直接提交 TiDB**,不经过 Redis,也不经过 Kafka。一次存盘是一个 TiDB 事务,写权代次和整笔存盘序号在同一个事务里核对(§3)。
3. **缩小崩溃丢失窗口:资产和关键进度约 1 秒内存,其余按内容分六行、定时 60 秒只写有变化的行,位置只顺带写。**(用户 10-30 定「关键立存加拆热行」,11-05 改成按内容分六行,§4,总表见 §4.7)
4. **正常运行不丢、不回档。** 只有进程崩溃、强杀、存储损毁、人为失误才会丢,且丢的是「回到上一次成功存盘」,不会混版本、不会被旧写覆盖(§5)。
5. **发号不依赖 TiDB / MySQL**:照旧向发号器申请号段,发号器的计数器换成 etcd;ID 是 64 位,不带分区、地域、代号、时间、节点等任何含义,崩不崩溃都不重复(用户 10-24、10-30 定,§6)。
6. **路由用落点目录**(玩家 → 集群 + 库),不把分区写进 ID(用户 10-30 质疑后改定,§7)。合服改成别名合服、去掉围栏(用户 10-30 同意,§7.1)。
7. **所有层都靠加机器扩。** 数据面全部可水平扩展;控制面(etcd、TiDB 的 PD)是单 leader,只让它们承担低频写,并按地域、集群各起一套(§8)。
8. **同一套代码按预算分三档部署**:MySQL 主从 / 单个 TiDB 集群 / 多个 TiDB 集群。后端档位已落码,部署参数 `-DatabaseBackend`(§9.1,未编译)。
9. **MMO、SLG、MOBA 都适用。** SLG 也默认用 TiDB;单张大地图超过一个进程的容量时要拆图(§10)。
10. **先用一个 TiDB 集群上线**,把以后改不了的东西(ID 位宽、打散常量、表结构)一次定对;压测之后再拆多集群(§13)。

### 2.1 Redis 该用的地方(该用的一定要用)

用户 10-24 / 10-30 的口径:「该用 redis 的地方用 redis」。下表是改造后 Redis 继续承担的协调用途。键名与读写方以[玩家态 Redis 集群化](./redis-player-store-cluster.md) §5.1、§5.2 为准 [D],这里只按用途归类。

| 用途 | 键族(举例) | 写方 → 读方 | 为什么放 Redis |
|---|---|---|---|
| 在线位置与换场景 | `player:{<pid>}:location` 及修订号 / 下限、离场等待、换线冷却、进场去重 | scene_manager → C++、player_locator、login、guild、trade、mail、match、player_inbox | 高频读写、需要 Lua 原子比较;丢了玩家重新进场即重建 |
| 交接标记 | `player:{<pid>}:handoff` | C++ ↔ scene_manager | 交接过程中的短期协调;正确性由 TiDB 写权行兜底(§3.2) |
| 写权代次的投影 | `player:{<pid>}:owner_epoch` | scene_manager → C++、login、player_inbox | 路由与快速拒绝用;**权威在 TiDB**(§3.2),这一点与 TiDB 决策 §9.3 表 C「铸造照旧在 Redis」不同,以本文为准推进,落码前在第 1 批规格里定稿 |
| 会话与登录 | `player:session:*`、会话租约、gate 索引、AFK 通行、`player_locker:*`、`login_generation`、登录幂等 | player_locator、login → friend、guild、mail、match、login | 有 TTL 的短期状态,丢了重新登录即可 |
| 登录排队、准入与限流 | `queue:*`、`admit:*`、gate 排空标记;Java 网关 Bucket4j 令牌桶;sa-token 会话 | login、Java 网关 | 高频计数与过期,天然适合 Redis |
| 战斗互斥 | `battle:lock:*`、`battle:ctx:*` | C++ → guild、match 只读 | 短期互斥,有 TTL 与 reaper 兜底 |
| 场景路由与节点负载 | 场景路由、人数计数 | scene_manager、C++ | 可从运行中的节点重算 |
| 选主锁与短租约 | 排队调度、对账、补偿等单例任务的锁 | 各服务 | 租约天然要 TTL |
| 跨进程通知 | Pub/Sub:`assetop:wake`、`task:result:notify*` 等 | 各服务 | 只是唤醒信号,丢了靠轮询补 |
| 同步摘要 | `player:{<pid>}:sync_digest` | friend、guild、match → C++ | 只是提示,丢失或过期时客户端全量拉一次 |
| 匹配排队 | MatchRedis 排队池与匹配锁 | match | 排队状态短命,可重建 |
| 各服务私有的协调用途 | chat、friend、guild、match 的限流、配额、排队 | 各服务 | 同上 |
| 能从 TiDB 重建的展示缓存 | 好友档案摘要、在线目录、公会展示缓存(cache-aside) | friend、guild | 只做加速;必须能从 TiDB 重算,不得成为唯一来源 |

- **排行榜**:本仓 rank 已全部走 SQL,不用 Redis(TiDB 决策 §9.3 表 C [D])。以后若用 ZSET 做实时榜,榜单必须能从 SQL 重算。
- **Redis 自身也要水平扩展**:玩家相关的协调键按 `{player_id}` 分片成 Cluster,控制域按用途和 zone 拆(§8.4)。去掉存档后内存从 TB 级降到几十 GB 级(推算 [I]),但会话、位置、排队的读写量仍然很大,所以仍要分片。
- **改造时要一起改的读方**:match 的组队在线判定、friend 的在线推荐和好友档案、login 的选角外观补齐,今天读的是父快照(TiDB 决策 §9.3 表 B),要改成读位置 / 会话,或读 TiDB / 展示投影。

### 2.2 以后新功能怎么判断放 Redis 还是 TiDB

沿用 TiDB 决策 §9.2 的判据,看值,不看键名里有没有 player_id:

- 值是玩家持久数据的内容、它的副本或中转载荷,丢了只能从 TiDB 找回 → **放 TiDB**。
- 值是代次、租约、锁、位置、标记、计数、队列成员这类协调信息,丢了能按协议重建或按 TTL 失效 → **放 Redis**。
- 只做加速、真源在 TiDB、正确性从不依赖它的读缓存 → 逐项裁定,默认不新增。
- 资产、充值、交易、结算这类「丢了就是事故」的东西,一律不以 Redis 为准。

## 3. 存盘路径:直接提交 TiDB

### 3.1 流程

1. scene 在定时或事件触发时,把**有变化的行**序列化(§4),通过异步 RPC 交给存盘服务。scene 的 tick 不等回包([scene 线程模型](./scene-node-threading-model.md))。
2. 存盘服务开一个 TiDB 事务:锁该玩家的写权行 → 核对写权代次与整笔存盘序号 → 写入脏行 → 推进序号 → 提交。
3. 回包到 scene:成功就记下「已确认的版本」;被拒(代次过期)就销毁这个玩家的实体;结果未知(超时)就用**同样的内容和同一个序号**重试。
4. 存盘服务由 go/db 改造而来(用户 10-30 定),无状态多副本,复用现有行围栏判定(`go/db/internal/kafka/player_row_fence.go` 的 `savePlayerRow`:代次小判 stale、同代次序号小判 older、相同判 equal [C])。

### 3.2 写权:任何时刻只有一个写者

- **写权代次以 TiDB 为准。** 存档库的写权行(`player_store` 的 kind 0)记着代次 E、持有者、整笔序号与 `released`。目标 scene 认领时在一个事务里把新代次写进写权行(只增不减,比库里旧就拒绝)并读出全部行;每笔存盘在同一个事务里比对 E 与整笔序号(存盘规格 §2~§4)。代次由 scene_manager 进场时铸造,铸造的持久化与已确认位点见[进场按 zone 路由](./enter-scene-zone-routing.md)。10-30 写这一条时,入场登记只把 owner_epoch 写进 `account_role_admission.identity_proto`,不能比较、也不抬玩家行围栏(TiDB 决策 §9.4 第 3 条);这个缺口由写权行补上,和 Java 版把写权放在玩家行里同一个形状。
- **Redis 里的 `owner_epoch` 降为路由投影**,丢了能重建,不再是写权依据。这样「Redis 回退导致代次倒退、旧档覆盖新档」这一整类问题(G1、G3、R-G1-1,见[Redis 回退守卫](./zone-redis-regression-guard-20261022.md))不复存在。
- **整笔存盘序号单调递增**,放在写权行上。一次存盘整笔比较、整笔拒绝。评审发现:如果逐行判围栏、又跳过未变化的行,超时晚到的旧事务可能让两行落成内存里从未同时存在过的版本组合;整笔序号可以避免这个问题。
- **没有旁路。** 写玩家行的入口都经过写权行:存盘、认领、建角初始行、判死释放(存盘规格 §5.5)。其余入口不写玩家行:GM 回档在新路径上直接拒绝,调试导入按配置拒绝(存盘规格 §5.6);合服走别名合服,只写映射(§7.1);搬库按逻辑库整库搬,冻结期间写者闸门挡住所有写([全层水平扩展规格](./horizontal-scale-logical-db.md) §8)。旧路径的 `save_barrier_restore` 已删除。

### 3.3 交接与加载

- **下线、换场景、跨节点**:最终存盘和「释放写权」在同一个事务里提交;提交成功后才放人。目标 scene 在事务里认领(代次加一)之后再读档。移交请求带令牌,回包丢失时重试也不会重复移交。
- **加载**:同一玩家的所有行要在同一个一致性视图里读出——一条语句读出全部行,或者先锁写权行再读。读已提交隔离下,同一事务里的两条 SELECT 不保证读到同一个快照。
- **热加载代价**:断线重连、同节点重登复用节点上还在的实体,不读库;换节点或实体已销毁时才认领并从 TiDB 读全部行(一条语句,上一条)。Redis 父快照已随旧路径删除。读的耗时在压测里复核(AGENTS §6),不是待定项。
- **停机、发版**:先排空,所有在线玩家的最终存盘提交成功后进程才退出;K8s 的停机宽限时间要配够。

### 3.4 资产与跨服务

- 资产变化和它的幂等记录在同一个事务里提交,TiDB 决策 §8.4 的资产原子范围不变。
- 对方服务(公会、交易、邮件、收件箱)只认 TiDB 里的提交记录(强读),不认 scene 内存或 Redis 投影:账本读走 data_service 的 `ReadPlayerStoreAsset`,一条语句读写权行和钱包行(存盘规格 §5.5)。10-30 时 guild 还有一档 `AssetOp.RequireSQLCommit=false`,在线时按 scene 回包里的 Redis 快照终结;这一档已随旧路径删除,配置里已没有这个键。
- 自动放弃(对方等太久就退款)判断玩家是否在线时,读 TiDB 的写权行,不读 Redis 位置。评审发现:如果只按 Redis 位置判断,Redis 丢键时可能一边退款、一边又把这笔资产存进档,造成一物两得。
- 战斗结算原件移出 Redis,走 match 写 SQL 原件加收件箱(TiDB)的新路径(TiDB 决策 §9.3 表 A)。
- 玩家之间转移资产(例如 PvP 抢夺)要走带操作号的资产通道,不能靠两次独立存盘;或者设计成系统掉落,不从对方身上拿。代码里目前没有 PvP 抢夺玩法 [C]。

### 3.5 Kafka 还用不用

存档不走 Kafka;跨 zone 本来就不搬数据。Kafka 只做一件事:**发出去就不用等结果的异步通知和事件流**。原则和 Redis 一样:该用的用。下表按 2026-10-30 的代码盘点 [C]。

**保留:**

| Topic | 谁发 → 谁收 | 干什么 |
|---|---|---|
| `gate-cmd_g<N>`、`scene-cmd_g<N>` | login、scene_manager、player_locator、mail、match、friend、player_inbox 等 → C++ gate、scene | 控制面命令与推送:绑定会话、进世界、踢人、跨 zone 跳转通知、玩家路由事件、组队刷新、收件箱唤醒、给玩家推消息。按节点分区,不随玩家数增加 topic |
| `match-results` | battle → match(评分)、guild(帮会历练结算) | 对局结果事件 |
| `transaction_log_topic_g<N>` | C++ scene → data_service | 审计流水,异步批量落库 |
| `player_snapshot_topic_g<N>` | C++ scene → data_service | 回档用的玩家快照。它带玩家数据的历史副本,但只是归档,不是真源;丢了只少回档点,不影响存档 |

**退役或清理:**

| Topic | 处理 |
|---|---|
| `db_task_zone_*` | 存盘和登录读任务的管线,随新存盘路径退役;连带 go/db 的存盘消费者、saveoutbox 补投、重试与死信队列里承载玩家行的部分。逐项裁定,裁定之前照旧(TiDB 决策 §9.1 第 3 条) |
| `gate-<id>`、`scene-<id>` 旧单节点 topic | 生产者已切走,K8s 已关,本机开关 `DisableLegacyPerNodeTopic` 还是 false,确认后关闭并删除旧路径 |
| `match-rating-snapshot` | 发布开关缺省关闭(`RatingSnapshotPublishEnabled: false`),排行走 SQL;确认没有读者后删除 |
| `game-events` | 配置里的默认值,代码里没有使用,删配置 |

存盘退出后,Kafka 流量的大头就没了(2000 万在线推算 0.35~2.8 GB/s [I]),分区数和磁盘预算要按剩下的 topic 重算。

### 3.6 备选:保留 Kafka → go/db

| | 直接提交 TiDB(采用) | 保留 Kafka |
|---|---|---|
| 提交点 | 一个事务;只有「提交了」和「没提交」两种状态 | 多一个「已进 Kafka、还没进 TiDB」的中间状态 |
| 登录、交接、资产到账 | 看事务结果 | 要等 Kafka 里的存盘落进 TiDB,需要另外记录「在途存盘」 |
| 唯一多出的好处 | — | TiDB 故障同时 scene 崩溃时少丢一点 |
| 额外部件 | 无 | 消费组、再平衡、重试与死信队列、分区数契约 |

用户的底线是「正常运行不丢、不回档」,Kafka 的好处只在双重故障时体现,所以不采用。

## 4. 崩溃丢失窗口:关键变化立即存 + 拆出热行(用户 10-30 定)

### 4.1 现状 [C]

- 周期存盘:每名玩家每 300 秒整份存一次,环境变量 `SCENE_PLAYER_SAVE_INTERVAL_SECONDS`(缺省 300,0 为关闭),按 `playerId % 间隔` 摊到每一秒(`cpp/libs/services/scene/core/system/redis.cpp`)。整份序列化后做脏比较,相等就跳过。
- 立即存盘:资产通道、战斗结算、收件箱会立即触发,带 500 毫秒节流(`asset_op_system`、`player_battle`、`player_inbox_system`)。
- 结果:scene 崩溃最多丢 300 秒的非资产进度(位置、打怪经验、任务进度等)。

### 4.2 决定

1. **关键变化立即存。** 保留现有立即存盘触发,并逐个系统补齐「丢了玩家会明显感知」的事件:升级、任务完成与领奖、稀有掉落、副本通关、充值到账等。立即存盘仍有节流,同一玩家在节流窗口内的多次变化合并成一次。具体事件清单在落码前逐系统确定。
2. **拆出热行,定时存盘只写有变化的行。** 玩家存档从「一行多个 BLOB 列」改成同一玩家的多行。2026-11-05 起按「大小 × 变化频率 × 和谁一起变」分成位置、角色、钱包、背包、成长、资料六行,每行声明存盘方式,位置只顺带写([存盘规格 §1.1](./player-save-direct-commit.md))。10-30 的初稿是「热行 + 按职责分组(资产、成长、档案)」,把频率和领域混在一维里,位置一动整个热行跟着写,改几个铜板整个背包跟着写,所以改掉。
   - 定时存盘 60 秒,每次只写有变化的行;只有位置变了的那一笔推迟,最长 300 秒(两个数 2026-11-12 定案,理由见 §4.5)。
   - 为什么必须拆行:TiDB 一条 SQL 行就是一个 KV,只改一列也要重写整行(TiDB 决策 §8.1),「只写变化的列」省不了写入量。
   - 「重要」和「经常变」要的东西相反:重要的(资产、账本)要快存,靠资产通道先提交后认账和关键进度事件;经常变但不重要的(位置)要少存、合并着存。一致性不靠存得勤,靠「一次存盘是一份完整快照、同一事务同一序号」(§3.2、§4.3)。

### 4.3 必须守住的约束

- 一次存盘的所有脏行在**同一个事务**里提交,带**同一个整笔序号**(§3.2)。
- 脏判断以「上一次**确认提交**」为基准,不以「上一次发出」为基准;结果未知的存盘重试时带同样的内容和同一个序号,否则会漏写某一行。
- 加载按 §3.3 在同一个一致性视图里读出全部行。
- 拆行是玩家表结构变更,按 TiDB 决策 §8.6 覆盖 proto 源与生成器、建表、装卸代码、快照与回档、合服与搬迁工具;新表名按职责命名,不再用 `_1`、`_2` 编号。项目未上线,直接以新结构起步,不做存量兼容。
- 本条拆分的理由是存盘频率,不是行大小。§8.3「测量支持才拆」的口径针对的是大小;间隔已在 §4.5 定案,压测按 AGENTS §6 复核事务数与写入量。

### 4.4 效果与代价(推算 [I],未实测)

- 资产、升级、任务完成等关键进度基本不丢,只差节流窗口(约 1 秒);打怪经验这类非关键进度最多丢一个定时间隔(60 秒),位置最多回到 300 秒前。
- 2000 万在线时:整行每 300 秒存一次,约每秒 3.3 万笔事务,每笔 11~33 KB(写入 0.37~1.1 GB/s);热行每 60 秒存一次,按一半玩家无变化计,约每秒 17 万笔小事务,按热行 0.5 KB 估约 85 MB/s。位置走动时几乎每次都在变,跳过率会比整行低,实际笔数可能更多。
- 写入字节可能下降,事务数上升。事务数是 TiDB 最敏感的指标(每笔都要取时间戳,§8.1 第 3 条);间隔已定为 60 秒(§4.5),扛不住靠多集群,调大间隔旋钮只作应急。
- TiDB 整体故障期间所有存盘都提交不了,丢失量取决于故障时长,与本条无关,靠降级模式控制(§5)。

### 4.6 判脏的开销、常驻内存和后续优化(2026-11-01 讨论,2026-11-11 定案)

**现在的做法**:每次存盘拼出整份 `PlayerAllData`,按行(kind)投影并确定性序列化(`player_store_projection.cpp`),和上一次确认提交的字节 `confirmed[kind]` 比较(`player_store_client.cpp`),只写不同的行。玩家数据在一张表 `player_store` 里;2026-11-05 之前分四行业务数据(`HOT`、`ASSET`、`GROWTH`、`PROFILE`),之后分六行(`LOCATION`、`CHARACTER`、`WALLET`、`BAG`、`GROWTH`、`PROFILE`,规格 §1.1)。

**为什么不用旧做法**:旧路径用 `MessageDifferencer` 比整份。
- 反射逐字段比较,比直接比字节慢得多,设计时写的「远低于 100µs」是估算。
- 位置一变整份都算变了,活跃玩家基本跳不过,只有挂机玩家省得到。
- 当年不比字节,是怕 protobuf 升级后字节变化造成误判。误判只会多写一笔,方向安全,这个理由不成立。

**为什么不用手写脏标记**:快,但漏标一处就静默丢数据,而且很难查出来。

**开销排序**(经验判断,未实测):写库远大于序列化,序列化大于比字节。所以:
- **不做「常变的行不比较」**:热行约 0.5 KB,比较几乎不花钱。去掉之后,站着不动的玩家每次都要写一笔,事务数反而上升,而事务数正是 TiDB 最敏感的指标(§4.4)。
- **要省 CPU,该省的是序列化**:现在每次存盘都要把所有行序列化一遍才能比较,大行没变也一样。

**常驻内存**:每个玩家三份,ECS 实时数据、`confirmed`、`PlayerLastPersistedSnapshotComp`。快照不只用于比较,资产、结算、收件箱拿它当「已提交」的证据,所以不能简单去掉。

**tick 尖刺**:周期存盘原来每秒跑一次,在游戏线程上一口气做完这一秒的玩家(`cpp/libs/services/scene/core/system/redis.cpp`)。周期从 300 秒缩到 60 秒之后,工作量是原来的 5 倍。2026-11-11 起改为每 0.1 秒一个槽,见下表。

**定案(2026-11-11,负责人要求不等压测、按标准做法定)**。估算口径:protobuf 序列化约每秒 1 GB,满背包的整份行约 15 KB,一次序列化约 15 µs;一个 scene 1 万人在线、周期 60 秒,每秒约 167 次存盘尝试,序列化合计约 2.5 ms/s,不到一个核的 0.3%。实测数字出来后写回本节核对,估算错一个数量级才重开对应一行。

| 原来的触发条件 | 定案 | 代价 |
|---|---|---|
| 热行事务数压不住 | **2026-11-05 已改为缺省**:位置单独成行 `LOCATION`,存盘方式「只顺带」,定时存盘只遇到位置变化时推迟,别的行要写、非定时存盘(含下线、交接)一定带上,兜底 300 秒(规格 §1.1)。不再「比脏时排除 `transform`」:单独成行之后比脏照常比,只在「要不要发这一笔」时看存盘方式 | 崩溃时位置回到几分钟前。位置不是资产,可以接受 |
| 周期存盘回调造成 tick 尖刺 | **2026-11-11 已落码(未编译)**:定时器每 0.1 秒一个槽,一个周期 `interval × 10` 个槽,按 `playerId % 槽数` 分;每个玩家每周期仍恰好一次,单次回调约「在线人数 / 槽数」(1 万在线、60 秒周期约 17 人)。单次仍超 10 毫秒时 `[SaveTiming]` 升 WARN | 定时器多跑 10 倍,每次遍历在线表,1 万在线约几十微秒 |
| 序列化占 CPU 明显 | **定为不做**:按上面的估算,全量序列化不到一个核的 0.3%;变化提示要在货币、背包、任务、等级等全部领域入口打标记,还要兜底全量比较和抓漏标,多一套必须永远维护对的规则,换来的 CPU 可以忽略。每次存盘照旧全量序列化、按字节判脏,不存在漏标丢数据。规格 §1.1「变化提示」那段保留为「真要做时的规则」 | 每次存盘多花约 15 µs |
| 内存吃紧 | **定为不做**:`confirmed` 每人约等于一份序列化行(满背包约 15 KB,1 万人约 150 MB),比 ECS 实时数据和快照都小。换成哈希要多一个依赖、失去按字节对照排障的能力,还要论证碰撞;精确比较更简单 | 每人多一份行字节 |
| 每次确认提交深拷贝快照(`PlayerLastPersistedSnapshotComp::Replace`) | **定为不做**:一次深拷贝与一次序列化同一量级,可以忽略。快照是资产、结算、收件箱的「已提交」证据,独占一份不会被别处改到;改成共享已提交的消息要改它的所有读者和退出路径,收益不抵风险 | 每次提交多一次深拷贝 |
| `ASSET` 写入量大 | **2026-11-05 已定并落码(未编译)**:货币和两本账本、限购进 `WALLET`,背包单独 `BAG`。同一次存盘的脏行本来就在一个事务里提交,不影响一致性 | 每笔多一行。上线后再改要迁移存档,所以**首次上线前定** |

要看的数据:每行的大小(`player_store_row_bytes`)和写入频率、热行事务数、scene 的 tick 耗时和内存占比。不要拆到每个道具一行,除非这些数据支持。

### 4.7 存盘时机总表:什么数据什么时候存,为什么不用手写脏标记(2026-11-12)

负责人 2026-11-12 问:不要再分 `player_database` 与 `player_database_1` 两个库表;之前说过加脏标记会因为漏标而忘记存,重要数据(比如金钱)要马上存,各种分层、分频率,有没有更好的办法。这一节把答案收在一处;细节仍以各原节为准。

**结论**

1. **不再分两个库表。** 一张表 `player_store`,每个玩家按内容分六行:位置、角色、钱包、背包、成长、资料(§4.2,存盘规格 §1.1)。两个库表原来的用意是「重要数据放主表、登录立即加载,不重要的放另一张」,这条轴现在由「存盘方式 + 触发点」承担;`player_database_1` 是另一个消息,字段号与主表重叠、加载要单独解析、世代要盖两份,只剩负担,2026-11-06 已删(存盘规格 §1.2)。
2. **不用手写脏标记。** 「哪些行要写」由字节比较算出:每次存盘把整份数据按行投影并序列化,和上一次**确认提交**的字节比,只写不同的行,同一事务、同一整笔序号(§4.3、§4.6)。没有标记,就没有漏标。
3. **「重要」和「常变」是两条轴,分开处理。** 常变决定怎么分行:小而常变的不和大而少变的放一行。重要决定什么时候存:按丢了的代价定,重要的快存,常变但不重要的少存、合并着存,而不是「常变就马上存」。

**总表**

| 数据 | 什么时候存 | 谁触发 | scene 崩溃时最多丢 |
|---|---|---|---|
| 货币、物品 | 变动后约 1 秒内提交;同一玩家 1 秒内的多次变动合成一笔 | 记流水这一个收口(`TransactionLogSystem::SetAssetChangedHook`):货币和背包的每次变动都由 `CurrencySystem`、`BagService` 记流水,玩法代码绕不开;流水被拒收(号段断供、单条超限)时照样触发 | 约 1 秒,加一次提交的耗时 |
| 资产通道、战斗结算、收件箱记账 | 记账后立刻存 | 各自记账之后请求存盘 | 不丢已确认的:对方只认 TiDB 里的提交才认账(§3.4) |
| 任务完成与领奖、等级变化、强化结果、宝宝发放、战斗道具预留的占用与释放、断线、进场审计快照、邮件发件 | 约 1 秒内提交,窗口内合并 | 领域入口显式调 `RequestKeyProgressSave`。强化结果(这一级不收费时没有流水)和宝宝(不在背包里)走不到上一行,所以显式调 | 约 1 秒,加一次提交的耗时 |
| 其余:经验、当前血蓝、技能、属性点、任务进度、资料 | 60 秒定时,只写有变化的行 | 定时器每 0.1 秒一个槽,按 `playerId % 槽数` 分摊,每名玩家每周期一次 | 60 秒 |
| 位置 | 不单独触发存盘,随别的存盘顺带写;兜底 300 秒 | 「只顺带」的行(存盘规格 §1.1) | 300 秒 |
| 下线、交接、疏散、停机 | 一定存,带写权释放 | 生命周期 | 不丢(§5.1) |

一次存盘写的是当时**所有**有变化的行(存盘规格 §1.1 原则 4),所以任何一次快存都会把别的行里已有的变化顺带写出去:「其余」一行的 60 秒是上限,不是典型值。三个旋钮:定时间隔 `SCENE_PLAYER_SAVE_INTERVAL_SECONDS`(60 秒)、位置兜底 `SCENE_PLAYER_PIGGYBACK_FALLBACK_SECONDS`(300 秒)、关键进度窗口(常量 `key_progress_save::kWindow`,1 秒)。

**为什么「重要数据马上存」不靠每个玩法打标记**

- 脏标记只回答「哪些行要写」,这件事字节比较已经算得出来,不需要标记。真正难的是「什么时候存」。让每个玩法自己决定这次重不重要,和手写脏标记是同一类规则:漏一处没有任何报错,平时也看不出来,只在崩溃时才多丢(属性同步漏标,客户端马上看得出;存盘漏标不会)。
- 所以按一个机械事实触发:动了货币或物品。这个事实必然要记流水,收口只有一处(`TransactionLogSystem::RecordEntry`);新玩法只要走货币、背包接口就自动带上,不存在「忘了」。通知跟着「资产变了」走,不跟着「流水收下了」走:txlog 号段断供、单条超限时流水被拒收,货币、物品照样已经在内存里变了,同样请求存盘(11-12 先挂在流水入队之后,号段断供期间所有资产变动都会退回 60 秒定时存盘,当晚挪到判定之后)。不经过货币、背包的几类关键进度(上表第三行)在领域入口显式请求,那也不是标记行,只是提前存一次。
- 漏接显式请求的后果:崩溃时这部分多丢到 60 秒的定时间隔。方向是安全的(多丢,不会错写,也不会回到混版本),下线、交接、停机照常存,正常路径不丢。
- 两名玩家之间的转移:流水只收「恰好一名玩家」的记录,两边都填或都不填的拒收并打 ERROR(`TransactionLogSystem::RecordEntry`);两名玩家之间转移资产记成两条(转出方一条、转入方一条,同一个 correlation_id),各进各的队列,各自触发收口。玩家之间转移资产本来就要走资产通道(§3.4),资产通道记账后立刻存。所以没有绕开这个收口的流水。(11-12 先写的「`LogItemTransfer` 没有调用方」已过时:审计发件箱会话同日删掉了这个接口。)

**比较过的其他做法**

| 做法 | 没选的原因 |
|---|---|
| 手写脏标记(像属性同步那样) | 漏标静默丢数据;要加兜底全量比较和抓漏标,等于多维护一套必须永远对的规则,换来的是不到一个核的 0.3% 序列化 CPU(§4.6)。真要做时的规则留在存盘规格 §1.1「变化提示」 |
| 每次改动同步写库 | 只有它能做到崩溃也不回档;事务数是 TiDB 最敏感的指标(§4.4),本方案不做(§5.2) |
| 按领域分热、资产、成长几组 | 10-30 的初稿。把频率和领域混在一维里:位置一动,整个热行跟着写;改几个铜板,整个背包跟着写(§4.2) |
| 每个道具一行 | 没有数据支持拆到这个粒度(§4.5、§4.6);拆了一次存盘写的行数、读一份背包扫的行数都会涨(推算 [I]) |
| 两个库表(`player_database` / `player_database_1`) | 见结论 1 |

## 5. 什么情况下会丢,什么情况下保证不丢

### 5.1 正常运行保证不丢、不回档

正常下线、换场景、跨节点、发版和停机(先排空)、TiDB 变慢(存盘排队重试,下线和换节点等提交完才放人)都不丢;新档不会被旧档覆盖。

### 5.2 会丢的情况

| 情况 | 丢什么 | 怎么防 |
|---|---|---|
| scene 进程崩溃(`kill -9`、内存耗尽、程序崩溃、所在机器宕机) | 上次成功存盘之后的进度:关键进度只差节流窗口,其余最多一个短间隔 | §4 |
| 发版或停机时还没排空就被强杀 | 没排空的玩家回到上次存盘 | 停机宽限时间配够,排空完成才退出 |
| TiDB 或存盘服务整体不可用,期间 scene 又崩溃 | 故障开始之后的进度 | TiDB 跨三个可用区;故障时进入降级,暂停会产出资产的玩法和新登录 |
| 同一份数据的多数副本同时损坏(三副本坏两个盘) | 已提交的数据也可能丢,只能从备份恢复 | 三副本分散在不同可用区;全量备份加日志备份,可恢复到任意时间点 |
| 整个地域的机房不可用 | 取决于异地容灾:TiCDC 异地同步官方 RPO 小于 10 秒,只用 BR 是分钟级([TiDB Phase 1](./tidb-phase1-and-launch-readiness.md) §8 [W]) | 做异地容灾 |
| 人为失误或代码 bug(GM 误操作、跑错脚本、字段忘了存) | 不确定 | 时间点恢复、应用级回档、测试 |

## 6. 发号:不依赖 TiDB / MySQL

### 6.1 机制

用户 10-30 定:**ID 是 64 位;用发号器申请;一定不重复、全局唯一,崩不崩溃都一样;Lua 里 ID 当字符串;先不考虑 JavaScript、JSON 的精度问题。**

v1.3 的「etcd 计数器 + 时间下限」经正确性评审被否决:时钟跑快过的发号器会把计数器抬到未来,之后 etcd 回退、时钟恢复,等真实时间追上来就会重号,而那时时钟完全正确;时钟门禁还会让一次坏时钟停掉全服发号。下面是修正后的设计,评审记录见 `docs/handoff/player-save-direct-commit-20261030/id-issuer-review.md`。

- **调用方不改。** C++ 的 `GuidSegmentClient`、Go 的 `go/shared/idsegment` 仍向 `data_service.AllocateIdSegment` 申请 `[lo, hi)` [C]。双缓冲预取、动态步长、发现号段重叠即拒绝都保留。「号段必须递增」这条要放宽:多个发号器副本各发各的块,同一个客户端先后领到的段不保证递增(落码时发现,2026-10-30)。
- C++ Scene 每次领段由所属 EventLoop 的作用域持有并等待 gRPC 完成，之后按原请求编号交给号段客户端。客户端的兜底超时和 10 秒迟到认领窗口继续独立工作。开始停机时关闭新的请求，已经发出的结果在退出存盘期间仍可补入缓冲。节点拆除前取消剩余本地等待，手里已有的号仍按原规则发放。
- **发号器从内存发号段,不是每次都写存储。** 发号器进程先预留一大块号,记录落盘后,再从这块里切号段给调用方。一块用完(或用掉一半时后台预取)才碰一次存储。所以 `id_segment` 表的单行热点和 etcd 单键争用都不存在。
- **预留记录写三份,三份互相独立。** 主记录和副记录分别放在本地域两套独立的 etcd 集群里,第三份在全世界共用的全局号源登记处,都只增不减。一块号只有在三份都写成功之后才能发出去。任何一份或两份丢失、回退,剩下的仍然盖得住所有发过的号。登记处同时把每个地域码唯一绑定到一个部署环境(K8s 集群)里的一对本地 etcd 上。详见 §6.3。
- **所有种类共用一个计数器。** 今天每种 `biz_tag` 一个计数器,不同种类的数值可能相同。共用之后,系统里任意两个 ID 都不相同。`biz_tag` 只用来校验和记指标,未登记的种类照旧拒绝。
- **打散不决定唯一性,只解决索引热点。** 发号器发出的是递增的计数器值,直接用的话新号都挤在索引最右边一个 Region。客户端发号时过一遍 63 位内的公开混合函数:`x ^= x>>30; x = x*C1 mod 2^63; x ^= x>>27; x = x*C2 mod 2^63; x ^= x>>31`,`C1`、`C2` 用 SplitMix64 的两个奇数常量。每一步都可逆,所以一一对应;没有循环;0 只对应 0,而计数器恒大于 0。Go 与 C++ 用同一组固定样例对拍,并测逆函数往返。
- **ID 不带业务含义**:不带分区、地域、时间、节点的语义,没有任何代码解析它。注意打散是公开可逆的,从 ID 能反算出计数器,所以这是「不依赖」,不是「保密」;权限判断不得依赖 ID 猜不到。
- **位宽**:类型是 64 位(`uint64`、`BIGINT UNSIGNED`)。**值只用低 63 位,最高位恒为 0(负责人 2026-10-31 定)**:2^63 约 922 亿亿,用不完;而代码里有依赖最高位的地方——Java 网关的 `playerId` 是有符号 `long`(`LoginResponse`、`LoginRpcClient` [C]);trade 的守卫表靠 `| 1<<63` 区分哈希键和 ID 键(`market.go` [C])。若要用满 64 位,这些地方要先全部改掉。(2026-10-31 重新核对:player_locator 原来的 `locationKey(int64(playerID))` 已随 Redis 键改名消失,`auction.go` 也不再用最高位。)
- **Lua 里 ID 一律当字符串**(用户 10-30 定):Redis Lua 的数字是浮点数,超过 2^53 会丢精度。脚本里 ID 只做字符串比较和拼键,不用 `tonumber` 计算或比较;有序集合的分数也是浮点数,不拿 ID 当分数。现有 `tonumber(` 约 96 处(30 个文件 [C])。2026-10-30 逐处看过:全部是计数、时间戳、版本号、代次和 TTL,没有处理 ID 的,不用改;有序集合的分数也全是时间。打散之后所有 ID 都超过 2^53,以后新写脚本要守这条。
- **唯一性只依赖五点**:预留记录只增不减;一块号三份记录都落盘后才发;CAS 只有一个预留者成功;一个地域码只绑一个部署环境里的一对本地 etcd、一生只认领一次;打散一一对应。正常路径不依赖时钟和租约。

**计数器结构**(63 位,只有发号器知道,客户端不配、不解析):

| 字段 | 位数 | 说明 |
|---|---|---|
| 地域 | 6 | 放在最高位。64 个码,0 只给 dev、test;由发号器配置,和记录里的地域核对,并由全局号源登记处唯一绑定到一个部署环境里的一对本地 etcd(§6.3),对不上拒绝预留。客户端拿到的 `[lo, hi)` 已经包含它,不需要、也不允许配置。这个「发号码」平时等于地域的存档库编号(部署参数 `-Region`,§7.2);事故换码时只换发号码(`-IdIssuerRegion`),存档库编号不变 |
| 时间 | 33 | 秒,从 2026 年起,约 272 年 |
| 序号 | 24 | 每秒约 1677 万个,是 2000 万在线推算峰值(约每秒 116 万条流水 [I])的 14 倍以上 |

计数器值连续,号段 `[lo, hi)` 就是这个 63 位上的连续区间,所以客户端的范围校验把上限改成 2^63,「必须递增」改成「不能和最近接受过的段重叠」。发号器发段时不要求 `hi-lo` 等于请求的步长,可以截短到块尾(客户端已支持)。

### 6.2 崩溃也不重复

| 情况 | 结果 |
|---|---|
| 调用方进程拿到号段后崩溃 | 没用完的号作废,重启后申请新段;只有空洞,没有重号。今天的 C++ 客户端就是这个语义:不持久化游标,优雅关服也不把尾巴还回去(`guid_segment_client.h` [C]) |
| 申请请求超时,不知道发号器发了没有 | 重新申请,上一段作废;不重号 |
| 发号器进程崩溃 | 手里这块剩下的号作废。重启后预留新块,新块一定在两份记录之上 |
| 多个发号器副本 | 每个副本独占自己预留的块,互不重叠;预留时靠 CAS 决定谁成功 |
| 进程卡死很久才恢复 | 手里的段或块是它独占的,接着用也不重号。这是号段比 snowflake 强的地方:不依赖租约和时钟 |
| etcd 切 leader、单节点宕机 | 多数派确认才算提交;没确认的预留不会被使用 |
| **一套本地 etcd 整体丢数据,或被人从旧备份恢复** | 另外两份记录盖得住所有发过的号,下一次预留自动跳到它们之上,不用人工处理(§6.3) |
| **本地两套 etcd 同时被恢复到旧快照(两条记录都在)** | 登记处盖得住,下一块从登记处水位之上开始,上报 `records_behind_registry`;时钟正常、计数器跑在时钟前面也不重号(§6.3) |
| 本地两套 etcd 都丢了数据 | 拒绝发号,运维按登记处水位恢复(`-id-issuer-recover -id-issuer-rebind`) |
| 登记处丢数据或回档 | 本地两份盖得住;丢了的码由 `-id-issuer-recover` 按本地记录重新登记 |
| 本地和登记处都没有这个码的记录 | 没有可信上界,拒绝,不猜起点;退役这个码,换一个新码 |
| **三份记录一起回档,或本地回档的同时登记处丢码** | 活着的发号进程记得自己确认过的水位:下一块从它之上开始,作证检查把低的记录抬回去;登记处丢码时重新登记还加时钟推得出的上界(§6.3) |
| 另一套环境配了同一个地域码、或者克隆了快照 | 登记处只认绑定的那个部署环境(K8s 集群身份)和其中那一对 etcd,另一套初始化和发号都被拒绝。同一份清单部署出的 etcd 集群号相同、集群级备份恢复带走了集群号,也照样拒绝(§6.3) |
| 时钟跑快、跑慢、回拨 | 不会重号。时钟只作为第三道防线抬高块的起点;跑快只浪费值域 |

### 6.3 etcd 丢数据或回退:三份预留记录 + 全局号源登记处(2026-11-05 修订)

任何发号方案都有「记录不能回退」这个前提,放 TiDB 表也一样。解决办法是**先把上限写进几份互相独立的记录,再发号**,和 TiDB 的 TSO 先持久化时间窗口上限是同一思路。

**为什么从两份改成三份**(2026-11-05 评审):两份本地记录都在、都被恢复到同一份旧快照时,发号器分不出这和正常状态有什么区别,只能按 `max(两份记录, 时间下限)` 接着发。而计数器每次预留都前进一块(约 256 秒的序号),发号器重启得多就会跑到时钟前面,所以时间下限低于已发区间,即使时钟完全正确也会重发。原来手册里「余量加一天 / 30 天」证明不了盖住了历史预留。要识别这种回档,必须有一份不和本地两套一起回档的证据。另一个问题是地域码:两对互相独立的 etcd 配同一个码就能各自发号,防重只靠人工登记表。这两件事都需要一个所有环境共用的仲裁者,合成一个就是全局号源登记处。

**三份记录**,都只增不减,一块号只有三份都写成功才能发:

| 记录 | 放在哪 | 管什么 |
|---|---|---|
| 主记录 | 本地域的 `etcd` | 本地域的水位 |
| 副记录 | 本地域的 `etcd-id-secondary` | 同上,两套独立 etcd 是强规定(AGENTS §7) |
| 登记处 | 全局号源登记处 `etcd-id-registry`,全世界一套,每个地域码一个键 | 这个码的水位,加上地域码绑定:发号世系(`authority`)、部署身份(`deployment`)、绑定的两套本地 etcd 的集群号、预留次数。另有一个「下一个可认领的码」 |

```
预留一块(很少发生):
  先读 G,再依次读 P、S                    // 三套独立 etcd,各自线性读,不是跨集群原子快照
  核对:G 存在且未退役;P、S 的世系等于 G 的;本进程所在 K8s 集群的身份和两套本地 etcd 报的集群号等于 G 绑的;P、S 不能都不存在
  若 max(P, S) > G.水位,复读登记处          // 完整记录有变化则从头重读;复读失败则拒绝,此时尚未写任何记录
  start = max(P, S, G.水位, now_floor)
  end   = start + 块大小
  CAS 主记录 P → end                     // 冲突就从头再来,这是多副本之间的仲裁点
  CAS 副记录 S → end
  CAS 登记处 G → 水位 end,预留次数 +1     // 写序固定:登记处最后写
  三份都成功后,才可以从 [start, end) 发号段
```

- **为什么不重号**:发出去的每个号都小于当时三份记录的值。任何一份或两份丢失、回退,剩下的那份还在,下一块的 `start` 自动跳到它之上。本地两套一起回档时靠登记处;登记处丢失或回档时靠本地两份。手里已有块的发号器不受影响,因为块在内存里、从不回读。
- **水位差异的诊断**:写序是本地两份先、登记处最后,读序是登记处先、本地两份后。这样正常并发提交不会把旧本地值和新登记处值拼在一起,误报双本地回档。本地两份都落后先读到的登记处,上报 `records_behind_registry`。本地高于登记处时先复读登记处,完整记录变了就整轮重读,避免把已经提交的并发预留说成登记处落后;版本未变才上报 `registry_behind`。登记处落后超过一块既可能是回档,也可能是多次预留没完成登记处写入,不能只凭差距断言回档。诊断在本轮写入之前完成,随后写失败仍保留差异信号;成功预留仍从三份水位和时间下限的最大值之上继续。
- **地域码唯一绑定**(2026-11-11 按审核交接 §6.2 修订):登记处里一个码只认一条世系、一个部署环境和其中的一对本地 etcd。部署环境的身份是 `k8s:<kube-system 命名空间的 UID>`,data-service 运行期经 K8s API 读(`internal/clusteridentity`)。
  - **为什么只比 etcd 集群号不够**:etcd 的集群号只由成员 peer 地址和引导令牌算出(etcd 3.6.16 `computeMemberID`,引导时不带时间),而三份清单的令牌和地址只由 `-InfraNamespace` 推出。所以同一份清单部署到两个 K8s 集群,集群号相同,原来的绑定分不出两套环境;集群级备份恢复(Velero、卷快照)还会把数据目录里的集群号一起带到别的集群。两套环境都拿到发号资格之后,登记处在时两边靠它串行;登记处一旦回档或丢码(§6.2 说能自愈的两类事故),就会重号。
  - **为什么身份要运行期读**:渲染进 ConfigMap、Secret、环境变量的值,会和 PVC 一起被集群级备份恢复带走。kube-system 的 UID 由 API server 建集群时生成,按对象恢复出来的都是新 UID,带不走。data-service 的 ServiceAccount 只多一条权限:get `namespaces/kube-system`。身份第一次需要时读,成功后缓存到进程结束;读不到那次预留或运维操作失败、不写任何记录,指标 `identity_error`。dev 不核绑定,不读。
  - **结果**:另一套环境配同一个码,初始化被拒(码已认领),直接发号也被拒;同一份清单部署到另一个 K8s 集群、集群号完全相同,同样拒绝。拿别人的 etcd 快照或整个数据目录克隆过来:世系和集群号都对得上,部署身份对不上,照样拒绝。同一个 K8s 集群里同一对 etcd 的多个副本照常发号;同一个 K8s 集群里原地恢复 etcd,身份和集群号都不变,不用 rebind。
  - **令牌**:三套 etcd 的引导令牌也带上 kube-system UID,新部署出的 etcd 集群号各不相同(etcd 的建议做法)。已有数据的 etcd 忽略令牌,改它不影响在跑的集群。这只是加固,判定靠部署身份。
  - **拦不住的情形**:整个 K8s 控制面连同 kube-system 一起从备份克隆出第二个集群(UID 也被复制),或者在同一个 K8s 集群里拷贝 etcd 数据目录、强制起成另一套集群。这两种都要有人刻意做,这时两边只能靠登记处水位串行,登记处完好时不重号。
  - 本字段出现之前写的登记处记录没有部署身份,生产预留拒绝,`-id-issuer-recover -id-issuer-rebind` 补上。项目未上线,没有存量。
  - **两份本地记录也写上部署身份**(2026-11-12):每次预留、初始化、恢复建记录时,写下它的那个环境的身份。
    - 为什么:部署身份原来只存在登记处。登记处丢了这个码,幸存的本地记录只带世系,证明不了谁是绑定的那一份。别的 K8s 集群里要是有原地域 etcd 数据的克隆(集群级备份恢复),它跑不带 rebind 的 `-id-issuer-recover` 就能按自己那份过期的水位抢先重新登记,绑定到自己。原地域被挡在外面,克隆从过期水位往上发的号和原地域发过的重叠。
    - 规则:登记处有这个码时仍以登记处的绑定为准,不看本地记录里的身份。登记处没有这个码时,只有「在的本地记录都是本环境写下的」才重新登记;否则(拷来的记录,或没有身份的旧记录)拒绝(`ErrForeignRecords`),`-id-issuer-rebind` 也不放行。
    - 为什么 rebind 也不放行:登记处在的时候,错误的 rebind 只影响可用性,水位由登记处盖住,不会重号。登记处没有这个码时,拷来的记录就是唯一的水位,而它可能比原环境发过的号旧(备份之后原环境还在预留)。这和「拿不到可信上界就拒绝、换码」是同一条原则:灾备环境遇上登记处同时丢码,只能按运维手册 §4.5 换一个发号码,新码的值域和旧码不相交。
    - 本环境自己写的本地记录在同一个 K8s 集群里被回档,同时登记处丢码(三处同时出事):记录自己查不出来。2026-11-12 起由两样东西兜住,见下面「活着的进程作证」和「重新登记的时间上界」。
- **用过的码永不再分配**:码按从小到大认领,认领时把「下一个可认领的码」推过去(一个 Txn 里核对和写入)。哪怕一个码的记录丢了,它也小于「下一个可认领的码」,初始化照样拒绝。退役的码留墓碑,预留、初始化、恢复都拒绝。
  - **认领只能一个接一个**:初始化只能认领「下一个可认领的码」本身,大于它拒绝(`ErrRegionOutOfOrder`),什么都不写。跳过去的码再也不能认领,码一共只有 63 个,一次填错(5 写成 50)就会烧掉中间整段。
  - **声明指针不强制等于已有最大码 +1**,只要求大于全部已有码,取台账里用过的最大码 +1。重建时某个用过的码既没有幸存记录、也漏补了墓碑的话,强制「已有最大码 +1」会把它重新放开,新地域就和它当年发的号撞上。现规则最坏只是填大了浪费几个码,是可用性问题,不是唯一性问题。重建流程要求给每个用过、没重新登记的码补墓碑(运维手册 §4.3)。
  - **「下一个可认领的码」有三种状态**(2026-11-12):没有(新世界没开启,或者登记处整个丢了);重建中(`-id-registry-rebuild` 声明的,`{"next":N,"rebuilding":true}`);已开放(`-id-registry-open` 之后)。只有已开放才能认领。
    - 为什么要「重建中」:原来重建时先补记录、最后开启,补墓碑时没有指针可以对照,填错的码也会写进去,之后开启必须高于它,就被它卡住,只能手工删登记处记录(审核残余)。现在先声明指针,补记录都按它核对,填错的写不进去;没有指针时补墓碑一律拒绝。声明到开放之间不许认领:在用的地域还没全部重新登记时,新地域可能认领到一个台账漏记、又还没登记回来的码。
    - 有地域记录却没有指针的登记处,一定丢过数据(生产只有 Recover 会在没有指针时写记录),直接开启会跳过上面那段窗口,所以拒绝(`ErrRegistryNeedsRebuild`),要先声明重建。结束重建时 `-id-registry-next` 必须等于登记处里现在的值(重建期间可能被推高过),否则拒绝(`ErrNextRegionMismatch`),让运维对着台账再确认一次。
  - **有了指针之后,有记录的码都小于它**(2026-11-12)。顺序认领靠这一条才不会卡死:认领只认指针指着的那个码,它要是已经有记录(墓碑,或重新登记的在用码),就既认领不了、也推不过去,后面的码永远用不上。会破坏它的只有「给没有记录的码补一条」,所以登记处在这个写入里守住它(`Registry.CompareAndSwap` 的契约,和写入同一个事务):
    - 码小于指针:直接写,这是用过的码丢了记录。
    - 在用的码不小于指针(Recover 凭幸存的本地记录重新登记,说明重建时声明得太低、台账漏记了它):写入,指针推到它后面;重建中推完仍在重建中。有本地记录作证,不是填错。
    - 墓碑恰好在指针上:写入,指针加一。这是「跳过一个码」的唯一办法,一次只能跳一个。
    - 墓碑大于指针:拒绝(`ErrRegionOutOfOrder`),什么都不写。没有证据说明中间的码用过;放它进去会卡死,把指针直接推过去又等于填错一次烧掉一段。
    - 还没有指针:在用的码直接写(dev 第一次预留时认领,或者在用的地域先于声明重建重新登记,发号尽早恢复),声明指针时再核对它高于全部已有记录;墓碑拒绝(`ErrRegistryNotOpened`)。
- **首次初始化和事故恢复分开**,都是运维显式跑的入口,不并进 `-migrate`:
  - `-id-registry-open`:世界第一次部署时开放认领(下一个可认领的码 = 1),这时登记处里不能有任何码的记录;登记处整个丢了、重建做完时结束重建,值必须等于登记处里重建中的那个值。没开放时任何初始化都拒绝。
  - `-id-registry-rebuild`:登记处整个丢了数据之后声明重建,值取台账里用过的最大码 +1。扫描已有码之后,事务同时复核指针不存在、地域键范围在扫描后没有新增或更新,冲突则有界重读,保证并发的重新登记不会越过「指针高于全部已有码」的检查(世界第一次开放时同样这样复核「一条记录都没有」)。
  - `-id-issuer-init`:只给从没认领过的码。认领之后、建本地记录之前中断过,而这个码还没发过号(预留次数 0)时,再跑一次接着做完。本地有记录而登记处没有、发过号的码本地都没了,都是事故,拒绝。
  - `-id-issuer-recover`:只按幸存的证据取上界。登记处丢了这个码 → 重新登记,前提是本地记录是本环境写下的(拷来的记录不是可信上界,见上面「两份本地记录也写上部署身份」),水位取本地两份的最大值和时钟推得出的上界里大的那个(见下面「重新登记的时间上界」),本地两份随即抬到新水位;本地两份都没了 → 按登记处水位重建,但要 `-id-issuer-rebind` 确认(两份都没了就证明不了这两套 etcd 还是原来那两套);etcd 换成新集群(集群号变了)或灾备到另一个 K8s 集群(部署身份变了)→ 同样要 rebind,rebind 把绑定改到本部署环境和这两套 etcd,原来那一份从此预留被拒;本地只缺一份或落后 → 抬到三份里的最高值(不跑也行,下一次预留自动对齐;重新登记之后抬本地记录中断了,重跑一次就走这里做完)。本地和登记处都没有这个码 → 没有可信上界,拒绝,只能退役这个码、换一个新码。
  - `-id-issuer-retire`:码永久退役,登记处没有这条记录也写墓碑(要有指针可以对照,只限用过的码,或恰好是下一个可认领的码,见上)。要退役的不是配置里的码时用 `-id-issuer-retire-code <码>` 指明:配置里的地域码有部署注入的值把关,不为此去改配置。码还在用时只能从绑定它的部署环境执行:本地记录的地域和世系、部署身份、两套 etcd 的集群号都要对得上,否则拒绝(审核交接 §6.3)。退役没有撤销入口,staging 和生产又共用登记处,配置里地域码写错就会从别处退掉一个在用的生产码。绑定它的地域已经不在、没法在那里执行时,确认之后加 `-id-issuer-retire-unbound` 放行。登记处没有这条记录时(重建时补墓碑)不核绑定。
- **旧发号进程不用先停**:三份记录每次预留都重读,旧进程下一次预留只能落在可信上界之上或被拒;它们内存里的块都在上界之下,接着发也不重号。
- **预留冲突之后先退避再重试**(2026-11-12,不等压测,按 AGENTS §11.3 的重试规定定):同一个地域的全部 data-service 副本共用这三份记录,整地域冷启动时会同时预留。一次预留最多 8 轮;某一轮 CAS 冲突之后,下一轮开始前等 `[0, 上限)` 里的随机时长,上限从 10 毫秒起逐轮翻倍、封顶 320 毫秒,7 次等待最多共约 1 秒,远小于 10 秒的预留预算。不等的话,副本们会同步地反复相撞:每撞一次,先写成功的那几份记录白白前进一块(只浪费值域,不重号),8 轮很快用完。等待受预留的 ctx 约束,发号器关闭时立即返回。这几个数没有实测依据,只是保证「不同步相撞、总等待远小于预算」;压测之后可以调,不影响唯一性。
- **时间下限**仍然保留,是第四道防线:只抬高起点,`now` 不在可表示范围内时这次不采用、告警。计数器比时钟超前 7 天以上只告警(`ahead_of_clock`)。
- **活着的进程作证**(2026-11-12,审核残余「三处同时出事」):
  - 三份记录一起回档(本地两套被恢复到旧快照、登记处同时回档),或者本地两套回档的同时登记处丢了这个码,记录自己证明不了什么。但这时发号进程多半还活着:etcd 恢复不会重启 data-service。
  - 每个进程记住自己确认过的水位 W:自己三份都写成功的块尾,以及作证检查读到的登记处水位。登记处最后写,读到的值另外两份也写到过;三份记录只增不减,所以任何一份低于 W 都只能是被回档或丢了,没有并发误报。
  - 两处用到 W:每块的起点不低于它(三份都低于它时上报 `records_behind_issuer`);作证检查在第一次预留成功之后起,每 10 秒线性读一次三份记录,把低于 W 的抬回 W(不存在的建出来),写序同预留。登记处丢了这个码时只抬本地两份,不替它建登记处记录:本地两份是 Recover 重新登记时唯一的上界,抬高才盖得住;建登记处记录是要人看过的恢复操作。码退役、rebind 到别处、世系对不上时什么也不做。只抬高、不预留新块,和并发预留冲突了也无害,下一轮再看;本进程正在预留时跳过这一轮。
  - 代价:每个副本每 10 秒三次线性读,其中一次跨地域。60 个地域、每地域 10 个副本,登记处每秒约 60 次读,etcd 负担得了。
  - 盖不住的:出事时全部进程都已经重启过;或者别的副本在最近一个检查间隔里预留、随即连同三份记录一起丢掉了那一块(四件事同时发生)。
- **重新登记的时间上界**(2026-11-12,同一条残余):登记处丢了这个码、凭本地记录重新登记时,水位取本地两份的最大值和「现在的时间下限 + 7 天 + 一块」里大的那个,本地两份随即抬到新水位。
  - 推理:每块的起点比当时的时间下限超前 7 天以上就告警;没告警过,发过的号就都在「当时的时间下限 + 7 天 + 一块」之下,而当时的时间下限不超过现在的。这和时间下限是同一类用法:时钟只往上抬,坏时钟最多让上界不够高,不会让结果比不加更差。
  - 本地记录比这个上界还高,说明计数器曾经超前时钟 7 天以上,推理不成立:它要是也被回档过,没有任何东西盖得住,拒绝(`ErrNoTrustedBound`),换码。时钟不在可表示范围内也拒绝,修好再跑。
  - 代价:计数器一次跳到时钟前面 7 天(约 10^13 个号,一个地域码约 1.4×10^17 个),之后几分钟会有 `ahead_of_clock`。正常运行时计数器紧跟时钟:一块是 256 秒的序号,要持续每 256 秒预留一块以上才会跑到时钟前面,只有崩溃循环才会。
  - 运维前提:重新登记之前确认这个地域从没出现过 `ahead_of_clock`(运维手册 §4.3)。没有自动化:告警只在日志和指标里,丢码时登记处里的痕迹也跟着丢了。
- **两份本地记录都不存在、登记处也没有这个码**:可能是新地域,也可能是全丢了。登记处靠「下一个可认领的码」区分:没认领过的码才能初始化,认领过的码只能恢复。生产环境(`AllowAutoSeed=false`)拒绝发号;dev(`AllowAutoSeed=true`)三份放同一套 etcd,缺什么第一次预留时自动补。dev、test 不核地域码绑定,自动认领也不走「下一个可认领的码」,所以不许连共用登记处:配置里显式写了 `RegistryEtcd` 或 `RegistryTLS` 就拒绝启动。
- **硬校验**:`end` 不得超过本地域的值域上限,时间字段不得溢出;记录的地域位必须等于配置;三份记录两两不能在同一套 etcd 上(配置比地址,运行期比 etcd 自报的集群号);否则拒绝发号。
- **块大小**:2^32 个号(约 43 亿)。用掉一半时后台预取下一块,留出处理某一套 etcd 故障的时间。
- **代价**:多一个全世界共用的 3 节点小集群(`deploy/k8s/manifests/infra/etcd-id-registry.yaml`),只有一个集群托管它(`k8s_deploy.ps1 -HostIdRegistry`),别的集群经私网用 `-IdRegistryEtcd` 访问。每预留一块号多一次跨地域的 CAS,预取在后台做,延迟不在发号路径上。登记处不可达时新块预留失败,发号器手里的块还能用很久(按峰值也有一小时以上 [I]),用完才 fail-closed。这是有意的取舍:跨环境的唯一性只能靠一个共用的仲裁者,「每个地域一整套」在发号这一项上让步。
- **登记处只走双向 TLS**(2026-11-11):
  - 全世界一个 CA(世界 CA)。登记处 etcd 的服务端证书和每个地域的客户端证书都由它签。登记处开 `--client-cert-auth`,发号器只认世界 CA 签的服务端证书(`LoadRegistryTLS`)。
  - 这同时钉住了「地域连的是哪一套登记处」:地域配置里只有地址,地址写错、被改,或者别的集群误起了一套登记处,都会握手失败,而不是悄悄在第二个世界里认领码。
  - 客户端证书每次握手从文件重读,换证书不用重启。世界 CA 换代按运维手册 §4.8 新旧并存过渡。
  - 生产三个文件必填(`IdSegment.Issuer.RegistryTLS`),dev 不开 TLS。仍只走私网。

**还会不会重号**:要本地两套 etcd 和登记处三处同时恢复到一致的旧状态(或本地回档、登记处同时丢码),而且出事时没有一个发号进程活着作证、重新登记的时间上界也盖不住(这个地域出现过 `ahead_of_clock`,或者时钟比当初预留时还慢),才可能。登记处不许从备份恢复,它整个丢了数据时从各地域的本地记录重建(运维手册 §4.3),所以前一半已经要求有人违反运维规定。手工改记录同理。另一条路是两套环境同时拿到同一个码的发号资格、登记处又回档或丢码;部署身份进绑定之后,这只剩上面「拦不住的情形」两种刻意操作。

已有的防线保留:

- **客户端校验**:拿到的段不能和最近接受过的 16 段重叠,否则整段拒收(`client.go`、`guid_segment_client.h` [C]);上限校验放宽到 2^63。这只是兜底,窗口之外的重复查不到。

### 6.5 退路

只想消掉索引热点、不在乎发号依赖谁时,最省事的是保留 data_service 号段、只加一层打散,不到 10 个文件。它不满足「不依赖 TiDB / MySQL」,只作退路。

## 7. 路由:落点目录

- **目录**:「玩家 → 集群 + 库」。现有的 `player_route` 表与落点记录里的 `storage_id` 就是它,映射提案 §15 正在改成直读 TiDB;以后把 `storage_id` 从「选库」扩成「选集群 + 库」([玩家存储落点](./player-storage-placement.md) §0 第 7 条:今天只选库名、不选机器)。
- **建号时选集群**:按地域和各集群的余量挑一个写进目录,亚洲玩家落在亚洲集群。
- **目录不是单点**:读多写少,各服务缓存;目录表按 player_id 哈希分散到各个集群。
- **到了目标集群再核一次**:用那边的路由行在同一个事务里核对;搬走的玩家在旧集群留一条「已搬到某集群、版本 v」,旧写一律拒绝并转发。
- **扩容**(2026-10-31 改由[全层水平扩展规格](./horizontal-scale-logical-db.md) §8 按逻辑库整库搬,下面按玩家搬迁不做):加集群 → 新玩家落新集群 → 需要时按批搬迁老玩家。搬迁沿用现有 relocate 的「冻结 → 拷贝 → 切换」,把它从同一个库实例扩成跨集群(今天只支持同实例,[TiDB Phase 1](./tidb-phase1-and-launch-readiness.md) §8)。
- **为什么不把分区写进 ID**:分区位一旦写进 ID 就永远改不了——分区数定死、热分区拆不开、单个玩家搬不走、建号那一刻就决定了住处。目录路由的代价只是多一次可缓存的查询,加上要把搬迁协议做扎实。
- **合服围栏**:见 §7.1。
- **SLG**:路由单位是世界,「世界 → 集群」同样是一张目录表。

### 7.1 合服:去掉围栏,改成「别名合服」(用户 10-30 同意)

用户 10-30 回复:「存盘不能再按归属区选 Kafka topic 和数据库可以的,能水平扩展就行」。本文按此推进:存盘不再按归属区选 topic 和库,合服改成别名合服、去掉围栏。这改变了映射提案 §15「保留合服围栏落库」的结论,但切换排在新存盘路径之后,在那之前 §15 照旧。

**围栏的问题 [C]**:`zone_merge_fence` 每个 zone 64 行。`LockRoleRoutes`(`go/shared/placement/role_route_sql.go`)每次都对其中一行 `FOR UPDATE`,调用方是聊天、公会、匹配组队、收件箱、角色首次提交。TiDB 默认不支持共享锁,所以只是想看一眼牌子的读者也要拿排他锁,互相排队。按每人每 20 秒一次写、持锁 20 毫秒推算,单 zone 在线约 6.4 万到顶 [I];拆多集群时还要把围栏写满每个集群。

**根因**:今天合服要列出玩家清单、改每个人的归属,清单列完之后不能再有人登记或改动,所以才需要牌子。不改每个人的归属,牌子就不需要了。

**做法**:合服只写一条「5 区 → 6 区」的映射,用现有的 `zone_merged_into` 表(已是永久记录 [D])。

1. 玩家行、路由行都不动,`home_zone` 还是 5。
2. 所有按区分组的地方(榜单、频道、市场、公会、进场判断)先把 `home_zone` 解析成最终区再用。解析收口到一个函数;映射表各服务缓存,变更走通知加版本号;支持连续合服(5 → 6 → 7)。
3. 合服过程中有人在 5 区建号也不丢:他的 `home_zone` 是 5,解析出来就是 6 区。不需要清单,也不需要牌子。
4. `LockRoleRoutes` 去掉围栏这一步,只保留每个玩家自己路由行的锁和 home / rev / frozen 复核。每个玩家锁自己的行,互不排队,加机器就能扩。
5. 榜单、公会、市场这些按区存的业务数据,仍由各业务的合并任务处理(`merge_zone` 现有的公会 zone_id、聚宝斋 market_zone、公会榜等步骤),在维护窗口里进行,只影响这些业务自己。
6. 撤销合服:删掉映射;合服后新建的号按它们自己的 `home_zone` 留在各自的区。

**前提**:存盘不再按归属区选 Kafka topic 和库(C++ 存盘今天按 home_zone 选 `db_task_zone_<z>` [C])。否则别名合服之后,5 区的 topic、go/db、库都下不了线。这一条等新存盘路径(§13 A3~A6)落地后才成立。

**时机**:项目未上线,上线前不会发生合服,所以不做中间方案,等 A6 之后直接切(§13 A6b)。在那之前围栏原样保留。

**代价与待验证**:所有按区分组的入口都要走解析函数,漏一处就会分错组,要用契约测试钉住;映射缓存滞后窗口内的写,由业务合并任务兜底;拆多集群时映射放在控制面,不再需要逐集群写围栏。

**不停服合服(2026-10-30 用户确认接着做,本段取代下面「落码口径」里的合服顺序和第 5 条的维护窗口)**:

做法只有一句:**合服只写一条映射,不动任何数据,所有按区比较和查询在读的时候解析。** 这是路由表合并的标准做法,没有数据搬动就没有「搬动期间的一致性」问题。

| 按区的东西 | 怎么处理 |
|---|---|
| 玩家 `home_zone` | 不动。`GetPlayerHomeZone` 已经返回最终区 |
| `guild.zone_id`、`trade_listing.market_zone`、队伍 `zone_id`、匹配票 `zone_id` | 不改写。记录里存的是原始区,比较两边都先 `Final()`;按区查询用 `zone IN Members(z)` |
| 公会榜 `guild_rank:zone:{z}`(可重建缓存) | 写入按 `Final(guild.zone_id)`;guild 的周期任务把已合走区的旧榜折进最终区(`ZADD NX` 后删,新分数不被旧分数盖) |
| 玩家存档、资产、在途结算、邮件、收件箱 | 都按 `player_id` 存,与区无关,不受影响 |
| 场景节点、gate(物理资源) | 合服不碰。在线玩家留在原节点继续玩,新登录按最终区分配 gate。源区节点的下线是运维之后单独做的排空,和合服解耦 |

**接口**:`placement.MergedZones` 是一份不可变快照,`Final(z)` 沿链解析,`Members(z)` 返回最终解析到 z 的所有原始区(含 z 自己)。`placement.MergedZoneCache` 定时重读(默认 5 秒),启动读不到拒绝启动,刷新失败继续用旧值并计指标(告警 `DataServiceMergedZoneRefreshFailing`)。data_service 从 `zone_merged_into` 读,新增 RPC `GetMergedZones` 给 guild、trade;match 已有全局库连接,直接读表(2026-10-30 已落码,未编译)。

**match 的口径(2026-10-30)**:票、队伍、申请、邀请、开战原件都记路由行上的原始区(所以队伍的归属改读 `player_route`,不再问 data_service,它回的是最终区)。同区判定、范围树、按区候选都按最终区算;票和投影之间的相等比较核的是抄写有没有过期,不解析。同区只在 launch 诞生时判一次:合服提交、撤销都不重判在途的票和队伍,它们走完这一局,记录和路由行始终对得上,恢复循环不会因为映射变化报错。撤销的边界见 [手册 §7](../ops/merge-zone-runbook.md)。

**为什么缓存滞后不影响一致性**:映射只放宽「同区」判定,不决定任何资产。滞后窗口里各服务看到的最终区可能短暂不同,最坏结果是一次可重试的「不同区」拒绝;记录里存的原始区,窗口过后都解析到同一个最终区,不会留下错误状态。

**工具**:`tools/merge_zone` 只剩三个模式:`merge`(前置校验后在一个事务里写映射)、`unmerge`(删映射)、`audit`(只读,列映射和解析结果)。不要清单、不要停服证据、不要 zone-down、不踢人、不解散队伍。

**完成条件**:

- 归属合并:映射提交即完成,各服务 2 个刷新周期内全部生效。
- 数据归并:不需要。玩家存档留在原来的库,靠 `player_route.storage_id` 找到。
- 源资源退役:场景节点、gate 按现有排空流程随时下线,在线玩家被踢后重连到目标区,战斗结算走收件箱,不丢。源库不退役:单集群里只是一个 schema;要回收属于阶段 C 的分区搬迁。

**撤销**:删映射即可,不用写回任何东西。合服期间新建的公会、商品记的是目标区,撤销后留在目标区(只影响这些对象在哪个区展示,不影响资产),手册里写明。

**前提**:`player_store` 写权判定与区无关(B8 已完成);匹配、队伍、公会、交易的同区判定全部改成解析后比较(2026-10-30 已落码,未编译,验证见手册 §11)。

**落码口径(2026-10-30,A6b)**:

- **解析收口**:解析规则只有一份,对外只通过 `placement.MergedZones`(`Final`、`Members`),沿链解析(5→6→7),跳数上限 16,成环报错。按区分组的调用方几乎都经 `data_service.GetPlayerHomeZone` / `BatchGetPlayerHomeZone` 取归属,所以在这两个 RPC 的出口解析:它们返回的 `home_zone_id` 就是最终区。`go/match/internal/authority` 直接读 `player_route.home_zone` 和 `zone_merged_into`,记录写原始区,比较时两边解析。
- **原始归属这几处用,不解析**:`RegisterPlayerZone` 写入、路由工具、match 写进票和队伍记录的区(比较时才解析)。(这里原来还写着「go/db 按 `home_zone` 选库」,不对:go/db 选库只认目录里的 `storage_id`,不看 `home_zone`,见 §7.2「核对结论」。)
- **缓存**:data_service 启动时读一次 `zone_merged_into`,读不到拒绝启动;之后定时重读(默认 5 秒)。方案里说的「变更通知加版本号」先不做:合服频率极低,只靠定时重读,滞后上限是一个周期,`merge_zone` 写完映射后等 2 个周期再跑业务合并任务。
- **合服顺序**:前置检查 → 映射冲突检查 → 公会重名检查 → 清单落盘 → **写映射** → 等缓存 → 公会合并 → 交易合并 → 公会榜。映射先写,新建的号、新建的公会从这一刻起都归到目标区,不会有漏网的行,所以不需要任何闸门。清单仍在第一次写之前落盘,撤销靠它。
- **删除**:`zone_merge_fence` 表、`merge:in_progress:{zone}` 键及其镜像、`GetPlayerHomeZoneResponse.home_zone_merging`、scene_manager 的可重试码 21、guild 的 `MergeFence`、`RemapHomeZoneForMerge`、`merge_zone` 的玩家映射改写、玩家行拷贝、落点钉住、回填、搬库。`LockRoleRoutes` 只锁每个玩家自己的路由行并复核 home / rev / frozen,`route_meta` 一并移出这条路径。
- **跨集群搬迁**:按逻辑库整库搬(`tools/dbmove`,[全层水平扩展规格](./horizontal-scale-logical-db.md) §8);存档库 `player_store_<id>_db` 也是逻辑库,走同一套工具。按玩家搬(旧 relocate)不做(负责人 10-31 定),随旧表删除。

### 7.2 存档库和区脱钩(2026-11-05 定;A17a、A17b、A17c 都已落码未编译)

负责人 11-05 要「可读可扩展移动」。今天存档库跟着区走,这是剩下的一处「区 = 物理位置」。

**脱钩前的做法 [C]**(A17b 之后已删):新号的 `storage_id` 由 login 按建角的区给出,配了旧键 `Placement.NewPlayerStorageId` 就用它;`storage_id < 1000000` 对应库名 `zone_<id>_db`,`≥ 1000000` 对应 `player_store_<id>_db`(`go/shared/placement`)。所以缺省是一个区一个存档库。

**问题**:

- 区是玩法分组,会别名合服(§7.1);存档库是物理落点,会整库搬迁([全层水平扩展](./horizontal-scale-logical-db.md) §8)。绑在一起,合服之后 `zone_5_db` 里住的是 6 区的玩家,库名就对不上了。
- 搬迁的最小单位是逻辑库,而且不做按玩家搬库(10-31 定)。按区分库时,单位的大小跟着区的人数走:新区热、老区冷,一个大区装满一个集群之后拆不开。
- 只配一个全局库(`NewPlayerStorageId`)更糟:整个地域只有一个搬迁单位。

**决定**:

1. 每个地域上线前定一个固定的存档逻辑库数 K,上线后不改,和目录分片数 `Directory.LogicalShards` 同一条规矩(AGENTS §7 第 6 条)。初值 64,开发 1。
2. `storage_id = 1000000 + 地域码 × 1000 + 片号`(片号 0..K-1),库名沿用现有规则 `player_store_<storage_id>_db`,比如地域 1 的 7 号库是 `player_store_1001007_db`。现有的 `DefaultGlobalStorageID = 1000000` 正好是地域 0(dev、test)的 0 号库,命名代码不用改。这里的地域码是部署参数 `-Region`,是地域的永久编号;发号器的码平时等于它。发号器出事故换码时(运维手册 §4.5),只换发号码(`-IdIssuerRegion`),这里的编号和库名都不变,老玩家照常存盘(2026-11-11 定)。
3. 建号时按 `player_id % K` 在本地域的库里选一个,写进 `player_route.storage_id`;之后读写只认目录,不再按 ID 或区计算。发号打散之后 ID 均匀(§6),取模就是均匀分布;记进目录是为了以后可以不按公式放。
4. 区只是 `player_route.home_zone` 上的玩法属性,合服、排行、频道照旧按它解析(§7.1)。新号不再落到 `zone_<n>_db`;项目未上线,`zone_<n>_db` 这类存档库直接退役、清库,不做迁移。
5. 扩容就是把一个逻辑库整库搬到新集群(`tools/dbmove`),64 个库最多能摊到 64 个集群;冻结一个库只暂停 1/64 的玩家存盘。

**代价**:每个 go/db 进程要为它写到的每个存档库各开一个连接池、各注册一份写资格(每个逻辑库一份闸门,§2 的规格),K=64 时池数是今天的几十倍。做法和 data_service 已经做过的 64 片目录一样:按需开池、每池上限调小、计入连接总账(`Get-MysqlConnectionLedger`)。

**核对结论(2026-11-06 读代码)**:
- 选库只认目录:go/db 认领前经 data_service 的 `GetPlayerRoute` 读 `storage_id`,没有落点就拒绝,不回落 `home_zone` 或本进程的区(`go/db/internal/playerstore/placement.go`);存盘用认领时返回的那个。§7.1「原始归属这几处用」里「go/db 按 home_zone 选库」是旧说法,以这里为准。
- scene 选「本 zone 的 go/db」不用改:go/db 的库名白名单列出全部存档库,哪个 go/db 都能写哪个库,按区选 go/db 只是分摊负载。
- 全部存档库清单 `DB_ALLOWED_DATABASES` 只有一份:go/db 的白名单、data_service 的写资格和存档库白名单、迁移建库都从它来。脱钩只改这份清单的内容和 login 的选库,不改这套机制。
- go/db 仍然一区一个进程,但 A17c 起不再开本区库 `zone_<ZoneId>_db`:写者闸门在每个存档库里各一份,`ZoneId` 只剩注册发现(scene 按区找 go/db 分摊负载)。

### 8.1 单个 TiDB 集群加机器解决不了的四类

1. **单调递增索引尾部**(开服建角潮):号段单调发号时,新建角色的 INSERT 只写主键索引最右边一个 Region;`PRE_SPLIT_REGIONS` 只预切行数据,不切索引([TiDB Phase 1](./tidb-phase1-and-launch-readiness.md) §5 [D])。→ §6 可逆打散。
2. **单行热点**(一行只在一个 Region leader 上,悲观锁排队)。清单:
   - 聊天每发一条消息,都在同一个事务里锁角色路由,再对 `account_role` 加 `FOR UPDATE`(`go/chat/internal/authority/store.go` 的 `lockActor` [C]),是事务量最大的一项 → 改成会话级令牌,在聊天自己的库里复核。**已落码,未编译**:校验挪到发送事务之外,普通读 `player_route` 和 `account_role`,结果按 (actor, account, owner_revision) 在进程内缓存(`ActorVerifyTTLSeconds`,生产 30 秒,0 = 每次都校验),发送和拉取事务里只剩聊天自己的表;代价:角色被挂牌或过户后旧会话最多还能发 TTL 秒的聊天,限流从精确变成近似(超额上限是这名玩家同时在途的请求数,gate 还有第一道限频),同一 request_id 的并发首发改由主键裁决、输家撞 1062 转读原件;
   - 评级游标 `match_rank_source` 每局 `FOR UPDATE` 一次 → 拆片。**已落码,未编译**:来源表和 outbox 主键加 `shard`(`battle_id % 64`),每局只锁一片,发布循环按片推进,停写逐片取锁;榜的幂等和连续改成按 (shard, cursor),`rank_board.committed_cursor` 改存各片批次总数,封榜按总数核齐。拆片破坏了「批次全局有序」,而批次是绝对分,旧批次晚到会把榜分退回旧值,所以批次带 `score_version`(这名玩家第几局,在玩家行锁下递增),榜上旧版本迟到直接跳过;代价:榜多一列、每批多一条取本片游标的读,榜分在投递途中不保证与全局提交顺序一致,只保证每名玩家最终落在最新版本;
   - guild、trade、mail 的哨兵守卫行 → 撤掉,状态行在首次提交时预建。**已落码,未编译**:`guild_player_state(0)`、`trade_player_op_seq(0,0)`、`mail_box(0)` 都撤了,状态行在业务事务之前的短事务里 `INSERT IGNORE` 预建,查重靠唯一索引撞 1062。它们防的都是 MySQL 上的 1213(唯一索引查重的 S next-key、首插者回滚的间隙继承),不管对错;TiDB 没有这些环,MySQL 档由 `retryOnDeadlock` / `WithTxRetry` 吸收。代价:MySQL 档这几条路径的死锁从 0 变成偶发;mail 的 `MaxActiveSystemMails` 变成软上限,并发发件可能略超(读侧有 LIMIT,发件方只有运维和帮会公告)。trade 的 `trade_commerce_guard` 没动:它按拍品、按盘口各一行,串行的是撮合本身,不是全服排队;
   - 登录读账号目录 → 命中即只读。**已落码,未编译**:`Read` 先无锁读,命中只读返回,只有 create=true 且没命中才进加锁建行路径(锁内复核);代价:Read 不再排在同账号在途的建角后面,提交前读到的是提交前的列表,调用方都不依赖那次排队(改归属的操作按 owner_revision 复核);
   - `route_meta` → 移出提交路径。**已落码,未编译**:建角的 `lockInitialPlayerRoute` 改普通读 `writable`,`FOR UPDATE` 只留在修库、解冻、建池探针这些低频路径;读到旧值不是问题,提交点的保证靠写者闸门:事务持着 `writer_slot` 行锁并在持锁后复核过 `route_meta`,`Catalog.Freeze` 拿到全部 slot 锁才能推进 epoch,冻结只能排在在途事务提交之后,`route_tool` 的冻结流程不用改。写者闸门每笔事务还要普通读这一行两次,读负载靠缓存表(TiDB 运维步骤,S2 档起必选);
   - 合服围栏 `zone_merge_fence`(聊天、公会、匹配组队、收件箱、建角每次都锁一行)→ 改别名合服后删除(§7.1);
   - 自增主键 → 应用发号;号段领段行 → 随 §6 消失。
3. **时间戳(TSO)**:每个事务都要向唯一的 PD leader 取时间戳;按官方文档,读已提交隔离下每条语句默认都要取 [W]。→ 先减少每笔事务的语句数(上面的单行热点清理同时起这个作用),压测出单集群上限,再按 §8.2 拆多集群。
4. **跨地域**:单集群跨地域要求延迟小于 30 ms([TiDB Phase 1](./tidb-phase1-and-launch-readiness.md) §8 [W])。→ 每个地域一套集群,不把一个集群拉到多个大洲。

### 8.2 拆成多集群的前提

> 2026-10-31:本节的「同集群放置」和「只拆聊天」被[全层水平扩展规格](./horizontal-scale-logical-db.md)取代:服务之间不跨库、每个逻辑库自带闸门、过户靠角色护栏。下面留作当时的分析。

- **拆开跨服务的同事务耦合**:聊天、公会、匹配、收件箱等在同一个事务里同时锁角色目录和路由。不拆开就只能一个集群——拆早了,这些事务会跨集群,原子性保证不了。先拆聊天(§8.1 第 2 条)。
- **同集群放置**:玩家行、写权行、路由行、角色目录、入场登记放在同一个集群,保证 §3、§15.3 的同事务核验成立。
- **名字与账号目录按哈希分到各集群**:开服建角峰值在 S3 档推算为每秒 1~5 万([容量模型](./capacity-model-hok-scale.md) `C_p` [I]),放在单一全局库会成为单集群瓶颈和全球单点。

### 8.3 控制面

etcd 和 TiDB 的 PD 都是单 leader,加机器提升不了写能力。只让它们承担低频写:发号器从内存发号段,只在预留新块时写 etcd,频率极低;分区与集群登记很少变。再按地域、按用途(发号与服务发现分开)、按集群各起一套,不让一套承担全部。

### 9.1 后端档位(2026-10-30 落码,未编译,待 Codex 验证)

`RequireTiDB` 已删,换成档位 `Backend: tidb | mysql`。不写就是 tidb,其余值启动时拒绝;**`tidb` 和 `mysql` 都能过门禁,和 `Mode` 无关**,原来「生产必须 TiDB」的门禁只剩「档位合法」[C]。

| 入口 | 档位从哪来 |
|---|---|
| chat、mail、rank、friend | yaml 顶层 `Backend` |
| data_service、route_tool | `SnapshotMySQL.Backend` |
| db | `ServerConfig.Database.Backend` |
| guild(含 assetopfix)、trade、player_inbox | `MySQL.Backend` |
| match | `GlobalMatch.Backend` |
| writer_authority、admission_recover、maintenance_phase、password_admin、merge_zone | 环境变量 `MMORPG_SQL_BACKEND`(这些工具不读服务 yaml;`-local-mysql` 与 `LOGIN_PASSWORD_MIGRATION_ALLOW_LOCAL_MYSQL` 已删) |

`go/shared/authoritysql` 是唯一判定点:`ParseBackend`(空串 = tidb),`Open`、`OpenForMigration`、`PinCurrentSession`、`AssertCurrentSession` 收 `Backend`,零值按 tidb,非法值在碰服务器之前就拒绝。

| 档位 | 每条物理连接(含回池复用) | 业务池投入使用前 |
|---|---|---|
| tidb | 固定 RC、严格 sql_mode、锁等待,加 `tidbSettings`(`tidb_snapshot`、`tidb_read_consistency`、`tidb_txn_mode`、`tidb_read_staleness`、`tidb_low_resolution_tso`、`tidb_replica_read`、`tidb_constraint_check_in_place_pessimistic`,最后一项要求 TiDB ≥ 6.3);接到 MySQL 时 SET 失败 | `SELECT tidb_version()` + 读回全部强读变量。行为未变 |
| mysql | 先读 `VERSION()`、`@@version_comment`、`@@read_only`、`@@super_read_only`,不是 TiDB 且两个开关都是 0 才往下走;再固定 RC、严格 sql_mode、锁等待。不发任何 `tidb_*` | 再读一次上述四项加 `@@transaction_isolation`,必须 READ-COMMITTED |

- 两个版本串都看:TiDB 配了 `server-version` 时 `VERSION()` 里没有 TiDB 字样,`@@version_comment` 不受影响(friend 的 sqldialect 2026-10-13 实测)。MariaDB 和 5.7.8 之前的 MySQL 没有 `super_read_only`,读不到就拒绝。
- 只读开关逐连接核,不只启动时核一次:主从切换后同一地址可能已经是从库。复用时发现降级,这条连接被隔离,下一条新连接被拒绝,业务看到报错而不是写进从库。
- 旧 `requireTiDB=false` 分支不是「什么都不核对」:它照样固定 RC 和严格模式,只是不核对引擎。依赖这一点的只有 dev 本地 MySQL 和两组测试夹具(`storetest.NewEmptyDB`、guild 的 `openEconomyFlowDB`,`AllowMySQL=true`,MySQL 和 TiDB 端点都可能连)。已并入 mysql 档,没有保留第三种连接:夹具改为先问真实引擎再选档位,所以 `AllowMySQL` 夹具连 TiDB 时比以前多了强读固定。本地 MySQL 只要不是只读实例就不受影响。

### 9.2 TiDB 专属依赖盘点

按 `grep -E "tidb_|@@tidb|SHARD_ROW_ID|PRE_SPLIT|NONCLUSTERED|CLUSTERED|AUTO_RANDOM|FLASHBACK|cached|ALTER TABLE .* CACHE"` 逐处看过(`go`、`tools/merge_zone`,不含 `go/proto` 与测试),另查了优化器提示和共享锁语法 [C]。`AUTO_RANDOM`、`FLASHBACK` 没有命中;`cached` 命中的都是普通变量名。

| 位置 | 内容 | mysql 档 |
|---|---|---|
| `authoritysql/pool.go` | `tidbSettings`、`tidb_version()`、`@@tidb_*` 读回 | 按 Backend 不发 |
| `authoritysql/pool.go` `open` | 从 DSN 删 `tidb_*` 参数 | 两档都删,DSN 带了也发不出去 |
| `friend/internal/svc/servicecontext.go` | DSN 的 `tidb_*`、`@@tidb_*` 读回 | 按 Backend 不发 |
| `match/internal/authority/schema.go` | DSN 的 `tidb_*` | 按 Backend 不发 |
| `merge_zone/current_tidb.go` | `pinCurrentSession`、`requireCurrentSession`(原 `pinCurrentTiDB` 等) | 按 Backend;mysql 档 DSN 里任何 `tidb_*` 都删掉,读回走 `AssertCurrentSession` |
| `data_service/internal/store/route_store.go` | `@@tidb_txn_mode`、`@@GLOBAL.tidb_enable_check_constraint` | 运行时 `serverIsTiDB` 分支,MySQL 上不发 |
| `data_service/internal/store/route_tidb.go` | `route_tool tidb-prepare`:`ALTER … ATTRIBUTES`、`SPLIT TABLE`、`TIDB_PK_TYPE` | 同上,打印 SKIP 后退出 0 |
| `data_service/internal/store/schema.go` | 不改 `player_name` 主键、`snapshot_guid_nz` 生成列表达式 | 同上,走 MySQL 分支 |
| `friend/internal/data/recommend_sql.go` | 优化器提示 `INL_JOIN`、`QB_NAME` | 按 sqldialect 方言渲染,MySQL 用 `SEMIJOIN` |
| DDL(data_service、authoritysql、proto2mysql 生成的建表) | `/*T![clustered_index] …*/`、`/*T! SHARD_ROW_ID_BITS=… PRE_SPLIT_REGIONS=… */` | MySQL 当普通注释,无需处理 |
| `asset_store.go`、`asset_op_repo.go`、`route_store.go`、`cli.go` 等 | `tidb_lock_unchanged_keys`、`ALTER TABLE route_meta CACHE`、`tidb_table_cache_lease` | 只在注释和帮助文本里,不发语句 |

`serverIsTiDB` 这几处没有改成读配置:`Open` 已保证档位和真实引擎一致,运行时判引擎结果相同,而且这些函数只拿到 `*sql.DB`,改成读配置要穿透整个 store 层。遗留一点:`serverIsTiDB` 只看 `VERSION()`,TiDB 配了 `server-version` 时会判成 MySQL(`tidb-prepare` 跳过、强读核对跳过),和 `Open` 的判据不同。这是原有问题,未改。

落码时顺带修掉一处真问题:match 的 `TeamLaunchTickets`、`sqlTeamStore.read`、`readMembers` 原来在非 TiDB 上开 `READ ONLY` 事务,而写者资格门要在同一事务里锁 `writer_slot`(`FOR UPDATE` 或 `UPDATE lock_touch`),MySQL 的只读事务里这两种都报 1792 [I:读 MySQL 行为推断,未实测]。旧代码里这条路径走不到(非 TiDB 时 `ConfigureRoleAuthority` 之前就 panic),改成档位后会走到,所以三处都不再设 `ReadOnly`;tidb 档行为不变。

### 9.3 mysql 档已知差异(只记录,不改业务)

- **间隙锁**:TiDB 没有间隙锁,MySQL 有。全部池子固定 RC,RC 下基本只剩记录锁,但 match 的三处读事务显式用 RR,里面的 `FOR UPDATE` 在 MySQL 上可能带 next-key 锁;`snapshot_store` 的 `NOT EXISTS` 退路本来就靠 RR 间隙锁,只在唯一键缺失时走,mysql 档上线前必须跑过 `-migrate`。
- **共享锁**:TiDB 默认把 `FOR SHARE` 当空操作(Java 版真库测试踩过,PROGRESS 有记录),MySQL 是真锁。Go 版业务代码没有显式共享锁读,但 MySQL 撞唯一键时隐式取 S 锁,S → X 升级在 8.0.29 之前会成环,所以 guild 启动时要求 MySQL ≥ 8.0.29(`CheckServerVersion`)。
- **死锁与锁等待**:MySQL 上 1213、1205 会比 TiDB 常见。写者池的 `guardedConn` 把业务语句上的 1213、1205、9007 判为确定回滚(COMMIT 还没发,回滚后这笔不可能提交),保留原错误、不隔离连接,所以 `retryOnDeadlock`、`WithTxRetry` 能整笔重试(10-30 修正,此前一律变成结果未知,重试永远不触发)。COMMIT 上的错误仍是结果未知。回归里要量重试率。
- **锁权限**:MySQL 的 `SELECT … FOR UPDATE` 除 SELECT 外还要 UPDATE、DELETE 或 LOCK TABLES 之一。写者门的 `SELECT_ONLY` 锁原语在只授 SELECT 的账号上过不了,mysql 档应选 `LOCK_TOUCH`;跨 schema 的 `account_role … FOR UPDATE` 也要按 MySQL 重核授权。
- **丢数据窗口**:TiDB 多数派提交,MySQL 异步复制切主可能丢已提交事务。本批只保证连到主库,不保证切主不丢;mysql 档上生产要半同步或等价方案,切主后旧主要置只读。发号不依赖 MySQL(§6),但写权代次和玩家存档都在 SQL 里,异步复制切主丢事务时都可能回退,§5 的「不回档」承诺不成立 [I]。
- **DDL**:TiDB 在线 DDL,MySQL 的部分 ALTER 会锁表或重建表,迁移时长另算。
- **排序规则**:MySQL 默认 `utf8mb4_0900_ai_ci`,TiDB 默认 `utf8mb4_bin`。抽查建表语句,字符串键都显式写了排序规则或用 `VARBINARY`,两档比较语义相同 [C,抽查]。
- **`binlog_format`**:RC 要求 ROW,MySQL 8 默认就是。没有加启动核对,错了第一条写就会报错。

### 9.4 mysql 档要跑的真库回归

本批没有跑过任何一项,全部待 Codex。

1. 启动门禁:连主库能起;连 `read_only=1`、`super_read_only=1` 的从库拒绝;`Backend: mysql` 连 TiDB、`Backend: tidb` 连 MySQL 都拒绝;非法值拒绝。运行中把主库置只读,确认复用连接被隔离、新连接被拒绝。

SLG 补充:

## 11. 跨 zone 对战

**所有 zone 之间都能互相打。** 玩家不搬家:任何 zone 的 scene 都能按目录找到玩家所在的集群并加载;同一时刻只有一个 scene 持有写权,换 zone 就是一次交接(§3.3)。三种打法都有路径:

1. 传送到对方 zone 的地图,同场景 PvP(跨 zone 场景传送已落码,交接时源端等 SQL 确认 [D])。
2. 跨 zone 匹配进 battle 节点打竞技场、战场(全局排队池、全局 battle 池已有 [D])。
3. 大型跨服战场:单独起战场实例,每局结束后结果结算进各自存档。

注意:

- 玩家之间转移资产走资产通道(§3.4)。
- 跨 zone 传送今天依赖所有 zone 共享同一个 Redis 里的父快照(CZ-2);存档移出 Redis 后改成目标 scene 从 TiDB 加载,不再要求共享这个 Redis(TiDB 决策 §9.5)。
- 跨地域对打:数据没问题,存盘与加载跨洋只是慢一点;实时 PvP 受物理延迟限制,建议放在专门的战场实例,选双方延迟都能接受的位置。

## 附录 A:会话讨论记录(关键发现、比较过的方案、更正过的说法)

本附录记录「玩家数据存储方案」会话里正文没有展开的讨论,供以后追溯「为什么这么定」。数字除注明外都是推算 [I]。

### A.1 最初的问题与前提

- 用户的问题(10-23):「玩家数据的存储读取不是已经上了 TiDB 吗,还要不要用 Redis 存玩家数据?」
- 核对结果(10-23 当时):「上了 TiDB」只是 SQL 落地层要求连 TiDB——go/db 等服务的配置要求 TiDB,本机全球同服验收环境用的是 TiDB;K8s 部署脚本要求传入 TiDB 地址,但仓库里没有 TiDB 集群清单 [C]。存盘链本身没变:scene 先写 Redis 父快照,再经 Kafka 由 go/db 写进 SQL。

### A.2 旧存盘链里 Redis 的真实角色(为什么不能直接删)

- **Redis 是存盘链上第一个持久点,不只是缓存。** C++ 一次存盘是一段 4 键 Lua:校验 `owner_epoch`、写父快照(首次存盘后不带 TTL)、写存盘屏障的 pending、写两条完整的 DBTask 意图和补投索引;Lua 成功之后才发 Kafka。scene 崩溃或 Kafka 丢消息时,go/db 的 saveoutbox 从 Redis 取出意图补投(`redis_client.h` 的 `kSaveWithCommitBarrierLuaScript`、`go/db/internal/saveoutbox` [C])。
- **go/db 每条写任务约 11 次 Redis 往返**:排序锁、游标、已落库代次、落点读取、令牌发布脚本(子表缓存 + 资产证据 + 两表确认)等([存盘管线瓶颈](./db-task-pipeline-bottlenecks.md) §6 [D])。
- **10-17 起加载只在 SQL 已追平时才用父快照**(`parent_commit_barrier.go` 的 `route()` [C])。所以离线玩家的父快照只是已提交 SQL 的副本,却是 Redis 常驻内存里最大的一项。
- 所以「不要 Redis 存玩家数据」不是删一层缓存,而是要给提交点、写权核对、在途判断找新的承载——本文 §3 的答案是全部放进一个 TiDB 事务。

### A.3 当时比较过的三种方案与评审结论

| 方案 | 内容 | 两位评审(正确性 / 容量运维)的结论 |
|---|---|---|
| A 保持 | 父快照常驻 + 子表缓存,Redis 上 Cluster | 不推荐:内存随累计角色数无上限增长(30 天 2~6 TB,主节点数由内存决定,约 50~250 个,而按读写量只需 18~56 个);它声称的「游戏不受 TiDB 时延影响」大半已不成立(见 A.4) |
| B 收窄 | TiDB 为真源,Redis 只留在线玩家的父快照与控制态,离线卸载,子表缓存停写 | 当时两位评审都推荐的开服前路线;收益主要在内存,时延和耦合几乎没改善 |
| C 移出 | 存档只在 TiDB,存盘同步提交,写权进 TiDB | 终态一致性最强(Redis 回退导致代次倒退这一整类问题消失,Java 版已是这个形状);当时的稿子有缺陷、缺实测,评审建议作为上线后候选 |

用户 10-24 定「玩家数据不进 Redis」,方向就是 C。本文按评审意见补上了 C 的缺陷:整笔序号整笔比较(§3.2)、自动放弃读写权行(§3.4)、移交带令牌(§3.3)、没有旁路(§3.2);实测要求见 §13 阶段 B。

### A.4 评审中的其他发现

- **子表缓存没有生产读者**,只剩调试工具在读,却占 0.6~1.2 TB、每秒 8.9~22.2 万次写([共享 Redis 按用途拆分](./shared-redis-split-by-purpose.md) §19)。
- **战斗后排下一局要等两表 SQL 确认**:战斗锁 `battle:lock` 保留到双表确认后销账才删,最长 180 秒(`player_battle.h` 的 `kSettlementLockHoldSec` [C]);match 见到锁就拒绝排队。`player_battle.cpp` 里「快路径把它压到一次 Redis 往返」的注释,评审认为已过时。收件箱确认、跨节点交接同样要等 SQL 确认。
- **guild 资产通道缺省按 Redis 快照终结**:`AssetOp.RequireSQLCommit: false` 是有意的灰度缺省(`go/guild/etc/guild.yaml` 注释写明了打开的前提 [C]);新路径下这一档不再存在(§3.4)。评审另指出 [存盘围栏](./db-write-fencing-mysql.md) 里「资产成功只由 TiDB 强读证据决定」的说法与代码不符,证据其实是 go/db 发布到 Redis 的投影。
- **SQL 行内围栏只挡一类旧写**:代次更小的写判 stale、同代次序号更小判 older;代次更大就整行覆盖,行不存在直接插入,不核对内容(`player_row_fence.go` [C])。所以单靠旧的行围栏挡不住所有迟到写,本文改为写权行加整笔序号。

### A.5 「Redis 不也会丢吗」

- Redis 默认每秒刷一次盘,崩溃丢约 1 秒;主从是异步复制,切主时可能丢掉已经确认过的写(K8s 的 `redis` / `redis-ha` 只配了 `--appendonly yes` [C])。
- TiDB 三副本多数派提交,单台机器坏了不丢已提交的数据。
- 旧方案只在「TiDB 故障、Redis 正常、scene 又崩溃」这种双重故障下多保住一点进度,代价是平时多出 Redis 丢数据和回退的问题。所以「存储挂了 + 进程崩」是任何存储都有的问题,直接提交 TiDB 不比原来差。

### A.6 SLG 为什么不直接用 Redis 当主存储

- **快靠的是地图服内存,不是 Redis**:Redis 在另一台机器上,每次读写多一次网络往返;它在 SLG 里唯一的作用是崩溃后从哪里恢复。
- **放 Redis 的问题**:会丢、会回退(同 A.5);查不了(同盟全部领地、州城归属、战报历史、客服流水都要按条件查);跨对象改动没有跨 slot 原子(攻城易主、同盟仓库、交易);备份只有整实例快照,不能按时间点恢复,赛季归档不顺手。
- **成本对 SLG 不是主要理由**:单服几千到一万人,整服数据几 GB 量级 [I]。「Redis 太贵」在 MMO(全量常驻 TB 级)成立,在 SLG 不成立。
- **想要 KV 形态时**:落盘的 Redis 兼容存储(Apache Kvrocks、Pika、Tendis)数据在磁盘上,成本和持久性好很多,但查询和跨分片事务的问题仍在。
- 本仓 SLG 笔记原来的口径不统一(2026-11-01 更正,这里原来写的「只有行军与地块的检查点放了 Redis」不对):`slg-interview-qa.md` 是「MySQL 持久化,Redis 放在线状态、排行榜、热缓存」;`slg-server-complete-framework.md` §12.3 把玩家资料、资源、武将、部队、建筑、邮件都写成 Redis 结构,`slg-server-framework-complete.md` §14.1 写「玩家数据(热)放 Redis」,`slg-server-mainprog-interview-qa.md` Q10 写资源变化先写 Redis 再经 Kafka 落 MySQL、恢复后以 Redis 为准。这几篇下面都还有 MySQL 持久化一层,没有一篇是「全在 Redis」。2026-11-01 已全部按本文改写,写法见框架笔记 §12。

### A.7 TiDB 与业界实践的外部资料([W],子代理检索,主会话未逐条复核)

- TiDB v8.5 官方 Sysbench(小行):主键点查 P95 约 1.9~2.6 ms,单行 UPDATE P95 约 10~13 ms(https://docs.pingcap.com/tidbcloud/v8.5-performance-benchmarking-with-sysbench)。官方没有几十 KB 大行的公开数据,要自测。
- 非聚簇主键的点查要先读索引再读行,多一次 KV 读(https://docs.pingcap.com/tidb/stable/clustered-indexes/)。两张玩家表同一事务写,预计不能走 1PC,可以走 async commit(https://docs.pingcap.com/tidb/stable/system-variables/)。
- 大于 32 KiB 的值进 Titan(v7.6 起新集群默认开),写放大更低、约 2 倍空间(https://docs.pingcap.com/tidb/stable/titan-overview/)。
- 缓存表、Stale Read、Follower Read 都不适合「每名玩家一行、在线时频繁覆盖写」的存档(https://docs.pingcap.com/tidb/stable/cached-tables/、https://docs.pingcap.com/tidb/stable/stale-read/、https://docs.pingcap.com/tidb/stable/follower-read/)。官方文档没有要求、也没有禁止在 TiDB 前加 Redis。
- 业界实践:Roblox 官方建议会话期间以服务器内存为准、定期与离开时写回,并用会话锁防旧写(https://create.roblox.com/docs/cloud-services/data-stores/player-data-purchasing);Halo 4/5 的 Orleans 以内存对象为准、由对象方法持久化(https://www.odbms.org/blog/2016/02/orleans-the-technology-behind-xbox-halo4-and-halo5-interview-with-phil-bernstein/);腾讯 TcaplusDB 把缓存与持久化合一(https://www.tencentcloud.com/document/product/1016/30267);Pokémon GO 以 Spanner 作主事务库(https://cloud.google.com/blog/topics/developers-practitioners/how-pok%C3%A9mon-go-scales-millions-requests)。没有查到以 TiDB 作大型 MMO 唯一存档库的具名公开案例。
- 率土之滨本身(2026-11-01 主会话检索,中英文关键词):没查到官方公开的服务端存储方案,不能断言它用 Redis 还是别的;本仓 `docs/notes/slg/` 是「率土风格」的设计和面试笔记,不代表它的真实架构。公开文章里有先写 Redis 再回写 MySQL 的做法(https://topic.alibabacloud.com/a/high-speed-game-data-server-design-architecture-based-on-memory-and-redismysql_1_47_30082932.html),也有团队把 Redis 当玩家第一数据库(https://blog.csdn.net/chengwuqing9207/article/details/100992529、https://blog.csdn.net/chinabhlt/article/details/102563320,两篇原文都打不开,无法确认是哪一篇)。这几条都只看到搜索摘要,只说明有人这么做,不改变 A.6 的判断。
- 官方口径(2026-11-01 主会话抓取官方页面核对):Redis Cluster 是异步复制,切主时可能丢掉已确认的写,多键操作要求所有键在同一个 hash slot(https://redis.io/docs/latest/operate/oss_and_stack/management/scaling/)。TiDB 顺序主键的写入集中在一个 Region,是典型写热点(https://docs.pingcap.com/tidb/stable/troubleshoot-hot-spot-issues/);单行默认上限 6 MiB(https://docs.pingcap.com/tidb/stable/tidb-limitations/);`SPLIT TABLE` 可手工预切(https://docs.pingcap.com/tidb/stable/sql-statement-split-region/);PITR 由全量快照加日志备份组成,恢复期间目标表不能读写(https://docs.pingcap.com/tidb/stable/br-pitr-guide/);TTL 是后台清理,不保证到期立刻删除(https://docs.pingcap.com/tidb/stable/time-to-live/)。

### A.8 讨论中更正或推翻过的说法

| 原来的说法 | 更正 |
