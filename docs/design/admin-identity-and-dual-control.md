# 后台管理员身份与高风险动作双人复核

状态:负责人 2026-11-26 批准「7 批全做」(含新增 `nimbus-jose-jwt` 依赖)。各批落码进度见 §8 表格最后一列与 `docs/PROGRESS.md`;全部未编译,待 Gemini 验证。
来源:`docs/handoff/server-code-completion-20261120.md` §3.2「交易人工判定的审批流」;`docs/design/payment-recharge.md` §5.4 对支付人工动作也要求「双人审批,同一事务写审计,审批 id 随请求传给商城」,同样没有落码,由本设计一并覆盖。

本文用到的四个词:

- **后台**:`java/gm_admin`,基于 JeecgBoot 的独立 GM 管理系统(`docs/design/jeecg-gm-administration.md`)。
- **资源服务**:真正持有数据并执行动作的服务,如 `go/trade`、`go/mail`、`java/mall_game`。
- **发起人**:提出一条高风险动作的管理员。**批准人**:核对后放行它的另一名管理员。
- **流水**:后台管理库里的 `gm_command` 表与它的审计表 `gm_command_audit`。

## 1. 需求分析

| 编号 | 要求 | 判据 |
|---|---|---|
| R1 | 每个动作能追到具体的人 | 人手里不再有共享口令;操作人不由请求方自己填 |
| R2 | 身份由外部身份提供方给出 | 生产环境后台不保存口令,登录走 OIDC |
| R3 | 资源服务知道是谁在操作 | 身份放在带签名的请求里下传,资源服务写进自己的留痕 |
| R4 | 高风险动作分两段 | 发起 → 另一人批准后才执行;「两人不同」在服务端判定;批准的是冻结后的原样载荷;申请会过期 |
| R5 | 全程留痕 | 发起、批准、驳回、执行、结果各记一条,只追加 |
| R6 | 可重放、幂等 | 结果未知时用原请求号重试,不会执行两次 |
| R7 | 守住项目约束 | 不丢数据、强一致、可水平扩展、代码易懂;一库一服务,事务里不调 RPC(AGENTS §7) |
| R8 | 不挡本机开发 | 开发环境一个人能跑通;生产缺配置时拒绝,不放行 |

## 2. 现状

盘点逐条核对过代码(2026-11-26)。结论先说:**除后台之外,没有一个入口分得清是哪个人;后台分得清人,但口令存在自己库里,也没有第二人批准。**

| 入口 | 怎么鉴权 | 操作人从哪来 |
|---|---|---|
| `java/gateway_node` 的 `/admin/**`(区服、白名单、公告、RPC 热关停、配置表指针)与 `/mall-admin` 页 | 全员共用一把 `X-Admin-Key`(`AdminApiKeyFilter`) | 热关停和配置表两处读可选请求头 `X-Admin-Operator`,自由文本;其余不记 |
| `java/mall_game` 的 `/internal/admin/*`(SKU、人工订单 / 退款 / 寄售 / 收入争议) | HMAC,主体固定为 `admin` | 幂等表 `commerce_admin_command(actor, request_id)` 的 actor 就是 `admin` |
| **后台** `java/gm_admin`(邮件、活动发奖、七项玩家 GM) | JeecgBoot 原生登录,账号口令在后台自己的库 | 登录主体的用户名;同一人建草稿、同一人发送(`GmCommandJournal` 目前写的是「仅草稿创建者可发送」) |
| login `LoginAdmin`、player_inbox `PlayerInboxAdmin`、data_service 回收五个入口 | 共享静态口令 `x-admin-token` | 回收请求里有自由文本 `Operator`;其余没有 |
| trade `TradeAdmin`、mail `MailAdmin`、rank `RankAdmin`、match 运营入口 | `ServiceCallAuth`:每个调用方一把 HMAC 密钥,签名覆盖方法名与整个请求 | `caller` 是服务名(如 `ops-commerce`、`admin`);trade 另有自由文本 `operator`;mail 的请求里没有操作人字段 |
| C++ scene / gate 的 GM 管理 RPC | `gm_security.h` 的 HMAC 信封 | 场景玩家命令的签名含操作人;客户端 GM 指令在生产模式一律拒绝 |
| 直连数据库 / etcd 的命令行(`assetopfix`、`password_admin`、`create_residual`、`admission_recover`、`kafka_dlq`、`lexicon` 等) | 所持的数据库或 etcd 凭据 | 不记,或命令行参数自填 |

另有两处事实会影响落码范围:

- `mall_game` 的收入争议接口 `manual/incomes/dispute` 不在网关的命令白名单里,现在没有页面能调到它。
- `payment-recharge.md` §5.4 设计的 `payment_admin.proto` 与 trade 的 `ListManualCommerce` 等四个方法都还不存在。

## 3. 高风险动作分级

| 级别 | 判据 | 动作 | 要求 |
|---|---|---|---|
| **甲** | 改玩家资产、动真钱、销毁账号或角色,或者做完撤不回 | trade `ResolveManualContract` 的 EXECUTE(resume / reissue / refund / partial / redirect / void-auction);商城人工订单、退款、寄售、收入争议处置,以及 SKU 新建 / 改价 / 调库存;data_service `BatchRecallItems`(非演练)、`ResolveRecallOp`、`CancelRecallBatch`;全部邮件发放(个人、全服、活动发奖);player_inbox `GmSanctionPlayer`、`VoidItem`;login `ScheduleAccountDeletion`、`RemovePlayersFromAccounts`、`ResetAccountRealName`;rank `RemoveRankEntry`、`DeleteRankGeneration`;match `ResolveStrandedFormation`;支付人工动作(落码时) | 个人身份 + **双人复核** + 留痕 |
| **乙** | 影响可用性或对外内容,但能撤回 | 区服维护 / 开服 / 创角开关 / 容量、白名单、公告、RPC 热关停、剧本审核、赛事局标记、词库发布、配置表发布与回滚 | 个人身份 + 留痕,单人可做。热关停是应急手段,不能等第二个人 |
| **丙** | 只读,但读的是玩家数据 | 玩家查询、订单查询、人工待办列表、`debug_fetch` 导出 | 个人身份 + 访问留痕 |
| **丁** | 绕开服务直接改库 | §2 最后一行的命令行工具 | 不属于后台;见 §9 |

邮件整体归甲级而不按「带不带附件」拆,是为了让规则只有一句:**凡是进流水的写命令,都要第二个人批准。**全服公告即使没有附件,发错了也收不回。

## 4. 设计分析:三种做法与取舍

| 做法 | 审批记录放哪 | 优点 | 缺点 |
|---|---|---|---|
| A. **后台集中** | 后台管理库的流水 | 规则只有一处;流水已经有冻结草稿、过期、行锁单飞、审计轨迹;改动最小 | 后台进程被攻破就能伪造两个人 |
| B. 各资源服务自管 | 每个服务自己的库 | 批准与执行在同一事务 | 八个以上服务各写一套表和接口,规则散开 |
| C. 独立审批服务 | 新服务自己的库,签发带签名的批准凭据,资源服务验签 | 后台被攻破也伪造不了批准 | 新增一个服务:在本仓约 40~60 个文件,多一个要部署和轮换密钥的组件 |

**定案:A。**理由:

1. 后台的流水已经完成了八成:草稿冻结后不能改,发送只接受草稿号,`FOR UPDATE` 下单飞,结果未知时保留原请求号重试。双人复核只是把「谁可以发送」从「创建者本人」改成「另一个人」。
2. 按负责人 11-05 定的口径,安全方案先做减法、规则收一处。B 把同一条规则抄八遍。
3. C 防的是后台进程被攻破。这个风险真实存在(JeecgBoot 历史漏洞多),但现在后台已经持有邮件密钥、单人就能给任意玩家发附件,信任边界本来就在后台。本设计先用 §5.2 的办法把后台暴露面收到最小,并把资源服务侧的核对收在一个共享函数里(§5.5):以后要升到 C,只改这个函数和密钥配置,各服务的调用点不动。
4. 升级到 C 的触发条件写明:后台需要暴露到办公网之外,或者运营人数多到无法逐人背景可信时。

A 仍然满足「在服务端判定」:判定在后台服务端的数据库事务里做,浏览器不参与;资源服务再独立核对一次。

## 5. 方案

### 5.1 总体

```
浏览器 ──登录──> 身份提供方(OIDC)
   │                 │ 授权码
   ▼                 ▼
 后台(java/gm_admin):验 ID Token → 会话;流水记发起人、批准人
   │  ServiceCallAuth 签名的请求,里面带 AdminApproval{批准号, 发起人, 批准人}
   ▼
 资源服务:验调用方签名 → 核对两人不同 → 按批准号幂等执行 → 写自己的留痕
```

人只面对后台一个入口。网关的 `/admin/**`、各服务的管理 RPC 都变成后台的下游,它们的密钥只发给后台这个工作负载,不再发给人。命令行工具在生产只用于诊断和应急(§5.7)。

### 5.2 管理员身份:OIDC 登录

- **流程**:授权码 + PKCE(S256),带 `state` 与 `nonce`。后台是机密客户端,身份提供方返回的令牌只到后台服务端,不进浏览器;浏览器拿到的仍是后台自己的会话令牌(JeecgBoot 现有机制,与上游 `ThirdLoginController.saveToken` 同一写法)。
- **接口**:`GET /gm/sso/config` 告诉登录页当前是哪种模式;`GET /gm/sso/authorize` 生成 `state`、`nonce`、PKCE 校验串并存下(5 分钟内有效,只能用一次),返回跳转地址;`POST /gm/sso/token` 收 `code` 与 `state`,到令牌端点换 ID Token,校验通过后签发后台会话。回调地址就是后台前端的登录页:登录页带着授权码回来后把它交给后台,并立即从地址栏拿掉。
- **ID Token 校验**:签名(JWKS,算法只认非对称的 RS256 / ES256 / PS256,拒绝 `none` 与 HS*)、`iss` 逐字相等、`aud` 含本客户端号、`exp` / `iat`(容差 60 秒)、`nonce` 相等、主体声明非空。
- **操作人标识 = 身份提供方的主体声明**(缺省 `sub`,可用 `gm.oidc.subject-claim` 换成别的稳定声明),必须匹配 `^[A-Za-z0-9._@-]{1,64}$`,原样用作后台用户名。不另建「外部身份 ↔ 本地账号」绑定表:绑定表可以被本地管理员改绑,改绑之后同一个人就能以两个本地账号出现。姓名声明只进显示名。
- **角色来自身份提供方**:`groups` 声明(可配)按 `gm.oidc.role-mapping` 映射成后台角色,**每次登录整体替换**。角色到权限串的关系由 `GmInstallation` 的迁移写死在代码里。首个管理员也靠这张映射产生,不需要初始口令。
- **会话上限**:签发会话时把它在 Redis 里的键的过期直接设成 12 小时(`gm.oidc.session-hours`)。上游只在令牌自身过期(84 小时)时才给这把键续期,12 小时内不会发生,所以这个过期就是硬上限,不需要另建会话表,也不用每次请求多查一次。身份提供方停用某人后,他在后台最多再留 12 小时。(原生模式签发的会话能续到七天,所以从 `native` 切到 `oidc` 前要清掉旧会话键。)
- **登录中间态放管理库,不放 Redis**:`state`、`nonce` 与 PKCE 校验串存在表 `gm_oidc_attempt`,换码时先查后删,以「删到一行」为准,并发的第二个请求删不到就被拒绝。这样多副本之间天然一致,单测用内存库就能覆盖,扩展模块也不必引入 Redis 客户端依赖。发起授权不需要登录,所以未完成的行数设了上限(一万),过期的行在下一次发起时清掉。
- **两种模式,一个开关** `gm.identity.mode`:
  - `oidc`:生产用。原生口令登录、验证码、改密接口全部拒绝;**JeecgBoot 原生的 `/sys/**` 管理页(用户、角色、菜单等)整体关闭**,只留会话读取和登出。角色不在本地管,这些页面就没有存在的必要,关掉之后 JeecgBoot 的大部分历史漏洞面也一起没了。
  - `native`:本机开发用,行为与现在相同。**只在监听地址是回环时允许启动**,否则拒绝启动。
- **依赖**:JDK 没有 OIDC 实现。JWT 验签与 JWKS 拉取用 `com.nimbusds:nimbus-jose-jwt`(Spring Security 底层用的就是它,自带 JWKS 缓存、换钥重取与限速);换码是一次表单 POST,用 JDK `HttpClient`。不引 Spring Security(会与现有 Shiro 的自动装配冲突),不用上游的 JustAuth 第三方登录(它不验 ID Token、没有 `nonce` 与 PKCE,并且会自动建号)。**新增这一个依赖需要负责人点头**(AGENTS §11)。
- **身份提供方选哪家由负责人定**。代码只要求标准 OIDC(发现文档 + JWKS + ID Token)。企业微信、钉钉这类不是标准 OIDC 的,前面架一个 Keycloak 或 Dex 做转接。

### 5.3 两段式流水

在现有 `gm_command` 上加两列:`approver_name`、`approved_ms`。状态:

```
DRAFT(待批准) ──另一人批准──> SENDING ──> EXECUTED / DELIVERED
     │                           └──> REJECTED / UNKNOWN(可用原请求号重试)
     └──驳回或发起人撤回──> DECLINED
```

- **批准即执行**,沿用现有两步:第一步事务里锁行、核对、把状态改成 SENDING 并写入批准人;第二步在事务外调 RPC;第三步事务里写结果与审计。
- **「两人不同」写两遍**:Java 里先比较并给出明确报错(「发起人不能批准自己的申请」),UPDATE 的条件里再带 `operator_name <> ?`。用户名列是二进制比较,不受库的大小写规则影响。
- **批准人只记第一次**。结果未知后的重试不改批准人,任何有批准权限的人都能重试,因为这条命令已经过了双人。
- **申请过期**:创建后 24 小时内没人批准就不能再批(`gm.dual-control.approval-ttl`)。玩家 GM 仍是 5 分钟,邮件另受自身 `expireMs` 约束。
- **驳回**:每类命令一个 `…/decline` 接口,原因必填,命令进 `DECLINED`(与游戏服务拒绝执行的 `REJECTED` 区分开)。有放行权限的人可以驳回任何人的待批申请;只有发起权限的人只能撤回自己发起的那一条。驳回后同一个幂等号重放拿回的是被驳回的那一条,要再做同一件事必须换号重新发起。已经放行(进了 SENDING / UNKNOWN)的命令不能驳回。
- **权限**:发起与批准是两个权限串。邮件类沿用现有的 `…:prepare`(发起)与 `…:send`(批准并执行),不改名;新接入的类别用 `…:prepare` 与 `…:approve`。一个人可以两种权限都有,规则只看这一条命令上两人是否不同。七项玩家 GM 例外:每项只有一个权限串,发起和放行共用,所以发起人与批准人都持有它,区分全靠「两人不同」这一条。
- **标准角色由迁移建好**:`oidc` 模式下原生角色管理页关着,角色只能由 `GmInstallation` 的迁移(版本 7)写死三个:`gm_operator`(发起)、`gm_approver`(批准)、`gm_auditor`(只读)。身份提供方的分组经 `gm.oidc.role-mapping` 映射到这些角色编码(或全权的 `admin`)。
- **开关**:`gm.dual-control.enforce`。`oidc` 模式下恒为开,显式设成关则拒绝启动;`native` 模式缺省关(一个人跑通),可以显式打开用两个本地账号测。关着时流水的行为与引入双人复核之前相同:只有草稿创建者可以发送。
- **页面只做提示**:后台在总览与玩家命令目录里返回 `dualControl`,页面据此把按钮改成「批准并发送」,并把自己发起、尚未批准的申请标成「需要另一名管理员批准」、不显示放行按钮。真正的判定只在流水里,页面绕不过去。
- **审计双写**:审计行写进 `gm_command_audit`(新增事件 `APPROVED`、`DECLINED`),同一事务提交之后再打一行英文结构化日志进日志系统;事务回滚不打。库里的行以后若被改动,可以和日志对出来。

### 5.4 把身份传给资源服务

新增公共消息 `proto/common/base/admin_approval.proto`:

```proto
// 双人复核的批准记录。后台在批准时生成,随高风险管理请求下传,被 ServiceCallAuth 的请求摘要覆盖。
message AdminApproval {
  string approval_id = 1;    // 后台流水号;资源服务拿它做幂等键与留痕关联
  string proposer = 2;       // 发起人:身份提供方的主体
  string approver = 3;       // 批准人:必须与 proposer 不同
  uint64 approved_at_ms = 4;
}
```

- 甲级方法的请求各加一个 `AdminApproval approval` 字段。它在请求体里,所以现有 `ServiceCallAuth` 的签名天然覆盖它,不需要新的签名格式和新的密钥。
- 重试时后台按流水里存的批准人和批准时刻重建同一份 `AdminApproval`,请求摘要不变,资源服务按原请求号判重(mail 的判重本来就核全文摘要)。
- 乙级、丙级只传操作人:有 `operator` 字段的用它;网关 `/admin/**` 用现有的 `X-Admin-Operator` 头,由后台从会话里填。
- **不下传角色**。「谁能做什么」只在后台判一次;把角色传下去,等于在每个资源服务再养一份权限矩阵,两边迟早不一致。资源服务只需要知道:调用方是后台、两个人是谁、批准号是什么。

### 5.5 资源服务侧的核对

新增 `go/shared/dualcontrol`,一个函数:

```go
// Require 核对一条甲级请求带了合格的批准记录:批准号非空、两人都是合法主体且不相同、发起人与请求里的操作人一致。
func Require(approval *basepb.AdminApproval, operator string) error
```

- 每个甲级入口在执行前调一次。它防的是后台的缺陷和误配置,不是后台被攻破(§6 第 2 条)。
- 各服务一个配置项,**缺省开**;只有开发配置显式关。它与后台的开关互相独立:后台配错了,资源服务照样拒绝。
- `java/mall_game` 用同样的四条判断,十几行,不为它建公共库。

### 5.6 第一个接入的动作:交易人工判定

- `ResolveManualContractRequest` 加 `approval` 字段;`TradeCommerceManualAction`(合同上的人工处置留痕)加 `approval_id`、`proposer`、`approver`。
- EXECUTE 在配置为开时必须带批准记录,且 `approval.proposer` 等于请求的 `operator`。SHOW 与 DRY_RUN 不要求。
- **幂等**:先看留痕里有没有同一个 `approval_id`,有就回「已执行」和那条留痕(回包 `already_executed=true`),不再比较版本。这一步**排在版本比较之前**,而且锁外读、锁内各做一次:执行成功后版本已经加一,结果未知的重放若先比版本,只会得到「版本已变」,看不出是不是自己做的;锁外读之后、加锁之前,同一个批准号的另一次请求也可能刚提交。留痕只追加,看到就是已提交,所以锁外看到也能直接回。带同一个批准号的 DRY_RUN 同样报「已执行」,批准人据此知道不用再批。
- **放行的结果怎么记**:trade 回 OK(含重放)→ 流水记 `EXECUTED`;拒绝、合同不存在、版本已变 → `REJECTED`(要重新发起);读库失败(`RETRY`)、提交结果未知(gRPC `UNAVAILABLE`)、超时或断连 → `UNKNOWN`,可在原申请上「沿用原申请重试」,批准记录原样复用、请求摘要不变,trade 按批准号判重。交易人工处置因此与邮件一样属于「可重试」的命令;在线玩家的直接 GM 下游没有判重,仍然不能重试。
- **调用方与密钥**:后台以 `ops-commerce` 调用方签名(与 `commercefix` 同一个调用方,trade 只认它),密钥 `GM_TRADE_ADMIN_SECRET` 与 trade 的 `Commerce.ManualResolutionSecretEnv` 同值,只挂给后台工作负载。本机后台到 trade 还没有经过验收的转发,`run_local.py` 不放行这两个变量,交易页只读不可用(批 7 补本机转发)。
- **不带批准记录的应急出口**:trade 配置 `Commerce.ManualResolutionAllowUnapproved`(缺省 false)。打开时启动打一行 ERROR;之后每一次不带记录的 EXECUTE 都打 ERROR 并计入 `trade_manual_resolution_unapproved_execute_total`(批 7 据此加告警)。打开是一次走部署流程的配置变更,本身有记录。
- **两人以外的信息不下传**:批准记录只有批准号、发起人、批准人、批准时刻;角色与权限不下传(§5.4)。trade 的留痕 `TradeCommerceManualAction` 加 `approval_id`、`approver` 两个字段;发起人就是原有的 `operator`,不重复存。
- 后台新增「交易人工处置」页:列表(`ListManualContracts`)→ 详情(SHOW)→ 发起人选动作、填参数、原因和环境名,后台先跑一次 DRY_RUN,通过才冻结成草稿 → 批准人看到冻结的参数和当场重跑的 DRY_RUN 结果 → 批准后 EXECUTE。执行的结果由「合同在版本 V 的状态 + 动作 + 参数」决定,版本一变 EXECUTE 就拒绝,所以批准人看到的就是会执行的。
- 环境名 `expect_target` 仍由发起人手填(沿用现在防连错环境的做法),不由后台代填。

### 5.7 命令行工具与应急

- `commercefix` 等命令行在生产只做 SHOW 和 DRY_RUN。EXECUTE 不带批准记录,配置为开时被拒绝。
- 不给命令行加「批准人」参数:一个人在命令行里敲两个名字没有意义。
- 应急出口是把资源服务的那个配置项关掉。这是一次走部署流程的配置变更,本身有记录;关闭期间每一次不带批准记录的 EXECUTE 都触发告警。
- 生产环境里,管理调用方的密钥只挂给后台这个工作负载(部署契约测试守住)。

### 5.8 留痕

- 后台:流水表与审计表,只追加。每条审计事件同时打一行结构化日志(英文),进日志系统。库里的行被改了,可以和日志对出来。
- 资源服务:各写各的。trade 写合同上的留痕与 `[CommerceManual]` 日志行;商城写 `commerce_admin_command`(加发起人、批准人两列);mail 写在邮件行上。
- 下传的只有主体标识,不带姓名和邮箱,员工个人信息不进游戏服务的日志。

### 5.9 五条标准逐条对照

| 标准 | 怎么满足 |
|---|---|
| 不丢数据 | 草稿、批准、结果都先落库再继续;发送意图先于 RPC 落库;结果落盘失败保持 SENDING,不报成功 |
| 强一致 | 「两人不同」与状态迁移在同一条带条件的 UPDATE 里;后台与资源服务之间不做分布式事务,靠批准号幂等,未知结果用原号重试收敛 |
| 可水平扩展 | 后台多副本:流水靠行锁与条件更新,登录中间态与会话在 Redis;资源服务侧没有新增状态 |
| 代码易懂 | 规则在流水一处;资源服务一个函数;不加新服务、新签名格式、新密钥 |
| 性能 | 管理面请求量很小,不涉及热路径;登录热路径零改动 |

## 7. 思想分析:为什么是这样

- **认人靠外部,认动作靠流水。**「这是谁」交给身份提供方,「这件事谁提的、谁批的」交给流水。两件事各只有一个权威。
- **规则只写一处,核对可以多处。**判定只在流水;资源服务的核对是同一条规则的只读复查,不产生自己的状态。
- **批准的是事实,不是意图。**批准对象是一份冻结的载荷加一个批准号。之后的执行、重试、对账都指向同一个号。
- **缺配置就拒绝。**没配身份提供方、没带批准记录、开关没写,结果都是拒绝。
- **不为还没出现的问题加组件。**独立审批服务留成升级路径,并把以后要改的地方收在一个函数里。

### 11.1 批 4:商城人工单与 SKU 迁进后台

- **一个通用的「运营处置」类别 `OPS`,不按命令各建一类。**流水里只加一个类别,冻结 `{target, command, body, retryable}`,流水再补顶层 `requestId`(就是流水号,也就是批准号)。下游与命令的白名单只在 `GmOpsController.COMMANDS` 一处:发起人能填的字段、服务端填的字段(操作人、原因、冻结时刻、固定模式)、请求号字段、能否沿用原申请重试、有没有预览。
  - 为什么:批 4 的 7 条商城命令加批 5 的 12 条 gRPC 命令,按「一类一套」要抄 19 遍校验、列表、驳回与页面;规则还是那一条「凡是进流水的写命令都要第二个人批准」。
  - 权限按下游分:`gm:<target>:read / prepare / approve`(迁移 9 建商城的,迁移 10 建其余五个);标准角色照迁移 8 的分法。
- **商城侧的核对是「请求号就是批准号」**:商城请求里没有操作人字段,与 trade 的「发起人就是请求里的操作人」对应的约束换成这一条,一次批准只能执行一次,商城按 (主体, 请求号) 的既有判重自然做到。这条后来抽成 `go/shared/dualcontrol.RequireForRequest`,批 5 的 mail、rank、回收批次、收件箱处罚共用。

### 11.2 批 5:邮件、回收、收件箱、账号类、榜单、滞留阵容

- **邮件不改任何方法签名**:流水在放行时把批准记录放进交给发送方的冻结请求(`SendMailRequest.approval`;活动邮件放在建活动的那份请求里),`GameServices` 原样转成协议。草稿里不许自带 `approval`(冻结字段名单加了它)。
  - mail 按调用方要求:缺省只有 `admin`(后台与 `mailadmin`)要求带,系统生产方(rank 奖励、battle 掉落、match 赛事)不要求;带了就必须合格。导入名单与封存活动不要求:它们只能往已经批准创建的活动里按冻结的名单摘要导入与封存。
  - **部署顺序**:mail 的 `validateContent` 拒绝未知字段,所以 mail 要先于后台升级,否则后台带批准记录的发信会被旧 mail 拒绝。
- **账号类协议拆文件**:`LoginAdmin` 与只给它用的消息搬到 `proto/login/login_admin.proto`(同包、字段号不变,消息号按服务名+方法名取,也不变)。原因:`login.proto` 有客户端可见服务,客户端按 import 闭包生成,往里 import `admin_approval.proto` 会把批准记录带进 Unity。客户端可见的 `login.proto` 少了这几条服务端消息,要按 AGENTS §4 跑客户端三步脚本。
- **rank 只对调用方 `admin` 要求批准记录**:match 删除角色时会以 `match` 自动调 `RemoveRankEntry`,一刀切会让清理停摆。
- **能否重试按命令冻结**(`retryable` 随申请冻结,不随目录以后的改动漂移):下游按批准号判重或者重放天然收敛的命令可以沿用原申请重试;重放会被当成「已是终态」拒绝的两条——收件箱强制作废、滞留阵容终结——不能重试,未知结果停在 UNKNOWN,要人去下游核对后再决定是否重新发起。否则重试回来的「已是终态」会把一条其实已执行的命令记成 REJECTED。
- **预览不进流水**:回收批次与滞留阵容要先演练拿计划摘要(`expected_plan_digest` / `expect_digest`),摘要随申请冻结,批准时下游按它做比较,批准人看到的就是会执行的(与 trade 的版本比较同一思路)。预览只要查看权限。
- **原因按字节限长**:下游里最严的是 191 字节(match、trade),发起时就按 UTF-8 191 字节挡住(约 63 个汉字),不等到批准时才被下游拒绝。
- 收件箱作废的 `reason` 是作废原因枚举,申请原因写进 `note`(强制模式必填,进审计)。
- 下游的调用方证明:login、player_inbox、data_service 回收认共享口令 `x-admin-token`,rank(调用方 admin)与 match(调用方 `ops-formation`,不是交接单写的 `ops`)认 ServiceCallAuth。口令与密钥只挂给后台工作负载(§6 第 3 条)。
- 当场发现的:data_service 的 `AdminToken` 在 K8s 配置模板里没有渲染,回收五个入口在集群里目前是关的;接线随批 7 的清单另做。
- **各服务落码时定下的做法**(子任务回报后逐条核过):
  - **核对函数收紧**:`RequireForRequest` 起初把空操作人当成「请求没有操作人字段」,有操作人字段的请求带空操作人会先被当成已核过、再被业务校验拒掉(收件箱会先打一行「已核过」)。改成严格比对:请求里确实没有操作人字段的 mail、rank 显式传 `approval.GetProposer()`。
  - **回收的「登记已人工处置」(`RegisterRecallReviewHandled`)也按甲级**:登记之后这些流水永久按已消费处理、以后的回收都跳过,属于「做完撤不回」;§3 的清单原来漏了它。请求加 `approval = 10`,核「发起人就是操作人」,进运营处置目录(重放回「早已登记」,可以重试)。
  - **rank:后台经批准可以删任意榜上的单个条目**。原来只许开榜方删,而榜都是 match 开的,后台的删除永远被拒。整代隐藏仍只许开榜方(系统榜被整代隐藏后开榜方的提交会一直失败),所以目录里不放 `DeleteRankGeneration`。判重键 (榜, 代, 请求号) 不含调用方,后台批准号与 match 摘角色用的玩家号理论上可能撞号,两边都是 63 位打散值、概率可以忽略;真要杜绝就把调用方并进 `rank_mutation` 的主键(代码里记了 shortcut 注释)。
  - **mail:`admin` 恒在「要求批准记录的调用方」名单里**,配置只能往上加:能把 `admin` 拿掉,就能绕开应急开关打开时的逐条 ERROR 与计数。
  - **留痕落在哪**:商城、mail、收件箱、match 有表就加列;data_service 的批次与审计没有合适的列,批准号与批准人写进理由文本(`[approval_id=… approver=…]`),人工终结回收行只进日志行(理由落库有 191 字上限)。
  - **残余**:login 三个方法没有请求号,批准记录只绑定了操作人,拿到 `x-admin-token` 的人可以拿同一份记录去改别的角色——与 §6 第 3 条同一个信任边界。个人邮件行到期会被清理,行上的批准记录跟着没了,长期留痕在后台流水。

### 11.3 批 6:网关 `/admin/**` 收口

- **规则收在口令闸 `AdminApiKeyFilter` 一处,不在各控制器里各写一遍**:写操作(POST / PUT / PATCH / DELETE)必须带且只带一个合规的 `X-Admin-Operator`(与身份提供方主体同一字符集),否则 400;每次写操作在响应之后打一行 `AUDIT gateway admin write`(方法、路径、状态、操作人、口令种类、来源地址)。新加的管理控制器不会漏;热关停与配置表两个控制器原有的业务细节 AUDIT 行照旧。
- **机器口令** `admin.machine-key`:只能访问 `/admin/tables/**`(规范化路径与原始 URI 都要落在下面,不带 `..`),操作人必须是 `table-bundle`;人用的口令不能冒用 `table-bundle`。不配就没有这条路;两把口令相同或机器口令短于 32 字节拒绝启动。`table-bundle` 命令行用机器口令时带 `-operator table-bundle`(或 `MMORPG_ADMIN_OPERATOR=table-bundle`);命令行本身这次没改,它正被配置表热更那条线改着。
- **人用入口在后台**:`POST /gm/gateway/admin` 只转发白名单里的方法与路径(区服、白名单、公告、热关停),网关口令留在服务端,`X-Admin-Operator` 取登录会话;权限 `gm:gateway:write`(乙级,单人可做,给发起人与批准人两个标准角色)。页面是控制台里的「网关管理」卡片。
- 公网入口:`k8s_client_entry.ps1` 生成的 gateway Ingress 只路由 `/api`,契约测试已经钉着(`k8s_client_entry_contract.tests.ps1` 的 D91 两条),这次只核对、没改。

### 11.4 批 7:告警、K8s 清单与本机转发

- 告警:`deploy/k8s/dual-control-alerts.yaml`,每个资源服务一条「不带批准记录而被接受」的规则(trade 是 `TradeManualResolutionUnapprovedExecute`,与 trade 配置注释一致),5 分钟内有增长就响;契约测试 `tools/scripts/tests/dual_control_alerts_contract.tests.ps1` 钉住规则名单、指标名来自代码。集群里这些计数应当恒为 0。

### 11.5 负责人没想到、这次定下的做法

1. 带请求号的下游用「请求号就是批准号」代替「发起人就是操作人」(§11.1),一次批准只执行一次由下游已有的判重保证,不加新表。
2. 运营处置一个类别 + 一张目录(§11.1),规则、白名单、权限、重试性都在一处。
3. 能否重试随申请冻结(§11.2),重放会被判成终态的命令宁可停在 UNKNOWN 也不记错成 REJECTED。
4. 邮件经冻结请求带批准记录,不改发送方签名(§11.2)。
5. 网关的操作人与留痕收在口令闸一处,机器口令限定路径并固定操作人名(§11.3)。
6. 原因在发起时按下游最严的字节上限挡住(§11.2)。
7. 落码时补上清单漏掉的甲级动作:回收的「登记已人工处置」做完撤不回,同样要第二个人批准(§11.2)。
8. rank 的后台删除原来对系统开的榜一律被拒,放开成「经批准可删任意榜上的单个条目、整代隐藏仍只许开榜方」(§11.2)。
