## 0. 先读这节

**一句话**:摆摊 = 寄售(一口价挂卖) + 主城里看得见、点得开的摊棚。钱和货走寄售引擎;
地图上的摊棚只是"门面",由客户端照着服务端给的摊位列表画出来。

**打个比方**:摊位就是当铺柜台。

- **开摊**:卖家先把货交给柜台保管,货从卖家背包扣出,存进交易库。这一步只动卖家一个人。
- **买**:买家先付钱给柜台,钱从买家身上扣。这一步只动买家一个人。
- **交割**:柜台在账本上记「这 5 瓶药归买家」,先把药发给买家;买家收到后,再把钱(扣掉税)发给卖家。
  每一步仍然只动一个人。

**为什么不让两个人直接一手交钱一手交货?** 两个人的存档是**各存各的**。服务器每 300 秒给每个在线玩家存一次盘,
每个人的存盘时刻按玩家号错开。看一个例子:

| 时刻 | 发生了什么 |
|---|---|
| 10:00:00 | 小明把 1 把 +5 青锋剑卖给小红,内存里剑从小明转到了小红 |
| 10:00:30 | 轮到小红存盘:小红的存档里**有**这把剑 |
| 10:01:00 | 服务器崩溃。小明这一轮还没存盘 |
| 重启后 | 小明按上一次的存档恢复,剑**还在**他身上;小红的存档里也有。**一把剑变成了两把** |

走"柜台"就没有这种问题。每一步只改一个人的存档,而且每一步都带唯一编号,崩溃后按原编号重发,
已经做过的不会再做一遍。坏情况是"到账晚一点",不会凭空多出东西。

**这句保证有边界**:它成立的前提是寄售引擎本身的前置都做完了(§2.4 的 P-3、P-5、P-6)。
寄售引擎的文档里自己写着还有没关上的口子(玩家换服务器节点、Redis 数据回退、冷加载之间的竞态)。
这些口子没关之前,摆摊和寄售一样不能正式上线。

**推荐方向**(对应 Q7A、Q6A、Q1A,你可以在 §1 改;理由见 §2):

1. 成交走快照分支里写好的寄售引擎(Go `go/trade/internal/commerce`,Java `game-trade/commerce`),
   不在 scene 节点里让两人直接互换。
2. 摊棚由客户端画,服务端不新建摊位实体(和神秘商人同一个做法)。人和摊分开:开完摊,人可以走开,也可以下线。
3. **C++ 手写逻辑一行不改**:扣货、发货、扣钱、加钱都走已有的资产通道。
   不过摆摊的协议要加进已有的 `jubaozhai.proto` 和 `commerce.proto`,所以 C++ 生成物和 gate 的客户端消息白名单都要**重新生成、重新编译**。

**本文会用到的几个词**(都用上面"柜台"的比方):

| 词 | 意思 |
|---|---|
| 托管 | 卖家把货交给柜台保管:货从背包扣出,存进交易库 |
| 腿 | 柜台对**某一个人**做的一次收或发,比如"从小红身上扣 250 银两"。每条腿带唯一编号,可以重发,重发不会多做 |
| 推进循环 | 交易服务每秒做一次的事:把还没办完的单子往前推一步 |
| 白名单 | 允许拿来交易的物品和货币清单,默认是空的,也就是什么都不能交易 |
| SQL 落库证明 / `dual` 模式 | 玩家存档真正写进 MySQL 以后发出的凭证。数据库要开 `dual` 模式才会发这个凭证;没拿到凭证,就不算到账 |
| 归属围栏 | 防止"同一个玩家同时被两台服务器当成自己的"的保护。目前还有缺口没补上(P-5) |
| guard 行 | 交易库里专门用来排队的一行。谁要改某个摊,先锁住它,同一时间只有一个人能改这个摊 |

### Q1 离线摆摊:玩家下线以后,摊位怎么办?

| 选项 | 说明 | 影响 |
|---|---|---|
| **A(推荐)支持离线** | 下线后摊位照常营业,直到单次营业时长到期(默认 12 小时,见 Q15)。卖出的钱排队,上线后自动到账 | 本方案里**最省事**:开摊时货已经交给柜台,卖家在不在线都能成交。**代价**:下线的人也一直占着摊位点,得靠 Q5 防霸占 |
| B 不支持离线 | 下线(包括断线)就自动收摊,剩下的货退回 | 反而**更费事**:交易服务要不停检查摊主下线没有;退货只能等玩家在线才能到账,所以要等他下次上线 |
| C 付费代管 | 下线后继续营业,但按小时扣代管费(类似大话西游手游的「小金蟾」) | 多一套计时扣费;扣费失败时是收摊还是继续,也要另定规则 |

### Q2 交易货币:摊位上的东西用什么买?

| 选项 | 说明 | 影响 |
|---|---|---|
| **A(推荐)只用银两** | 银两 = `kCurrencyGold`,游戏里赚来的普通货币 | 结算、扣税、防转钱都只管一种余额;与聚宝斋 J-O4 的默认值一致 |
| B 银两或灵石,卖家自选 | 灵石 = `kCurrencyDiamond`,高级货币(聚宝斋文档里叫「元宝」) | 灵石一旦能在玩家之间流通,就等于开放了"拿高级货币换东西",要和充值、防洗钱一起考虑 |
| C 三种都行(含绑定灵石) | — | **不建议**。绑定货币本来就设计成不能流通(帮会契约 R1 也禁止捐绑定灵石) |

注意:寄售总白名单 `Commerce.CurrencyTypes` 现在默认是空的。选 A 就得把它配成 `[0]`,
而这会**同时打开**寄售、竞拍等其他玩家交易的银两结算。摆摊自己还有一道开关(§4.7),只能在总白名单里面再收窄,不能放宽。

### Q3 摊位费和交易税:怎么收费?

| 选项 | 说明 | 影响 |
|---|---|---|
| **A(推荐)只收成交税 5%** | 每成交一笔,从卖家收入里扣 5%(向上取整),这部分银两直接销毁 | 税在下单时就算好、写进购买单,结算时直接用,不需要退费路径。例:5 瓶 × 50 银两 = 250,税 13,卖家实得 237 |
| B 开摊费 + 成交税 | 开摊时扣一笔摊位费,成交时再扣税 | 多一次扣钱;开摊失败、提前收摊时摊位费退不退,都要另定规则。好处是能直接挡住"占着摊位不卖" |
| C 都不收(开服期免费) | — | 最简单,但游戏里的银两只进不出,没有回收 |
| D 只收摊位费 | — | 复杂度同 B,而且成交越多,回收的银两占比越少 |

税率写在配置表里,上线后可以调,改了只影响之后下的单。业界参考:梦幻西游 7%–18%,RO 5%(只对高价物品收)。
A 和 C 都挡不住霸占摊位,霸占的问题交给 Q5。

### Q4 能摆的地点:在哪里可以摆摊?

| 选项 | 说明 | 影响 |
|---|---|---|
| **A(推荐)天墉城固定摊位点** | 天墉城里预先摆好 N 个摊位点(默认 24 个,配置表加行就能加),空位先到先得 | 服务端只认摊位点编号,不用判断"这块地能不能摆";遮挡和美术只要在这 N 个点上逐个验收 |
| B 天墉城摆摊区里随便站 | 划一块区域,区域内任意位置都能摆 | 服务端要做区域判定和"两个摊别挨太近"的判定;玩家坐标是客户端上报的,只能软校验;摊位可能互相压住 |
| C 单独做一张集市地图 | 类似问道端游的「天上集市」,从天墉城传送进去 | 要新画地图,新做导航网格和出生点 |
| D 不要实体摊,只做界面 | 类似问道手游的集市 | 这其实就是寄售,快照分支里已经有了,不算摆摊 |

### 补充选择题(没回答的按推荐项做)

**Q5 怎么防止有人霸占摊位点?**(选了 Q1A 离线摆摊就必须定这一题)

- A(推荐)一人同时只能开一个摊,收摊或到期后要冷却 30 分钟才能再开。上线后看摊位点占用率(§4.11 的指标),长期接近 100% 就加摊位点,或者改成 B。
- B 开摊交一笔不退的摊位费,等于 Q3 选 B。
- C 缩短营业时长、拉长冷却,比如营业 4 小时、冷却 1 小时。
- D 不限制。

先把 A 的效果说清楚:按默认的营业 12 小时、冷却 30 分钟,一个人可以占住一个点 96% 的时间,每 12 小时只空出约 30 分钟。
全区只有 24 个点时,24 个普通玩家到期就重开,摊位就基本被长期占满了。A 只能保证"一个人只占一个点",挡不住长期轮流占点。
还是推荐 A,是因为现在还没上线、玩家不多,先不碰钱;上线后有了占用率数据,再决定加点还是收费。

**Q6 人和摊要不要绑在一起?**
A(推荐)人摊分离:开完摊,人可以走开、打怪、下线,摊照开;B 人必须守在摊旁,不能移动、不能战斗,离开就收摊(问道端游、RO 的做法)。
推荐 A:它和 Q1A 离线摆摊是同一个前提。选 B 要改 C++(移动锁、战斗互斥、视野协议里加摆摊状态),而且 Q1 也只能选 B。

**Q7 成交走哪条路?**
A(推荐)寄售引擎托管;B 同一条线的两个人在 scene 里直接互换(有 §0 那种复制风险);C 先做 B,以后再迁到 A。
推荐 A:这是唯一不会因为崩溃复制物品的做法。选 B 还得另造"两人存档同时落盘"的机制,目前仓库里没有。

**Q8 能摆什么?**
A(推荐)白名单里的可叠加物品(药、材料)和装备;B 只摆可叠加物品;C A 再加宝宝。

- A 的影响:装备按原件整件托管,随机属性、强化、宝石都保留,快照分支已经做到。但要先做 P-1c(§2.4),
  否则装备配置一加进总白名单,聚宝斋的材料市场里会多出一批"装备市场",这些市场托管必定失败。
- B 的影响:把摆摊自己的 `Stall.AllowInstances` 关掉就行(§4.7)。
- C 的影响:宝宝不只是改白名单。开摊协议的货位里没有宝宝字段,摆摊开关里也没有宝宝开关,要改协议和货位模型,两个版本同批改。

**Q9 一个摊能摆多少格?**
A(推荐)12 格,其中装备最多 8 格,同一种可叠加物品只能占一格;B 20 格,花银两能扩到 40 格(问道端游的做法);C 按等级逐步解锁。

- 寄售引擎一次托管的上限是:可叠加物品 16 种、装备 8 件、可叠加物品合计 4096 个、托管快照每笔 64 KiB。推荐项在这些上限以内。
- B 超出了一次托管的上限:要么一个摊拆成多张托管单,要么改引擎上限,S1 的工作量会明显增加。
- C 要知道玩家等级,问题同 Q13。

**Q10 可叠加物品能不能只买一部分?**
A(推荐)能,卖家标单价,买家自己选买几个;B 不能,每格整份卖,卖家自己拆份。
推荐 A,摆摊卖药、卖材料基本都是零卖。代价是寄售引擎要新加一种"一次托管、分次卖出"的单子(§4.2)。

**Q11 主城有好几条线,怎么办?**
A(推荐)全线同显:天墉城每条线看到的是同一批摊,在哪条线都能买;B 每条线各摆各的,只有同一条线的人能看到。
推荐 A。分线是服务器为了分流临时开的,人少了还会自动合并。摊位按线分,会把买家拆散,线一合并摊位还得跟着搬。
摊位在交易库里本来就是全局的,全线同显几乎不额外花钱。

**Q12 能不能远程买?**
A(推荐)一期只在客户端上做成"在天墉城里点摊棚才能买",另外给一个「本城摊位列表」方便找;B 做全服搜索、远程购买。
注意:A 只是客户端这么做,服务端不检查买家站在哪(交易服务拿不到玩家坐标)。改过的客户端可以远程买,但拿不到任何经济上的好处。
全服搜索本身就是寄售市场,快照分支里已经有了。

**Q13 开摊要不要门槛?**
A(推荐)一期不设等级门槛,靠白名单、交易税、交易流水和 Q5 控制风险;B 设等级门槛(比如 30 级)。
选 B 要改 C++:交易服务读不到玩家等级(聚宝斋 2026-09-14 核实),只能在 scene 扣货那一步顺带校验,这要改资产通道的签名字段。

**Q14 摊位名能不能自己起?**
A(推荐)能,最多 12 个字,走 `go/shared/playername` 那套校验(字符白名单和敏感词);B 不能,一律叫「某某的摊位」。
推荐 A:交易服务是 Go 写的,角色名那套校验可以直接拿来用。B 更省事,只是玩家没法给摊起名字。

**Q15 一次最长营业多久?**
A(推荐)12 小时,到期自动收摊,剩下的货退回;B 24 小时;C 3 天。
推荐 A:摊位点有限,时间越长越容易被占着不卖。B、C 不用多写代码,只是霸占会更严重(见 Q5)。

**Q16 一期防作弊做到哪一步?**
A(推荐)单价上下限(可以按物品单独配)+ 全量交易流水 + 大额成交告警;
B A 再加「买到的东西 N 小时内不能再卖」;C B 再加「珍品公示期」。
B 要给物品实例**新加**一个交易冷却截止时间字段:背包条目注释里预留的 9–12 号是绑定状态、可交易次数、过期时间、自定义数据,
没有这个用途的字段。C 还要给物品加上架时间。推荐把 B、C 都放到二期。

**Q17 摊主被封号或冻结了,摊位怎么办?**
A(推荐)封号时立即收摊,剩下的货和已经卖出的钱都排队,解封上线后再到账;B 不管,摊照开。
推荐 A,否则被封的工作室号还能接着在线下卖货、收钱。实现方式是 GM 封号流程顺带调一次收摊。

**Q18 从别的区跨过来的玩家,能不能在本区开摊?**
A(推荐)不能,只能在自己的归属区(home zone)天墉城开摊;B 能。
推荐 A:摊位点按区划分,跨区访客占点会挤掉本区玩家,合服时也更难收拾。

**Q19 同一个账号的几个角色,能不能各开一个摊?**
A(推荐)能,一个角色一个摊;B 一个账号只能开一个摊。
推荐 A:交易服务能不能拿到账号还**没核实**(§11)。选 B 要先核实这一点,还要多一张按账号记的表;而且换个账号就绕过去了。

## 2. 为什么这么设计

### 2.1 现状

- 两个仓库(服务端、客户端)的主干、全部分支和全部提交历史里,都**没有**摆摊代码或文档。
  客户端里唯一叫 Stall 的东西,是天墉城地图上的装饰摊棚 `MarketStall`。
- 仓库里也没有"两名玩家之间直接交换资产"的实现。`TX_TRADE` 已经在 scene 的 `TRADE_CREDIT` 流白名单里,
  但没有任何写入方;`LogItemTransfer` 原来只有定义、没有调用,2026-11-12 随审计发件箱删掉:一条流水只能指名一名玩家、随他的存盘提交,
  两名玩家之间的转移记成转出、转入两条(同一个 correlation_id,`docs/design/player-audit-outbox.md` §5.4)。

### 2.2 两条路的比较

## 4. 服务端设计(go/trade,Java 版同构)

### 4.1 放在哪

放在 **go/trade 的寄售引擎**里(快照分支 `internal/commerce`),Java 版放在 `game-trade/commerce`。理由有两条:

- 快照分支 `jubaozhai-market.md` §15.1 写明:玩家之间的交易、寄售、材料撮合、竞拍,都由 Go `internal/commerce`
  和 Java `game-trade/commerce` 承担;`java/mall_game` 只管官方商品。摆摊也是玩家之间的交易,放在这里就不会出现第二套订单。
- 资产通道规定,每条流只能由一个服务分配编号(I6)。`TRADE_DEBIT` / `TRADE_CREDIT` 两条流本来就归 trade 独占,
  所以 C++ 侧的流规则白名单、调用方白名单和密钥都不用改。

**不设"收益箱"**:初稿打算把卖家收入先存在交易库里,攒够了再合并到账。评审指出,这等于在交易库里存玩家余额,
违反引擎自己写明的约定("这张表只保存合同、托管证据与待办,绝不保存玩家余额",快照 `trade_table.proto:164`)。
改成和寄售一样,**每卖一笔,单独给卖家发一笔钱**。卖家离线时这些发放排队等待:
排队超过 16 笔就延后分配编号,不报错;等卖家期间按退避延后检查,不在推进循环里空转。这两点都要等 P-1b 修好才能做到。

**容量要在 S1 实测**:最坏情况是很多离线卖家各有几十笔等着打钱。S1 要量出"待打钱单数 × 每推一步的成本",
确认 P-1b 的按行延后能让推进循环的耗时不随这类单子的数量增长。

### 4.3 状态与推进

**摆摊的单子有自己的推进函数,不进引擎现有的通用分支。** 这是评审提的 P0。引擎按阶段名字符串分支,不看单子类型:
单子一旦叫 `open`,到期或者卖家调用通用的 `CancelCommerceOrder`,引擎就会用 `Transfer` 把**整个托管包**原样退给卖家,
已经卖出去的那部分也会退回去,等于刷物。所以:

1. kind 6、7 **在 `Tick` 这一层就分派出去**(竞拍的 `bid_ready` 交给 `acceptBid` 就是这么做的),交给摆摊专用的推进函数。
   通用的 `advance()` / `plan()` 不处理 6、7。专用函数先锁 guard,再按下面的锁顺序锁父单、货位、子单。
2. 非终态的阶段名一律加 `stall_` 前缀。终态的阶段名沿用引擎的 `done`,这样已有的 `MarkCommerceOpsConsumedTx` 和终态清理照常生效;
   终态之间靠 status 区分。
3. 通用的 `Mutate`(确认、购买寄售、取消)碰到 kind 6、7 一律返回 `kTradeOrderStateConflict`。收摊只能走 `CloseStall`。
4. 退货包按"货位剩余量"计算(可叠加物品是剩余数量,装备是没卖出、也没被预留的那几件),用新函数生成,**不调用 `Transfer`**。

**截止时间在玩家离线时不起作用,所以不能让摊位点或收摊去等截止时间。**
资产通道的规则(不变量 I7):玩家不在线时,交易服务不能自己判定"这一笔没扣";截止时间过了,只是改发"中止"指令,
而这条指令也要等玩家上线、scene 记了账才算数,中间可能等很久。因此下面的设计里:

- 摊位点、owner 行一到时间就释放,**不等**扣货的最终结论;
- 收摊**不等**付款腿的结论;
- 结论晚到的那些货,由当时负责它的那张单子自己退回。

**摊位单**

| 阶段 | 引擎 status | 在推进循环的扫描里吗 | 说明 |
|---|---|---|---|
| `stall_escrow` 托管中 | 3 | 在 | 托管腿的截止时间 = 数据库当前时间 + `StallRule.escrow_timeout_ms`(默认 60 秒),**不用营业到期时间** |
| `stall_escrow_expired` 托管超时 | 6 | 在 | 截止时间一过,在同一个事务里删 `trade_stall_spot`、清 owner 的 `current_stall_id`(不写冷却),然后只等托管腿的最终结论:结论是"已扣",就建退货腿转 `stall_return`;结论是"没扣",直接到终态 |
| `stall_check` 托管后复核 | 3 | 在 | 托管成功后,按快照逐件复核:装备的配置号在白名单里,单价符合 `StallGoodsRule`。通过就进营业;不通过就转 `stall_return`,并做和"进入收摊"一样的释放(见下面的副作用) |
| `stall_open` 营业中 | 12(新增 `STALL_OPEN`) | **不在** | 营业中的摊不进推进循环。到期另外用 (kind, status, expires_ms) 索引单独扫描(快照的 `trade_table.proto:170` 已经有这个索引)。`expires_ms` 在进入营业的那个事务里,按数据库时间计算 |

```
     │截止时间到
     ▼
stall_escrow_expired ──结论"已扣"──▶ stall_return
                     └─结论"没扣"──▶ done(7)
```

每条边**在同一个事务里**要顺带做的事:

| 边 | 顺带做的事 |
|---|---|
| 进入 `stall_open` | 城市版本号加 1 |
| 离开 `stall_open`(收摊、到期、封号、白名单撤掉) | 删 `trade_stall_spot`;owner 行的 `current_stall_id` 清零,写 `last_close_ms`;`trade_stall` 改状态;城市版本号加 1;把所有付款腿还没有结论的子单标成"父单已收摊" |
| `stall_check` 复核不通过 | 删 `trade_stall_spot`;owner 行的 `current_stall_id` 清零(不写冷却);`trade_stall` 改状态 |
| `stall_escrow` 截止时间到 | 同上一行 |
| 扣出被拒 | 同上一行,然后直接到终态 |
| 进入终态 | 调 `MarkCommerceOpsConsumedTx`;做守恒检查(§4.2) |

- 收摊时如果还在 `stall_escrow`,记下"要收摊",等托管有了结论再走上表。
- "白名单撤掉"的触发时机:trade 只在启动时加载配置,所以每次启动时扫一遍所有 `stall_open` 的货位,不合规的摊转收摊。

**摊位购买单**

| 阶段 | 引擎 status | 说明 |
|---|---|---|
| `stall_pay` 付款中 | 3 | 付款腿(`TRADE_DEBIT`)的截止时间 = 下单时的数据库时间 + `StallRule.payment_timeout_ms`(默认 60 秒)。买家离线时,同样要等他上线才有最终结论 |
| `stall_deliver` 发货中 | 4 | 收货腿(`TRADE_CREDIT`):装备只放整件原件,不放实例号;可叠加物品用配置号加数量 |
| `stall_payout` 给卖家打钱 | 4 | **收货腿成功之后**才建卖家收款腿 |
| `stall_refund_goods` 把预留的货退给卖家 | 4 | 只在"付款没成,而父单已经收摊"时出现:把这张单预留的货直接退给卖家。装备用下单时复制进来的原件,可叠加物品用配置号加数量 |
| 终态 `done` | 11 / 7 / 10 | 11 = 成交;7 = 没成交(预留已经退回货位,或者已经退给卖家);10 = 人工核查 |

付款腿有了结论以后:

- **付款成功**:进入 `stall_deliver`,不管父单是不是已经收摊,货都归这张购买单负责。
- **付款没成,父单还在营业**:在同一个事务里把预留数量退回货位,到终态 7。
- **付款没成,父单已经收摊**:进入 `stall_refund_goods`。父单退货时没算这部分,所以不会重复退。

**买家处理中的计数什么时候减 1**:收货腿成功的那一步减 1,这一步只记账,不建新腿;下一轮推进再单独建卖家收款腿。
付款没成、到终态 7 或进入 `stall_refund_goods` 时,也减 1。这个上限是用来保护买家自己的,不该被离线卖家拖住。

**为什么要等买家收到货再给卖家打钱**:收货腿可能被永久拒绝。比如运营发现某物品被刷了,对它做全服封禁,
所有还在路上的这种货都会被拒。如果卖家此时已经拿到钱,客服再给买家退款,就等于凭空多出一份钱。
先发货、后打钱,收货被拒时那笔钱还留在购买单上,人工处理时默认用它退给买家。
**代价**:买家迟迟不腾背包,卖家的钱也会跟着晚到。

**锁顺序**:所有摆摊事务都按这个**固定的表顺序**加锁(参照 `acceptBid`):

`trade_commerce_guard`(guard_id = 摊位单号)→ `trade_stall_owner` → `trade_stall_spot` → `trade_stall_buyer` → `trade_stall`
→ 父单(摊位单)→ `trade_stall_slot`(按货位号升序)→ 子单(按单号升序)→ `trade_stall_city_version` → seq → outbox。

不需要的表跳过,但顺序不能反。购买单的推进只要会碰父单、货位或买家计数,也要先拿同一把 guard。
guard_id 用摊位单号,不会和竞拍(用拍品单号)、材料撮合(用哈希,最高位置 1)的 guard 撞号。

### 4.4 关键流程

**开摊** `OpenStall`

1. 只读预检(在提交事务里还会再判一次):
   - 摆摊开关打开,并且本区不在 `Stall.DisabledZones` 里;
   - 摊位点在 `StallSpot` 表里;
   - 摊主当前所在区 = 他的归属区(Q18),当前所在 scene 属于这座城。读法是先读 `player:{id}:location`,拿到 `scene_id` 和 `zone_id`,
     再对照分线目录,查这个 scene 属于哪张地图(**实现时要核实具体读法**);
   - 可叠加物品在白名单里,单价在上下限之内;装备这一步只能查摆摊开关里的 `AllowInstances` 和件数,
     因为交易服务读不到背包,还不知道装备的配置号(要到托管后再复核);
   - 总格数不超过 `max_slots`(12),装备格数不超过 `max_instance_slots`(8),超了返回 `TooManySlots`;
     引擎自己的上限(可叠加物品 16 种、合计 4096 个)作为第二道关;
   - 摊位名通过 `playername` 校验。
2. **先按请求号查一次**:同一个请求号已经建过摊,直接返回那个摊。客户端超时重发时,不会被自己上一次的 owner 行挡成「已经有摊」。
3. 一个事务(锁顺序见 §4.3):
   - `SELECT … FOR UPDATE` 锁 owner 行。没有这一行就插入;有的话,`current_stall_id` 不是 0 就回「已经有摊」,
     冷却还没过(`last_close_ms + reopen_cooldown_ms` 晚于数据库当前时间)就回「收摊冷却中」;都没问题就更新 `current_stall_id`。
     上一个摊还在退货中,不妨碍开新摊。
   - 插入 `trade_stall_spot`,主键冲突就回「摊位点已被占」。
   - 写摊位单、`trade_stall`、`trade_stall_slot`、托管腿。**这一步城市版本号不加 1**,要等进入营业中才加。
   - 事务失败后再按请求号查一次,命中就返回原来那个摊。
4. 资产通道把货从卖家身上扣出,之后按 §4.3 往下走:扣成功进 `stall_check`;被拒到终态 7;截止时间到了进 `stall_escrow_expired`。
   装备按原件整件扣出(快照分支已经做到:保留 GUID、成长数据和未知字段)。

**购买** `BuyStallGoods`(请求里带:请求号、摊位号、货位号、数量、看到的单价、看到的货位版本号)

1. 预检:不是自己的摊;数量在 1 到剩余可卖数之间;总价不溢出;成交额大于税(§4.5);这件货此刻还在白名单里。
2. 一个事务:锁摊位的 guard → 锁 `trade_stall_buyer`,复核"处理中的购买 < `max_inflight_purchases`(默认 4)"
   → 核对摊位单是营业中、`expires_ms` 晚于数据库当前时间 → 锁货位,核对货位版本号和单价,预留数量
   → 建购买单(写进算好的税和卖家实得,以及要发的货)和付款腿。
   同一个请求号重复发来,返回同一张单,不会重复下单。
3. 付款腿、收货腿、卖家收款腿都由推进循环按 §4.3 往下走。

**改价** `UpdateStallPrice`:只改交易库(锁 guard 和货位,核对货位版本号,写新单价,版本号加 1)。
不碰资产;已经在处理的购买按下单时的价格成交。

**收摊** `CloseStall`,以及**到期**:离开营业中,马上转 `stall_return`,见 §4.3。到期由单独的扫描触发,用数据库时间判断。

`CloseStall`、`UpdateStallPrice`、`GetMyStall` 在哪张地图都能用。只有开摊要求人在天墉城。

### 4.5 税

- **在下单事务里算好**,写进购买单;结算只读这几个字段,不再看当时的税率。
  所以改税率只影响之后下的单,多个 trade 副本滚动发布时也不会算出两种结果。
- 公式:`税 = ceil(成交额 × tax_bps / 10000)`,为了防溢出写成 `成交额 / 10000 × bps + ceil(成交额 % 10000 × bps / 10000)`;
  `卖家实得 = 成交额 − 税`。
- 配置校验:`0 ≤ tax_bps < 10000`,启动时检查 `max_unit_price × 4096 × tax_bps` 不会溢出 uint64。
- `卖家实得 ≤ 0` 就拒绝下单。比如单价 1 银两只买 1 个,税向上取整也是 1,卖家一分都拿不到。
- 税不发给任何人,等于直接销毁。Go、Java、客户端 C# 各写一个函数,三边共用同一组测试数据(包括「单价 1 × 1 个被拒」和向上取整的边界)。

## 7. 安全与防作弊

- 客户端只发三样东西:选了自己的哪些货、看到的价格和版本、请求号。所有判断都在服务端重做一遍。
  客户端不提交物品原件,也不报告"我已付款"。
- 能摆什么由白名单决定,默认是空的,也就是一律不能摆(默认拒绝)。
- 一人一摊、摊位点唯一、处理中的购买数上限,都在提交事务里靠主键或行锁保证,不只靠预检(AGENTS §11.3)。
- 不能买自己的摊。同账号小号之间互买(用来转钱)一期不拦(交易服务能不能拿到账号还没核实),
  靠全量流水和大额告警事后追查。
- 摊位名走角色名那套校验(字符白名单 + 敏感词)。
- 开摊时只检查"人在自己区的天墉城",不检查"人站在摊位点旁边"(交易服务拿不到坐标,坐标本来也是客户端报的)。
  改客户端的人最多能在城里稍远的地方开摊,没有经济上的好处。

## 8. 一期不做 / 二期

1. 补货、单格下架。一期只能改价,或者整摊收摊再重开。
2. 收购摊(买家先冻结钱求购),工作量接近再做一套托管。
3. 全服搜索、远程购买(那就是寄售市场)。
4. 「买到后 N 小时内不能再卖」、珍品公示期、开摊等级门槛(Q13、Q16)。
5. 服务端推送,一期客户端轮询(§4.6)。
6. 宝宝上摊:引擎已经支持宝宝原件托管,但开摊协议的货位里没有宝宝字段,摆摊开关里也没有宝宝开关,要改协议(两个版本同批)。
7. 卖出提醒:一期看「我的摊位」里的成交记录,以及到账时现有的货币变动提示。
8. 摆摊专用流水类型 `TX_STALL_*`(§4.9)。
