## 6. 助手完整正式答复

明白，你问的是：**怎么提高自己的编程思维，让代码考虑得更周全，少漏条件、少出逻辑漏洞。** 刚才我理解偏了。

这项能力可以刻意练习。我建议你先养成一个习惯：**写代码时，除了想“怎样才能做成”，还要追问“我凭什么认为这样一定成立，有没有反例”。**

比如一个很普通的扣道具逻辑：

```python
if owned_count >= consume_count:
    owned_count -= consume_count
```

正常输入下看起来没问题。但如果 `consume_count = -3`，扣除就变成了增加。

这里漏掉的是一个没有说出来的前提：**扣除数量必须是正整数。** 很多“不够严密”，就藏在这种默认前提里。

我建议按下面四个习惯练。

**① 写之前，先用几句话说清“什么叫正确”。**

以扣道具为例：

- 输入要求：扣除数量必须是正整数。
- 成功结果：数量准确减少指定值。
- 失败结果：数量不足时明确报告失败，原数量不变。
- 始终成立的规则：道具数量不能为负。

这些分别对应“前置条件、后置条件、不变量”。名字不用急着记，先练习把这几句话写出来。

如果连“失败后应该怎样”都还没想清楚，就说明现在开始写实现，容易把模糊的地方随手决定掉。

**② 按类别找反例，别只凭感觉多想一想。**

给自己固定一张检查表：

| 遇到的东西 | 主动检查什么 |
|---|---|
| 数字 | 0、负数、最小值、最大值、溢出 |
| 集合 | 空集合、只有一个、重复元素、首尾位置 |
| 条件判断 | 小于、恰好等于、大于；多个条件同时成立 |
| 查找操作 | 找不到、找到一个、找到多个 |
| 修改数据 | 中途失败后，是否已经改了一半 |
| 有状态的功能 | 第一次调用、再次调用、调用顺序改变 |

**只挑与当前功能有关的项。** 比如没有共享状态的简单函数，就不必硬套并发问题。

这相当于给思考安装一个检查清单，减少对“今天够不够细心”的依赖。

**③ 读自己的代码时，逐步解释“为什么”。**

例如：

```python
if owned_count >= consume_count:
    owned_count -= consume_count
```

你应该能解释：

> 已知原数量非负，扣除数量为正，并且扣除数量不超过原数量，所以扣完后数量仍然非负。

如果解释过程中冒出“这里应该不会为空”“别人应该已经检查过”“正常不会走到这里”，就把它圈出来，再确认：

**这是有明确保证的前提，还是我自己的猜测？**

已经由类型、构造函数或调用约定保证的事情，可以依赖它；没有保证的，就需要补上约束或处理。严谨也不意味着每一层都重复塞满检查。

**④ 每次修 bug，都提炼成一条以后能复用的问题。**

例如：

- 这次少写一个 `=` → 下次每个阈值都检查“恰好等于”。
- 这次改到一半才报错 → 下次检查“验证和修改的顺序”。
- 这次两个布尔值出现矛盾组合 → 下次考虑用一个明确的状态表示。

这样积累的是检查方法，后面遇到不同功能也能用。

你最初问的“有没有专门教这个的文章”，有，下面三篇比较对口：

1. **[MIT：Testing——如何系统地挑选测试用例](https://web.mit.edu/6.005/www/sp16/classes/03-testing/)**  
   **最建议先读。** 重点看 *Choosing Test Cases by Partitioning* 和 *Include Boundaries in the Partition*。它教你把输入分成不同类别，再检查边界，正好解决“我总是想不全有哪些情况”。英文，配有简单例子和练习。

2. **[MIT：Specifications——把函数的行为约定说清楚](https://web.mit.edu/6.005/www/sp16/classes/06-specifications/specs/)**  
   教你说明调用前需要满足什么、调用后保证什么、哪些数据会被修改。适合练习“先把正确性想清楚，再写实现”。

3. **[微软：在域模型层中设计验证](https://learn.microsoft.com/zh-cn/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/domain-model-layer-validations)**  
   中文。重点看前半部分“不变量”和修改地址的反例：代码先改了几个字段，后面验证失败，结果对象已经改坏了一半。虽然示例是 C#，这个思考方法适用于其他语言。

**最实用的练法：每天挑一个自己写的小函数，先写行为约定，再列边界和反例，最后对照代码检查。** 先自己做一遍，再让 AI 补漏，并要求它给出具体输入和执行过程。你练到的就是“自己发现漏洞”的能力。
