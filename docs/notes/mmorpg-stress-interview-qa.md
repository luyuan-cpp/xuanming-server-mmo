# MMORPG 项目压测容量与瓶颈优化面试回答

整理日期：2026-10-18。用于回答“游戏压测怎么做、上限怎么定、遇到什么瓶颈、怎么突破”。下面的口述稿基于本仓 C++ 节点与 Go 微服务版的历史压测，案例主要发生在 2026 年 5—6 月。独立 Java 版没有复用这些实测结论。

面试时先讲两分钟口述稿，再根据追问选择案例展开。历史轮次的指标有观测窗口、缓存命中和重试差异，数字均保留原指标名称与适用范围。

Go、MySQL 并发扣款与受影响行数、事务与锁、Redis 超时任务及 Big Key、pprof、Kafka 顺序与幂等等基础追问，见 [Golang 后端面试详细问答](golang-backend-interview-qa.md)。

## 两分钟口述稿

> 我的项目是多 zone 的 MMORPG 服务端，C++ Gate 和 Scene 负责连接与场景，Go 服务负责登录、场景编排和数据处理，HTTP 入口是 Java Gateway。
>
> 我们做过 2.5 万和 4.5 万机器人配置档位的登录进场压测。这些数字代表配置规模；稳定在线和单场景同屏，需要分别验证。
>
> 排查时先看机器人失败和延迟，再拆 EnterGame 的 preload、apply，继续看缓存检查、Kafka 发送、等待回执和场景编排，同时对照 DB 处理量和 Kafka lag。
>
> 典型问题是扩大 MySQL 池后，延迟下降，积压仍然很高。查消费循环才发现 partition 内还是串行处理。后来在同一 partition 内按玩家 key 分子队列，不同玩家并行，同 key 串行。对应轮次末次 lag 从约 8 万降到约 4 千，代表当时的积压改善，容量倍数还要同口径验证。
>
> 还遇到过 Pub/Sub 接收端同步 LPOP，数据写好了回执却在排队，以及场景编排同步等待旧节点释放。我们推进回执异步处理并收敛为有界 worker，释放操作也改为异步派发。包含释放异步化的那轮，apply 成功样本平均约 418ms 降到约 67ms，随后加载链又暴露出压力。
>
> 继续突破上限，就找下一个饱和点再复测。正式定容量，还要按真实行为和热点分布验证尾延迟、错误率、tick 和数据正确性，确认队列不持续增长，并按故障和扩容时间留余量。

## 怎么回答上限是怎么定的

### 先说清本项目已经测到什么

历史 45k 复盘记载的单 zone 拓扑是 2 个 Gate、4 个 Scene，login、db、data_service、scene_manager、player_locator 各 1 实例，加 1 个 Java Gateway。这个拓扑来自当时的测试记录，不代表后续每一轮部署都完全相同，也不替代机器 CPU、内存、磁盘及网络配置。

R18 记录了 18 分钟观察窗口。`conn`、`login_ok`、`enter_ok` 是累计事件计数，包含重新连接或重复尝试的影响；例如累计连接数可以超过配置的 45,000 个机器人。现有记录没有提供足以认定 45k 满员稳态容量的同时在线曲线和持续达标证据。

历史负载偏重登录、进场与轻量动作，没有覆盖真人移动、AOI 密集同步和热点战斗的完整负载。当前 stress profile 配置的动作权重为施法 85、切场 15、间隔 5 秒，但施法可能因没有技能或目标而不发送，不能换算成每个机器人实际战斗请求率；当前代码也不能反向证明每个历史轮次的行为。

可以直接说：

> 目前有证据的是这些配置档位下的登录进场压测，以及各轮瓶颈的改进。稳定在线上限和单场景同屏上限，需要按各自负载再验证；我不会直接用累计登录量来报在线容量。

来源：[45k 压测拓扑](../stress/stress-1zone-45k-2026-05-partition-10.md)、[R18](../stress/stress-1zone-45k-2026-06-04-round18.md)、[容量模型的口径说明](../design/capacity-model-hok-scale.md)、[动作配置](../../robot/logic/ai/action.go)、[机器人动作实现](../../robot/logic/ai/robot_ai.go)。

### 再说明完整的容量验收方法

下面是继续验收容量时采用的方法，不能把尚未执行的部分说成历史成绩。

1. 固定版本、机器资源、部署拓扑、数据规模和冷热缓存条件，定义新老玩家比例、操作频率、场景分布及同屏密度。
2. 阶梯加压，每档保持到足以观察多次存盘、定时清理等周期；在最后达标档与首个失败档之间细化负载，给出已验证范围。
3. 用玩家体验和正确性定判据：登录与操作的 P95/P99、错误率、场景 tick 超时、状态及资产正确性。当前 Scene 线程设计记载逻辑帧间隔约 33ms，验收时需要确认实际配置并预留帧内余量。
4. 检查队列是否持续增长、内存是否持续上涨，以及降压后能否按预定时间恢复。Kafka 在停压后归零，只说明最终追上，不能证明运行期间没有排队。
5. 验证登录突发、玩家集中、节点故障和扩容等待，再确定开服放行人数。预留比例要能由故障模型解释。

本仓已有的过程约束是：保留上一轮 `prev-summary.txt` 基线，按统一脚本汇总，采集 ramp 完成、稳态中段和末段快照，并做二维对照。历史复盘只使用既有汇总及复盘材料；新压测按 [AGENTS.md §6](../../AGENTS.md) 执行。

来源：[Scene 线程模型](../design/scene-node-threading-model.md)、[登录排队压测手册](../ops/login-queue-stress-runbook.md)、[汇总脚本](../../tools/scripts/stress_summarize.ps1)。

## 案例一 数据库连接池扩大后仍然积压

### 可以直接说

> 一开始我们怀疑 MySQL 连接池不够，把最大连接数从 10 调到 30 后，成功路径的平均等待确实下降，但 Kafka 仍有大约 8 万条积压。继续查代码发现，每个 partition 只有一个 worker，整个批处理链串行执行，连接池再大，也不能让这个 worker 同时处理不同玩家。
>
> 我们在 partition 内增加了 4 个子队列，按玩家 key 固定路由。在同一 Kafka partition 内，不同玩家可以并行，同 key 的写、读和批量合并仍然在同一子队列执行。对应轮次积压降到约 4 千，机器人最大登录耗时也下降了。这说明要同时检查资源池和实际执行并发。

### 怎么定位和优化

历史处理链是 Kafka partition → worker → MySQL 访问 → Redis 回写及通知。扩大连接池没有消除积压，于是检查 `worker.start`，发现它同步调用 `processTaskBatch`，每个 partition 的任务仍串行处理。

当时的改动是 `SubShardCount=4`，在同一 Kafka partition 内按 `task.Key` 固定分片。同 key 的任务由同一个子队列串行执行，读任务在该队列中等待前面的写完成。这只是分区内部的顺序保证；现行分区契约还记录了历史 Go 与 C++ 生产者曾用不同算法，子队列改造本身不能保证跨生产者的同玩家读写一定落到同一 partition。

| 历史指标 | R6 连接池调整后 | R7 增加子队列后 |
|---|---:|---:|
| Kafka 末次记录 lag | 80,055 | 4,233 |
| robot 最大登录耗时 | 571ms | 209ms |
| EnterGame 累计失败占比 | 约 29% | 17.8% |

这些是对应轮次的观测结果。R6 带有旧积压，轮次时长等条件也有差异，不能据此宣称严格的吞吐或稳定在线提升倍数。R7 仍有内部失败，机器人最终失败为零也不能证明所有玩家请求都没有经历等待或重试。

**继续追问并发正确性时：**固定 key 路由的保证有范围：同一个路由规则和执行属主内可以保序；跨进程、再平衡、变更子队列数还需要单独处理在途任务交接及存储围栏。旧报告中的 4 路是当时的配置，不是当前调优推荐值。

来源：[连接池调整复盘](../stress/stress-1zone-25k-2026-05-28-maxopenconn.md)、[子队列复盘](../stress/stress-1zone-25k-2026-05-28-subshard.md)。当前顺序与交接约束见 [存盘管线](../design/db-task-pipeline-bottlenecks.md)、[消费组交接](../design/db-consumer-group-per-zone.md)。

## 案例二 数据已经写好 回执仍在排队

### 可以直接说

> 有一轮机器人最终没有报入场失败，但服务端 preload 仍然大量超时。我们把缓存检查、Kafka 发送和等待回执拆开看，发现主要时间花在 callback_wait。沿着返回链检查，数据库结果已经写到 Redis，Pub/Sub 的接收协程却在逐条同步做 LPOP。
>
> 接收循环每收到一条通知都等待一次 Redis 往返，负载高时后面的通知不断排队，等处理到时回调可能已经过期。我们先把 LPOP、解码和回调移出接收循环，后续再采用有界 worker 和队列控制并发，避免异步任务无上限增长。

### 定位证据和修改过程

当轮记录的 `callback_wait` 成功样本为 2,437、失败样本为 44,444。约 95% 是这个阶段样本中的失败比例，EnterGame 累计失败占比另为 17.8%，二者分母不同。

旧接收循环包含同步 LPOP，历史诊断记录单次往返约 5—10ms。按 5ms 作量级估算，串行每秒处理约 200 条就没有余量；这解释了为什么数据库能完成，通知派发仍可能跟不上。该估算只针对当时的串行链路，不能当作 Redis 的通用性能上限。

第一次改动让接收循环只取走回调登记，耗时处理异步执行。后续 R15 又把无界 goroutine 改为 16 个 worker、容量 4,096 的队列，并联动 DB 并发和等待预算。

### R14 和 R15 的整批观察结果

| t18m 指标 | R14 | R15 |
|---|---:|---:|
| `callback_wait{success}` 平均 | 274.5ms | 31.4ms |
| `preload_failed` 累计 | 3,663 | 0 |
| `apply_failed` 累计 | 0 | 1 |
| EnterGame success 累计 | 84,706 | 45,764 |

R15 同时修改了 DB 子队列数 4→8、MySQL 最大连接数 30→60、回调 TTL 5→8 秒和有界 worker；两轮成功处理的累计量也不同。因此可说“整批改造后的该轮回执等待下降、preload 超时为零”，不能把收益单独归因给 worker 池，也不能只凭零超时认定延长 TTL 没起作用。`preload_failed=0` 同时不等于全链路零失败。

**继续追问队列满了怎么办时：**有界池需要明确饱和行为、超时、取消及恢复方式，并保留可观测性；只把积压从 Kafka 移到进程内存，不能算解决容量问题。历史的 16/4096 需要随新负载重新验证。

来源：[串行 LPOP 诊断](../stress/stress-1zone-25k-2026-05-29-dispatcher-async-lpop.md)、[R14 原始汇总](../stress/prev-summary-round15.txt)、[R15 联动改造](../stress/stress-1zone-45k-2026-06-01-round15.md)。

## 案例三 场景编排同步等待拖长入场

### 可以直接说

> 我们还遇到过数据加载已经较快，入场 apply 仍然慢的情况。继续拆场景编排，发现 `dispatchReleasePlayer` 同步等待下游释放，等待预算到 500ms，拖住了当前链路。后来把释放派发改成异步，并记录异步处理结果。
>
> 包含这项修改的 R14，apply 成功样本平均从 417.7ms 降到了 66.5ms。不过同轮 preload 又出现 3,663 次失败，说明编排等待减少后，下游加载链的压力变得更明显，需要继续优化。

### 数据和设计边界

| t18m 指标 | R13 基线 | R14 |
|---|---:|---:|
| apply 成功样本平均 | 417.7ms | 66.5ms |
| preload 失败累计 | 0 | 3,663 |

R14 还包含日志降噪等改动，表格属于整轮前后观察。这里的 apply 平均不能替代客户端完整进场延迟，也不能根据累计 success 数直接声称在线容量提升。

**继续追问异步是否影响一致性时：**先确定接口承诺的是“请求已派发”还是“玩家已释放”。异步派发不能把资产、所有权和路由的提交条件提前当作成功；需要确认的状态仍应通过应答、屏障或状态机处理，失败必须可追踪。这个案例的性能数字只证明对应阶段的观测变化，不代替迁移正确性验收。

来源：[R14 释放异步化复盘](../stress/stress-1zone-45k-2026-06-01-round14.md)、[R13 基线汇总](../stress/prev-summary-round14.txt)。

## 案例四 Kafka 配置正确但实际分区没有全部认领

### 可以直接说

> 还有一次我们发现配置里是 10 个 partition，实际消费却没有用满。我们分别核对生产端配置、broker 元数据和 consumer assignment，发现当轮 broker 已有 10 个分区，consumer 只认领了 partition 0。
>
> 回看启动顺序，DB 先启动时 topic 被自动创建成 1 个分区，Login 后启动再扩到 10。我们让 DB 在订阅前也完成 topic 初始化校验，避免依赖生产端先启动，并增加分区认领不足告警。历史后测认领数从 1 变成 10，但全链路仍有其他超时，所以我们继续往后排查。

### 可引用的数据

历史验证表记录：认领分区数 1→10，最大分区 lag 约 2,400→13。这支持当轮消费覆盖恢复，不能扩展成“Kafka 加分区必然线性扩容”。

原文的完成计数 427→4,596 缺少同长观测窗口，不作为“吞吐提升 10.7 倍”的证据。也不把当轮现象泛化为 Sarama 永远不会发现新增分区。

**继续追问能否在线加分区时：**本项目现行 DBTask 契约禁止在同一 topic generation 原地增加分区。扩容必须停写、排空旧 generation 的 Kafka 及重试任务、处置未决死信，再切换新 generation。分区数变化会改变同 key 的路由，旧分区尚有任务时，新旧任务可能并行执行；历史开发期修复不能作为在线扩分区的操作建议。

来源：[分区未认领复盘](../stress/stress-1zone-45k-2026-05-31-db-kafka-partition-starvation.md)、[当前分区契约](../design/db-task-kafka-partition-contract.md)。

## 案例五 TCP 连接正常但 Gate 控制命令停滞

### 可以直接说

> 有一轮玩家能连上 Gate，EnterGame 也能应答，但一直等不到 scene ready。我们没有停在“登录接口成功”这一层，而是继续查绑定和路由命令。现场记录里 Gate 消费组出现无活跃成员，命令 lag 曾到一万七千多，玩家记录里 `scene_notified` 还是零。
>
> 查代码发现 Kafka poll 和 TCP accept、RPC 回调共用 EventLoop，消费驱动会受到主循环负载影响。后来把 Kafka 拉取移到独立线程，业务回调通过 `queueInLoop` 回到原业务线程，保留 ECS 的线程归属。

### 怎么解释根因和结果

当轮记录了 `scene_ready_timeout=23,784`，preload 失败占比约 0.6%。这些现象说明要把“TCP 连通、登录应答、数据加载、路由绑定、场景就绪”分开观察。

改动还包含 consumer 参数、空 GroupID 保护和服务发现日志降噪。该篇复盘把后测列为待验证，不能单独报这项改动带来的容量增长。关于失活原因，口述限定为“观察到消费组失活、命令积压，代码存在共用主循环的驱动耦合”；当时没有足够的 poll 间隔测量来证明具体哪次停顿触发了超时。

旧文中的 `gate-1`、`gate-group-1` 是历史 topic 和 group 名称。当前节点命令已有共享分区寻址，不能把旧名字讲成现行架构。

来源：[Gate 消费链复盘](../stress/stress-1zone-45k-2026-05-30-gate-kafka-consumer.md)、[当前控制面 topic 分区](../design/control-plane-topic-partitioning-20260908.md)、[当前 Scene 线程归属](../design/scene-node-threading-model.md)。

## 案例六 排队放行时过早签发 Gate token

### 可以直接说

> 压测还暴露过一个生命周期问题：排队系统在放行时就签 Gate token，但客户端是轮询取结果，拿到 token 后还要建连接和验签。前面的等待会消耗 token 有效期，负载高时就更容易过期。
>
> 我们把签发点后移到客户端取走放行结果时。R17 到 R18，18 分钟时累计 login_fail 从 1,000 降到 504，但仍然没有归零。后续又调整有效期和重试计数，并给 token 重取设置次数上限，避免无限重试掩盖故障。

### 这组数字能证明什么

| 指标 | R17 | R18 |
|---|---:|---:|
| t18m 累计 login_fail | 1,000 | 504 |
| t18m robot max_login | 8.468s | 9.398s |
| t18m EnterGame apply 平均 | 36.0ms | 36.0ms |

可表述为“累计登录失败次数下降约一半，修改部分生效”，不能说登录失败率减半或所有延迟都改善。后续延长 TTL、重试计数调整和最多 20 次 token 重取是另外的改动，R18 文档仍把其 R19 验证列为待执行。

原文 `now-expire` 的 66 秒、403 秒是已经过期的时长，不能当成剩余有效期或签发到验签的耗时。延长 TTL 本身也不增加处理吞吐，还会改变票据有效窗口，需要与身份、用途、目标及重放约束一起考虑。

来源：[R18 token 签发时机复盘](../stress/stress-1zone-45k-2026-06-04-round18.md)、[R17 服务端汇总](../stress/prev-summary-round18.txt)。

## 补充案例 先排除发压端限制

### 可以直接说

> 我们也踩过发压端的坑。机器人登录会连续请求 HTTP 登录和分配 Gate，如果连接复用不好，就会增加连接创建、销毁和临时端口消耗。我们检查了客户端 Transport，改为进程共享 HTTP 客户端并增加空闲连接保留。这个经历让我在宣布服务端到顶之前，先确认发压机的实际发送速率、连接状态和资源占用。

当前机器人 HTTP Transport 的空闲连接池参数可在 [http_client.go](../../robot/http_client.go) 核对；历史复盘记录了共享连接池调整，但没有隔离这项修改的吞吐对比，因此不报提升倍数。`MaxIdleConnsPerHost` 控制空闲连接保留，不能解释为每个 host 的最大并发请求数。

临时端口复盘记录了调优前后的失败和耗时变化，但同文仍保留异常出现在哪台机器待确认的问题，不能说已经严格证明是 Gate 或 robot 某一侧端口耗尽。另一次 HTTP mock 测试采用每请求启动 curl 进程，进程创建成本是当时的诊断方向，也缺少替换发压器后的隔离对照。

来源：[三 zone 复盘](../stress/stress-3zone-2026-05-23-postmortem.md)、[临时端口复盘](../stress/stress-test-2026-05-ephemeral-port.md)、[HTTP 登录测试](../stress/stress-test-2026-05-http-login.md)。

## 面试官问还能怎么突破上限

可以这样回答：

> 我会先确认要提高的是登录速率、全服总在线，还是一个场景的同屏人数。登录和数据链可以继续检查同步往返、按 key 并行度、回执投递、批处理和共享依赖；多个独立场景可以分配到更多 Scene 节点。单个热点场景则要看业务主线程、AOI 查询、变化集同步和广播扇出。每项都需要 profiling 或压测支持，再做前后对照。

| 下一步方向 | 本项目需要守住的边界 |
|---|---|
| 增加 Gate 或 Scene 实例 | Gate 有长连接和会话状态；Scene 有权威 gameplay 状态，需要明确分配、重连、迁移和排空 |
| 增加 DB 与回执并发 | 保留同玩家顺序、幂等和围栏；检查 SQL、Redis、Kafka 是否成为新的瓶颈 |
| 减少同步等待和重复 I/O | 保留接口的成功语义；回调要处理取消、超时及对象生命周期 |
| 优化单场景热点 | 先量出 tick 中各阶段成本；当前 Scene 业务状态归属一个 EventLoop，不能直接并发写同一 ECS |
| 优化 AOI 与下行 | 检查候选查询、变化集、重复编码和扇出；降低频率或可见范围时要明确体验变化 |
| 拆分或减少共享依赖访问 | 按当前拓扑核算 Redis、etcd、数据库、Kafka 的总量与热点，新增节点后重新验收 |

以上属于进一步优化方向，历史 45k 登录测试没有证明 AOI、真人战斗或跨区域容量收益。千万在线等目标来自容量规划，不能当作压测成绩。

来源：[容量规划](../design/capacity-model-hok-scale.md)、[Scene 线程模型](../design/scene-node-threading-model.md)、[AOI 设计](../design/aoi_priority_design.md)。

## 常见追问的直接回答

### CPU 没满为什么已经到上限

> 我会看线程和依赖。一个场景主线程、一个串行 worker、一条回执消费链，或者数据库锁和连接等待，都可能先到边界。全机平均 CPU 会把这种局部饱和掩盖掉。本项目的 partition 内串行处理，就是连接池扩大后仍然积压的例子。

### 加一倍机器是不是就能多一倍玩家

> 要看负载能否独立分配，以及共享依赖还有没有容量。不同场景可以横向分摊；同一个热点场景还受它的权威状态、计算和广播成本限制。增加业务节点后，也要重测 Redis、数据库、Kafka 和注册发现的总负载。

### 为什么不直接加大连接池和线程池

> 先确认调用链是否真的有可并行任务。本项目扩大 SQL 池后，partition 的串行循环仍然限制执行并发。池变大还可能增加数据库争用和排队，所以需要同时看实际并发、等待时间、下游容量与状态顺序。

### 把超时改长一点是不是就好了

> 延长等待预算可以减少一部分超时报错，但处理能力没有因此增加，队列可能继续增长。本项目 callback_wait 的问题需要继续处理串行回执和消费并行度。调整 TTL 要连同端到端预算、取消和锁生命周期一起验证。

### 机器人零失败为什么还要继续查

> 重试可能把阶段失败掩盖掉。历史某轮 robot 最终失败为零，但服务端仍有大量 preload 失败。还要看首次成功率、重试次数、完整完成时间和内部各阶段失败，确认体验与服务端成本。

### 成功请求平均很快 能不能证明性能好

> 要同时看成功和失败的样本数。大量慢请求超时退出后，只统计成功样本会显得很快；不同缓存路径的平均值也不能混用。历史 preload 均值和 callback_wait 均值来自不同样本，不能简单相加或当成同一条请求的阶段耗时。

### 你能给一个确定的容量数字吗

> 我能给出历史测试的配置档位、拓扑、观察窗口及对应指标。4.5 万机器人档位的登录进场测试有记录；45k 满员稳定在线、真人高密度战斗和单场景同屏上限，目前这些记录还不足以定数。正式结论需要附上行为模型、实际同时在线曲线、尾延迟和持续达标时间。

### 怎么让下一轮结果更可信

> 先保存上一轮汇总，固定版本、资源、数据和缓存条件，明确实际输入。尽量每轮只改变一个主要因素，不能隔离时就按整批改造报告。分阶段采样，使用统一汇总，对比吞吐、尾延迟、失败和积压，同时确认发压机没有先饱和。历史的 R15 就应按整批效果描述。

## 面试时使用数字的口径

| 记录里的量 | 可以怎么说 | 不能替换成什么 |
|---|---|---|
| `robot_count=45000` | 配置的机器人规模 | 满员稳定 CCU、45k 同屏 |
| 累计 `conn`、`enter_ok` | 连接或成功事件次数，可能受重连及重试影响 | 独立玩家数、每秒吞吐 |
| 某阶段 success 平均 | 该阶段成功样本的平均耗时 | 全请求 P99、玩家完整进场耗时 |
| 末次 lag | 该时刻的积压 | 全程无积压、固定吞吐上限 |
| `login_fail` 累计下降 | 同观察时点的失败次数下降 | 未知分母下的玩家失败率下降 |
| 多项一起修改后的指标变化 | 整批改造在该轮的观察结果 | 某一个补丁的独立收益 |
