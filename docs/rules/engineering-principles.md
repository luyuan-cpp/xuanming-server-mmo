# 工程设计与编码原则

> 对应根索引 [AGENTS.md §11](../../AGENTS.md#11-工程设计与编码原则强制)。适用于新增、修改、重构和评审。“成熟工程团队标准”是模块接口清楚、接缝明确、改动可审、结果可验证，不是堆设计模式、层数、文件数或框架。

原则冲突时按以下顺序取舍：

`正确性 / 安全 / 数据一致性 / 向后兼容 > 简单 / 可读 / 与仓库一致 > 可维护 / 可测试 > 有数据支撑的性能 > 假想扩展`

已经文档化的 SLO、容量上限和 per-tick 热路径预算属于正确性约束，不降级为普通性能偏好。偏离本文件原则必须有当前需求或证据支撑，并在代码注释、设计文档或交付说明中记录原因与代价。

## 1. 模块与职责（§11.1）

- **单一职责（SRP）**：一个模块只对一种变化原因或一类业务角色负责；这不等于“一个类只能有一个方法”。总是一起变化的规则放在一起，独立变化的策略、存储、传输和副作用分开。
- **高内聚、低耦合**：相关状态与行为就近收口；模块只了解完成职责所需的信息，依赖单向且不得形成循环。
- **信息隐藏与深模块**：用小而完整的接口隐藏验证、顺序、错误模式、配置与性能细节。承担协议转换、隔离外部依赖或稳定接缝的薄适配器有明确价值；避免没有隔离、转换或契约价值的连续透传层、万能管理器和需要调用者拼装内部步骤的接口。
- **接口是完整契约**：除类型外，还必须明确输入约束、不变量、顺序、所有权、错误、超时、幂等、线程模型和性能特征。调用者不依赖未承诺的实现细节。
- **开闭原则（OCP）**：面对已经确认且反复出现的变化轴，在接缝后增加适配器，避免每个新变体都修改全部调用者；扩展点必须受真实需求约束。
- **里氏替换（LSP）**：任何实现或子类型替换后都保持接口契约，不得加强前置条件、削弱后置条件或改变错误语义。
- **接口隔离（ISP）**：调用者只依赖自己需要的能力；但不得机械拆成大量单方法接口和透传层。
- **依赖倒置（DIP）**：业务策略不依赖数据库、网络、框架或全局单例的具体细节；依赖在清晰接缝处注入。
- **组合优于继承**：优先组合可替换行为构建能力；继承只用于真正稳定的 is-a 契约，避免复杂、脆弱且难以局部替换的继承树。
- **23 种经典设计模式的使用原则**：如果某个结构确实适合用 GoF 23 种设计模式（如策略、状态、工厂、适配器、责任链、观察者、装饰器、模板方法、命令等）来解耦、消除巨型 `if/switch` 分支或隔离明确变化轴，**主动采用或向程序建议采用，并明确告诉程序为什么用这个模式**（解决了什么具体耦合/扩展/维护痛点、替代了什么更糟的写法）；严禁为了套模式而无故堆砌抽象层。
- **系统 / 模块间消息通信（Actor 隔离，强制）**：
  - **状态私有**：每个业务系统 / 模块（如场景、战斗、背包、社交、公会等）独占自身可变状态，禁止跨模块直接读写内部字段，禁止在消息中传递可变对象引用或裸指针（避免“假隔离”导致并发踩内存）。
  - **不可变消息驱动**：跨系统、跨线程、跨进程交互一律通过显式定义的**不可变消息**（Mailbox 投递 / 领域事件 / RPC / Kafka）通信，严禁跨模块直接同步调用内部实现，也禁止通过全局单例、静态变量或共享缓存绕过消息通道。
  - **串行消费与防错**：每个 Actor / 所属 EventLoop 在自身线程或队列中串行消费收到的消息，靠消息所有权与幂等键保证一致性，而非跨模块加锁；跨模块消息契约须显式处理超时、乱序与重复投递。
  - **作用边界清晰（防过度设计）**：上述约束适用于**系统 / 模块之间与跨线程、跨进程边界**；单个模块内部仍用正常直接方法调用，**严禁把模块内部普通函数或内聚逻辑无意义地拆成消息**。

## 2. 简单、标准、可读（§11.2）

- **KISS**：选择满足当前需求的最简单完整方案。优先标准库、仓库现有模式和团队已采用的成熟依赖。
- **第三方开源库选型（先标准库，再找同语言 GitHub 高 Star，交由程序决策）**：
  1. **标准库与现有依赖优先**：先用当前开发语言的标准库和仓库已有成熟依赖；能用标准库简洁解决的，不引入新第三方库。
  2. **按当前开发功能的语言去 GitHub 找同语言成熟库**：标准库没有、且用成熟开源库比手写更稳妥时，**开发什么语言的功能就找该语言的库**（C++ 功能找 C++ 库、Go 功能找 Go 库、Java 功能找 Java 库、C# 功能找 C# 库、Python 功能找 Python 库），优先选该语言同类头部高 Star、近期活跃、安全无高危漏洞、许可证兼容的项目（Star 门槛随该语言生态体量浮动，例如 Go / Java / Python / JS 大生态通常参考 ≥ 2 万 Star，C++ / C# 游戏细分等生态体量较小则不死卡 2 万，按该语言同类头部综合评估）。
  3. **交由程序决定并说明原因**：不擅自默默引入新依赖，把候选库与“是否自研”交给程序决定，并清楚说明为什么（标准库或现有能力缺什么、该库解决什么核心痛点、引入成本/维护与安全风险、以及替代方案对比）。安全永远优先于 Star 数（存在已知高危漏洞或已停维的库直接排除）。
- **YAGNI**：不实现没有调用者、验收标准或近期计划的能力；扩展性以真实变化为依据。
- **DRY**：一条业务知识只有一个权威来源。只消除会共同变化的重复，不因几行形似代码就过早抽象。
- 控制流保持直线化：优先早返回和小范围变量，减少无必要的深层嵌套、隐藏跳转和跨层回调；函数保持同一抽象层级。
- 命名清晰易懂、语义准确并标明单位（见 [naming-and-boundaries.md](naming-and-boundaries.md)）。注释解释“为什么、约束和风险”，不复述代码“做了什么”。
- **显式依赖**：依赖通过参数、构造函数或装配层传入；时间、随机数、I/O 和副作用必须显式可见。限制全局状态、静态可变状态和隐式初始化顺序。
- **非必要不写宏定义（C++ 强制）**：宏定义晦涩难懂、破坏 IDE 跳转、让编译报错指向展开处而非源头、且调试器看不到真实符号。**凡是能用 `constexpr` / `consteval` / `inline` 函数 / 模板 / 普通枚举 / `using` 写清楚的，一律不写宏定义**；特别严禁 X-macro（`#define FOO_LIST(X) X(a) X(b)` 再展开成枚举 / 数组 / switch）以及任何“用宏拼出声明”的写法。
  - **正确做法**：需要枚举与名称/属性表同步时，写普通枚举 + 一张平铺常量表，用 `static_assert(数组长度 == 枚举 kCount)` 保证两者不脱节；枚举最后一项固定为 `kCount`。示例见 `cpp/libs/modules/id_segment/guid_segment_registry.{h,cpp}`（`GuidKind` + `kGuidKindNames`）。
  - **仅在确实无法替代的极少数场景才允许写宏**：① 头文件卫士（优先 `#pragma once`）；② 平台 / 编译器条件编译；③ 必须捕获 `__FILE__` / `__LINE__` 的日志与断言（C++20 优先 `std::source_location`）；④ **必须往调用方注入控制流**（`return` / `continue` / `break`）因而函数写不出来的守卫宏（例如 `cpp/libs/engine/core/macros/return_define.h` 的 `ECS_GET_OR_RETURN` 系列）。
  - 判据：**如果不用宏也能写，就绝不写宏；非写不可的宏必须写明理由。**
  - 枚举显式写出底层类型，宽度按**枚举项个数**选，不要跟着“被编号对象”的位宽走。典型误判：`GuidKind : uint8_t` 数的是 GUID 的**种类数**（现 3 种），与 guid 值本身是 `uint64` 毫无关系；真要放宽时先问一句：**这个数字最大能到多少？**
- **裸指针 / 原始指针使用约束（C++ 强制）**：避免悬垂指针、野指针与隐式所有权模糊，严格区分“持有”与“瞬时借用”：
  - **严格禁止**：① 类 / 结构体 / 联合体的**非静态成员**放裸指针（含 `const char*`、函数内局部结构体及测试夹具成员）；② **容器元素**存裸指针（如 `std::vector<T*>`、`std::unordered_map<K, T*>`）；③ 裸 `new` / `delete`（所有权一律走 RAII 与 `std::make_unique` / `std::make_shared`）；④ **业务函数主动返回裸指针**（改用值、引用、`std::optional<...>` 或智能指针）。
  - **允许的有限场景（仅瞬时借用，严禁持有）**：
    - **函数参数**：允许传指针（如表达可空参数或对接既有/生成接口；只借用不转移所有权，非空场景优先用引用，严禁存入类成员或容器）。
    - **局部变量与唯一边界例外**：允许用局部原始指针接收外部返回，但**仅限**接收 **ECS 组件指针**（如 `entt::registry::try_get<T>()`）、**配置表行指针**（如 `*TableManager::Instance().FindById*(...).first`），以及调用无法改签名的外部/框架/生成代码/C API（如 Protobuf 生成的 `mutable_*()` 与 RPC 回调签名、muduo / 系统 C 接口）的返回值；**只允许在调用接缝处就地判空使用或立即转为引用/值，严禁存入类成员/容器，也不得继续向外层业务接口传递**。
  - **替代写法**：只读字符串用 `std::string_view`；连续数组视图用 `std::span`；非空借用用引用（`T&` / `const T&`）；可空借用成员用 `std::optional<std::reference_wrapper<T>>`；独占/共享/弱引用所有权用 `std::unique_ptr` / `std::shared_ptr` / `std::weak_ptr`。
  - **门禁与预检**：`.githooks/pre-commit` + CI `test_cpp_no_raw_pointer_member.py` 机械强制拦截**类/结构体/联合体非静态成员**（MSBuild 全量 Clang AST 门禁按需传 `/p:RunNoRawPointerMemberCheck=true` 触发，首错即停），其余条目由本规范与代码评审约束；交付前须跑 `python tools/scripts/tests/test_cpp_no_raw_pointer_member.py`，门禁口径、排除边界与拼接注意见 [cpp-runtime-and-build.md](cpp-runtime-and-build.md#c-类成员不放裸指针no-raw-pointer-member-门禁)。
- 改动保持小而完整、可独立审阅和回滚；不在功能改动中夹带无关格式化、重命名或顺手重构。

## 3. 正确性与生产质量（§11.3）

- 在系统接缝校验不可信输入；内部不变量尽早断言或显式失败。错误不得吞掉、伪装成功或静默降级；安全、权限、玩家资产和数据完整性路径默认 fail-closed。可用性优先的路径若选择 fail-open，必须记录风险依据并配套日志、指标和测试。
- 能在副作用前安全完成的纯校验应先完成；提交点仍须用同一并发控制机制原子复核权限、版本和状态，不能让预检代替提交校验。跨存储、跨服务或异步流程必须明确原子范围、提交点、回滚/补偿、重试与幂等语义。
- 重试只能用于可重试且幂等的操作，必须有超时、次数上限、退避与必要的抖动；支持取消并释放文件、锁、连接、线程与定时器等资源。
- 并发代码必须写清状态所有者、同步方式和生命周期；共享可变状态不得依赖“通常不会并发”的假设。进程内耗时和超时预算用单调时钟与截止时间；跨进程绝对截止时间使用协议约定的时钟和格式，并明确时钟偏差与过期语义。不得用“重试次数 × sleep”代替时间预算。
- 安全遵循最小权限、默认拒绝、纵深防御和敏感信息最少暴露；真实 secret、token 和密钥值不得硬编码或进入日志、指标、错误响应。主体标识只在确有诊断需要时最小化、脱敏并受控记录，不得外发给无权调用者。K8s 上工作负载的密钥只放 Secret：ConfigMap 与 `-DryRun` 输出里只出现变量名，经 `secretKeyRef` 注入，各档位同一条注入路径，细则见 `deploy/k8s/AGENTS.md`（2026-11-10~11）。
- 已发布协议、持久化数据、外部配置和滚动升级接缝优先向后兼容。破坏性变更必须有版本、迁移、灰度与回滚方案，并验证新旧版本并存窗口。
- 关键路径提供结构化日志、低基数指标和必要追踪；日志通过受控关联标识定位请求、阶段和结果，但不得使用 `player_id` 等高基数值作指标 label。
- 性能优化必须由 profiling、benchmark 或压测数据驱动；先修算法、I/O 和数据结构瓶颈，不以牺牲正确性和可读性换未经测量的微优化。
- **禁止用定时器掩盖时序问题**（移植自 `xuanming-server` `CLAUDE.md §16.10`）：Timer / Tick / Delay / `time.Sleep` 不得用于掩盖本可确定的依赖就绪或初始化顺序；判别口诀为**“到期后假设成功的是掩盖（禁止），到期后重查权威的是兜底（有界 deadline 必需）”**。
- **推送不承担正确性**（移植自 `xuanming-server` `protocol-ordering-rules.md`）：RPC 响应应自洽完整，异步推送不向发起者重复投递，且每个客户端展示状态必须具备权威查询拉取兜底（界面进入 / 断线重连 / 切前台 / 主动 resync / watchdog 触发），防止异步推送丢失导致状态永久漂移。
- **数据库广度与深度双守卫及默认只报告清理**（移植自 `xuanming-server` `CLAUDE.md §9.24`）：新增集合序列化列须控制写入侧字节上限（使用 `go/shared/dbguard.CheckPayload` 提供 80% 预警与超限 fail-closed），表行数与 `AVG_ROW_LENGTH` 走 `dbguard.Guard.Check` 估算观测不阻断启动，运维语义保留期清理默认 `report_only`（COUNT 与 DELETE 共享同一 WHERE）。
- **跨 zone 共享存储里的实例身份要集群内唯一；存活用租约，不周期写键**（2026-11-26）：写进 etcd、Redis 这类各 zone 共用的存储时，实例键用 `namespace/Pod 名`（或 Pod UID），不能只用 Pod 名，因为各 zone namespace 里的 StatefulSet 是同名的。实例存活用租约续期表达（etcd lease keepalive、Redis 续过期），状态值只在变化时写，写入量要和状态变化次数成正比，不和「实例数 × 时间」成正比。配置表热更的 sidecar 两条都踩过，见 [config-table-hot-reload.md](../design/config-table-hot-reload.md) §19 第 8、15 条。
- **有上限的资源和数据上限放在一起算；回退分清「本来没有」与「有但没拿到」**（2026-11-26）：卷的 `sizeLimit`、内存 limit 这类超了就驱逐或杀进程的上限，要和「单份数据上限 × 同时存在的份数」写成一个算式，放大时一起改。缺数据时回退到缺省数据，只限「本来就没有」；「有，但这一次没拿到」必须 fail-closed 并告警，不能静默退回旧数据。部署依赖运维预置的 Secret 这类外部前置条件时，在任何写操作之前只读核对（只看键名与长度，不读值）。见 [config-table-hot-reload.md](../design/config-table-hot-reload.md) §19 第 3、9、13 条。
- **崩溃与 P0 事故独立建档关闭门禁**（移植自 `xuanming-server` `CLAUDE.md §16.9`）：凡确认崩溃、runtime fatal、未恢复 panic、数据损坏/回档、脑裂或大面积不可用 P0，当次按 [docs/incidents/template.md](../incidents/template.md) 建档并登记 [docs/incidents/index.md](../incidents/index.md)，关闭审核清单全部满足前不得标记已关闭。

## 4. 测试与评审（§11.4）

- **面向接口测试**：接口同时是调用面和测试面。优先验证可观察行为与契约，避免测试私有实现步骤；测试替身通过同一接口注入。
- 缺陷修复原则上先写能稳定复现问题的回归测试；红/绿运行证据按 [ai-workflow.md](ai-workflow.md) 执行。确实无法先写时，必须说明原因并给出替代验证。
- 按改动风险覆盖正常、边界、失败、回滚、幂等、并发和兼容场景中适用的部分；测试必须确定、可重复。单元测试不得依赖执行顺序、真实墙钟或外部残留状态；集成测试必须隔离输入、限定等待并清理自身状态。
- 评审既检查代码，也检查遗漏的同类入口、调用点、生成源、配置、迁移、监控、文档和清理路径。新增状态或规则时必须搜索所有创建、读取、更新、迁移、销毁与恢复路径并逐项对齐。
- **文本契约测试跟着改名走**（2026-11-26）：`tools/scripts/tests/*_contract.tests.ps1` 里有大量按源码文本写的正则断言（成员名、函数签名、函数体里的调用顺序）。改成员名、函数签名或挪函数时，同批 `grep` 这些测试并改掉。不改的后果不只是跑起来变红：「不得出现」类断言（`Assert-NotMatch`）按旧名永远匹配不到，守卫空转且没有任何报错。2026-11-25 全仓去掉 C++ 成员尾下划线后，battle 准入契约测试有 21 处脱节、其中两条空转，就是这样漏掉的。复核别人改过的文件时，把契约测试里的断言模式取出来，在现代码上逐条匹配一遍（纯文本匹配，不算运行测试）。
- **同一次判定只取一次时刻**（2026-11-26）：函数收了 `now` 参数，就不在里面再取时钟；一次判定里的各个分支都用调用方给的那个时刻。两处各取一次，临界点上会得出相反的结论（一处判「已逾期」、另一处算出的年龄还不够），单测注入的时刻也管不到里面那一次。
- **多方共用的格式用真实产物测**（2026-11-26）：几个组件共用的文件格式、JSON 字段名、指标名与标签（导表器写的清单、业务进程写的状态文件、告警引用的指标），要定一个事实源（生成它的代码或类型），其余各方照它对齐；单测读仓里真实的产物或事实源类型，不读测试自己拼的形状。配置表热更的 sidecar 按对象解析清单，导表器写的是数组，单测用自拼的对象形状一直是绿的，线上一个包都下不来（[config-table-hot-reload.md](../design/config-table-hot-reload.md) §19 第 1 条）。
- **告警三核对**（2026-11-26）：加或改告警时逐条核对三件事。引用的指标和每个分组标签，在代码里真的写出；指标真有抓取路径（Pod 的 `prometheus.io/*` 注解只能指一个端口，sidecar 的端口要另配 PodMonitor）；判据要的是「现在的状态」还是「发生过的事件」，状态用 gauge，不拿 counter 的 `increase` 去凑。三条都写进该告警的契约测试。见 [config-table-hot-reload.md](../design/config-table-hot-reload.md) §19 第 10~12 条。
- 合并前执行受影响范围的格式化、静态检查、构建和测试；按现有门禁区分静态、编译、单测、集成、真实环境和压测证据，任何未执行项都明确报告。

## 5. 执行与完成门禁（§11.5）

1. 动手前能用一句话说明目标模块的职责、调用者、变化原因和不变量；复杂跨模块变更先落对应设计文档。
2. 先找仓库现有实现、标准库和成熟依赖，沿用已有分层、命名、错误语义和测试方式。新增接口或接缝必须对应真实变化点、外部系统隔离或测试隔离需求；只有一个实现且没有上述需求时保持具体。
3. 实现保持最小且完整，不夹带无关重构，不新造平行框架，不复制第二份业务真相。原则冲突或确需偏离时记录证据、原因和代价。
4. 完成时按风险检查 `SRP / OCP / LSP / ISP / DIP / 高内聚、低耦合 / 信息隐藏 / KISS / YAGNI / DRY / 组合优于继承 / 显式依赖 / 面向接口测试`，以及 `失败 / 数据 / 并发 / 兼容 / 安全 / 可观测性 / 改动范围` 中的适用项；不适用项无需逐项罗列。
5. 按协作分工完成相应构建、测试和 lint；只报告实际证据、未验证项和剩余风险，不用静态阅读代替运行证据。

## 6. 实例与布局分层（§11.6，数据层 / 显示层）

一条记录只回答一个问题：**「它是什么」，还是「它摆在哪」**。实例是数据层的真相，摆放只是显示层的一种策略。两者写在一起时，实例记录会被迫携带在别的场景毫无意义的位置字段，而换一种摆法就要同时改协议、改存储、改客户端。

适用于任何「多个实例 + 有位置概念」的系统：背包 / 仓库 / 装备、宠物出战、队伍站位、技能栏与快捷栏、时装外观、坐骑、好友分组、邮件附件。参考实现与完整推导见 [bag-instance-layout-split.md](../design/bag-instance-layout-split.md)。

- **实例层只描述实体**：身份（guid）、模板（config_id）、数量、状态、时间戳。不含 `pos` / `slot` / `index` / `bag_type` / 站位 / 排序等「摆在哪」的字段。判据：同一实例记录被邮件附件、掉落、交易、战斗快照复用时，如果需要写下「这个字段在这里被忽略」的注释，就说明分层错了。
- **布局层只描述排列**：容量、槽位、占位（footprint）、顺序、整理策略。扁平、固定槽、格子是同一模型下的三种布局策略，不是三套系统；新增一种摆法只应新增一个布局实现，不改实例层，也不改调用方。
- **接缝判据（可 grep，硬约束）**：布局层源码里不得出现任何领域概念——本仓库即 `config_id` / `ItemComp` / `ItemTable` / `entt`。布局层需要的领域信息（如格子占位 w×h）由桥接层显式传入，布局层不得自行反查配置表。这条缝一旦漏，两层就退化回一层。
- **「是什么」不与「在哪」共用一个字段**：`equip_slot`（部位即位置）这类设计在「一个部位要放两件」时立刻破产。正确形状是实例上写**种类**（`equip_kind`），槽位由**配置表**枚举（`EquipSlot` 表中多行同 kind ＝ 同部位多槽）。同理，不得用 `active_xxx_id` / `equipped_xxx` 这类标量字段表达「当前出战/装备的那一个」——它把「同时出战两个」写死成了协议变更；用槽位表承载，数量变化只改表。
- **集合顺序必须显式**：`repeated` / `vector` 的下标不得承载业务语义。位置要么写成字段，要么由槽位表给出；靠下标兜住的顺序会在序列化、合并、跨服迁移、并发写入中的任一环节静默丢失，且丢失时无任何报错。
- **显示态不进持久化记录**：在线状态、客户端展示缓存、以及任何可由数据层重算的派生排列，不得写进要落库的 message。持久化结构里凡是注释「仅内存 / 不入库」的字段，都应移到独立的运行时结构——注释拦不住序列化。
- **命名跟着分层走**：通用接口名不得泄漏某一种布局的实现细节（`GridsNeededFor` 这种名字把「要几个实例」和「占几格」混成一件事，应为 `StacksNeededFor`）。

新增或修改上述系统前，先按本节确认分层再动手；已上线结构受向后兼容约束，改动需配版本、迁移与回滚方案。

## 7. 连接与回调生命周期（§11.7，muduo，强制）

**应用层不拥有连接，也不裸绑自己。** 存连接只存 `weak_ptr`、用时 `lock()`；绑进回调只绑 `weak_ptr<自己>`，对象没了回调自动失效。

这是 2026-09-13 gate 在 `TcpConnection.cc:71 assert(state_ == kDisconnected)` 崩溃、随后又暴露 use-after-free 的完整教训，推导与证据见 [incident-gate-tcpconnection-dtor-assert-2026-09-13.md](../ops/incident-gate-tcpconnection-dtor-assert-2026-09-13.md) §8.0。所有坑的共同根源只有一个：应用层和 muduo 抢连接的所有权，或者把裸 `this` 交给 muduo 之后自己先死了。

- **连接的所有权只在 muduo（`TcpServer` / `TcpClient`）手里。** 应用层任何寿命长于一次回调的地方——成员、ECS 组件、容器、定时器 / `queueInLoop` 闭包、thread_local——只能存 `std::weak_ptr<TcpConnection>`，用时 `lock()`，锁不住就当连接不存在。**禁止**长期持有 `TcpConnectionPtr` 强引用：它会让死连接连同 fd、缓冲区、`RpcChannel` 一起钉在内存里（muduo 的 `handleClose` 不关 fd，留给析构），还会把 `TcpClient::~TcpClient` 的 `use_count()==1` 判断带偏、跳过 `forceClose()`。
- **绑进 muduo 回调（`set*Callback`、定时器、`queueInLoop`）的对象一律以 `weak_ptr<自己>` 捕获**（`enable_shared_from_this`），回调先 `lock()`，失败即返回。muduo 会把回调拷到 `TcpConnection` 上，且 `forceClose` 一律排队到下一轮，所以“对象已析构、回调才到”是必然而非偶然。**禁止**用裸 `this` / 裸指针 `std::bind` 进这些回调；与被绑对象同寿命的成员（如 `RpcServer` 自己的 `tcpServer`）除外。
- **拆对象就是直接销毁。** 有了上两条，不需要析构函数摘回调，不需要“延迟关闭”兜底列表，不需要“DOWN 时记得清 X”的手动约定；剩下的 DOWN 清理只有记录卫生的意义。任何“为了不崩而不销毁”的写法都是在掩盖上两条的违例，必须回到根因。
- **节点摘除只在 `queueInLoop` 里做**，不在连接自己的回调栈上。
- **关机先排空再 `quit()`**：`quit()` 经**两跳 `queueInLoop`** 排到队列末尾，靠 FIFO 让排队的 `forceCloseInLoop`（第一趟）与 `connectDestroyed`（第二趟）都跑完；少一趟就是 `TcpConnection.cc:71` 或 `Channel.cc:43` 的 assert。关闭完成标记和通知必须在最后一跳的 `quit()` 之后、完成锁内发出，解锁后不再访问 Node，保证析构等待与 fallback 不会提前结束。**不要用定时器**：Windows 的 loop 是 `poll → handleEvents → timerQueue_->loop() → doPendingFunctors`，定时器恰在 N+1 趟到期时 `quit_` 先置位、只剩一趟——它“通常”能跑完，不是“必然”。

新写或修改任何持有连接、绑进回调的类时只问两句：**「我存的是 weak 吗？」「我绑的是 weak 吗？」** 两个都是，这一类问题与你无关。参考实现：`RpcChannel`、`RpcClient::connect()`、`RpcSession`、`RpcDoneCallback`、`BattleClientEdge::DirectSession`、`muduo_grpc::Server`、`muduo_grpc::ServerCall`、`TimerTaskComp`、`LoopTaskScope`。回归测试：`cpp/tests/rpc_controller_test/rpc_client_lifecycle_test.cpp`、`rpc_channel_loopback_test.cpp`、`cpp/tests/muduo_grpc_test/server_test.cpp`。

### 新代码异步回调标准（冷热分离，强制）

凡新增或改造涉及**回调、定时器、`queueInLoop`、RPC 回包、Redis/Kafka 异步响应**的 C++ 代码，必须按以下四类形态选型（禁止自造第 5 种），遵守 5 条捕获红线并配套生命周期测试：

#### 1. 选型标准（冷热分离，四选一）

| 场景 | 唯一允许的标准形态 | Cache / 生命周期特性 |
|---|---|---|
| **ECS 实体异步 / 定时器 / 回包**（业务最常见） | 按值捕获 `entt::entity`（MSVC 注意用初始化捕获 `[entity = entity]` 防 C3495）+ 业务身份（`player_id` / `seq`），回调回 loop 后 `registry.valid(entity)` + 核对身份 + `try_get<Comp>()` | **零 `shared_ptr`、零堆分配、100% 保住 ECS 连续内存与 CPU Cache Line**（`entt::entity` 自带 generation 版本号，销毁/复用自动失效） |
| **多步异步业务流**（发请求 → 等结果 → 继续执行） | 协程 + `LoopTaskScope` / `loop_async::AwaitCallback`（跨 `co_await` 同样只带值语义身份，不跨挂起持组件指针） | 宿主析构时 `LoopTaskScope` 自动 `Stop()` 截断挂起，热路径组件无侵入 |
| **独立长生命周期基础设施对象**（Client / Session / Channel / Edge） | 继承 `std::enable_shared_from_this<T>` + **私有构造函数 + `static Create(...)` 工厂** + `Start()` 中捕获 `weak_from_this()` | 冷路径连接级对象（非紧循环数组扫描），工厂杜绝栈上 / `unique_ptr` 误建 |
| **极少数冷路径非共享句柄壳**（如 `TimerTaskComp`、`LoopTaskScope`） | 内部 `struct State` 由 `std::shared_ptr<State>` 持有，回调只捕 `std::weak_ptr<State>` | **硬红线：仅限冷路径调度句柄，严禁把热路径 ECS 业务数据塞进 `State`**（避免破坏连续内存、触发随机跳指针 cache miss 与原子计数开销） |

#### 2. 回调捕获硬红线（新代码 5 条铁律）

1. **禁止默认捕获 `[=]` 和 `[&]`**：成员函数里的 `[=]` 会隐式捕获裸指针 `this`，`[&]` 会捕获悬垂局部引用；所有异步 lambda 必须显式列出每个捕获变量。
2. **禁止捕获裸 `this`、裸指针与外部对象引用 `&obj`**：唯一例外是与宿主严格同寿命的内部成员（如 `RpcServer` 持有的 `tcpServer`），且必须加注释写明寿命绑定关系（宿主若须保地址稳定须显式禁移动）。
3. **禁止用 `std::bind` 绑异步回调**：既禁止 `std::bind(..., this, ...)`（UAF），也禁止 `std::bind(..., shared_from_this(), ...)`（与连接/回调形成强引用循环，泄漏内存与 fd 并破坏 `~TcpClient` 判定）；统一写显式捕获 `weak_ptr` 或值语义身份的 lambda。
4. **不在构造函数里绑回调**：`enable_shared_from_this` 构造期控制块尚未就绪，一律挪到 `Start()` / `connect()`，入口首行 fail-fast 断言 `if (weak_from_this().expired()) LOG_FATAL`（参考 `RpcClient::connect()`），回调首行固定写 `auto self = weakSelf.lock(); if (!self) return;`。
5. **跨异步边界只携带值语义身份与自有结果**：不把 ECS 组件指针/引用或配置表行指针带过回调或 `co_await` 边界，回调回到 EventLoop 后重新 `valid()` + `try_get` 查当前状态。

#### 3. 必补生命周期测试（缺一条不合入）

- 新增或改造含异步回调 / 定时器 / 连接的类时，必须附带一条**「先析构再触发回调（Destroy-Before-Callback）」**回归测试：挂上回调 / 投递 `queueInLoop` / 设短定时器 → **立刻销毁对象** → 跑完 EventLoop 让滞后回调真正触发 → 断言**不崩、无状态副作用、无连接泄漏**（参考 `cpp/tests/rpc_controller_test/rpc_client_lifecycle_test.cpp`）。
