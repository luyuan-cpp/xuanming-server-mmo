# 位图（Bit）存储规范与策划删表 ID 约束

> 对应根索引 [AGENTS.md §13.3](../../AGENTS.md#13-架构构建与编码细则) 与 [data/AGENTS.md](../../data/AGENTS.md)。本文完整说明何时优先使用位图存储、导表器 `bit_index` 机制如何运作，以及上线后删除配置表 ID 时**策划**与**程序**必须共同遵守的红线。

## 1. 适用边界：什么时候优先用 bit 存储

### 优先使用 bit（位图）的场景
凡是玩家针对**配置表稳定 ID** 的**纯布尔状态**（只记录 `0 / 1`：是否完成、是否已领取、是否已解锁、引导步骤是否走过等），**优先采用位图存储**，例如：
- 主线 / 支线任务完成状态；
- 一次性成就 / 图鉴 / 称号解锁状态；
- 固定档位奖励领取状态；
- 新手引导完成标记。

优势：
- 内存与落盘体积最小（1000 个条目仅占 125 字节），O(1) 读写；
- proto 持久化使用紧凑 `bytes` 字段（第 `i` 位落第 `i / 8` 字节的第 `i % 8` 位，低位在前，末尾全 `0` 字节不写，见 `cpp/libs/engine/core/utils/bit_index/bit_index_util.h`）；
- 运行期 C++ 内存优先使用 `std::bitset<kXxxBitmapCapacity>`（编译期定长、缓存友好、零堆分配）；仅当确实需要不重新编译的运行时表热重载新增位时，才改用 `boost::dynamic_bitset` 或 `std::vector<bool>`。

### 不适合直接塞进永久单调 bitset 的场景
1. **带额外字段的状态**：需要同时记录进度计数、领取时间戳、到期时间、附加参数等，不适合只用 1 bit。
2. **高频轮换 / 周期重置的限时运营活动**：例如每周新加几十条限时活动 ID，多年累积会导致全局位图无限膨胀且旧位永不能回收。正确做法是**按 `activity_id` / 期次独立存档**（每期内部可以用小位图存当期档位，活动过期整条清理）。
3. **可重复主键的表**：schema 声明了 `(cfg_multi) = true` 的表没有唯一位序，与 `(cfg_bit_index) = true` 互斥，导表器会直接报错拒绝。
4. **直接用配置表 ID 当 bit 下标**：策划表 ID 常从 `100001` 等大号或稀疏号段起编，直接当下标会让每个玩家内存暴涨几十 KB。**禁止直接用表 ID 当位下标**，必须走导表器生成的 `ID -> 紧凑 bit_index` 映射。

## 2. 领取状态归属（业务表自持，不绑公共奖励表）

1. **历史问题**：此前 `RewardBitset` 的位索引以 `reward_table_id` 为键；修改或删除奖励表条目会直接破坏已保存的玩家领取记录。
2. **正确方案**：每个业务系统（任务、成就、每日登录等）各自持有自己的领取状态位图，位序来自**该业务系统自己的表**（例如 `mission_table_id_bit_index.h`），**而不是**公共 `Reward` 表。
   - `Reward` 表 ID 只是纯数据引用（“发放什么物品/货币”），不再作为持久化主键；
   - 修改某个任务的奖励引用 ID，不会影响玩家的已领取状态；
   - `RewardClaimSystem` 退化为纯“发放奖励物品”工具，不再管理领取状态。

## 3. 导表器如何处理删表 ID（核心机制与三大风险）

导表器实现位于 `tools/data_table_exporter/core/generators/bit_index_gen.py`，位序映射持久化在：
`tools/data_table_exporter/state/mapping/table_index_mapping/<表名小写>_mapping.json`（纳入 Git 管理）。

### 3.1 删除表行本身 → 安全（空位永久保留不回收）
- 表里删掉某个 ID 后，导表器会在 `*_mapping.json` 里**永久保留该 ID 原先占用的 bit 位作为占位**，并在导表日志中打印 warning 提示哪些 ID 已从表中移除且位序永久保留；
- 新加的表 ID **永远只会从 `max(已分配位序) + 1` 往后追加**，绝不捡走已删 ID 腾出的空位。

### 3.2 最致命的坑：「删了又复填同一个 ID」或「手改 / 重建 mapping.json」
1. **旧 ID 复用串味（P0 级存档污染）**：
   - 举例：策划把旧任务 ID `105` 删了，过两个版本又把 `105` 拿去配成另一个完全不同的新任务/新奖励——因为 `mapping.json` 里 `105` 仍绑定在原来的 bit 位上，所有做过旧 `105` 的老玩家会凭空显示**“已完成 / 已领过”新 `105`**！
2. **破坏或重建 mapping.json（P0 级全表错位）**：
   - 如果有人删除、手改 `*_mapping.json`，或者对已上线发布过的表误用 `--bitindex-bootstrap` 从空重建，整张表的位序会整体重排，全服老玩家的存档位图瞬间全部错位损坏。
   - 导表器采用 **fail-closed**：状态文件缺失、JSON 损坏、存在负位序或两个 ID 占同一位时，直接抛 `BitIndexStateError` 中止整次导表。

### 3.3 热更与灰度 / 混跑的坑（删行 vs 业务代码兼容）
1. **已完成的旧 bit 位影响统计口径**：
   - 已删任务的 bit 位在老玩家存档里继续保持 `1` 本身不会导致串位（只占 1 bit 废位）；
   - 但如果业务代码把 `completedMissions_.count()` 直接当作“当前有效任务完成总数”去算成就、解锁条件或进度百分比，**就会把已删任务的旧 bit 算进去**，导致计数错误！
2. **进行中 / 待领取状态查表为空**：
   - 如果玩家正处于“已接取未完成”或“已完成未领奖”状态时，策划就把该表行物理删掉了，服务端读档或运行时调用 `FindById(id)` 会返回 `nullptr`；
   - 如果业务代码没做判空容错（自动放弃 / 安全跳过 / 补发保底奖励），轻则任务栏或红点异常，重则登录加载报错或卡死。
3. **灰度 / 滚服（新老版本混跑）高位 bit 被旧版本截断**：
   - 新版本表新增了 ID（分配了更高的 bit 位序），玩家在新版本节点置位并存盘后，如果因灰度、回滚或切线落到旧版本节点，旧二进制的 `std::bitset<kXxxBitmapCapacity>` 装不下这个高位 bit；
   - 旧版本读盘时必须像 `MissionsComp::unknownCompletedBits_`（见 `cpp/libs/modules/mission/comp/mission_comp.h` 与 `mission_comp.cpp`）那样，把超出当前容量的高位 bit **原样保存并在存盘时原样写回**，严禁静默截断丢弃。

## 4. 给策划的红线清单

1. **上线后绝不复填已删除/废弃的旧 ID（最核心）**：删掉或下线某条任务/成就/奖励后，该 ID **永久作废**，绝不能拿给新内容重用；新内容一律顺延分配新 ID。
2. **优先“下架/禁用”而非直接物理删行**：凡是老玩家可能仍处于“进行中 / 待领奖 / 展示历史记录”的表，优先通过状态列（如停用、不可接取）或断开入口引用来下架，保留表行，避免老玩家查表为空。
3. **确需物理删行时必须提前同步程序**：先和程序核对是否存在按完成总数统计的逻辑、以及进行中/待领奖玩家的清理或补发方案；**严禁手工编辑或删除** `tools/data_table_exporter/state/mapping/table_index_mapping/*_mapping.json`。
4. **区分“改奖励内容”与“重置领奖资格”**：只想改某任务的奖品内容时，直接改奖励引用即可；如果想让已经领过奖的老玩家重新再领一次，必须新建一条业务 ID，不得复用旧 ID。

## 5. 给程序的红线清单

1. **优先位图 + 强制走导表器 `(cfg_bit_index) = true`**：纯布尔完成/领取/解锁状态优先用位图存储；**严禁直接用表 ID 当 bit 下标**，统一经导表器生成的 `<Sheet>BitMap` 映射位序，落盘用紧凑 `bytes` 位图（`bit_index_util.h`）。
2. **状态归属业务表**：每个业务系统把 `(cfg_bit_index) = true` 打在**本系统的业务表**上，不把持久化状态绑在公共 `Reward` 表上。
3. **守护 `*_mapping.json` 权威文件**：纳入 Git 严格 Code Review，**禁止手改、禁止删除、禁止压缩空位**；已上线发布过的表严禁使用 `--bitindex-bootstrap`。
4. **代码对删行与混跑高位 bit 免疫**：
   - 读档与运行期遍历“进行中 / 待领奖”ID 查表时，`FindById == nullptr` 必须显式安全处理（跳过 / 自动放弃 / 补发），不得空指针崩溃或阻塞登录；
   - 统计“当前有效完成数”不得无脑调用 `bitset.count()`，必须按当前有效表行集合过滤计数；
   - 所有持久化位图组件读盘遇到 `index >= kXxxBitmapCapacity` 的高位 bit 时，必须参照 `MissionsComp::unknownCompletedBits_` **原样缓存并回写**，防止灰度/回滚丢数据；
   - 高频轮换的限时活动不放入永久单调递增的全局位图，按活动/期次隔离存储并支持过期整条清理。
