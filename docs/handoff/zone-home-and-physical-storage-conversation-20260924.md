## 2026-09-28 续录：合服后哪些服务和数据库会变

本节回应用户“那物理服务器和逻辑服务器合服后 哪些服务数据库是要变的呢”，属于现行代码与文档的解释性校准，不新增决策或宣称实际合服验收。完整答复及此前复核、提交状态问答原样收在文末“后续问答原文补录”。

### 三种变化分别看

- **逻辑合服**：改变玩家与按区业务的归属，以及选服、登录、进场的目标。
- **存储迁移**：改变玩家数据实际读写的落点；需要搬数据和安全切路由，不能只改地址。
- **部署合并或缩容**：改变哪些进程承接请求、哪些机器可以退役；要检查容量与机器上其他服务，不能从逻辑服已合并直接推出整台机器可以关掉。

本仓当前 `home_zone` 仍牵动 `zone_N_db` 主数据路由，因此逻辑合服同时需要复制源玩家的数据。数据库名不同不等于物理机器不同：两个逻辑库可以在同一个数据库实例，也可以位于不同机器。

### 当前 102 服并入 101 服时的变化清单

| 对象 / 责任服务 | 当前变化 | 保持不变或条件边界 |
|---|---|---|
| 角色身份、账号与角色绑定 | login 需在条件满足时刷新返回列表的归属；现有合服工具不重写账号 blob | `player_id`、账号身份及绑定保持；不是重新建号 |
| 归属目录 / data_service | `player:zone:{id}` 从 102 改成 101 | 改记录不要求 mapping Redis 换机器 |
| 玩家主数据 / scene、go/db | 按玩家表清单把源玩家行从 `zone_102_db` 复制到 `zone_101_db`；失效共享玩家缓存 | 只处理迁移清单里的数据，不是所有数据库整库合并；不会因此重编玩家 ID |
| 玩家数据 Redis | 源、目标使用不同数据 Redis 集群时复制 `player:{id}:*` | 使用同一数据集群时无需跨集群复制；共享缓存仍按工具规则失效 |
| 持久化 Kafka 路由 | 原 102 玩家后续存盘按 home_zone 选择 `db_task_zone_101`（使用 topic generation 时带对应后缀） | 切换前处理完旧 topic 与重试等任务并落库；不要求迁移整个 Kafka 集群 |
| 公会 / guild | 源公会 `guild.zone_id` 改为 101，失效公会缓存 | 公会 ID、全局成员关系保留；改数据归属不等于搬整个公会库 |
| 公会榜单 / Redis | 合并 `guild_rank:zone:102` 至目标榜单 | 不能把“当前工具合并公会榜”扩写为已处理所有未来榜单 |
| 交易 / trade | `trade_listing.market_zone` 改为 101 | `seller_zone_at_listing` 保留历史区号；收藏引用不随合服重建 |
| 好友、好友申请、公会成员 | 当前全局关系表按玩家 ID 引用，合服后沿用 | 不需要把好友关系从一个区复制到另一个区 |
| 聊天 / chat | 当前世界频道使用全服唯一 `chat:{world}:log`，私聊按玩家 ID 组织 | 不存在按本次逻辑合服合并两份区内世界聊天库的步骤 |
| 选服 / login / gate / scene / scene_manager / player_locator | 处理旧入口、目标承接、重新建立在线状态；按选项清理源区 scene_manager 热状态 | 当前 SOP 停相关区进程后开放目标区；进程实例变化不等于底层物理机器一定迁移 |
| 合服通知与旧状态 / login Redis | 为迁移玩家写 `player_merge_notice:{pid}`；按流程处理旧会话与缓存 | 临时状态和通知变化不表示账号身份改变 |

真实步骤见 [合服工具入口](../../tools/merge_zone/main.go)、[玩家表复制](../../tools/merge_zone/player_rows.go)、[交易处理](../../tools/merge_zone/trade_step.go)；全局关系与当前执行窗口见 [合服 SOP](../ops/merge-zone-runbook.md) §7 / §8。聊天范围见 [chat_logic.go](../../go/chat/internal/logic/chat_logic.go)。

部署还需单独辨别：本仓的 `db / data-service / login / player-locator / scene-manager` 当前按 zone 部署；data_service 的服务发现与共享存储具有全局语义。不能因为它提供全局目录就推断只存在一个进程。chat、friend、trade 等使用全局业务服务池。guild 的全局业务与数据成立，但 K8s manifest / ConfigMap 是否齐备应以 [部署说明](../../deploy/k8s/README.md) 为准，不能据本表宣称部署链已验收。部署配置来源为 [k8s_deploy.ps1](../../tools/scripts/k8s_deploy.ps1)；三个 zone 含义见 [微服务 zone 契约](../design/microservice-zone-contract-20260914.md) §0。

### 路由例子与必要顺序

```text
合服前：player_id=90002 → home_zone=102 → db_task_zone_102 → zone_102_db
合服后：player_id=90002 → home_zone=101 → db_task_zone_101 → zone_101_db
```

上图是正常存盘路径，省略了事件、缓存及 consumer 等中间环节，不是新的直接调用接口。合服时先阻止新写入，等待已有异步任务处理并落库、核对前置条件与清单，然后复制玩家行及必要 Redis 数据、处理公会/市场/公会榜等业务，最后切换归属映射并验证目标读写。不得删除未处理任务来满足“队列为空”，也不能只改 `home_zone` 而让唯一主数据仍留在旧库。详细顺序、围栏和回退仍以 SOP 为准。

角色列表刷新保留前文的条件限制：resolver 未装配、禁用、映射缺失或查询失败时可能保留旧归属。进场 gate/scene 落点与 home_zone 也不是同一信息；跨 zone 游玩不等于搬库。正常存盘按 `PlayerHomeZoneComp` 选 topic，缺失或值为 0 时当前代码仍有回退到进程 zone 的分支，不能把上述正常示意图当作所有异常分支已经封闭的证明。

### 只搬物理机器，以及未来全局数据层

只把玩家库从机器乙搬到机器丙、业务仍属于 102 时，`home_zone` 可以保持 102。变化的是承接实例、连接配置或内部存储路由；地址若由代理或服务发现屏蔽，业务配置也未必直接改成新 IP。退役机器前须逐项确认它承载的其他账号库、全局业务服务、Redis/Kafka 等已有承接者；不能因它曾服务 102 就一并删除。

全局玩家表 Phase 2 完成后，逻辑合服仍修改 home_zone、按区业务数据和入口承接，但玩家主数据留在同一全局数据层，不再因合服做 `zone_src_db → zone_dst_db` 复制。数据库内部节点重平衡属于物理存储管理，不一定对应某个玩家“物理服字段”。这是 [TiDB 决策 §D7](../design/global-data-layer-tidb-decision.md) 的目标；当前 home_zone topic 路由已先行落码，不能据此认定全局玩家表收敛已完成。


## 直接回答：“合服改逻辑服字段，搬迁改物理服字段？”

**概念上可这样区分，但本仓当前不能照这个口诀直接操作。**

- “逻辑归属”回答玩家按哪套区服规则参与榜单、频道、市场等。本仓有 `player_id → home_zone_id` 的 Redis 权威映射 `player:zone:{player_id}`；它不是一列可任意改的“逻辑服字段”。
- “物理存储落点”回答玩家档现在哪个库或数据层。它可以由独立路由表、分片映射、部署配置或数据库自身管理，不要求每个玩家有一个“物理服字段”。本仓**没有已核实的两列独立字段**。
- 当前 Phase 2 **之前**，`home_zone` 与 `zone_N_db` 玩家主数据落点仍耦合。合服必须先按 [合服设计 §3.1a](../design/server_merge_design.md) 把源区玩家行拷到目标库，必要时拷 Redis blob、合并业务数据，再改 `player:zone` 映射。只改映射、把旧库原地留下，会让读写去目标库却找不到档。
- [TiDB 决策 §D7](../design/global-data-layer-tidb-decision.md) 的 **Phase 2 目标**是全局玩家数据层：届时合服改 `home_zone` 逻辑归属并处理榜单、市场、公会等业务，玩家主数据零跨库迁移。其中全局玩家表收敛尚未完成；按 `home_zone` 选存盘 topic 已先行落码，见该决策文首 2026-09-20 修订；所以“先只改逻辑归属、以后再考虑搬主数据”不能写成本仓当前合服 SOP。
- 在同一套全局身份命名空间下，`player_id` 作为角色身份保持不变。若合并两个本来互不共享发号体系的系统，要先验证 ID 无碰撞、引用能连续，不能无条件承诺每个原数字都可保留。

**本仓当前合服先搬主数据、再改 `home_zone`；按已选定的全局数据层目标，完成全局玩家表收敛后，合服改逻辑归属即可，无需跨库搬玩家主数据。**如果将来单独做物理存储重平衡，具体改的是数据层路由或 TiDB 内部 placement，不一定存在一个玩家“物理服字段”。

## 本仓的几个“zone”与“服务”

| 名称 | 具体含义 | 当前证据 |
|---|---|---|
| `player_id` | 全局唯一、稳定的 uint64 玩家身份；不编码业务区服 | [AGENTS.md](../../AGENTS.md) §4、[合服设计](../design/server_merge_design.md) §2；当前建角发号优先号段、可按配置回退 Snowflake，见 [createplayerlogic.go](../../go/login/internal/logic/clientplayerlogin/createplayerlogic.go) |
| `home_zone_id` | 玩家**逻辑归属**；用于业务分组，也参与当前数据路由 | [router.go](../../go/data_service/internal/routing/router.go) 的 `player:zone:{id}` 映射；[TiDB 决策](../design/global-data-layer-tidb-decision.md) §D1 |
| physical zone | 一组 gate/scene 等进程的部署单位；玩家可跨 zone 进场 | [TiDB 决策](../design/global-data-layer-tidb-decision.md) §D1、[跨 zone 说明](../design/microservice-zone-contract-20260914.md) |
| `zone_N_db` / `db_task_zone_N` | 当前按 zone 派生的玩家库名和持久化 topic；不能仅凭名称推断独立物理机器 | [config.go](../../go/db/internal/config/config.go) 第 229–245 行、[合服设计](../design/server_merge_design.md) §3.1a |
| 接入 `GateZoneId` | 本次网络连接落在哪个 gate zone | [entergamelogic.go](../../go/login/internal/logic/clientplayerlogin/entergamelogic.go) 的进场路径；[进场路由说明](../design/enter-scene-zone-routing.md) |
| 玩家运行位置 | 当前在哪个 scene/zone 持有运行时状态 | `player_locator` 与重连路由；属于在线场景位置，不是长期玩家主数据的库地址 |

原对话还出现“逻辑服务进程”一词，指 login、data_service、friend 等服务发现与调用。这与“玩家属于哪个逻辑服/zone”不同；也与“数据库实际在哪台物理机器”不同。

本仓**没有** `xuanming-server` 的 `player_id % 4096 → logical_cell → (RegionID, CellID)` 路由链，也不是 F 仓当前 Python 服务器。不要把原对话里的具体取模公式当成本仓代码事实。这个公式的通用教训仍适用：从 ID 可以稳定算出数据桶，不能从余数知道玩家当前地理位置或哪台对局 DS 延迟最低。

## 登录、进场与存储分别怎样找

1. **账号登录拿身份**：login 从账号/角色数据取得 `player_id` 与角色列表。
2. **尝试刷新逻辑归属**：[loginlogic.go](../../go/login/internal/logic/clientplayerlogin/loginlogic.go) 第 220–250 行在 resolver 已装配、刷新未禁用且查询获得有效映射时，用当前 `home_zone` 覆盖**返回给客户端的角色列表副本**中的 zone_id，不回写账号 blob。resolver 未装配、开关关闭、映射缺失或 RPC 失败时保留建角 zone，登录仍可返回；因此“登录成功”不能证明列表里必然是合服后的最新归属。
3. **决定连接/进场 zone**：[entergamelogic.go](../../go/login/internal/logic/clientplayerlogin/entergamelogic.go) 第 615–682、722–745 行分别处理重定向票据、重连位置、首次进入时可选的 home_zone 引导与当前 gate zone。首次按 home_zone 重定向有开关且默认关；它找的是 gate/scene 入口，不是把数据库地址交给客户端。
4. **数据服务的 Redis 路由**：[router.go](../../go/data_service/internal/routing/router.go) 用 `player:zone:{player_id}` 查 home zone，再选配置的 Redis 客户端。这是 data_service 的数据代理路径。
5. **场景的实际存盘链**：[scene_manager](../../go/scene_manager/internal/logic/enterscenelogic.go) 解析 home zone，将当次决策的 `home_zone_id` 放进 `RoutePlayerEvent`；C++ 持有 `PlayerHomeZoneComp`，[SavePlayerToRedis](../../cpp/libs/services/scene/player/system/player_lifecycle.cpp) 第 2327–2367 行据此选择 `GetDbTaskTopic(homeZoneId)`，由对应 go/db 消费并写入 [配置派生](../../go/db/internal/config/config.go)的 `zone_N_db`。当前代码在组件缺失或值为 0 时会计数并回退到进程 zone；这里记录实际分支，不能据此保证所有异常写入都按权威 home 路由。正常的跨 zone 游玩仍写 home 库，进入别区的 gate/scene 不等于搬库。

目前没有独立“每玩家物理数据库字段 + 登录查它”的完整二元路由。Phase 2 的全局玩家表收敛目标尚未完成；`home_zone` 存盘 topic 这部分已先行落码。未来全局玩家层由 TiDB 处理其内部分片；这是本仓已选路线，并不意味着分离逻辑归属和物理落点只能采用 TiDB。

登录时回答“哪个逻辑服”和“哪个物理存储服”，要先问说的是**当前实现**还是**目标架构**：当前 home_zone 映射存在，但仍同时牵动按 zone 的数据链；目标架构才把逻辑归属与全局玩家数据层解耦。客户端只拿角色/进场所需信息，不拿 `zone_N_db` 的 DSN。

## 同一个 A/B→C 例子，在本仓不同阶段结果不同

| 阶段 | 合服前 | 合服动作 | 合服后玩家主数据 |
|---|---|---|---|
| **当前 Phase 2 前** | A 的 `home_zone=A`，行在 `zone_A_db`；B 类似 | 冻结与预检；复制玩家行、必要的 Redis blob；处理公会/市场/榜单；最后改 `player:zone` 映射 | 源玩家行已在目标 `zone_C_db`；不可只改映射把数据留在旧库 |
| **Phase 2 目标** | `home_zone=A/B`，玩家主数据按 `player_id` 在全局 TiDB 层 | 改 `home_zone` 映射与业务数据；按决策排空旧 topic、切路由 | 玩家主数据仍在同一全局数据层，无按 zone 主数据拷贝 |
| **原对话的通用假设** | 独立逻辑服 A/B，存储 DB-A/DB-B | 若存在独立的身份→逻辑归属和身份→物理存储目录，可先逻辑合服、后另择时搬库 | 这是解释模型，不是本仓当前已支持的执行顺序 |

本仓现行 [merge-zone-runbook.md](../ops/merge-zone-runbook.md) 是可执行操作来源。`server_merge_design.md` §3.1a 明确要求玩家行复制早于映射切换。[工具实现](../../tools/merge_zone/main.go) 第 335–338 行默认拒绝单独使用 `-skip-player-rows`，但同时传入 `-i-know-global-player-table` 可显式声明全局玩家层已上线；这个参数只代表调用者声明，工具在此处不验证全局数据层是否真正完成，不能把有此开关当作 Phase 2 已验收的证据。

## “以后搬库，ID 不变”在本仓如何理解

物理存储方案将来可以变化，例如先把若干 `zone_N_db` 逻辑库迁到 TiDB，再完成全局玩家表收敛；这些是数据层迁移，与把角色重新发号不同。迁移时要停止或围栏新写入，等待已有异步任务实际处理并落库；按当前合服 SOP 确认 Kafka 消费 lag 为 0，retry、processing、dead 队列中的任务已处理完毕，再复制校验及切换。不得直接删除未处理的消息来满足“队列为空”。还要维持单写者与幂等，确认读写新落点后再按保留策略退役旧落点。合服还要处理业务表、排行榜、同名、市场等冲突。当前工具对 Phase 2 前合服有自己的预检、清单、围栏、拷贝、映射和回退步骤，详见权威 SOP；不能拿原对话里针对“独立物理路由目录”的 CAS 示例替代它。

不变的是**在同一无碰撞身份体系内的 player_id 和仍以该 ID 引用角色的关系**。可能变化的是 `home_zone`、接入 gate/scene、按 zone 派生的数据链或未来全局存储层的物理 placement；这些变化各有不同的权威、前置条件与切换顺序。

#### 助手答复（原文）

我上条讲得绕了。**错的不是取模，而是用取模结果代表玩家所在地区。**

例如两个都在北京的玩家，ID 分别算出 17 和 3000，就可能被分到相距很远的机房；一个玩家去了纽约，ID 不变，取模结果也不会变。ID 只能帮你**均匀分数据**，无法告诉你玩家在哪里。旧设计也把 `% 4096` 称为逻辑 Cell。[旧扩容设计](F:/Pandora-Moba/Server/docs/design/scale-cellular-20m.md:99)

解决时把三个问题分别处理：

- **玩家档存在哪个区服**：创建角色或选服时确定一个持久的 `home_region`；转服走明确的数据迁移。当前 `PlayerData.region` 已有字段，但还没有写入入口。[字段](F:/Pandora-Moba/Server/app/player_data/proto/player_data.proto:85) · [建档入口](F:/Pandora-Moba/Server/app/services/rpg_player_profile.py:357)

- **这一局在哪个机房打**：根据参战玩家的实际延迟和 DS 容量选址，不能由某一个玩家的 ID 决定。

“全球同服”指玩家共享身份、社交等全局服务，**不要求所有对局都在同一个物理地区运行**。当前拍板也是玩家数据分服、其余可单例服务全球同服。[现行设计](F:/Pandora-Moba/Server/docs/design/06-social-global-services.md:28)

#### 助手答复（原文）

可以。先把 `region` 这个词拆开看：它可能指**数据放哪儿**，也可能指**玩家在哪儿**，还可能指**这局在哪儿打**。文档那句话把这几件事混在了一起。

假设旧系统用数字 ID，按 `ID % 4096` 分配：

| 玩家 | 人在哪里 | ID | 算出的编号 |
|---|---|---:|---:|
| 小明 | 北京 | 100 | 100 |
| 小红 | 纽约 | 4196 | 100 |
| 小刚 | 北京 | 101 | 101 |

小明和小红相隔很远，却得到同一个编号；小明和小刚都在北京，却得到不同编号。**这个编号像仓库的“货架号”，只适合找数据，不能当城市名。**小明出国后 ID 也不会变，所以取模更不可能反映他现在的位置。

因此，`% 4096` **用于逻辑数据分片没有错**。错的是拿它决定“玩家属于哪个地理区”或“战斗房间放在哪个机房”。旧扩容设计实际上也称它为 *logical_cell*（逻辑单元）。[旧扩容设计](F:/Pandora-Moba/Server/docs/design/scale-cellular-20m.md:99)

在这个项目里，合理的流程是三条分开的线：

```text
登录找玩家档：玩家 ID → 查权威的所属区服 → 到该区服读取玩家档
区服内找数据：玩家 ID → 算逻辑分片号 → 查分片与数据库的映射
开始一场比赛：比较全队延迟 + DS 容量 → 选择这场比赛的机房
```

“所属区服”可以在创建角色、选服时确定。玩家旅行时只改变**本次连接的入口**，不会悄悄搬走玩家档；真正转服要走数据迁移。“这场比赛的机房”则每局重新选择：北京和纽约玩家组队时，需要按双方延迟作取舍，ID 的末位帮不上忙。

**全球同服**的意思是大家能共享账号、好友、匹配等全局体系；它不意味着玩家档和每场战斗都必须挤在同一物理机房。当前项目已拍板“玩家数据分服，其余可单例服务全球同服”，但玩家档的 `region` 目前还没有写入入口，所以多区归属这一步尚未接通。[现行设计](F:/Pandora-Moba/Server/docs/design/06-social-global-services.md:28) · [当前字段状态](F:/Pandora-Moba/Server/app/storage/sql_schema.py:51)

#### 助手答复（原文）

用 **A 服、B 服合成 C 服** 举例。这里先约定：

- **逻辑服**：玩家看到的区服，决定哪些玩家在同一套区服规则下。
- **物理存储**：玩家档、背包实际存放的数据库或分片。

**合服不一定要立刻合库。**可以先让 A、B 玩家都属于 C，数据暂时仍分别放在原来的库里：

| 项目 | 合服前 | 逻辑合服后 |
|---|---|---|
| 玩家 ID | 甲=`u甲`，乙=`u乙` | **不变**；好友、邮件仍引用这些 ID |
| 玩家所属逻辑服 | 甲=A，乙=B | **变为 C** |
| 玩家档物理位置 | 甲在 DB-A，乙在 DB-B | **可以暂时不变** |
| `ID % 4096` 的逻辑分片号 | 各自一个编号 | **不变**；它不决定 C 服在哪 |
| 全球好友、邮件服务 | 共用全球服务 | **继续共用** |

所以登录时，需要一张**权威路由目录**，把“属于哪个逻辑服”和“档案实际在哪”分开记。例如目标设计可以是：

```text
合服前：u甲 → 逻辑服 A，玩家库 DB-A
        u乙 → 逻辑服 B，玩家库 DB-B

合服后：u甲 → 逻辑服 C，玩家库 DB-A
        u乙 → 逻辑服 C，玩家库 DB-B
```

将来真要把两套玩家库搬进 DB-C，再迁移玩家档、背包等数据并核对，最后把目录里的物理位置切到 DB-C。切换时要阻止旧库继续接受写入；**只修改玩家档的 `region` 字段，不会自动把数据搬到另一个数据库**。

### 登录时怎么找

目标流程是：

```text
客户端 → 网关 → 全局账号服务验证密码/token，得到 user_id
                     ↓
              查玩家路由目录
              得到「逻辑服 C、物理分片 DB-A」
                     ↓
              找到负责 DB-A 的玩家服务 → 读取玩家档和背包
                     ↓
              组装登录结果；好友/邮件另向全球服务查询
```

这里有两次不同的“找”：

1. **找逻辑服务进程**：例如 `friend.list` 找 `friend` 服务，读取玩家档找 `rpg` 玩家服务。现行代码已能按操作前缀和进程配置找到服务；`ctx.get("rpg")` 也会按配置选本地对象或远端代理。[操作路由](F:/Pandora-Moba/Server/app/transport/rpc.py:200) · [服务装配](F:/Pandora-Moba/Server/app/main.py:115)
2. **找玩家的物理库**：先用 `user_id` 查权威目录得到分片，再由负责该分片的玩家服务连接对应数据库。**这一层按玩家选库的目录，目前还没有实现。**现行进程是在启动时按配置创建一套存储连接，不会在每次登录时根据玩家换库。[存储创建](F:/Pandora-Moba/Server/app/main.py:72) · [数据库配置](F:/Pandora-Moba/Server/app/core/config.py:1163)

客户端不需要拿到 DB-A 的地址；登录回包给它的是 token、玩家视图和进场恢复信息，不是数据库连接信息。[登录回包](F:/Pandora-Moba/Server/app/services/auth.py:1679)

### 第 6 轮

#### 用户原话


#### 助手答复（原文）

对。在**同一套全局身份体系**下，甲的唯一 ID 应始终是 `u甲`。但物理搬库不只是“ID 不变、改个地址”，还要把数据安全地搬过去。

例如甲已属于 C 服，档案目前在 DB-A，要搬到 DB-C：

```text
搬前：u甲 → C 服 → DB-A
搬后：u甲 → C 服 → DB-C
```

实际步骤是：

1. **限制 DB-A 对甲的新写入**，避免搬运期间背包、金币又发生变化。
2. **复制并核对**甲的玩家档、背包及玩家域相关记录，确认 DB-C 中的数据完整。
3. **原子切换路由目录**：把 `u甲 → DB-A` 改成 `u甲 → DB-C`，同时提高路由版本。
4. **让旧写入失效**：拿着旧版本请求 DB-A 的操作必须被拒绝；新请求才去 DB-C。
5. 验证甲能从 DB-C 登录、读档和写档后，再退役 DB-A 的旧副本。

所以，**不变的是甲的 ID、所属 C 服，以及好友等以 ID 建立的关系；变的是玩家档的实际存放位置和系统查找它的路由记录**。这是一套应实现的搬库流程；当前仓库还没有这套按玩家选择数据库的路由与搬迁能力。

~~~~markdown
## 1. 先把三个东西分清楚

| 名称 | 表示什么 | 举例 |
|---|---|---|
| 逻辑服 | 玩家属于哪个区，参加哪个区的业务 | `home_zone=102` |
| 服务进程 | 具体干活的程序 | login、gate、scene、db、guild |
| 物理机器 | 运行程序、存放数据的电脑或云服务器 | 机器甲、机器乙 |

**一个逻辑服可以用很多台机器；一台机器也可以同时运行多个服务、存放多个数据库。**

因此，`zone_102_db → zone_101_db` 表示玩家数据换了数据库，**不能仅凭这个名字判断是否跨了物理机器**。

## 2. 你当前项目合服后，玩家这条链怎么变

假设玩家乙的 ID 是 `90002`。

```text
合服前：

玩家乙：player_id = 90002
逻辑归属：home_zone = 102
正常存盘：db_task_zone_102 → db 服务 → zone_102_db


102 并入 101 后：

玩家乙：player_id = 90002       ← 不变
逻辑归属：home_zone = 101      ← 改变
正常存盘：db_task_zone_101 → db 服务 → zone_101_db
                                            ↑
                              这里必须已经有乙的玩家数据
```

**所以你当前项目必须先复制玩家数据，再切换归属映射。**否则乙被路由到 101 库，档案却还只有 102 库里有。

## 3. 具体哪些服务、数据库要变

### ① 登录、选服、网关、场景服务：入口和承接进程会变

102 合到 101 后，要让原来 102 的玩家能够进入合并后的目标服：

- 选服入口需要处理原 102 服的维护、下架或引导。
- login 根据最新归属返回角色信息，并配合进场路由。
- gate、scene、scene_manager 等由目标部署承接玩家。
- 当前合服 SOP 会停相关区的进程，合服验证后开放目标区。

这里是**运行实例和流量去向的变化**，通常不需要为每次合服重写一套登录、场景代码。目标区也可以增加实例承接人数，并不代表所有人挤进一个进程。

另外，当前登录角色列表的归属刷新有配置及查询成功的条件，不能只凭“登录成功”就认定它一定拿到了最新归属。[登录刷新代码](/D:/luyuan/wuxingqitan/mmorpg/go/login/internal/logic/clientplayerlogin/loginlogic.go:234)

### ② 数据库与数据：逐项看

| 对象 | 102 → 101 后具体改变什么 | 是否必须把整个库搬到另一台机器 |
|---|---|---|
| **玩家归属映射** | `player:zone:90002` 的值由 `102` 改为 `101` | 不需要；修改映射记录 |
| **玩家主数据库** | 当前必须把源玩家的数据从 `zone_102_db` 复制到 `zone_101_db` | 不一定跨机器，但当前必须完成跨库复制 |
| **玩家数据 Redis** | 源、目标使用不同数据集群时，需要复制相关玩家数据；相关缓存也要按流程失效 | 是否搬取决于是否共享存储 |
| **公会数据库** | 源区公会的 `guild.zone_id` 改为 `101`，公会缓存失效 | 不需要为合服搬整个公会库 |
| **交易数据库** | 商品的 `trade_listing.market_zone` 改为 `101`；上架时的历史区号 `seller_zone_at_listing` 保留 | 不需要搬整个交易库 |
| **公会排行榜 Redis** | 将 102 的公会榜合入 101 的榜 | 修改榜单数据，不必搬 Redis 机器 |
| **好友数据库** | 好友关系继续使用原来的 `player_id`，不因合服重建 | 不需要；当前好友表是全局表 |
| **公会成员关系** | 玩家仍属于原公会，成员引用继续有效 | 不需要因合服重建成员关系 |
| **账号身份、账号与角色绑定** | 合服不要求重新注册账号，也不要求重新生成角色 ID | 是否搬账号存储，是另外的部署事项 |

这里最容易误解的是公会：

> **“公会现在归 101 服管理”需要改；“公会成员是谁”通常不需要改。**

好友也类似：甲的好友是 `player_id=90002`，乙合服后还是这个 ID，所以好友关系自然保留。

### ③ Kafka、Redis、服务发现：路由和临时状态会变

- **Kafka**：原 102 玩家后续存盘走目标 `db_task_zone_101`。切换前，旧任务必须处理完成并落库，不能直接删除积压消息。
- **Redis**：除归属和业务数据外，还要处理缓存、旧会话、场景热状态、合服通知标记。
- **服务发现**：旧进程退出、目标进程启动或扩容时，注册信息会相应变化。

**这些通常不要求更换整套 Kafka、Redis、etcd 集群。**

## 4. 那“物理合并”又改变什么？

假设合服后，你还想把机器乙退役：

```text
原来：
机器甲：运行 101 的服务
机器乙：运行 102 的服务

合服后：
目标部署承接全部玩家
机器乙准备退役
```

这时要检查机器乙上实际还承担什么：

- **游戏服务进程**：停掉，或者在目标机器重新部署。
- **仍在使用的数据库**：需要迁到承接机器，并切换连接或存储路由。
- **共享 Redis、Kafka 等基础设施**：如果也在这台机器上，仍有其他服务依赖，就必须安排承接。
- **旧数据副本**：按备份和回退保留策略处理。

**因此，“102 逻辑服已经合掉”不等于“102 原来用的机器就可以直接删除”。**那台机器可能还承载其他全局服务。

反过来，**如果只是数据库从机器乙迁到机器丙，而玩家仍属于 102 服，那么 `home_zone` 可以不变**。变化的是数据库实际位置及其连接、路由配置。
~~~~
