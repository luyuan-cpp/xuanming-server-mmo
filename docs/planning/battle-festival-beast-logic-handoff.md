1. 按工作区父目录索引定位 C++/Go 服务端、Java 服务端及 Unity 客户端，逐仓读最新 AGENTS 和引用规则。以 Git remote 识别仓库，不硬编码盘符。
2. 按各仓门禁检查未提交改动、相关设计、最近提交和 PR/Issue。先列受影响的生成源与消费端，不覆盖并发工作；批次/授权遵守各仓规则。
3. Gemini 负责领域逻辑、源协议、配置、状态与测试，以及客户端非视觉数据适配；另一台电脑 Codex 负责界面、美术、布局、预告及状态表现。客户端代码落点在开工时明确归属，避免双方编辑同一视图文件。
4. 先完成下面的语义契约，使用正式生成器产出绑定后交 UI Codex；两端不各造一份消息结构，不手填消息号或 tip 数字。
5. 双版本必须分别记录实现与运行证据。Java 现有现代技能能力可能不足，目录/协议编译成功不等于本活动战斗可用；未达到要求的一版应保持入口关闭。

遵循 [AI 工作流](../rules/ai-workflow.md)的模型和生成/编译分工。本任务不包含上线部署、真实支付、数据库清空、提交或推送授权。

## 3. 最小领域与存储

职责保持清晰：scene 活动模块拥有个人活动进度与资格；宠物模块拥有实例创建、容量及转移策略；match 拥有可信准入和对局身份；battle 拥有局内预告、动作与终局原件。跨模块通过不可变命令/结果协作，同模块内部直接调用，不为本模板新建通用工作流框架。

### 3.1 配置与稳定身份

需要下列语义，具体 schema 由正式源契约表达：

- 活动实例身份、模板类型、配置版本、基线/生效起止、集中展示截止、名称/说明/资源引用。
- 首领/副本/奖励宠物的正式表引用，固定等级档、12 回合上限、3 回合周期、首次第 3 回合重击、前一整轮预告、重击倍率、三胜门槛。
- 稳定神兽奖励身份，跨复刻不变；与活动期次、宠物种类、公共 Reward 表引用分别区分。
- 专属赠送容量 1、该种类仅活动授权发放、禁止玩家间转移的配置策略。额外容量归宠物集合准入，不能在 `PetInstance` 放“活动槽位置”。
- 必需引用或枚举未知、负/溢出时间、重叠活动实例、等级档缺失、非法来源、错误的神兽阶级及获取类，启动/发布校验拒绝。正式开放只允许一个本模板实例，拒绝未完成的内容配置。

### 3.2 玩家持久数据

| 数据 | 所有者与含义 |
|---|---|
| 期次进度 | `activity_instance_id`、已确认胜场（0..3）、涉及的冻结规则/奖励身份；按期隔离 |
| 神兽资格 | 按稳定奖励身份保存已赚取、未领取/已领取及取得时冻结的奖励定义/版本；资格可以从不同复刻期取得，但只授予一次 |
| 领取回执 | 原请求身份/参数摘要、业务奖励身份、所得 pet_id、持久确认状态 |
| 宝宝实例 | 普通宠物持久模型，身份由现有永久号源发放；本活动不能伪造 guid |
| 去重 | 权威对局结果使用既有收件箱永久水位；客户端写请求使用既有持久请求账本 |

纯布尔资格可按[位图规范](../rules/bit-storage-and-table-ids.md)使用本业务稳定映射。期次进度独立保存，不在永久全局位图中每年追加大量周期位；回执有身份、时间和结果，不能压成一个已领 bit。清理旧期进度前须无待处理结算且资格已经转存；终身已领身份和未领取资格不随七天展示结束删除。

## 4. 权威流程与原子范围

### 4.1 开局

客户端提交活动实例、看到的配置版和持久化的请求 UUID。scene 从会话取本人身份，复核时间、资格、合法出战宝宝、可写状态及对局占用，通过受信内部消息请求 match。客户端不能直接提交奖励、胜场或宝宝实例。

scene 将核准的出战 pet_id 与其相关状态版本绑定本次开局意图，`PrepareBattleSnapshot/CreateBattle` 处在同一冻结/占用机制下重核本人归属、仍为该出战宝宝且存活，快照必须恰有这一只合法宠。低血但存活允许入局后补满，局外已倒地不合格；不能先用常规快照过滤掉阵亡宠再继续无宠建房。预检后换宠、取消出战或迁移使资格改变时，取消本次未成局意图、释放其占用并回可恢复的明确拒绝；不计进度，UI刷新后才可发新请求。

match 在持久化准入点复核 `[start,end)`、名单恰好一人及规则版本，冻结活动实例/奖励身份、准入时刻、对局配置、限时和结算策略。按已有持久意图编排建房；同键同参返回原在途/完成结果，同键异参拒绝。双端使用不同 UUID 也受同一角色对局占用限制。

普通 `JoinQueue`、自定义房或帮会入口不得绕过本准入启动活动配置并获取收益。配置只在对应入口白名单开放；不得仅以客户端送来的活动 ID 授权。

未在既有开局截止时间内完成建房，走作废补偿；已持久准入的正常在途局允许越过活动结束时刻。配置热更不改已建局原件，过期请求重放先查原回执，不能新开一局。

### 4.2 局内与结果

battle 的确定性状态必须保存预告发生回合、兑现回合、被点名 actor_id、动作类型与预告状态。重放恢复同一目标，不能用客户端动画时刻驱动选人。重击动作拥有本活动限定的尾部执行优先级，并在回合末清理前执行；每回合神兽仍只获得一次正常行动。

仅局内血蓝补满，动作校验拒绝背包道具及捕捉；配置禁产经验、银两、普通战利品。被冻结的活动结算策略禁止把该局人物/宝宝的血蓝、技能、条目、装备、Buff/冷却变更写回永久状态。它不是把整个玩家存档恢复为开局备份；并发到达的其他合法资产/邮件不能被回滚。

活动来源随**个人终局原件**走 battle → match 权威持久结果 → player_inbox → scene 应用，不另消费帮会 Kafka 假造进度。冻结活动期次不能只存在 `BattleResultEvent` 而在个人结算转换中丢失。

在收件箱首次应用的同一候选提交中：复核合法来源、正常胜利及未逃跑 → 胜场加一（上限3）→ 必要时建立永久待领取资格 → 沿既有材料入口计算本日实际额度 → 与收件箱水位、个人战果一起持久化。存盘确认后再向客户端公开进度、资格与奖励结果。

迟到的合法结果仍归开局期次；材料继续使用首次应用时的游戏日。活动进度与材料日键不共用一个字段。保留全部前置原件以支持下架/新一期后的旧结果核验，不依赖当前活动列表或最近十场战果。

### 4.3 领取

1. 先按本人＋请求身份查询原回执，同键同参返回原 pet_id，同键异参拒绝；再检查稳定奖励身份的终身已领记录。不能先看活动过期而拒绝原请求恢复。历史详情必须能独立返回永久资格及其冻结奖励定义/版本；新设备的首次领取提交这份资格版本，不依赖当前活动配置版。旧请求回放使用原回执参数，不因最新配表变化重解释。
2. 检查已赚取资格、可写/战斗/跨区状态、完整宠物表及额外赠送容量；普通栏已满不消耗赠送容量。专属容量异常已占用时不得创建第二只。
3. 宠物域使用现有号源准备完整候选，校验种类、固定资质、成长、技能资格和五阶身份；号源失败不消费资格。
4. 由同一玩家提交协调器将宠物实例、领取状态、终身唯一身份和请求回执一次提交。跨模块只传不可变准备结果；不要先调用会自行存盘的 GrantPet 再写领取 bit，也不要在 SQL 事务里发 RPC。
5. 持久确认后公开成功并刷新宠物列表。结果未知返回处理中并保留原请求；服务恢复后只可能回原实例或明确未成功，不能用新 UUID 再领。

同一角色另一个新 UUID 同时领取，也必须按稳定奖励身份收敛到同一结果。号段已取但事务失败允许废弃号段值，不允许复用永久 ID。不存在“发出宝宝失败所以补发相同价值金币”的静默降级。

### 4.4 交易与容量

用宠物域单一规则判断普通容量、该种类赠送容量和转移资格，商店、捕捉、活动、GM、存档恢复、交易回填与列表都需核对。普通来源不能借赠送容量多买一只；合法旧普通宝宝行为保持。

本种类的单宠转移在整单预检、副作用前被拒绝，并于公共扣出提交点复核；混合“普通物品＋钱＋神兽”的交易失败时全部不变。改名、取消出战或换区不能解除限制；同角色迁移不得误拦。绑定主体是角色 ID；既有整角色转让若合法执行，宝宝、永久资格与回执随原角色保留，不能因账号所有者变化重新发一只。本任务不新增角色交易能力。

以下名称只是沟通名，正式方法、字段号、枚举值、tip 与限流条目由现有管线分配。扩展既有服务优先，不为本活动建独立服务。

| 请求/推送能力 | 必须承诺的语义 |
|---|---|
| 活动目录扩展 | 新入口种类；有永久待领奖时即使无当期实例也能列出 |
| 读取活动详情 | 服务端时间、实例/配置版、开始/结束/展示截止、阶段、胜场/目标；独立的永久资格及冻结奖励版本、宝宝奖励摘要；可开始/不可开始原因、可领取/已领/处理中；本人在途操作类型/可恢复请求身份/状态、原 battle_id 或 pet_id。无当期实例也须支持历史资格查询 |
| 开始本活动挑战 | 原请求 UUID、实例、期望配置版；返回原请求状态与已有 battle_id；沿现有对局通知/票据继续 |
| 领取本主题神兽 | 稳定奖励身份、原请求 UUID、期望资格的冻结奖励版本；返回可恢复状态、持久确认标志、同一 pet_id 与权威详情版本。不得要求领取旧资格时提交新一期配置版 |

材料详情/领取、宝宝管理、易容/商城均调用现有能力，不复制第二套接口。64 位身份在 JS/JSON 适配层用精确字符串，客户端不能经浮点改写。错误响应给权威能力和原因；未知错误显示通用失败并允许安全刷新，不能伪成功。

## 6. UI 可依赖的状态

活动阶段与个人资格分开：未排期/预告/开放/集中领奖/历史，是排期状态；未达成/可领取/领取处理中/已领取，是个人奖励状态。历史活动仍可能可领取，开放活动也可能早已领过。

首次失败无数据时显示不可用而不是 0/3；刷新失败可保留旧视图但标记未同步、禁用依赖新资格的写按钮。在途写请求必须保存至本机稳定状态并与角色/会话绑定，换角不把旧回包写到新角色。重试用原请求身份，不能因超时自动生成新请求。

本机保存不是唯一恢复源：新设备通过本人权威详情查回在途操作与关联身份，继续查询/恢复同一局或同一领取。`durable=false`、RPC 超时或缺回包均保持处理中；只有权威明确拒绝/终止后才能创建新操作。身份回传仅限当前已认证角色，不能读取其他角色请求。

材料必须区分今日还能赚取的额度与已赚未领余额（后者可跨日）。活动主按钮按永久资格优先：可领取优先于新期0/3，领取处理中优先于再战；已领不因本期胜场归零重新显示“可得一只”。结算只在本局首次建立资格时展示新达成。

## 7. 漏洞与故障检查

| 风险 | 必须守住的结果 |
|---|---|
| 直接指定活动副本绕入口 | 无合法准入不给活动战斗/奖励；普通对局不能伪造来源 |
| 重投结算、两端并发、新 UUID 重领 | 一局一次进度，一种神兽最多一只；旧返回不覆盖新状态 |
| 只写已领位或只发宠 | 两者同一持久提交，失败保留完整可恢复状态 |
| 进活动刷满局外血蓝/清冷却 | 局外值按其原逻辑保留，活动没有免费恢复副作用 |
| 神兽和普通物品混单转走 | 整单无副作用地拒绝，不只在最后扣宠时失败 |
| 换期或清档复领 | 稳定奖励身份不变，终身回执不随期次清理 |
| 结束后补投结果丢进度 | 冻结原件可验证，归原期并能形成永久资格 |
| 普通宠物占赠送容量 | 普通容量和专属容量分开校验，出战容量仍为公共规则 |
