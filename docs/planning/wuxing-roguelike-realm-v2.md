## 一、需求分析

### 1.1 为什么这是当前唯一真正补齐体验拼图的高可玩性扩展
目前《五行奇谈》已覆盖以下核心维度：
- **首领试炼 + 试炼志 V1–V4**：固定机制攻坚与誓约挑战；
- **人宠会武 / 群仙问道赛 / 切磋坊**：PVP 博弈与阵法/3-Ban 策略；
- **万象残局坊 V1 + V1.5**：固定题面、固定种子的纯解谜。

唯一尚未拉满的高爽感拼图是 **「每局构筑不同、连招产生质变、短平快随时能停」的回合制轻肉鸽**。现役五行幻境 V1（10 层线性堆数值符印）存在三个体验短板：
1. **构筑质变不足**：V1 的 15 枚符印以线性百分比加成为主（如直伤 +8%、暴击 +12%），打 2 轮后手感趋同；
2. **节奏偏长且缺抉择**：10 层直来直去缺少路线分岔风险收益（打精英拿高品奇策 vs 走奇遇/休整稳健成型）；
3. **跨周清在途进度有挫败感**：玩家周日晚打到第 8 层周一清晨被清空，违背“随时能停、有空接着玩”的轻松定位。

### 1.2 核心玩法闭环（五行幻境 V2 · 6 关短局轻肉鸽）
1. **6 关紧凑分岔路线（单局约 8–10 分钟）**：
   - 第 1 关：**初探秘境**（普通战，战后必出 3 选 1 五行奇策）；
   - 第 2 关：**二选一分岔**（左路「精英强敌」战后必出灵/仙品奇策；右路「奇遇事件」无战斗 2 选 1：免费领 1 枚随机凡/灵奇策 或 全体本局恢复并强化下战开局护盾）；
   - 第 3 关：**灵脉试炼**（普通战，带当关固定五行灵脉词缀，战后 3 选 1 五行奇策）；
   - 第 4 关：**二选一分岔**（左路「精英强敌」必出灵/仙品奇策；右路「秘境休整」2 选 1：将已持有 1 枚低品奇策升品重铸 或 刷新 3 选 1 补齐同系共鸣）；
   - 第 5 关：**险境强敌**（高协同双怪/护卫战，战后 3 选 1 奇策成型）；
   - 第 6 关：**终局首领**（秘境首领决战，检验完整奇策流派与五行共鸣）。
2. **双模式零门槛准入**：
   - **本人流派模式**：带本人真实养成阵容与灵宠入场，开局满血满蓝、不消耗局外消耗品；
   - **公平试炼模式**：复用 `RankedPreset` 3×3 免费公平模板（人物 `101..103` × 灵宠 `201..203`），1 级零氪玩家同样可畅玩全部奇策构筑与 6 关首领战。两种模式分别记录个人最快通关回合与周榜。
3. **随时中断保存、永不因换周作废在途局**：
   - 玩家每打完 1 关或完成分岔/三选一即落盘权威状态，随时关客户端随时续打；
   - 每周一 05:00（UTC+8）换周时仅刷新「本周最速榜」与「周常首通荣誉位图」，**绝不清空玩家尚未打完的在途轮次**（在途局完成后归属开局对应周记账，或仅记个人历史最佳）。
4. **15 枚「机制改造型」五行奇策（5 行 × 3 档）+ 3 枚同系「五行奇策共鸣」**：
   - 所有奇策**只在当次秘境生效、通关或放弃出图立即清零**；
   - 奇策聚焦**改写回合规则与触发连招**（如破盾返蓝追击、玄毒传染全场、每回合首招 0 蓝、护盾碎裂全屏爆炎、反震翻倍附破甲、主角出手触发灵宠免费追击等）；
   - 同局集齐 **3 枚相同五行** 奇策即自动点亮对应「五行奇策共鸣」，产生明确高潮质变。

### 1.3 上位红线五问准入自检（全部通过）
1. **普通零氪 / 反「上班」**：零每日次数、零每日活跃条、零固定钟点、零缺勤血亏；提供公平 3×3 模式，1 级零氪 100% 平等体验全部 15 枚奇策与 6 关路线。
2. **个人开发者收入**：零数值售卖、零体力/门票收费、零抽卡氪金，靠高重玩度与构筑晒图提升长线留存，反哺现有官方外观与轻便利收入，无客服/资金风险。
3. **物价与长期循环**：全部奇策出图清零（零永久战力膨胀）；**不额外增发任何独立可交易货源或装备掉落**（若计入周常首通进度，严格复用既有两阶段 660/100 统一材料总账上限，不打破经济锚点）；其余奖励为纯展示荣誉榜、流派称谓与构筑复盘分享。
4. **防骗与资产安全**：纯单人 PVE 局内构筑，无交易/押注/消耗品扣减。
5. **商店过审与合规**：无外链、无诱导付费、无广告捆绑、无 UGC 自由图片；纯确定性服务端结算与既有账号注销清理闭环。

### 2.3 工程架构、水平扩展与强一致性方案（同步根治 V1 既有缺陷）

本次落地直接排查并当场根治了 V1 的两处结构性隐患（不等压测再补），确立标准生产级实现：

1. **无状态 Scene 水平扩展 + Redis Cluster 同槽 Hash-Tag 原子 Lua 双榜（根治 V1 进程内静态内存榜）**：
   - **原 V1 问题**：V1 将周榜保存在进程内 `gTowerWeeklyLeaderboard` 静态容器中，多副本 Scene 扩容后各实例榜单分裂、重启即丢，无法水平扩展。
   - **V2 标准方案**：
     - Scene 节点彻底无状态，可按 CPU 任意水平加减副本；每个工作线程仅保留一份轻量 `thread_local` 读穿缓存（按 `week_key` 切分，写入即本地热更新、读取按 **15 秒拉取冷却** 从 Redis Cluster 同步，避免高频 `GetWuxingTowerState` 打爆 Redis）。
     - **同槽 Hash-Tag 键设计**：本人流派榜与公平 3×3 试炼榜物理隔离，键名统一使用 `{weekKey}` 作为 Redis Cluster Hash Tag，保证 ZSET 与元数据 HASH 必然落在同一哈希槽，单条 Lua `EVAL` 原生兼容 Redis Cluster 零 `CROSSSLOT` 报错：
       - 本人流派：`wuxing:realm:lb:{<weekKey>}:self`（ZSET） + `wuxing:realm:lb_meta:{<weekKey>}:self`（HASH）
       - 公平试炼：`wuxing:realm:lb:{<weekKey>}:preset`（ZSET） + `wuxing:realm:lb_meta:{<weekKey>}:preset`（HASH）
     - **复合排序分值**：`score = bestFloor * 1,000,000 - (bestRounds == 0 ? 999,999 : min(bestRounds, 999,999))`，单次 `ZREVRANGE` 即可严格按「通关关数降序 → 全通回合数升序」稳定排位。
     - **原子 Top-200 裁剪、单调防倒退与 14 天 TTL**：单条 Lua 脚本在服务端原子执行「查旧分 `ZSCORE` 单调不倒退（仅 `newScore > oldScore` 才写，防同周重开低层局覆盖历史高分构筑与并发乱序回退）→ `ZADD` + `HSET` → 超 200 名原子 `ZRANGE` + `ZREM` 并同步 `HDEL` 淘汰者元数据 → 双方续期 `EXPIRE 1209600`（14 天）」，杜绝内存无限膨胀与僵尸元数据泄漏；同时 `OnTowerSettlementApplied` 拒绝低层/慢速重开局写榜、`RefreshTowerLeaderboardFromRedisIfDue` 异步回调拒收旧周迟到回包，客户端展示按 `Top 20` 投影返回。
     - **强降级安全**：单测或无 `tlsControlRedis` 环境自动安全退化到 `thread_local` 读穿缓存，不崩溃不阻塞。
2. **跨周保局强一致性（根治 V1 周一 05:00 清空在途局挫败感）**：
   - **原 V1 问题**：V1 换周 `EnsureWeeklyReset` 直接清空 `run_active` 与 `active_sigil_ids`，周一清晨中断未打完的对局。
   - **V2 标准方案**：将「本周榜单周期 `week_key`」与「本轮开局周期 `run_week_key`」彻底拆分为两个字段。换周时仅重置本周首通位图 `weekly_cleared_mask` 与本周最佳，**100% 完整保留在途轮次、已选奇策、当前分岔/事件与候选池**；结算时严格核对 `run_week_key == current_week_key`，旧周开局跨越周一完成后仍正常享受完整 6 关通关并更新个人永久历史最速（`best_rounds_self` / `best_rounds_preset`），但**绝不写入新周首通位图与新周榜**，兼顾反打卡体验与榜单公平性。
3. **公平 3×3 试炼服务端绝对权威合成（零客户端信任）**：
   - 客户端开轮时仅提交 `use_free_preset` + 白名单 ID（`101..103` / `201..203`，非法 ID 当场拒收）；开战时客户端仅发 `is_wuxing_tower = true`。
   - `Scene.PlayerBattleSystem` 校验在途局且无未处理三选一/分岔/事件后，若 `towerCtx.use_free_preset() == true`，由服务端直接合成受控 `RankedMatchContext{ season_id = 0, use_free_preset = true }` 走 `BuildCompetitiveBattleSnapshot` 生成标准公平 3×3 战斗快照，同时在 `TurnBattleEngine::UsesFreePreset()` 中认领 `towerContext.use_free_preset()`，并原样回传 `WuxingTowerSettlementEcho.use_free_preset`，全链路防篡改、防本人与公平混榜。
4. **连招防无限递归硬不变量与定点数封顶**：
   - 所有奇策派生追击、溅射、传染、爆盾均通过 `WuxingBoonRuntime::procDepth` 受控递增，**硬门禁 `procDepth <= 1`（`kBoonMaxProcDepth = 1`）**，从数学上消灭任何循环递归与栈溢出可能；同时全部派生真伤/护盾附伤/回合末灼伤统一采用整数定点数并带硬上限（`1800` / `1200` / `1500`），保证跨语言确定性与回放一致。

## 三、思想分析

1. **为什么升级现役 `WuxingTower` 而不是另起一个平行肉鸽系统？**
   - 玩家不需要在主界面里同时面对“五行幻境爬塔”和“五行奇策秘境”两个高度重叠的入口；把 V1 线性爬塔自然演进为 V2 6 关分岔奇策秘境，既让老入口焕发极高重玩价值，又避免重复维护两套 `Match/Scene/Battle` 协议管线与 UI 资产。
2. **为什么奇策全部做「机制连招」而不是继续加「+15% 攻击」？**
   - 回合制肉鸽的“再来一局”魔力来自**打破常规规则的爽感组合**（例如「润脉免耗 + 镜花水月」无限双发法术流、「镇岳倍反 + 坤元借力 + 3 土共鸣」护盾反震流、「玄毒蔓延 + 3 木共鸣」传染毒爆流）。所有数值仍带单次封顶与整数定点数，保证爽而不崩、确定性可回放。
3. **为什么保留在途进度跨周不清空？**
   - 严守“有空就玩、随时能停”的根本承诺：任何时候关掉游戏，下次回来都能从第 3 关或三选一界面无缝继续，彻底消除周日晚赶着清塔的“上班焦虑”。

## 四、漏洞分析与防线设计

| 风险 / 漏洞场景 | 攻击或异常手法 | 权威防线（Fail-Closed） |
|---|---|---|
| **1. 无限 SL 刷极品仙品奇策** | 反复断线或重开第 1 关刷出仙品开局，或重复发 `ResolveWuxingRealmEvent` 刷牌 | 候选池由 `(player_id, run_id, node_index)` 服务端确定性派生；休整重铸每轮限 1 次且写死 `reroll_count` 幂等落盘 |
| **2. 伪造 6 枚仙品奇策或跨关跳打首领** | 篡改入战请求塞入未持有奇策或直跳第 6 关 | 客户端仅发 `is_wuxing_tower=true`；`Scene.PrepareBattle` 强验 `pending_offer_boon_ids`、`pending_branch_choice_mask` 与 `pending_event_kind` 均已清空后，由权威存档注入 `WuxingTowerBattleContext` |
| **3. 连招无限递归死循环** | 「灵宠协战」「绝锋连斩」「焚盾爆炎」「玄毒蔓延」互相触发导致无限嵌套栈溢出 | 所有奇策派生伤害/追击/传染一律携带 `is_boon_proc = true` 深度守卫（最大触发深度 `= 1`，禁止奇策派生再次触发同类或异类奇策），并设单次伤害封顶 |
| **4. 公平模式与本人模式混榜作弊** | 用满配本人账号刷成绩冒充公平试炼榜，或公平模式带出局外属性 | 结算回传携带 `use_free_preset` 冻结布尔，双榜物理隔离；公平模式由 `Scene.PrepareBattle` 强制覆盖为 `RankedPreset` 白名单面板 |
| **5. 重复结算双推关卡** | 弱网重投同一 `BattleResultEvent` 导致连跳两关或领两枚奇策 | 沿用 `(run_id, node_index)` 严格比对 + 校验 `pending_offer_boon_ids.empty()`，重复结算幂等跳过 |
| **6. 跨周结算污染新周榜** | 上周开的局本周才打完，直接刷新本周最速榜 | 结算核对 `run_week_key == current_week_key`：跨周完成的旧局允许正常结算完局体验，但仅记个人历史最佳、不写入新周最速榜与新周首通位图 |
| **7. 奇策泄漏到普通 PVE / PVP** | 退出秘境后 `active_boon_ids` 未清影响论剑或野外战 | `TurnBattleEngine` 仅当 `hasTowerContext && realm_version == 2` 时启用奇策钩子；常规战斗与残局坊物理忽略该模块 |
